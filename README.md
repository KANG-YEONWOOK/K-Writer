# K-Writer

K-Writer는 AI가 사람처럼 자연스러운 한국어 글을 쓰게 하는 Claude Code, Codex 플러그인입니다. AI가 쓴 한국어 글은 문법에 맞아도 사람이 쓴 글보다 어색하게 읽히고 내용을 이해하기 어렵습니다. K-Writer는 글을 쓰는 스킬 세 개(write, techblog, brief)로 이 문제를 줄입니다. K-Writer는 사용자가 스킬을 호출했을 때만 동작합니다. 플러그인을 설치해도 스킬을 호출하지 않은 대화와 작업에서는 모델이 글을 쓰는 방식이 달라지지 않습니다.

## K-Writer가 줄이려는 문제

K-Writer가 줄이려는 문제는 사람이 쓴 글에는 드문 표현, 한 번 읽어서는 이해할 수 없는 문장, 문장이 이어지지 않거나 주제와 관계없는 내용이 들어간 구성, 자료에 없는 내용 네 종류입니다.

첫째 종류는 문법에는 맞지만 사람이 쓴 한국어 글에는 드물게 나오는 표현입니다. 아래 표에 이런 표현이 들어간 문장과 그 문장을 수정한 문장을 정리했습니다.

| 문제 | AI가 쓴 문장 | 수정한 문장 |
|---|---|---|
| "A가 아니라 B입니다" 같은 문형과 "핵심은" 같은 상투적인 표현을 반복합니다 | "캐시 문제가 아니라 배치 크기 문제입니다. 핵심은 배치 크기입니다." | "배치 크기가 원인입니다." |
| 쉼표를 너무 많이 사용합니다 | "캐시를 비우고, 서버를 재시작했습니다." | "캐시를 비우고 서버를 재시작했습니다." |
| 영어 표현을 직역합니다 | "새로운 문제가 열렸습니다."(open) | "새로운 문제가 발생했습니다." |
| 사람이 그 의미로 사용하지 않는 단어를 선택합니다 | "이전 판을 시험했습니다.", "결과 표를 함께 냅니다." | "이전 버전을 테스트했습니다.", "결과 표를 함께 출력합니다." |
| 설명할 내용을 물건이나 몸동작에 비유합니다 | "동작을 못 박았습니다.", "파일 대신 주소를 건넵니다." | "동작을 명확히 정의했습니다.", "파일 대신 URL을 전달합니다." |
| 제목과 소제목을 "~합니다" 같은 문장으로 씁니다 | (발표 자료의 제목) "배포 절차를 자동화했습니다" | "배포 절차 자동화" |

둘째 종류는 독자가 한 번 읽어서는 이해할 수 없는 문장입니다. 용어의 의미나 수치의 조건이 빠진 문장은 독자가 글쓴이에게 되물어야 하고, 두 가지로 읽히는 문장은 독자가 다시 읽어야 합니다.

| 문제 | AI가 쓴 문장 | 수정한 문장 |
|---|---|---|
| 처음 나온 용어를 설명하지 않습니다 | "write-back이라는 캐시를 사용합니다." | "write-back 캐시(쓰기를 캐시에만 먼저 반영하고 저장소에는 나중에 반영하는 캐시)를 사용합니다." |
| 수치가 무엇을 측정한 값인지 쓰지 않습니다 | "지연이 80% 줄었습니다." | "쓰기 비율이 30% 미만인 서비스에서 p99 지연이 4.2초에서 0.8초로 줄었습니다." |
| 무엇을 무엇으로 바꿨는지 쓰지 않습니다 | "실험 뒤에 배치 설정을 수정했습니다." | "실험 뒤에 무효화 메시지의 배치 크기를 100에서 10으로 바꿨습니다." |
| 어떤 값이 측정값이 아니라고만 하고 그 값이 얼마이고 누가 정했는지 쓰지 않습니다 | "타임아웃은 측정값이 아닙니다." | "승인 요청의 타임아웃 5초는 개발팀이 부하 테스트 없이 임시로 정한 값입니다." |
| 이유와 과정을 건너뛰고 결과만 씁니다 | "배치 크기를 10으로 줄였고 p99 지연이 0.8초가 됐습니다." | "배치 크기를 100에서 10으로 줄이자 메시지 하나가 실패했을 때 다시 보내는 메시지가 100개에서 10개로 줄었습니다. 재전송이 줄면서 p99 무효화 지연은 4.2초에서 0.8초로 줄었습니다." |
| 조사 없이 명사를 이어 붙여 줄여 씁니다 | "캐시 무효화 지연 원인 분석" | "캐시 무효화가 늦어지는 원인을 분석한 결과" |
| 꾸미는 말이 어느 말에 걸리는지 두 가지로 읽히게 씁니다 | "다른 리전처럼 쓰기 요청이 많은 서비스에서는 지연이 늘었습니다." | "쓰기 요청이 많은 서비스에서는 다른 리전에서와 마찬가지로 지연이 늘었습니다." |

셋째 종류는 문장 하나하나는 자연스러운데 문장이 앞 문장과 이어지지 않거나 글의 주제와 관계없는 내용이 들어간 구성입니다.

| 문제 | AI가 쓴 글 | 수정한 방법 |
|---|---|---|
| 앞뒤 문장과 이어지지 않는 짧은 선언형 문장을 씁니다 | "원인은 두 가지입니다. 배치 크기가 컸습니다. 재시도 간격도 짧았습니다." | 세 문장을 한 문장으로 합칩니다. "지연이 늘어난 원인은 큰 배치 크기와 짧은 재시도 간격입니다." |
| 뒤 섹션에서 다룰 세부 내용을 도입 문단에 씁니다 | (캐시 라이브러리를 소개하는 첫 문단에서) "설정 항목은 다섯 가지입니다. ttl은 ..." | 설정 항목의 설명을 "설정" 섹션으로 옮깁니다 |
| 글의 주제와 관계없는 내용을 씁니다 | (캐시 지연을 줄인 방법을 설명하는 글에서) "연구팀은 2019년에 설립됐고 구성원은 12명입니다." | 자료에 있는 내용이어도 글의 핵심 주제를 설명하지 않으므로 이 문장을 삭제합니다 |

넷째 종류는 자료에 없는 내용이고, AI는 다른 사람이 작성한 자료를 정리하면서도 "저희 팀이 직접 운영해 보니 지연이 줄었습니다."처럼 자료에 없는 경험이나 수치를 지어내기도 합니다.

이 중 표현의 문제는 AI가 쓴 글과 사람이 쓴 글을 측정한 값에서도 나타납니다. AI가 쓴 한국어 글의 표현을 분류하고 사람이 쓴 글과 비교한 GitHub 프로젝트 [im-not-ai](https://github.com/epoko77-ai/im-not-ai)에서 "A가 아니라 B입니다"처럼 한쪽을 부정한 뒤 다른 쪽을 말하는 문장은 1,000자당 AI가 쓴 글에 5.8회, 사람이 쓴 글에 0.6회 나왔습니다. LLM이 생성한 한국어 글을 가려내는 연구 [KatFishNet](https://arxiv.org/abs/2503.00032)에서 쉼표가 있는 문장의 비율은 LLM이 생성한 글이 61.0%, 사람이 쓴 에세이가 26.3%였습니다.

## 설치

### Claude Code

Claude Code 세션에서 marketplace(플러그인 목록을 제공하는 저장소)를 등록한 뒤 플러그인을 설치합니다.

```
/plugin marketplace add KANG-YEONWOOK/K-Writer
/plugin install k-writer@k-writer
```

새 버전으로 직접 업데이트하려면 터미널에서 아래 두 명령을 실행한 뒤 Claude Code를 다시 시작합니다.

```bash
claude plugin marketplace update k-writer
claude plugin update k-writer@k-writer --scope user
```

### Codex

Codex에는 `codex plugin add` 명령을 지원하는 버전의 Codex CLI에서 아래 두 명령으로 K-Writer를 설치합니다. 이 명령을 지원하는지는 `codex plugin --help`가 출력하는 명령 목록에 `add`가 있는지로 확인하고, 없으면 아래의 "스킬 폴더 직접 복사"로 설치합니다.

```bash
codex plugin marketplace add KANG-YEONWOOK/K-Writer
codex plugin add k-writer@k-writer
```

Codex에서 직접 업데이트할 때는 아래 두 명령을 실행하고 새 세션을 엽니다.

```bash
codex plugin marketplace upgrade k-writer
codex plugin add k-writer@k-writer
```

### 자동 업데이트

자동 업데이트를 켜 두면 새 버전이 나올 때마다 위의 업데이트 명령을 실행하지 않아도 됩니다.

K-Writer의 marketplace는 Anthropic의 공식 marketplace가 아니어서 Claude Code가 자동 업데이트를 기본으로 꺼 둡니다. 켜려면 세션에서 `/plugin`을 실행하고 Marketplaces 탭에서 k-writer를 선택한 뒤 auto-update를 켜거나, 사용자 설정 파일(`~/.claude/settings.json`)의 `extraKnownMarketplaces`에서 k-writer 항목에 아래처럼 `"autoUpdate": true`를 추가합니다.

```json
{
  "extraKnownMarketplaces": {
    "k-writer": {
      "source": { "source": "github", "repo": "KANG-YEONWOOK/K-Writer" },
      "autoUpdate": true
    }
  }
}
```

자동 업데이트를 켜면 Claude Code는 세션에서 첫 메시지를 받은 뒤 최대 10분 안에 marketplace를 새로 받고 설치된 K-Writer를 새 버전으로 업데이트합니다. 업데이트하고 나면 Claude Code가 `/reload-plugins`를 실행하라고 안내합니다. 이 명령을 실행하면 새 버전이 그 세션에 바로 적용되고, 실행하지 않아도 Claude Code를 다음에 실행할 때 적용됩니다.

Codex CLI 0.163.0에서 확인했을 때 Codex는 따로 설정하지 않아도 시작하면서 marketplace를 새로 받고 설치된 K-Writer를 새 버전으로 업데이트했습니다. 이 동작은 Codex 문서에서 확인하지 못했으므로, 새 버전이 적용되지 않으면 위의 업데이트 명령을 실행합니다. 설치된 버전은 `claude plugin list`와 `codex plugin list`로 확인합니다.

### 스킬 폴더 직접 복사

플러그인을 설치하지 않고 저장소의 `skills/` 아래에 있는 스킬 폴더를 개인 스킬 폴더에 복사해도 같은 스킬을 사용할 수 있습니다. 개인 스킬 폴더는 Claude Code에서는 `~/.claude/skills/`이고 Codex에서는 `~/.agents/skills/`입니다. 복사한 스킬은 Claude Code에서는 `/write`, Codex에서는 `$write`처럼 스킬 이름만으로 호출합니다. 복사한 스킬은 자동으로 업데이트되지 않으므로 새 버전이 나오면 다시 복사합니다. Codex에서 폴더도 복사하고 플러그인도 설치하면 스킬이 두 번 표시되므로 두 방법 중 하나만 사용합니다.

```bash
git clone https://github.com/KANG-YEONWOOK/K-Writer.git
mkdir -p ~/.claude/skills && cp -r K-Writer/skills/* ~/.claude/skills/   # Claude Code
mkdir -p ~/.agents/skills && cp -r K-Writer/skills/* ~/.agents/skills/   # Codex
```

### 필요한 환경

스킬이 글을 검사할 때 실행하는 Python 스크립트(검사 스크립트)는 Python 3.8 이상에서 외부 패키지 없이 실행됩니다. Python이 없으면 스킬은 검사 항목과 통과 조건을 정리한 문서를 읽어 글을 직접 점검하고, 자동 검사를 실행하지 못했다고 보고합니다.

## 스킬 사용법

쓰려는 글의 종류에 따라 스킬 세 개 중 하나를 선택합니다.

| 스킬 | 쓰는 글 | 사용자가 정하는 값 | 결과 |
|---|---|---|---|
| write | 기술 블로그 글이나 요약이 아닌 글입니다. 공지, 보고, 제안, 소개 글과 발표 자료(슬라이드)의 제목과 문구를 씁니다. | 자료나 주제, 목적, 분량, 어투(합니다체, 해요체, "~다"로 끝나는 해라체, 직접 입력) | 파일로 저장합니다 |
| techblog | 논문 PDF, 기술 문서, 웹 페이지, 붙여넣은 텍스트의 핵심 내용을 정리한 한국어 기술 블로그 글입니다. | 자료, 독자, 분량, 어투(합니다체, 해요체) | 파일로 저장합니다 |
| brief | 문서, 웹 페이지, 붙여넣은 텍스트, 대화 내용의 요약입니다. | 자료, 분량(한 줄, 한 문단, 자세히), 어투(합니다체, 해요체, 해라체, 직접 입력) | 대화에 보여 주고 `-o`를 붙이면 파일에도 저장합니다 |

자료 없이 주제만 받은 write는 사용자가 알려 준 사실과, 웹에서 출처를 확인한 일반 지식으로 글을 씁니다.

스킬은 Claude Code에서는 `/k-writer:write`, Codex에서는 `$k-writer:write`처럼 호출하고 뒤에 자료와 요청을 적습니다.

```
/k-writer:write meeting-notes.md 팀에 공유할 회의 정리 글로 써줘
/k-writer:techblog paper.pdf
/k-writer:brief report.pdf
```

스킬은 요청에 없는 값을 글을 쓰기 전에 한 번에 묻습니다. 예를 들어 `/k-writer:brief report.pdf`를 실행하면 brief가 분량과 어투를 물은 뒤 보고서를 요약합니다. 요청에 `--defaults`를 붙이면 스킬은 묻지 않고 기본값을 사용합니다. 기본값은 어투가 합니다체이고, 분량은 brief가 한 문단, write와 techblog가 자료에 맞춘 분량입니다. 스킬마다 사용할 수 있는 인자와 예는 [write](skills/write/README.md), [techblog](skills/techblog/README.md), [brief](skills/brief/README.md)의 README에 있습니다.

## 스킬이 글을 쓰는 과정

세 스킬은 글 전체의 주제, 문단마다 전할 내용, 문장마다 전할 내용을 먼저 정한 뒤에 문장을 쓰고, 다 쓴 글을 두 번 점검합니다. 쓸 내용을 정하지 않고 문장부터 쓰면 자료에 있다는 이유로 주제와 관계없는 내용이 글에 들어가고, 이유와 과정은 빠지고 결론만 남기 때문입니다. 스킬은 아래 여섯 단계를 순서대로 거칩니다.

1. 모델은 자료를 끝까지 읽고 글에 쓸 사실, 수치, 용어를 fact sheet라는 작업 파일에 모읍니다. 글의 수치와 주장은 이 파일에서만 가져옵니다.
2. 자료의 내용이 글에 다 들어가지 않으면 모델은 글에 반드시 들어가야 하는 내용을 자료 전체에서 먼저 추출합니다. K-Writer는 이 내용 하나하나를 핵심 요소라고 부르고, 요소 하나는 자료의 결론이나 그 근거가 되는 수치처럼 한 문장으로 말할 수 있는 내용입니다. 추출한 요소가 분량에 다 들어가지 않으면 모델은 추출한 목록에서 요소를 합치거나 꼭 필요한 요소를 다시 선택하는 일을 분량에 맞을 때까지 반복합니다. 예를 들어 brief의 한 문단 요약에는 요소 3~5개가 들어갑니다. 요소를 합칠 때는 두 문장을 이어 붙이지 않고, 같은 대상의 값 여러 개를 범위 하나로 말하는 것처럼 한 단계 위의 내용 하나로 다시 적습니다. 문장을 줄여 써서 글자 수를 맞추면 한 문장에 사실이 여러 개 들어가거나 주어와 조건이 빠지므로, 분량은 이렇게 요소의 수로 맞춥니다. 글자 수는 사용자가 요청에 적었을 때만 목표로 삼고, 다 쓴 글의 글자 수와 그 값의 차이가 10% 정도까지이면 분량에 맞는 글로 판단합니다. "300자 이내"처럼 상한으로 적은 값은 넘지 않게 합니다. 요약 스킬인 brief는 이 단계를 항상 거치고, write와 techblog는 자료의 내용이 사용자가 정한 분량보다 많을 때 거칩니다.
3. 모델은 글 전체의 핵심 주제, 단위마다 전할 내용, 문장마다 전할 내용을 설계 문서라는 작업 파일에 한 줄씩 적습니다. 단위는 소주제 하나를 다루는 문단이나 섹션입니다. 핵심 주제를 설명하지 않는 내용은 사실이어도 이 단계에서 제외하고, 독자가 스스로 채워야 하는 이유와 과정이 있으면 그 내용을 전할 줄을 추가합니다. brief는 2단계에서 남긴 핵심 요소가 문장마다 전할 내용이 되므로 설계 문서를 따로 작성하지 않습니다.
4. 모델은 K-Writer의 한국어 문장 규칙에 따라 설계 문서의 줄을 하나씩 문장으로 씁니다. 이 규칙은 "K-Writer가 줄이려는 문제"의 표에 있는 표현과 문장을 쓰지 않는 방법을 정한 문서입니다. 규칙은 사람이 쓴 글에서 표현과 쉼표의 빈도, 문장 길이, 앞 문장의 단어를 다시 사용한 문장의 비율을 측정한 값과 K-Writer 개발자가 AI가 쓴 글을 수정한 기록을 근거로 정했습니다. 모델은 문장을 쓸 때마다 그 문장이 한 가지 의미로만 읽히는지 확인하고, 한 단위의 문장을 모두 쓰면 문장들이 서로 이어지는지 확인합니다.
5. 검사 스크립트는 AI가 쓴 글에 자주 나오는 표현이 초안에 몇 번 나오는지 세어 기준치와 비교하고, 자료에 없는 수치와 설계 문서에는 있는데 초안에서 빠진 내용을 찾습니다. 기준치는 표현마다 허용하는 빈도이고 토스, 카카오, 당근, 네이버 D2, 우아한형제들, NAVER CLOVA 기술 블로그에서 사람이 쓴 글 600편을 같은 스크립트로 측정해 정했습니다. 모델은 빈도가 기준치를 넘은 표현을 수정하고, 자료에 없는 수치와 빠진 내용은 fact sheet와 설계 문서를 확인해 수정합니다.
6. 글을 쓴 모델은 자료를 이미 읽어서 글에 빠진 설명을 알아차리기 어렵습니다. 그래서 초안을 작성하지 않은 별도의 모델(subagent)이 자료 없이 글만 한 번 읽고 어색한 문장, 두 가지로 읽히는 문장, 설명이 빠진 용어, 건너뛴 이유나 과정, 글의 핵심과 관계없는 부분을 찾아 보고합니다. 글을 쓴 모델은 보고된 문장을 자료와 대조해 수정하고, 수정한 문장과 그 앞뒤 세 문장씩만 다시 확인합니다.

글을 설계하는 기준과 문장을 잇는 기준은 사람이 잘 쓴 글인 수능 국어 지문 82편, 신문 기사 1,200편, 논문 초록 301편, 대통령 연설문 412편을 측정해 정했습니다. 수능 국어 지문에서 문단 안의 문장은 81%가 바로 앞 문장의 명사를 다시 사용했고, 그래서 스킬은 문장을 앞 문장에서 말한 대상으로 시작합니다. 수능 국어 지문에서 문단의 핵심을 말하는 문장의 바로 다음 문장은 72%가 풀이, 예, 이유였고, 그래서 스킬은 정의나 주장 다음에 풀이나 예를 씁니다. 측정 방법과 전체 결과는 [`dev/baseline/write`](dev/baseline/write/README.md)에 있습니다.

## 실행 시간과 비용

스킬은 여러 단계를 거치므로 글 한 편을 쓰는 데 시간과 비용이 듭니다. 스킬을 한 번 실행하는 데 글의 길이에 따라 3.4분에서 29.7분이 걸렸고 비용은 1.36달러에서 8.63달러였습니다. 이 시간과 비용은 Claude Code를 대화 없이 실행하는 명령(`claude -p`)에 Claude Opus 5.5 모델을 지정해 글마다 한 번씩 실행한 결과입니다. 비용은 Claude Code가 실행을 마치면서 보고한 API 사용 금액입니다.

| 스킬 | 쓴 글 | 시간 | 비용 | 측정한 버전 |
|---|---|---|---|---|
| brief | 엔지니어링 노트의 한 줄 요약 | 3.4분 | 1.36달러 | 0.9.0 |
| brief | 엔지니어링 노트의 한 문단 요약 | 7.9분 | 2.40달러 | 0.9.0 |
| brief | Python 기능 제안 문서의 "300자 이내" 요약 | 8.1분 | 2.70달러 | 0.9.2 |
| brief | 개발 기록의 자세한 요약 | 19.0분 | 5.24달러 | 0.9.0 |
| write | 분량을 1,000자 안팎으로 정한 글 1건 | 14.6분 | 4.34달러 | 0.9.0 |
| write | 본문 1,200자 이하인 글 5건 | 건당 6.5~12.7분 | 건당 2.29~4.05달러 | 0.7.0 |
| write | 본문 6,567자인 글 1건 | 29.7분 | 8.63달러 | 0.7.0 |
| techblog | 엔지니어링 노트를 정리한 본문 4,000자 남짓한 글 | 24.1분 | 7.08달러 | 0.7.1 |

표에서 측정한 버전이 0.7.0과 0.7.1인 행은 그 뒤의 버전에서 다시 측정하지 않았습니다. 0.9.0에서 추가한 핵심 요소 추출을 거치는 글은 이 행의 값보다 시간과 비용이 더 듭니다. 예를 들어 표에서 분량을 1,000자 안팎으로 정한 write의 글 1건은 같은 요청을 0.7.0으로 실행했을 때 12.7분, 4.05달러였고 0.9.0에서는 14.6분, 4.34달러였습니다.

## 평가 결과와 한계

스킬로 쓴 글이 스킬 없이 쓴 글보다 나은지는 K-Writer의 이전 저장소인 [Skill-Techblog](https://github.com/KANG-YEONWOOK/Skill-Techblog)에서 techblog의 초기 버전(0.2.0)으로 평가했습니다. 평가에서는 자료 7건마다 스킬로 쓴 글과 스킬 없이 쓴 글을 judge 모델(글을 읽고 정해진 기준으로 판정하는 모델)에게 순서를 바꿔 두 번 보여 줬습니다. judge 모델은 한국어가 자연스러운지, 자료의 핵심을 정확하게 전달하는지, 구조가 읽기 쉬운지를 기준으로 더 나은 글을 선택했고, 7건 중 6건에서 두 번 모두 스킬로 쓴 글을 선택했습니다. judge 모델이 글의 수치와 주장을 자료 원문과 대조했을 때 자료와 다르거나 근거가 없는 주장은 스킬 없이 쓴 글에서 글당 중앙값 2건이었고, 스킬로 쓴 글에서는 7편 중 1편에서 1건 나왔습니다. 다만 judge 모델은 글을 쓴 모델과 같은 Claude 계열이라서 이 판정은 사람 독자의 평가와 다를 수 있습니다. write와 brief는 스킬 없이 쓴 글과 비교한 평가가 없고, 두 스킬과 0.2.0 뒤의 techblog는 이전 버전으로 쓴 글과 비교했습니다. 핵심 요소 추출을 추가한 0.9.0의 비교에서 brief의 한 줄, 한 문단, 자세한 요약은 judge 모델의 판정 두 번이 모두 0.9.0의 요약을 선택했습니다. write의 글 한 건은 judge 모델의 판정이 한 번씩 갈렸고 "300자 이내" 요약 한 건은 판정 여섯 번이 모두 이전 버전의 요약을 선택했지만, 두 글을 직접 읽은 저장소 소유자는 두 건 모두 0.9.0의 글이 더 읽기 쉽다고 판정했습니다. 버전별 결과는 [`EVALUATION.md`](EVALUATION.md)에 있습니다.

검사 스크립트는 정규식으로 표현을 세므로 잘못 검출하는 경우가 있습니다. 검사 스크립트가 비교하는 기준치도 대부분 기술 블로그 글에서 정한 값이라서 공지, 보고서, 메일 같은 글에는 맞지 않을 수 있습니다. 수능 국어 지문에서 정한 기준치는 write의 항목 세 개(지시어로 시작하는 문장, 번역투, "~라고 봅니다")뿐입니다. 핵심 요소를 추출하고 선택하는 일은 모델이 하고, 독자에게 더 필요한 요소를 남겼는지는 검사 스크립트가 확인하지 못합니다. 별도의 모델이 글을 읽는 점검은 글 하나에 한 번만 하고 실행할 때마다 찾아내는 문장이 달라서, 한 번에 찾지 못한 문장은 글에 남습니다. 스킬로 작성한 글에 자료와 다른 내용이 없다는 보장은 없으므로 글을 공개하기 전에 수치와 고유명사를 자료 원문과 대조해야 합니다.
