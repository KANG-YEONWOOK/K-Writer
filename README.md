# K-Writer

K-Writer는 AI가 사람처럼 자연스러운 한국어 글을 쓰게 하는 Claude Code, Codex 플러그인입니다. AI가 쓴 한국어 글은 문법에 맞아도 아래 표와 같은 문제 때문에 사람이 쓴 글보다 어색하게 읽히고 내용을 이해하기도 어렵습니다.

| 문제 | AI가 쓴 문장 | 수정한 문장 |
|---|---|---|
| 같은 문형과 상투적인 표현을 반복합니다 | "캐시 문제가 아니라 배치 크기 문제입니다. 핵심은 배치 크기입니다." | "배치 크기가 원인입니다." |
| 쉼표를 너무 많이 사용합니다 | "캐시를 비우고, 서버를 재시작했습니다." | "캐시를 비우고 서버를 재시작했습니다." |
| 영어 표현을 직역합니다 | "새로운 문제가 열렸습니다."(open) | "새로운 문제가 발생했습니다." |
| 사람이 그 의미로 사용하지 않는 단어를 선택합니다 | "이전 판을 시험했습니다.", "결과 표를 함께 냅니다." | "이전 버전을 테스트했습니다.", "결과 표를 함께 출력합니다." |
| 설명할 내용을 물건이나 몸동작에 비유합니다 | "동작을 못 박았습니다.", "파일 대신 주소를 건넵니다." | "동작을 명확히 정의했습니다.", "파일 대신 URL을 전달합니다." |
| 처음 나온 용어를 설명하지 않습니다 | "write-back이라는 캐시를 사용합니다." | "write-back 캐시(쓰기를 캐시에만 먼저 반영하고 저장소에는 나중에 반영하는 캐시)를 사용합니다." |
| 수치가 무엇을 측정한 값인지 쓰지 않습니다 | "지연이 80% 줄었습니다." | "쓰기 비율이 30% 미만인 서비스에서 p99 지연이 4.2초에서 0.8초로 줄었습니다." |
| 무엇을 무엇으로 바꿨는지 쓰지 않습니다 | "실험 뒤에 배치 설정을 수정했습니다." | "실험 뒤에 무효화 메시지의 배치 크기를 100에서 10으로 바꿨습니다." |
| 값이 얼마이고 누가 정했는지 쓰지 않고 측정값이 아니라고만 합니다 | "타임아웃은 측정값이 아닙니다." | "승인 요청의 타임아웃 5초는 개발팀이 부하 테스트 없이 임시로 정한 값입니다." |
| 자료에 없는 내용을 지어냅니다 | "저희 팀이 직접 운영해 보니 지연이 줄었습니다." | 자료에 있는 사실만 씁니다 |
| 앞뒤 문장과 이어지지 않는 짧은 선언형 문장을 씁니다 | "원인은 두 가지입니다. 배치 크기가 컸습니다. 재시도 간격도 짧았습니다." | "지연이 늘어난 원인은 큰 배치 크기와 짧은 재시도 간격입니다." |
| 뒤 섹션에서 다룰 세부 내용을 도입 문단에 씁니다 | (캐시 라이브러리를 소개하는 첫 문단에서) "설정 항목은 다섯 가지입니다. ttl은 ..." | 설정 항목은 "설정" 섹션에서 설명합니다 |
| 이유와 과정을 건너뛰고 결과만 씁니다 | "배치 크기를 10으로 줄였고 p99 지연이 0.8초가 됐습니다." | "배치 크기를 100에서 10으로 줄이자 메시지 하나가 실패했을 때 다시 보내는 메시지가 100개에서 10개로 줄었습니다. 재전송이 줄면서 p99 무효화 지연은 4.2초에서 0.8초로 줄었습니다." |
| 글의 주제와 관계없는 내용을 씁니다 | (캐시 지연을 줄인 방법을 설명하는 글에서) "연구팀은 2019년에 설립됐고 구성원은 12명입니다." | 글의 핵심 주제를 설명하지 않는 내용은 자료에 있어도 쓰지 않습니다 |
| 제목과 소제목을 "~합니다" 같은 문장으로 씁니다 | (발표 자료의 제목) "배포 절차를 자동화했습니다" | "배포 절차 자동화" |

K-Writer는 스킬 세 개(write, techblog, brief)로 이런 문제를 줄입니다. 세 스킬은 같은 글쓰기 순서와 같은 기준으로 글을 씁니다. 글쓰기 순서는 글 전체의 주제, 문단, 문장 순서로 쓸 내용을 먼저 정한 뒤에 문장을 쓰고 점검하는 순서입니다. 기준은 사람이 잘 쓴 글을 측정해 얻은 글의 구성과 표현입니다. K-Writer는 사용자가 스킬을 호출했을 때만 동작합니다. 플러그인을 설치해도 스킬을 호출하지 않은 대화와 작업에서는 모델이 글을 쓰는 방식이 달라지지 않습니다.

## 스킬이 글을 쓰는 과정

세 스킬은 아래 다섯 단계를 거쳐 글을 씁니다. 쓸 내용은 글 전체의 주제, 단위, 문장 순서로 정합니다. 단위는 소주제 하나를 다루는 문단이나 섹션입니다. 내용을 모두 정한 뒤에는 문장을 하나씩 쓰면서 문장, 단위, 글 전체 순서로 점검합니다.

1. 모델이 글을 쓰기 전에 한국어 문장 규칙을 읽습니다. 규칙은 사람이 쓴 글을 측정한 값과 K-Writer 개발자가 AI가 쓴 글을 다시 읽고 수정한 기록을 근거로 정했습니다. 측정한 글은 기술 블로그 글, 논문 초록, 수능 국어 지문, 신문 기사, 연설문이고, 측정한 값은 표현과 쉼표의 빈도, 문장 길이, 앞 문장의 단어를 다시 사용한 문장의 비율입니다.
2. 자료의 내용이 글에 다 들어가지 않으면 글에 반드시 들어가야 하는 내용을 먼저 추출합니다. K-Writer는 이 내용 하나하나를 핵심 요소라고 부릅니다. 요약 스킬인 brief는 항상 이 단계를 거치고, write와 techblog는 자료의 내용이 사용자가 정한 분량보다 많을 때 거칩니다. 분량마다 글에 담는 요소의 수는 스킬이 정해 두었습니다. brief는 한 줄 요약에 요소 1~2개, 한 문단 요약에 3~5개, 자세한 요약에 12~20개를 담고, 사용자가 글자 수를 정하면 그 글자 수를 문장 수로 바꿔 요소의 수를 정합니다. 모델은 먼저 분량을 고려하지 않고 자료 전체에서 핵심 요소를 추출합니다. 추출한 요소가 이 수보다 많으면 모델은 자료가 아니라 추출한 요소의 목록에서 다시 추출합니다. 한 문장으로 말할 수 있는 요소끼리 합치고, 그래도 많으면 독자에게 꼭 필요한 요소를 다시 선택합니다. 모델은 요소의 수가 분량에 맞을 때까지 이 일을 반복합니다. 분량은 이렇게 글에 담는 내용의 수로 맞추고, 정한 글자 수에 맞추려고 문장을 줄여 쓰지 않습니다. 사용자가 "300자 이내"처럼 글자 수의 상한을 정했을 때도 문장을 줄여 쓰는 대신 요소와 요소 안의 세부 값을 더 줄여 상한을 지킵니다. 글자 수에 맞춰 쓴 글에서는 한 문장에 사실이 여러 개 들어가거나 주어와 조건이 빠지기 때문입니다.
3. 문장을 쓰기 전에 글을 설계해 설계 문서에 적습니다. 먼저 글 전체의 핵심 주제를 한 문장으로 정합니다. 다음으로 글을 단위로 나눠 단위마다 전할 내용과 말할 순서를 정하고, 문장마다 전할 내용을 한 줄씩 적습니다. 핵심 주제를 설명하지 않는 내용은 사실이어도 이 단계에서 제외합니다. 독자가 스스로 채워야 하는 이유, 과정, 값이 있으면 그 내용을 전할 문장을 따로 적습니다. 그런 다음 설계 문서의 줄을 하나씩 글의 문장으로 쓰면서 문장마다 표현을 확인하고, 한 단위의 문장을 모두 쓰면 문장들이 서로 이어지는지와 설계한 내용이 빠지지 않았는지 확인합니다. brief는 2단계에서 마지막으로 남긴 핵심 요소가 문장마다 전할 내용이 되므로 설계 문서를 따로 쓰지 않습니다. 문단이 여럿인 요약은 문장을 쓰기 전에 핵심 요소를 문단마다 묶고 문단마다 전할 내용을 정합니다.
4. 초안을 작성하면 검사 스크립트가 AI가 쓴 글에 자주 나오는 표현을 세어 기준치와 비교하고, 자료에 없는 수치를 찾습니다. 기준치는 토스, 카카오, 당근, 네이버 D2, 우아한형제들, NAVER CLOVA 기술 블로그에서 사람이 쓴 글 600편을 같은 스크립트로 측정해 정했습니다. 모델은 빈도가 기준치를 넘은 표현을 수정하고, 사람이 쓴 글에도 있는 표현은 빈도가 기준치 이하가 되면 더 수정하지 않습니다. 설계 문서가 있으면 스크립트는 글을 설계 문서와 대조해 설계에는 있는데 글에서 빠진 문장과 수치도 찾습니다. 2단계에서 핵심 요소를 추출한 글은 요소마다 적어 둔 키워드(대상의 이름, 수치, 조건)가 글에 있는지도 확인합니다.
5. 초안을 작성하지 않은 별도의 모델(subagent)이 자료 없이 글만 한 번 읽어 스크립트로 찾을 수 없는 직역과 어색한 문장, 설명이 빠진 용어, 문단의 내용과 이어지지 않는 문장, 이유나 과정을 건너뛴 부분, 글의 핵심과 관계없는 부분을 찾아 보고합니다. 글을 쓴 모델은 자료를 확인하면서 보고된 문장을 수정합니다. 수정한 뒤에는 글 전체를 다시 점검하지 않고, 수정한 문장과 그 앞의 세 문장, 뒤의 세 문장만 다시 읽어 확인합니다.

어느 단계에서든 글의 수치와 주장은 사용자가 제공한 자료와 사용자가 알려 준 내용에서 가져옵니다. write가 자료 없이 주제만 받았을 때는 웹에서 출처를 확인한 일반 지식도 함께 사용합니다.

## 잘 쓴 글에서 가져온 구성과 표현 기준

세 스킬은 사람이 잘 쓴 글을 측정해 얻은 기준에 따라 글의 구성과 표현을 정합니다. 측정한 글은 2007~2023학년도 수능 국어 지문 82편, 2013~2015년 신문 기사 1,200편, 2018~2019년 논문 초록 301편, 2003~2019년 대통령 연설문 412편입니다. 수능 국어 지문 중 문단 구분이 남아 있는 46편은 문단과 문장이 하는 일도 분류했습니다. 수능 국어 지문은 독자가 한 번 읽고 이해하도록 다듬은 설명문이라서 구성과 문장 연결의 기준으로 삼았습니다. 신문 기사와 논문 초록은 내용이 지금의 사실과 다를 수 있으므로 글을 쓰는 방식과 표현만 측정했습니다.

| 기준 | 사람이 쓴 글에서 측정한 값 | 스킬이 이 기준을 사용하는 곳 |
|---|---|---|
| 문단 하나는 한 가지 내용을 다룹니다 | 수능 국어 지문 46편의 문단 207개를 분류한 모델은 문단마다 개념 하나, 단계 하나, 견해 하나처럼 한 가지를 다룬다고 기록했습니다 | 설계할 때 단위마다 전할 내용을 한 문장으로 정합니다 |
| 추상적인 문장 다음에 풀이, 예, 이유를 씁니다 | 수능 국어 지문 46편에서 문단의 핵심을 말하는 문장의 바로 다음 문장은 72%가 풀이, 예, 이유였습니다 | 설계할 때 정의나 주장 다음에 올 문장을 정합니다 |
| 새 대상은 글의 앞쪽에서 소개합니다 | 수능 국어 지문에서 문장의 명사 중 그 글에 처음 나오는 명사의 비율은 글의 첫 10%에서 84%, 마지막 10%에서 38%였습니다 | 설계할 때 단위의 순서를 정합니다 |
| 글의 끝에서 앞 내용을 다시 요약하지 않습니다 | 수능 국어 지문 46편 중 앞 내용을 다시 정리하는 문장으로 끝난 글은 5편이었습니다 | 마지막 단위를 앞 내용의 요약으로 쓰지 않습니다 |
| 문장은 앞 문장에서 말한 대상으로 시작합니다 | 수능 국어 지문에서 문단 안의 문장은 81%가 바로 앞 문장의 명사를 다시 사용했고, 그 명사는 문장의 앞쪽에 있었습니다 | 문장을 쓸 때와 단위를 점검할 때 확인하고, 검사 스크립트가 앞 문장과 이어지지 않는 문장을 찾습니다 |
| 명사 사이의 관계를 조사와 서술어로 풀어 씁니다 | 조사 없이 명사를 넷 이상 이은 구는 수능 국어 지문에서 1,000자당 0.17개, 신문 기사에서 1.23개였습니다. 스킬은 명사를 풀어 쓰는 수능 국어 지문을 기준으로 삼습니다 | 문장을 쓸 때 지키고, 검사 스크립트가 명사를 이은 구를 찾습니다 |
| 한 문장에는 사실 하나와 그 사실의 조건이나 이유를 씁니다 | 수능 국어 지문의 문장 길이는 공백을 포함해 중앙값 59자였고 한 문장의 절은 평균 2.3개였습니다 | 핵심 요소와 설계 문서의 줄 하나에 내용 하나를 적습니다 |
| 전하는 일에 맞는 서술어를 사용합니다 | 사람이 쓴 글에는 문장이 전하는 일마다 자주 사용하는 서술어가 있었습니다. 이유를 밝히는 "~때문이다"는 수능 국어 지문의 문장 중 3.1%에, 조사한 결과를 전하는 "~것으로 나타났다"는 논문 초록의 문장 중 1.8%에 나왔습니다 | 이유, 결과, 결정, 계획처럼 문장이 전하는 일마다 서술어를 정해 둔 표를 읽습니다 |

이 기준 중 글의 구성은 세 스킬이 함께 읽는 `planning.md`에, 문장의 표현은 `style-guide.md`에 있습니다. 검사 스크립트와 별도 모델의 점검도 같은 기준으로 글을 확인합니다. 측정 방법과 전체 결과는 [`dev/baseline/write`](dev/baseline/write/README.md)에 있습니다.

## 설치

### Claude Code

Claude Code 세션에서 marketplace를 등록하고 플러그인을 설치합니다.

```
/plugin marketplace add KANG-YEONWOOK/K-Writer
/plugin install k-writer@k-writer
```

새 버전으로 업데이트하려면 아래 명령을 실행한 뒤 Claude Code를 다시 시작합니다.

```bash
claude plugin marketplace update k-writer
claude plugin update k-writer@k-writer --scope user
```

### Codex

`codex plugin add` 명령을 지원하는 Codex CLI에서 아래 명령을 실행합니다.

```bash
codex plugin marketplace add KANG-YEONWOOK/K-Writer
codex plugin add k-writer@k-writer
```

업데이트할 때는 아래 명령을 실행하고 새 세션을 엽니다.

```bash
codex plugin marketplace upgrade k-writer
codex plugin add k-writer@k-writer
```

### 스킬 폴더 직접 복사

플러그인을 설치하지 않고 `skills/` 아래의 스킬 폴더를 개인 스킬 폴더에 복사해도 같은 스킬을 사용할 수 있습니다. 개인 스킬 폴더는 Claude Code에서는 `~/.claude/skills/`, Codex에서는 `~/.agents/skills/`입니다. Codex에서 폴더를 직접 복사하고 플러그인도 설치하면 스킬이 두 번 표시되므로 둘 중 하나만 선택합니다.

```bash
git clone https://github.com/KANG-YEONWOOK/K-Writer.git
mkdir -p ~/.claude/skills && cp -r K-Writer/skills/* ~/.claude/skills/   # Claude Code
mkdir -p ~/.agents/skills && cp -r K-Writer/skills/* ~/.agents/skills/   # Codex
```

### 필요한 환경

Python 3.8 이상이 있으면 스킬은 외부 패키지 없이 검사 스크립트를 실행합니다. Python이 없으면 스킬은 검사 항목과 통과 조건을 정리한 문서를 읽어 글을 직접 점검한 뒤, 자동 검사를 실행하지 못했다고 보고합니다. 스킬마다 추가로 필요한 도구는 각 스킬의 README에 있습니다.

### 실행 시간과 비용

스킬을 한 번 실행하는 데 드는 시간과 비용은 자료와 글의 길이에 따라 다릅니다. 현재 버전은 0.9.0이고, 0.9.0에서 다시 측정하지 않은 경우에는 가장 최근에 측정한 버전의 값을 적었습니다. 아래 값은 Claude Code를 대화 없이 실행하는 명령(`claude -p`)에 Claude Opus 5.5 모델을 지정해 케이스마다 한 번씩 실행한 결과이고, 비용은 Claude Code가 실행을 마치면서 보고한 API 사용 금액입니다. K-Writer 0.7.0의 글쓰기 스킬 write 6건 중 본문이 1,200자 이하인 글 5건은 건당 6.5~12.7분, 2.29~4.05달러가 들었고 본문이 6,567자인 글 1건은 29.7분, 8.63달러가 들었습니다. write는 0.7.0부터 문장을 쓰기 전에 설계 문서를 작성하므로 0.6.0보다 시간과 비용이 더 듭니다. 같은 날 같은 자료 4건을 두 버전으로 실행한 합계는 0.6.0이 49.5분, 13.91달러였고 0.7.0이 58.8분, 18.08달러였습니다. techblog는 엔지니어링 노트 한 건을 본문 4,000자 남짓한 글로 정리하는 데 0.6.0에서 18.9분, 5.01달러가 들었고 설계 단계를 추가한 0.7.1에서 24.1분, 7.08달러가 들었습니다. 요약 스킬 brief는 0.6.0에서 8건을 실행했을 때 한 건에 4.7~12.9분, 1.54~3.82달러가 들었습니다.

0.9.0에서 추가한 핵심 요소 추출은 시간과 비용을 더 늘립니다. 글을 쓰기 전에 요소를 추출하고 줄이는 단계를 거치기 때문입니다. brief에는 0.8.0에서 설계 단계를, 0.9.0에서 핵심 요소 추출을 추가했습니다. 두 단계가 모두 없던 0.7.1과 지금의 0.9.0으로 같은 자료를 요약했을 때의 시간과 비용은 다음과 같습니다. 한 문단 요약은 6.1분, 1.93달러에서 7.9분, 2.40달러로 늘었고, 개발 기록 한 편을 자세히 요약하는 데는 10.3분, 3.07달러에서 19.0분, 5.24달러로 늘었습니다. 이 자세한 요약에서 모델은 처음에 요소 46개를 추출한 뒤 20개로 줄였습니다. 한 줄 요약 한 건은 0.9.0에서 3.4분, 1.36달러가 들었습니다. write는 분량을 1,000자 안팎으로 정한 글 한 건이 0.7.0의 12.7분, 4.05달러에서 0.9.0의 14.6분, 4.34달러로 늘었습니다. 분량을 정하지 않은 write와 techblog의 글은 핵심 요소를 추출하지 않으므로 0.9.0에서 다시 측정하지 않았습니다. 실행 조건은 [`EVALUATION.md`](EVALUATION.md)의 K-Writer 0.9.0 섹션, 0.8.0 섹션, 0.7.0과 0.7.1 섹션, 0.6.0 섹션에 있습니다.

## 스킬

K-Writer를 설치하면 write, techblog, brief 세 스킬을 사용할 수 있습니다. 세 스킬은 같은 한국어 문장 규칙과 어투 규칙에 따라 글을 쓰고 같은 검사 스크립트로 점검하지만, 글의 목적을 정하는 방식은 다릅니다. write는 글의 종류를 미리 정해 두지 않은 기본 스킬이라 자료나 주제, 목적, 분량, 어투를 모두 사용자에게 받고, 요청에 없는 값은 글을 쓰기 전에 묻습니다. 자료 없이 주제만 받으면 웹에서 출처를 확인한 일반 지식도 함께 사용합니다. techblog와 brief는 글의 목적과 구성을 미리 정해 둔 스킬이라 목적을 묻지 않습니다.

| 스킬 | 하는 일 | 사용자가 정하는 값 | 호출 | 문서 |
|---|---|---|---|---|
| write | 자료(파일, URL, 붙여넣은 텍스트)나 주제로 목적에 맞는 글을 씁니다. 공지, 보고, 제안, 소개 글처럼 기술 블로그 글이나 요약이 아닌 글을 쓸 때 사용합니다. 발표 자료(슬라이드)에 넣을 제목과 문구도 씁니다. | 자료나 주제, 목적, 분량, 어투(합니다체, 해요체, "~다"로 끝나는 해라체, 직접 입력) | Claude Code `/k-writer:write`, Codex `$k-writer:write` | [사용법과 작성 과정](skills/write/README.md) |
| techblog | 논문 PDF, 기술 문서, 웹 페이지, 붙여넣은 텍스트의 핵심 내용을 한국어 기술 블로그 글로 정리합니다. | 자료, 독자, 분량, 어투(합니다체, 해요체) | Claude Code `/k-writer:techblog`, Codex `$k-writer:techblog` | [사용법과 작성 과정](skills/techblog/README.md) |
| brief | 문서, 웹 페이지, 붙여넣은 텍스트, 대화 내용을 요약합니다. | 자료, 분량(한 줄, 한 문단, 자세히), 어투(합니다체, 해요체, 해라체, 직접 입력) | Claude Code `/k-writer:brief`, Codex `$k-writer:brief` | [사용법과 요약 과정](skills/brief/README.md) |

예를 들어 Claude Code에서 `/k-writer:brief report.pdf`를 실행하면 brief가 분량과 어투를 물은 뒤 보고서를 요약합니다. `/k-writer:write`만 실행하면 write가 어떤 자료나 주제로 글을 쓸지부터 묻습니다.

## 검사할 표현을 정한 근거

어떤 표현을 검사할지는 AI가 쓴 한국어 글을 분석한 연구와 측정 결과를 근거로 정했습니다.

- LLM과 관련된 문체 변화를 분석한 [Lee(2026)](https://arxiv.org/abs/2609.07447)에 따르면 한국어 학술지 초록 398,296건에서 "단순한 X를 넘어"가 들어간 초록의 비율은 2019년 0.12%, 2026년 4.93%였습니다.
- AI가 쓴 한국어 글의 표현을 분류하고 사람이 쓴 글과 비교한 GitHub 프로젝트 [im-not-ai](https://github.com/epoko77-ai/im-not-ai)에서 "A가 아니라 B입니다"처럼 한쪽을 부정한 뒤 다른 쪽을 말하는 문장(부정 대구)은 1,000자당 AI가 쓴 글에서 5.8회, 사람이 쓴 글에서 0.6회 나왔습니다.
- LLM이 생성한 한국어 글을 가려내는 연구 [KatFishNet](https://arxiv.org/abs/2503.00032)에서 쉼표가 있는 문장의 비율은 사람이 쓴 에세이가 26.3%, LLM이 생성한 글이 61.0%였습니다.
- 2020년 이전에 사람이 쓴 글에서 "~합니다"나 "~한다"처럼 문장으로 끝난 제목과 소제목은 기술 블로그 글의 소제목 3,259개 중 5.2%, 정부 부처의 보도자료를 모아 공개하는 정책브리핑의 보도자료 제목 1,598개 중 16.5%였습니다. Claude Fable 5.2가 스킬 없이 작성한 발표 자료 6편에서는 슬라이드 제목 56개 중 37.5%, 부제 56개 중 44.6%가 문장으로 끝났습니다. 다만 사람이 만든 발표 자료의 제목은 측정하지 못해서, 위의 비율은 서로 다른 종류의 글에서 측정한 값입니다. 측정 방법과 한계는 [`dev/baseline/headings`](dev/baseline/headings/README.md)에 있습니다.
- 2007~2023학년도 수능 국어 지문 82편 중 문단이 구분된 46편에서, 같은 문단의 앞 두 문장에 나온 단어를 다시 사용하지 않고 지시어나 접속어로 시작하지도 않는 문장은 100문장에 2.4개였습니다. Claude Fable 5.2가 스킬 없이 작성한 보고서 4편에서는 16.1개, 설계 단계가 없던 K-Writer 0.6.0까지의 스킬로 작성한 글 14편에서는 8.1개였습니다. 다만 사람이 쓴 신문 기사 399편에서도 15.1개여서 글의 종류에 따라 값이 다르고, 보고서와 K-Writer로 작성한 글은 표본이 작습니다. 그래서 검사 스크립트는 이런 문장의 수로 글의 합격 여부를 판정하지 않고, 모델이 다시 읽을 문장을 찾는 데만 사용합니다. 측정 방법은 [`dev/baseline/write`](dev/baseline/write/README.md)에 있습니다.
- 사람이 쓴 기술 블로그 글 600편에서 "버전"은 1,305번 나왔지만 version을 의미하는 "판"은 한 번도 나오지 않았습니다. K-Writer 개발자의 컴퓨터에 남은 작업 기록에서 Claude Opus 5.5가 스킬 없이 작성한 개발 문서와 대화 답변(한글 81만 자)에는 같은 의미의 "판"이 74번 나왔습니다. 이 글들은 개발자가 모든 작업에서 모델이 따르도록 설정한 지시문이 있는 상태에서 작성됐고, 평가 기록 문서인 [`EVALUATION.md`](EVALUATION.md)는 이 점을 측정의 한계로 밝힙니다.

## 스킬의 지침 문서에 사용하는 단어

모델이 스킬의 지침 문서에 있는 단어를 글에서도 그대로 따라 사용한다는 것은 K-Writer 0.3.1에서 확인했습니다. 0.3.1 스킬의 지침 문서는 "낱말"을 107번 사용했고 그 문서를 읽고 작성한 글 9편에도 "낱말"이 29번 나왔습니다. 사람이 쓴 기술 블로그 글 600편에서 "낱말"은 한 번도 나오지 않았습니다.

그래서 K-Writer 0.4.0부터는 스킬의 지침 문서도 사람이 쓴 글에서 사용하는 단어로 작성합니다. 글쓰기 평가에 사용하려고 만든 가상의 개발 노트 한 편을 K-Writer 0.3.1과 0.4.0의 techblog로 각각 정리했습니다. 두 최종 글 중 0.3.1의 글에는 version을 의미하는 "판"이 1번 나왔고, "낱말", "시험"처럼 사람이 쓴 글에서는 다른 단어를 사용하는 표현이 있는 문장이 14개 있었습니다. 0.4.0의 글에는 둘 다 없었습니다.

다만 이 비교는 버전마다 한 번씩만 실행했습니다. 또한 비교에 사용한 가상 노트는 규칙을 만드는 과정에서도 사용한 자료라서 이 비교는 독립된 평가가 아닙니다. AI가 쓴 글의 단어 선택 문제를 다룬 외부 자료의 목록과 측정값은 [`plain-terms.md`](dev/baseline/techblog/plain-terms.md)에 있습니다.

## 평가 결과

같은 자료로 스킬을 사용해 쓴 글과 스킬 없이 쓴 글을 비교한 평가는 K-Writer의 이전 저장소인 [Skill-Techblog](https://github.com/KANG-YEONWOOK/Skill-Techblog)에서 진행했습니다. K-Writer 0.1.0의 techblog는 Skill-Techblog 0.11.0과 같은 파일이고, 아래 결과는 그보다 이전 버전인 Skill-Techblog 0.2.0의 techblog로 쓴 글을 평가한 값입니다. 그 뒤의 버전으로 쓴 글은 대부분 이전 버전으로 쓴 글과 비교했고, 그 결과는 [`EVALUATION.md`](EVALUATION.md)에 있습니다.

평가에서는 Claude Opus 5.5가 Skill-Techblog 0.2.0의 techblog로 논문 PDF 5편, 영문 엔지니어링 블로그 글 1편, Python 기능 제안 문서(PEP) 1편을 정리한 글과, 같은 모델에 같은 자료를 스킬 없이 "한국어 기술 블로그 아티클로 정리해 달라"고 요청해 얻은 글을 비교했습니다. 이 평가의 judge 모델(글을 읽고 정해진 기준으로 판정하는 모델)은 Claude Sonnet입니다.

- 같은 자료로 쓴 두 글을 judge 모델에게 순서를 바꿔 두 번 보여 주고, 자연스러운 한국어인지, 자료의 핵심을 정확하게 전달하는지, 구조가 읽기 쉬운지를 기준으로 더 나은 글을 선택하게 했습니다. 자료 7건 중 6건에서 두 번 모두 스킬로 쓴 글을 선택했고 나머지 1건은 순서에 따라 판정이 달라졌습니다.
- 스킬 없이 쓴 글은 목록 비중, 1,000자당 굵은 글씨 수, 1,000자당 세 항목 나열 수, 연결어미 뒤 쉼표의 비율이 사람이 쓴 글의 중앙값과 비교해 지표에 따라 2~12배였습니다. 스킬로 쓴 글은 이 네 지표가 사람이 쓴 글의 중앙값과 비슷하거나 그보다 낮았습니다. 사람이 쓴 글의 값은 2025년 이전의 토스, 카카오, 당근 기술 블로그 글(합니다체 57편, 해요체 31편)의 중앙값입니다. 이 값은 K-Writer 0.2.0에서 표본을 600편으로 늘리기 전에 측정했습니다.
- 검사 스크립트를 통과한 글은 스킬 없이 쓴 글 7편 중 3편이었고, 스킬로 쓴 글은 합니다체 4편과 해요체 3편이 모두 통과했습니다.
- 글의 수치와 주장을 자료 원문과 대조한 judge 모델은 자료와 다르거나 근거가 없는 주장을 스킬 없이 쓴 글에서 글당 중앙값 2건 찾았고, 스킬로 쓴 글에서는 7편 중 1편에서 1건 찾았습니다.

문체를 0~2점으로 채점한 judge 모델의 평균 점수는 스킬 없이 쓴 글이 1.58점이었고 스킬로 쓴 글은 합니다체가 1.50점, 해요체가 1.58점으로 차이가 작았습니다. judge 모델과 글을 쓴 모델이 같은 Claude 계열이므로 이 평가의 판정은 사람 독자의 평가와 다를 수 있습니다.

K-Writer 0.7.0에서 추가한 설계 단계의 효과는 0.7.0으로 작성한 글과 설계 단계가 없던 0.6.0으로 작성한 글을 비교해 확인했습니다. write에 같은 자료와 요청 네 건을 주고 두 버전으로 글을 한 편씩 쓴 뒤, 글을 쓰지 않은 모델(Claude Fable 5.2)에게 어느 글이 어느 버전인지 알리지 않고 두 글을 비교하게 했습니다. 판정은 건마다 두 글의 순서를 바꿔 두 번 받았습니다.

- 어느 글이 독자에게 더 나은지를 묻는 전체 판정은 여덟 번 모두 0.7.0의 글이었습니다. 내용의 순서와 문장의 연결은 여덟 번 중 일곱 번 0.7.0의 글이 나았고 한 번은 차이가 없었습니다.
- 독자에게 필요한 이유, 과정, 수치가 다 있는지는 한 건에서 0.7.0의 글이, 다른 한 건에서 0.6.0의 글이 나았고 두 건은 차이가 없었습니다. 0.6.0이 나은 한 건은 500자 안팎으로 쓴 제안 글이고, 0.7.0의 글은 분량에 맞추면서 자료의 수치 하나를 제외했습니다.
- 글의 핵심과 관계없는 문장은 본문이 6,500자를 넘는 한 건의 0.6.0 글에서만 지적됐고, 나머지 세 건에서는 두 버전 모두 지적이 없었습니다.
- techblog는 노트 한 건으로 0.6.0과 0.7.1을 비교했는데 두 판정이 서로 다른 글을 선택해서 어느 버전이 나은지 확인하지 못했습니다.

이 비교는 버전마다 글을 한 번씩만 썼고 판정한 모델도 글을 쓴 모델과 같은 Claude 계열이므로 참고값입니다. 판정 기준과 판정 결과는 [`EVALUATION.md`](EVALUATION.md)의 K-Writer 0.7.0과 0.7.1 섹션에 있습니다.

K-Writer 0.8.0에서 brief에 추가한 설계 단계의 효과는 0.8.0의 요약과 0.7.1의 요약을 비교해 확인했습니다. 비교한 방법은 0.7.0의 비교와 같습니다. 개발 기록을 자세히 요약한 한 건에서는 두 번의 판정이 모두 0.8.0의 요약을 선택했고 문단의 구성과 문장의 연결을 이유로 들었습니다. 엔지니어링 노트를 한 문단으로 요약한 한 건에서는 두 번 모두 0.7.1의 요약을 선택했습니다. 0.8.0의 요약이 노트가 밝힌 한계 두 가지 중 하나를 빠뜨렸기 때문입니다. 이 한계는 설계에는 적혀 있었지만, 문단이 하나인 요약은 설계 문서를 쓰지 않아서 검사 스크립트가 설계와 요약을 대조하지 않았습니다. 그래서 brief가 설계한 내용을 한 줄씩 요약과 대조하도록 수정하고 다시 실행했습니다. 다시 쓴 요약은 두 번 모두 독자에게 더 낫다는 판정을 받았지만, 문장의 자연스러움과 자료와의 일치에서는 두 번 모두 0.7.1의 요약이 낫다는 판정을 받았습니다.

이 비교도 버전마다 요약을 한 번씩만 작성했고 판정한 모델은 요약을 작성한 모델과 같은 Claude 계열입니다. 판정 결과는 [`EVALUATION.md`](EVALUATION.md)의 K-Writer 0.8.0 섹션에 있습니다.

K-Writer 0.9.0에서 추가한 핵심 요소 추출의 효과는 0.9.0으로 작성한 글과 이전 버전으로 작성한 글을 비교해 확인했습니다. 비교한 방법은 0.7.0의 비교와 같습니다. 요약 네 건과 write의 글 한 건을 0.9.0으로 작성하고, 같은 자료와 요청으로 0.7.0, 0.8.0, 0.8.1이 작성한 글과 짝지어 순서를 바꿔 두 번씩 판정했습니다.

- 엔지니어링 노트를 한 문단으로 요약한 한 건은 300자 안에 맞춰 작성한 0.8.0의 요약과 비교했습니다. 0.9.0의 요약은 글자 수 대신 요소 다섯 개로 분량을 정해 399자였고, 두 번의 판정이 모두 0.9.0의 요약을 선택했습니다. 0.8.0의 요약에서는 주어와 서술어가 맞지 않는 문장과 한계 두 가지를 한 문장에 이은 문장이 지적됐습니다.
- 같은 노트를 한 줄로 요약한 한 건과 개발 기록을 자세히 요약한 한 건도 두 번의 판정이 모두 0.9.0의 요약을 선택했습니다. 다만 자세한 요약에서 한국어 표현은 두 번 모두 근소하게 0.8.0의 요약이 낫다는 판정이었습니다.
- 사용자가 "300자 이내"로 글자 수를 정한 요약 한 건은 0.9.0으로 세 번 실행했고, 여섯 번의 판정이 모두 근소하게 0.8.1의 요약을 선택했습니다. 이 요약의 자료는 Python 인터프리터의 동작을 바꾸자는 제안 문서입니다. 0.9.0의 요약은 그 문서가 제안한 방법이 동작하는 과정의 일부와 속도 추정의 조건을 제외했습니다.
- write로 1,000자 안팎의 글을 쓴 한 건은 두 번의 판정이 서로 다른 글을 선택했습니다. 문단의 순서와 문장의 연결은 두 번 모두 0.9.0의 글이 나았고, 내용의 충분함과 자료와의 일치는 두 번 모두 0.7.0의 글이 나았습니다.

이 결과는 첫 실행의 판정을 본 뒤 요소를 선택하는 규칙을 수정하고 다시 실행한 결과입니다. 처음 규칙은 결론 다음에 한계와 비용을 먼저 남기게 했고, 수정한 규칙은 결론, 근거, 한계를 고르게 남기게 합니다. 수정하기 전의 첫 실행에서는 0.9.0의 한 문단 요약이 근거가 되는 수치 하나를 제외해서 두 번 모두 0.8.0의 요약이 선택됐습니다. 이 비교도 케이스마다 한 번에서 세 번만 실행했고 판정한 모델은 글을 쓴 모델과 같은 Claude 계열입니다. 첫 실행과 수정한 뒤의 판정 결과는 모두 [`EVALUATION.md`](EVALUATION.md)의 K-Writer 0.9.0 섹션에 있습니다.

## 한계

검사 스크립트는 형태소 분석기 없이 정규식으로 표현을 세므로 잘못 검출하는 경우가 있습니다. 그래서 기준치도 사람이 쓴 글에 같은 스크립트를 실행해 얻은 값으로 정했습니다.

문체를 측정한 사람이 쓴 글은 기술 블로그 글 600편, 논문 초록 1,206편, 수능 국어 지문 82편, 신문 기사 1,200편, 대통령 연설문 412편입니다. 이 중 항목의 통과 여부를 판정하는 기준치는 대부분 기술 블로그 글에서 정했습니다. write와 brief는 부정 대구처럼 특정 표현의 빈도를 세는 항목에 이 기준치를 가져와 사용하고, write는 그중 지시어로 시작하는 문장, 번역투, "~라고 봅니다" 세 항목만 수능 국어 지문에서 측정한 빈도로 판정합니다. 문장 길이의 변동이나 목록 비중처럼 글 한 편 전체에서 계산하는 항목은 write와 brief에서 판정하지 않습니다. 기술 블로그 글이 아닌 네 종류의 글은 한 편이 대부분 1,500자 미만이고, 이렇게 짧은 글에서는 이런 항목의 값이 문장 한두 개에 따라 크게 달라져서 기준치를 정하지 못했기 때문입니다. 네 종류의 글 중 수능 국어 지문, 신문 기사, 연설문은 스킬이 글을 설계하고 문장을 잇는 규칙을 정하는 데도 사용했습니다. 논문 초록은 사람이 쓴 요약의 예로 삼아 2018~2021년의 1,206편에서 문장 하나의 길이, 무엇을 바꿨는지 밝히지 않은 문장의 빈도, 해라체 문장 끝의 분포를 측정했습니다. 위 "잘 쓴 글에서 가져온 구성과 표현 기준"에 사용한 301편은 이 중 2018~2019년의 초록입니다. brief는 초록의 문장 하나의 길이(공백을 제외하고 중앙값 59자)를 사용자가 글자 수로 정한 분량을 핵심 요소의 수로 바꾸는 데 사용합니다.

글을 설계하는 규칙은 수능 국어 지문을 기준으로 정했는데, 수능 국어 지문은 시험에 출제하려고 쓴 설명문입니다. 공지나 보고서, 메일처럼 write가 실제로 쓰는 글은 측정하지 못했으므로 이런 글에서는 문단의 순서와 문장을 잇는 방식이 수능 국어 지문과 다를 수 있습니다. 또한 수능 국어 지문 46편에서 문단과 문장이 하는 일(정의, 풀이, 예, 이유 등)을 분류한 것은 사람이 아니라 모델이어서, 이 분류에서 계산한 비율에는 모델이 잘못 분류한 문장이 섞여 있을 수 있습니다.

핵심 요소를 추출하고 선택하는 일은 모델이 합니다. 검사 스크립트는 요소의 형식과, 요소마다 적어 둔 키워드가 글에 있는지만 확인합니다. 독자에게 더 필요한 요소를 남겼는지는 확인하지 못합니다. 분량마다 정한 요소의 수(한 줄 1~2개, 한 문단 3~5개, 자세히 12~20개)는 K-Writer 개발자가 정한 값이고 사람이 쓴 요약에서 측정한 값이 아닙니다. 사용자가 글자 수를 정한 요약은 위 "평가 결과"의 비교에서 0.9.0의 요약이 이전 버전의 요약보다 낫다는 판정을 받지 못했습니다.

초안을 작성하지 않은 모델이 글을 다시 읽는 점검은 실행할 때마다 찾아내는 문장이 다릅니다. 이 점검은 글 하나에 한 번만 하므로 한 번에 찾지 못한 문장은 글에 남습니다.

스킬로 작성한 글에 자료와 다른 내용이 없다는 보장도 없습니다. 글을 공개하기 전에 수치와 고유명사를 자료 원문과 대조해야 합니다.

## 개발

저장소의 구조와 스킬을 추가하는 방법은 [`ARCHITECTURE.md`](ARCHITECTURE.md)에 있습니다. 이 저장소의 README, 스킬의 지침 문서, 커밋 메시지 같은 한국어 글도 [`AGENTS.md`](AGENTS.md)의 작업 규칙에 따라 플러그인의 검사와 점검 절차를 거쳐 작성합니다.

```bash
python -m unittest discover tests        # 단위 테스트
python dev/sync_core.py --check           # 스킬 폴더의 core 복사본이 원본과 같은지 확인
python dev/borrow_thresholds.py --check   # write와 brief가 가져온 기준치가 techblog의 값과 같은지 확인
claude plugin validate .                  # 플러그인 manifest 검사
claude plugin eval . --allow-tools Write Edit --scaffold   # evals/ 케이스로 스킬이 있을 때와 없을 때를 비교
```
