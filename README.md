# K-Writer

K-Writer는 Claude Code와 Codex에서 사용하는 한국어 글쓰기 plugin입니다. 글쓰기 분야마다 skill을 하나씩 담고, 지금 담은 skill은 자료를 한국어 기술 블로그 글로 정리하는 techblog 하나입니다. 다른 분야의 skill은 이후에 추가합니다.

K-Writer의 techblog는 이전 저장소인 [Skill-Techblog](https://github.com/KANG-YEONWOOK/Skill-Techblog)에서 개발한 techblog skill에서 시작했습니다. K-Writer 0.1.0의 techblog는 Skill-Techblog에서 옮겨 올 때의 techblog와 같은 파일이고 K-Writer의 버전은 0.1.0부터 매깁니다. Skill-Techblog에서 techblog의 글을 같은 자료로 skill 없이 쓴 글, 사람이 쓴 기술 블로그 글, 기능을 넣기 전의 techblog가 쓴 글과 비교한 평가의 기록은 [`EVALUATION.md`](EVALUATION.md)에 있습니다.

## 글쓰기 분야와 skill

| 분야 | skill | 호출 명령 | 상태 |
|---|---|---|---|
| 기술 블로그 글 | techblog | Claude Code `/k-writer:techblog`, Codex `$k-writer:techblog` | 사용할 수 있음 |

아래 절에서는 skill마다 하는 일, 만든 방법, 그 분야의 글에 맞는 이유, 사용법을 설명합니다.

## techblog: 기술 블로그 글

techblog는 논문 PDF, 기술 문서, 웹 페이지, 대화에 붙여넣은 텍스트 같은 자료의 핵심 내용을 한국어 기술 블로그 글로 정리합니다. Claude Code와 Codex는 같은 글쓰기 지침과 검사 스크립트를 사용합니다. 검사 스크립트는 skill에 함께 들어 있는 Python 프로그램 세 개(`lint_ko.py`, `revise_ko.py`, `tone_check.py`)입니다. 이 프로그램들은 정해 둔 형태의 표현을 글에서 찾아 세고, 글에 쓴 수치가 자료에서 옮겨 적은 값과 같은지, 고치기 전의 글이나 다른 어투의 같은 글과 같은지 확인합니다. 글의 문체는 토스, 카카오, 당근 같은 한국 테크 기업의 기술 블로그 글을 기준으로 맞춥니다.

### 하는 일

글의 어투는 Default(합니다체)와 Casual(토스식 해요체) 중에서 선택합니다. Casual은 토스와 당근 기술 블로그의 해요체 글처럼 정중한 해요체로만 문장을 맺는 어투이고, "~더라고요", "~네요", "~잖아요" 같은 어미는 넣지 않습니다. 두 어투로 쓴 글의 내용은 같습니다.

글에는 자료에 있는 사실만 담습니다. skill은 글을 쓰기 전에 자료의 수치, 주장, 한계를 fact sheet에 옮겨 적습니다. fact sheet는 자료의 사실과 용어 표(글에 쓸 용어의 표기와 설명)를 모아 두는 작업 파일입니다. 글에 나온 수치가 fact sheet에 있는지는 검사 스크립트가 대조합니다. 글쓴이가 직접 겪은 것처럼 꾸민 경험과 자료에 없는 수치는 넣지 않습니다.

문장마다 무엇에 대한 말인지 드러나게 씁니다. 수치가 든 문장에는 그 수치가 무엇을 측정한 값이고 무엇과 비교한 값인지를 함께 밝힙니다. 구절이 가리키는 자료와 절차를 찾기 어려운 곳과 주어나 목적어가 빠진 곳도 점검합니다. 필요한 명사는 반복하고, 요청에서 글이나 문장의 길이를 제한하지 않았으면 길이를 줄이려고 설명을 생략하지 않습니다. 문장을 수정한 뒤에는 글 전체를 초안과 대조해, 수정한 문장 앞뒤의 문단과 결론에서 주체, 조건, 추정의 강도가 그대로인지 확인합니다.

이웃한 문장이 같은 서술어로 끝나면 동의어로 바꾸기보다 항목을 묶거나 두 문장의 관계를 밝혀 다듬습니다. 검사 스크립트의 `A8.same_predicate_adjacent` 항목은 이런 문장 쌍을 다시 읽을 후보로 보여 주고, 수정할지는 앞뒤 문장을 읽고 정합니다. 같은 종결어미(문장 끝의 어미)로 끝나는 문장이 네 개 이상 이어진 횟수와 평균 문장 길이도 판정에 넣지 않는 참고값입니다.

자료의 말을 옮기는 문장에는 누구의 말인지와 그 말이 주장인지, 결과인지, 추정인지를 밝힙니다. 여러 연구를 인용한 글에서는 "저자들은" 대신 연구 이름을 주어로 삼습니다. 영어 "the authors write"를 옮긴 "~고 써요" 대신 "~라고 말해요", "~라고 결론지었어요"처럼 자료가 한 일에 맞는 동사를 선택합니다.

한 글에서 한 낱말은 한 뜻으로만 사용합니다. 예를 들어 '사용하다'의 뜻으로 "쓰다"가 나온 글에서는 자료의 말을 옮기거나 값을 기록하는 자리에 "쓰다"를 넣지 않습니다. 같은 말이 되풀이되어도 동의어를 번갈아 넣지 않고 문장마다 실제로 하는 말에 맞는 낱말을 선택합니다.

기본 독자는 자료 분야의 지식이 충분하지 않거나 없을 수 있는 사람입니다. 그래서 글의 중심 대상과 처음 나오는 용어는 그 자리에서 무엇인지 설명합니다. 독자가 개발자라고 가정하지 않으므로 자료가 소프트웨어를 다루면 캐시, API, latency 같은 말도 설명할 대상입니다. 설명에는 "STG(stomatogastric ganglion, 위를 움직이는 신경절)"처럼 약어의 풀네임이나 이름을 옮긴 말만 붙이지 않고 그 대상이 무엇이고 무엇을 하는지를 씁니다.

영어 자료를 옮긴 문장도 사람이 쓴 한국어 기술 블로그 글에서 사용하는 말로 씁니다. 영어 구절을 낱말 그대로 옮긴 직역("변화가 남아 있다"), 범위를 "창"으로 나타낸 말("적분 창"), 영어 낱말을 따옴표째 문장에 끼운 말(`"likely"`로 쓴 추정), 숫자 뒤의 틀린 조사("0.7717이에요"가 맞는 자리의 "0.7717예요"), 가운뎃점 `·`, em dash `—`, en dash `–`는 사용하지 않습니다. 검사 스크립트가 이 가운데 정규식(정해 둔 규칙에 맞는 문자열을 찾는 데 사용하는 표기법)으로 찾을 수 있는 형태를 셉니다. 나머지는 이 절 끝에서 설명하는 후처리가 끝난 다음 subagent가 글을 문장마다 다시 읽어 찾고 수정합니다. subagent는 Claude Code나 Codex의 agent(요청을 받아 파일을 읽고 명령을 실행하는 AI)가 작업 하나를 맡기려고 따로 실행하는 또 하나의 agent입니다. subagent는 초안을 쓴 대화의 내용을 이어받지 않습니다.

서술어는 주어, 목적어와 이어 읽어 확인합니다. "새로운 문제가 열렸다", "문제가 닫혔다"처럼 한국어 글에서 사용하지 않는 짝과 여러 일로 읽히는 비유 동사는 그 자리에서 전할 일을 나타내는 서술어로 수정합니다. 이 기준으로 "새로운 문제가 열렸다"는 "새로운 문제가 발생했다"가 됩니다.

초안을 다 쓰고 점검한 뒤에는 후처리를 거칩니다. 초안은 모든 글에 같은 규칙과 같은 점검 기준을 적용해 만듭니다. 이렇게만 하면 수치가 많은 글에서는 같은 비교 기준이 문장마다 되풀이되고, 표를 넣은 글에서는 비교 기준이 표에만 있고 본문 문장에는 없는 곳이 생깁니다. 후처리에서는 초안을 쓰지 않은 subagent가 글 전체를 처음부터 다시 읽고 이런 곳을 그 글의 독자에게 필요한 만큼만 남기거나 채웁니다.

### 만든 방법

techblog의 글쓰기 규칙과 검사 기준은 사람이 쓴 기술 블로그 글의 측정값, AI 문체에 관한 연구 자료, 이 skill을 만든 사용자가 skill로 쓴 글을 다시 읽고 수정한 기록(사용자 검토), 실제 실행의 평가로 정했습니다.

사람 글은 토스, 카카오, 당근 기술 블로그에서 757편을 모은 뒤, 기술 글이면서 종결어미로 어투를 구별할 수 있는 문장의 90% 이상이 한쪽 어투인 224편을 검사 스크립트로 측정했습니다. 검사 스크립트 가운데 `lint_ko.py`는 부정 대구("A가 아니라 B입니다" 같은 문장), 쉼표, 굵은 글씨 같은 표현과 문장 길이를 세고 기준치와 비교하는 lint입니다. 기준치는 항목마다 통과, 경고, 불합격을 가르는 값이고, 많을수록 나쁜 항목은 대부분 사람 글 100편 가운데 95편이 넘지 않는 값까지를 통과로 판정합니다. 이 기준치는 2022-11-30 이전 합니다체 글 57편과 2024-06-30 이전 해요체 글 31편에서 holdout 22편을 뺀 66편으로 계산했습니다. 해요체 글은 2022-11-30 이전 글이 부족해서 기간을 2024-06-30까지 넓혔습니다. holdout은 기준치를 만들 때 일부러 빼 두었다가, 만든 기준치가 사람 글을 얼마나 통과시키는지 확인하는 데 사용하는 글입니다. holdout 22편에 skill의 글에 적용하는 통과 조건(한 번만 나와도 불합격인 표현과 불합격 항목이 없고 경고가 3개 이하)을 적용한 결과 19편(86%)이 통과했습니다. 이 판정에서는 skill의 글에만 적용하는 규칙(어투 혼용, 맞춤법 같은 항목)을 뺐습니다.

2025년 이후 글 136편은 AI 문체 연구가 지목한 지표가 2022-11-30 이전 글보다 높게 나와서 기준치 계산에 넣지 않고 비교에만 사용합니다. 예를 들어 합니다체 글 한 편에 든 부정 대구 문장 수의 중앙값은 2025~2026년 글이 4.0, 2022-11-30 이전 글이 1.0이었습니다. 저장소에는 사람 글의 원문을 두지 않고 URL 목록과 측정값만 둡니다.

AI 문체에 관한 연구 자료로는 어떤 표현을 셀지 정했습니다. 한국어 학술지 초록 398,296건을 분석한 Lee(2026)에서 "단순한 X를 넘어"가 들어간 초록의 비율은 2019년 0.12%, 2026년 4.93%였습니다. 2026년의 4.93%는 2018~2022년 값의 직선 추세로 예상한 값의 60.8배입니다. 한국어 AI 문체를 분류하고 사람 글과 AI 글을 측정한 GitHub 프로젝트 im-not-ai에서는 부정 대구가 AI 글에 사람 글의 9.2배 나왔습니다. LLM(Claude 같은 대규모 언어 모델)이 생성한 한국어 글을 가려내는 연구인 KatFishNet에서 쉼표가 있는 문장의 비율은 사람 에세이가 26.3%, LLM 글이 61.0%였습니다. 검사 항목과 항목별 기준치를 정리한 평가 기준 문서 [`rubric.md`](skills/techblog/references/rubric.md)에는 항목마다 근거 자료의 번호를 달았습니다. AI 문체 표현의 목록(`references/ai-patterns.md`)은 초안을 다 만든 뒤에만 읽습니다. Antislop(2025)은 언어 모델이 반복하는 상투 표현(slop)을 찾아 없애는 방법을 다룬 연구입니다. 이 연구 결과에 따르면 피할 표현의 목록을 초안 작성 전에 보여 주면 효과가 크지 않고 오히려 그 표현이 늘 수 있습니다.

한국어 문장 점검은 아래 "글을 쓰는 순서" 절의 6단계에서 subagent가 글을 문장마다 읽고 유형 목록에 해당하는 문장을 수정하는 점검이고, 그 유형은 사용자 검토 기록에서 나왔습니다. 사용자는 이 skill로 쓰고 lint를 통과한 신경과학 학습 노트 14편을 다시 읽고 414곳을 수정했습니다. 수정한 곳은 한 번 읽어서 뜻이 들어오지 않는 문장 200곳, 영어 관용구와 동사의 직역 81곳, 그 분야에서 사용하지 않는 번역어 41곳, 그 밖의 번역투 40곳, 영어 낱말을 문장 성분으로 끼운 말 33곳, 예스러운 말 17곳, 범위를 "창"으로 나타낸 말 2곳이었습니다. 이 가운데 정규식으로 셀 수 있는 형태만 lint 항목이 됐습니다. 이렇게 만든 검사 스크립트의 한국어 항목은 이 노트 14편과 다른 노트 5편에서 사용자가 수정한 문장 447개 중 16곳에만 걸립니다. 나머지는 6단계의 한국어 문장 점검이 20가지 유형([`korean-review.md`](skills/techblog/references/korean-review.md))으로 문장마다 읽어서 찾습니다. 기본 독자를 자료 분야의 지식이 없을 수 있는 사람으로 정한 것, 정보 전달 글에 맞는 동사("쓰다"보다 "사용하다")를 선택하는 기준, 서술어와 주어의 짝을 확인하는 점검도 사용자 검토(2026-10-18, 2026-11-02)에서 나왔습니다.

후처리는 초안을 쓰지 않은 subagent가 맡습니다. 초안을 쓴 대화에서 바로 후처리했을 때는 같은 자료 4건에서 후처리로 바뀐 절마다 후처리 전과 후를 judge(글을 읽고 두 글 중 더 나은 글을 선택하거나 점수를 매기는 모델)에게 비교하게 했습니다. 무승부를 뺀 판정의 68%만 후처리 쪽이었습니다. judge는 초안 쪽을 선택한 근거로 후처리가 설명 문장과 "다만"으로 시작하는 단서를 지운 곳과, 문형을 바꾸면서 주어와 서술어가 어긋난 문장을 들었습니다. subagent에게 후처리를 맡긴 뒤에는 앞의 4건에 1건을 더한 자료 5건 모두에서 judge가 같은 실행의 후처리 전 초안과 후처리를 마친 글을 순서를 바꿔 두 번 읽고 두 번 모두 후처리를 마친 글을 선택했습니다. 바뀐 절만 비교한 판정도 95%(무승부를 뺀 39번 중 37번)가 후처리 쪽이었고, 후처리가 만든 사실 오류는 없었습니다. 지금 6단계는 독자 점검, 후처리, 한국어 문장 점검, 수정 후 검토를 각각 다른 subagent에게 맡기며, 네 가지 일은 아래 "글을 쓰는 순서" 절의 6번에서 설명합니다.

fact sheet 대조는 자료에 없는 내용이 글에 들어가지 않게 하는 단계입니다. 글에 쓰는 수치와 주장은 fact sheet에서만 가져옵니다. 검사 스크립트는 글의 수치 가운데 fact sheet에 없는 값을 찾습니다. 평가에서는 fidelity judge가 글의 수치와 주장을 자료 원문과 하나씩 대조했습니다.

평가는 skill을 설치한 Claude Code를 headless 모드(`claude -p`, 대화 화면 없이 명령 한 줄로 실행하는 방식)로 실행해서 했습니다. 모델은 Claude Opus 5.5를 추론의 깊이를 높게 정한 설정(`--effort xhigh`)으로 사용했고, 사용자 설정이 결과에 섞이지 않도록 사용자의 CLAUDE.md와 auto memory를 껐습니다. judge 모델은 Claude Sonnet입니다. 같은 자료로 쓴 두 글을 비교하는 pairwise judge에게는 두 글을 순서를 바꿔 두 번 보여 주고, 두 번 모두 같은 글을 선택한 경우만 승패로 셉니다. 문장 단위로는 앞 문장을 읽어야 이해되는 문장의 비율, 1,000자당 어색한 문장 수, 설명이 빠진 말을 judge가 판정합니다. 자세한 방법은 [`EVALUATION.md`](EVALUATION.md)와 [`dev/dogfood/README.md`](dev/dogfood/README.md)에 있습니다.

### 기술 블로그 글에 맞는 이유

기술 블로그 글은 논문과 문서의 사실과 수치를 옮기는 글입니다. 그래서 techblog는 글을 쓰기 전에 수치와 주장을 fact sheet에 적고, 글을 쓴 뒤에는 글의 수치를 fact sheet와 대조합니다. 수치가 든 문장에는 무엇을 측정한 값이고 무엇과 비교한 값인지를 함께 밝혀서, 독자가 자료를 다시 열지 않고도 수치의 조건을 알 수 있게 합니다.

기술 블로그 글의 독자는 자료 분야의 지식이 충분하지 않거나 없을 수 있습니다. 그래서 techblog는 글의 중심 대상과 처음 나오는 용어를 그 자리에서 설명합니다. 6단계에서는 자료를 읽지 않은 subagent가 글만 읽고 설명이 빠진 말을 찾습니다. 자료를 읽은 agent는 빠진 설명을 이미 아는 내용으로 채워 읽기 때문입니다.

한국 테크 기업의 기술 블로그는 합니다체와 해요체로 씁니다. 측정한 사람 글에서 카카오 글은 합니다체로, 당근 글은 해요체로 쓴 글이 많았고 토스 글에는 두 어투가 모두 있었습니다. 그래서 techblog는 어투를 Default와 Casual 중에서 선택하게 합니다. Casual 글은 Default 초안의 문장 끝만 바꿔서 만들고, `tone_check.py`로 두 글의 문장 수와 수치가 같은지 확인합니다.

AI가 쓴 글에는 사람 글보다 훨씬 자주 나오는 표현 습관이 있습니다. "A가 아니라 B입니다" 같은 대구, 문단마다 붙는 굵은 글씨, 근거 없이 항목 셋으로 맞춘 나열, 앞 내용을 다시 요약하는 마무리 문장이 대표적입니다. 기술 블로그 글에서 이런 표현이 드러나면 독자는 글의 내용을 덜 신뢰합니다. 그래서 techblog는 사람이 쓴 기술 블로그 글의 분포로 lint 기준치를 정하고, 이런 표현의 빈도를 사람 글 수준으로 맞춥니다. 빈도를 0으로 만드는 것은 목표가 아닙니다. AI 모델의 글과 사람 글에 나오는 부정 대구를 비교한 논문 Boggia(2026)는 초안을 완성한 뒤 다시 작성하게 하는 사후 rewrite가 모든 장르에서 부정 대구를 0으로 만들어 사람 글과 다른 분포가 된다고 보고했습니다. 그래서 techblog는 기준치를 넘은 항목만 수정하고, 후처리에서도 글 전체를 다시 작성하지 않고 필요한 곳만 수정합니다.

영어 자료를 정리하면 영어 구절을 낱말 그대로 옮긴 직역과 그 분야에서 사용하지 않는 번역어가 생깁니다. 사용자가 이 skill로 쓴 학습 노트에서 수정한 414곳 가운데 직역, 번역어, 번역투가 162곳이었습니다. 그래서 techblog는 이런 표현을 lint와 6단계의 한국어 문장 점검으로 찾습니다.

### 사용법

Claude Code:

```
/techblog paper.pdf
/techblog casual https://arxiv.org/pdf/2309.06180 -o paged-attention.md --defaults
/techblog default design-doc.md 독자는 백엔드 개발자, 분량은 5,000자 안팎
/techblog casual --retone paged-attention.md
```

Codex:

```text
$techblog paper.pdf
$techblog casual https://arxiv.org/pdf/2309.06180 -o paged-attention.md --defaults
$techblog default design-doc.md 독자는 백엔드 개발자, 분량은 5,000자 안팎
$techblog casual --retone paged-attention.md
```

위 예시의 `/techblog`와 `$techblog`는 skill 폴더를 복사해 직접 설치했을 때의 이름입니다. plugin으로 설치해도 이 이름으로 호출할 수 있지만, plugin의 skill을 명시적으로 호출할 때는 `/techblog` 대신 `/k-writer:techblog`, `$techblog` 대신 `$k-writer:techblog`를 사용하거나 Codex의 skill 선택기(설치한 skill 목록에서 실행할 skill을 선택하는 기능)로 지정합니다.

위 호출은 각 제품의 대화 입력입니다. 셸에서 대화 없이 `codex exec`로 호출할 때는 셸이 `$techblog`를 셸 변수로 읽어 다른 값으로 바꾸지 않도록 `codex exec` 뒤의 호출 문자열 전체를 작은따옴표로 감쌉니다.

```bash
codex exec '$techblog default design-doc.md -o article.md --defaults'
```

글을 쓰기 전에 skill은 요청에 없는 설정값을 묻습니다. 새 글이면 독자, 어투, 분량이 질문 대상이고, 어투만 바꿀 때(`--retone`)와 짧은 글 모드(short, 프로그램이 만든 짧은 영어 글을 구조 그대로 한국어로 옮기는 모드)에서는 어투만 묻습니다. 요청에 이미 적은 값은 다시 묻지 않습니다. Claude Code는 선택지 질문 창으로 묻고 Codex는 대화에 선택지와 기본값을 적어 묻습니다.

| 설정값 | 기본값 | 다른 선택지 |
|---|---|---|
| 독자 | 사전 지식이 없는 사람(자료 분야의 지식이 충분하지 않거나 없을 수 있는 사람) | 그 분야를 공부하는 사람, 그 분야 실무자나 연구자, 직접 입력(예: 백엔드 개발자) |
| 어투 | Default(합니다체) | Casual(해요체) |
| 분량 | 자료 크기에 맞춤(논문 한 편이면 공백 제외 5,000~10,000자) | 짧게(3,000~5,000자), 자세히(10,000~15,000자), 직접 입력 |

`--defaults`를 붙이면 묻지 않고 빈 값을 기본값으로 채웁니다. `claude -p`, `codex exec`처럼 답할 사람이 없는 실행에서는 값을 모두 적거나 `--defaults`를 붙입니다. 질문을 보낼 수 없는 환경이면 skill이 기본값으로 진행하고 사용한 값을 보고합니다.

| 인자 | 설명 |
|---|---|
| `default`, `casual` | 글의 어투를 정합니다. 생략하면 skill이 묻고, `--defaults`가 있으면 Default(합니다체)로 씁니다. `합니다체`, `해요체`라고 써도 됩니다. |
| 자료 | 정리할 자료의 파일 경로(PDF, 마크다운, 텍스트)나 URL입니다. 생략하면 대화에 붙여넣은 텍스트를 자료로 사용합니다. |
| `-o <경로>` | 글을 저장할 파일 경로입니다. 생략하면 현재 폴더에 글 주제를 나타내는 영문 이름(예: `cache-invalidation-latency.md`)으로 저장합니다. |
| `--retone` | 이미 쓴 글의 어투만 바꿉니다. 문장의 순서, 수치, 고유명사는 바꾸지 않습니다. |
| `--keep-work` | 작업 중에 만든 파일인 fact sheet(`<이름>.facts.md`), Default 초안(`<이름>.draft.md`, Casual일 때), 후처리 전 초안 사본(`<이름>.unrevised.md`), 반복 후보 목록(`<이름>.repeats.md`), 독자 점검 결과(`<이름>.reader.md`)를 지우지 않고 남깁니다. 후처리 전 초안 사본과 6단계를 마친 합니다체 글을 비교하면 6단계에서 바뀐 문장을 볼 수 있습니다. |
| `--defaults` | 설정값을 묻지 않고, 요청에 없는 값은 기본값을 사용합니다. 자동 실행에 사용합니다. |
| 추가 지시 | 독자, 분량, 강조할 부분 같은 요청을 문장으로 덧붙일 수 있습니다. 독자와 분량을 적으면 그 값은 묻지 않습니다. |

위 표의 `<이름>`은 글 파일 이름에서 `.md`를 뺀 부분입니다. 예를 들어 글이 `paged-attention.md`면 fact sheet는 `paged-attention.facts.md`입니다.

#### 짧은 글 모드 (short)

짧은 글 모드는 Slack에 올리는 질문, 검토 요청, 답글, 보고, 진행 알림의 고정 문형과 작업 이름처럼 프로그램이 만든 짧은 영어 글을 같은 구조, 순서, 분량, 사실 그대로 한국어로 옮깁니다. 아티클 골격(제목, 도입, 마치며, 참고자료)과 분석은 더하지 않고 읽는 사람에게 직접 하는 말("원하시면", "답해 주세요")도 남깁니다. fact sheet와 subagent 후처리 없이 한 글을 몇 분 안에 끝내는 것이 이 모드의 목표입니다.

```
/techblog short question.en.md -o question.ko.md
/techblog short post-1.en.md post-2.en.md -o ko/ --terms terms.json
```

```text
$techblog short question.en.md -o question.ko.md
```

| 인자 | 설명 |
|---|---|
| `short`, `--short` | 짧은 글 모드로 옮깁니다. |
| 원문 | 영어 Markdown 파일입니다. 여러 개를 줄 수 있습니다. |
| `-o <경로>` | 원문이 하나면 결과 파일, 여럿이면 결과 폴더입니다. 폴더에는 원문마다 `<이름>.ko.md`로 저장합니다. |
| `--terms <JSON>` | `{"영어": "한국어"}` 용어표입니다. 버튼 이름, 단계 이름처럼 화면에 보이는 말을 맞출 때 사용합니다. |
| `casual` | 해요체로 씁니다. 생략하면 skill이 묻고, 기본값은 합니다체입니다. |

이 표의 `<이름>`은 원문 파일 이름에서 확장자(`.md`)를 뺀 부분이라, `post-1.en.md`의 결과는 `post-1.en.ko.md`입니다. `casual`을 생략하면 skill이 어투를 묻고, `--defaults`가 있거나 답을 받을 수 없으면 기본값인 합니다체로 옮깁니다. 결과는 `scripts/lint_ko.py --short --source <원문>`으로 검사합니다. 이 검사는 문장 단위 문체 항목(번역투, "물론입니다" 같은 챗봇 응답 흔적, 어투 혼용, 문장 부호)과 원문 대조 항목(F1~F8: 코드 블록, 문장 안에 끼운 인라인 코드, URL, 멘션과 `{link}` 같은 자리표시자, 숫자, 목록 항목 수, 헤딩 수, 용어표)을 보고, 사람 글의 분포로 정한 아티클 기준(문장 길이, 목록 비중, 질문 비율)은 보지 않습니다. 자세한 규칙은 `skills/techblog/references/short.md`에 있습니다.

### 글을 쓰는 순서

skill은 아래 순서로 글을 씁니다.

1. 자료를 끝까지 읽습니다. Claude Code는 파일 읽기 도구(Read)로 PDF를 20쪽 이하씩 나눠 읽고, Codex는 PDF 도구를 사용하거나 텍스트 추출과 페이지 확인으로 읽습니다. 웹 페이지는 본문 전체를 가져옵니다.
2. 글의 핵심 주제를 한 문장으로 정하고 자료의 수치, 주장, 한계를 fact sheet에 적습니다. 글에 쓰는 수치와 주장은 이 파일에서만 가져옵니다.
3. `references/style-guide.md`를 읽고 글의 제목과 절 구성을 정합니다.
4. Default(합니다체)로 초안을 씁니다. Casual로 요청해도 초안은 먼저 합니다체로 씁니다.
5. `scripts/lint_ko.py`로 초안을 검사하고 기준을 넘은 문장만 수정합니다. 이어서 문장을 하나씩 따로 읽어 무엇에 대한 말인지 알 수 있는지 확인하고 글의 수치와 주장을 fact sheet와 대조합니다.
6. 초안 사본과 반복 후보 목록을 만든 뒤, 자료와 fact sheet를 읽지 않은 subagent에게 먼저 독자 점검(`references/reader-check.md`)을 맡깁니다. 이 subagent는 글만 읽고, 독자가 처음 보는 말마다 글의 설명으로 답할 수 없는 질문(무엇인지, 무엇을 하는지, 이름이 무슨 뜻인지, 나열한 문장에서만 소개하고 따로 설명하지 않았는지)을 `<이름>.reader.md`에 적습니다. 자료를 읽은 agent는 빠진 설명을 아는 내용으로 채워 읽기 때문입니다. 그다음 초안을 쓰지 않은 subagent에게 후처리를 맡깁니다. 후처리 subagent는 초안을 처음부터 끝까지 읽고 독자가 읽다가 멈출 곳을 먼저 적습니다. 그다음 `scripts/revise_ko.py`가 찾은 반복 후보(같은 비교 기준의 반복, 비교 기준 없이 쓴 변화량, 같은 문형의 연속)마다 `references/revision.md`의 판단 질문(수정할지 정할 때 답하는 질문)에 답해 필요한 곳만 수정하고, 독자 점검 결과의 행마다 설명을 더하거나 더하지 않은 이유를 보고합니다. 초안에서 agent가 계산한 차이와 비율은 자료 원문의 표로 다시 확인합니다. 후처리 subagent가 끝나면 상위 agent(초안을 만들고 subagent에게 일을 맡긴 agent)가 초안 사본과 수정한 글을 비교해 검사 기준에 걸린 곳을 수정합니다.

   이어서 또 다른 subagent가 한국어 문장 점검(`references/korean-review.md`)을 합니다. 이 subagent는 제목부터 마지막 절까지 문장마다 읽고 유형 목록 20가지에 해당하는 문장만 수정한 뒤 수정한 곳을 표로 보고합니다. 유형에는 주어, 목적어와 어울리지 않는 서술어와 직역, 그 분야에서 사용하지 않는 번역어, 두 뜻으로 읽히는 문장, 숫자와 원어 뒤 조사, 출처를 밝히지 않은 주어와 직역한 인용 동사, 한 글에서 여러 뜻으로 사용한 낱말, 짝이 없는 부사, 이중 피동과 필요 없는 사동, 겹말, 헷갈리기 쉬운 말과 맞춤법, 같은 뜻에 사람 글이 더 자주 사용하는 동사, 이웃한 문장의 같은 서술어, 가리키는 대상이 글에 없는 구절이 있습니다. 이 점검은 서술어마다 주어, 목적어와 이어 읽고 영어로 되돌려 옮겨야 뜻이 통하는 짝인지, 독자가 무슨 일이 일어났는지 한 가지로 말할 수 있는지, 그 일이 자료가 밝힌 일과 같은지를 확인합니다("새로운 문제가 열렸다"는 "새로운 문제가 발생했다"로 수정합니다). 뜻이 흐린 문장은 수정하기 전에 그 문장이 말하려던 주장을 자료에서 다시 확인합니다. 상위 agent는 보고 표를 한 줄씩 읽고 수치나 사실을 바꾼 수정과 자연스러운 표현을 바꾼 수정을 되돌린 뒤 다시 검사합니다. 마지막으로 앞의 subagent들과 상위 agent의 대화를 이어받지 않은 새 subagent가 초안 사본과 수정한 글을 대조해, 수정한 문장 앞뒤의 문단과 결론에서 주체, 조건, 추정의 강도가 그대로인지 검토합니다(수정 후 검토). 이 subagent는 글을 직접 수정하지 않고 찾은 곳만 보고하며, 수정은 상위 agent가 합니다. 독립 subagent가 없으면 상위 agent가 독자 점검, 후처리, 한국어 문장 점검, 수정 후 검토를 차례로 직접 수행합니다.
7. Casual이면 6단계를 마친 초안의 문장마다 문장 끝(종결어미)만 해요체로 바꾸고, `scripts/tone_check.py`로 두 글의 문장 수와 수치가 같은지 확인합니다.
8. 작업 파일을 지우고, 글을 저장한 경로, 초안과 최종 글의 검사 결과, 후처리에서 수정한 문장 수를 짧게 보고합니다.

초안 규칙과 lint 기준치는 모든 글에 같게 적용됩니다. 그러나 어떤 형태가 읽기 쉬운지는 글마다 다릅니다. 같은 비교 기준을 문장마다 되풀이하는 것이 어떤 글에서는 필요하고 어떤 글에서는 읽기를 방해합니다. 그래서 후처리는 규칙 목록 대신 판단 질문("이 구절을 지우면 독자가 잃는 정보가 있는가", "이 형태가 이 글의 독자에게 더 읽기 쉬운 이유를 한 문장으로 쓸 수 있는가")으로 수정할지 정합니다. lint 기준치와 다른 형태라도 문장 길이, 문단 길이처럼 문장과 문단의 분포를 측정하는 항목의 경고라면, 독자에게 더 읽기 쉬운 이유를 한 문장으로 쓸 수 있을 때 그 형태를 남기고 남긴 이유를 보고합니다. 불합격 항목은 남기지 않습니다.

### 어투

Default 글은 카카오 기술 블로그처럼 합니다체로 씁니다. 절을 시작할 때 "~할까요?" 같은 질문을 넣는 것은 허용합니다.

Casual 글은 토스의 해요체 글과 당근 글처럼 정중한 해요체로 씁니다. 토스 기술 블로그 글 22편을 조사해 보니 해요체로만 쓴 글은 6편이었고, 나머지 글은 합니다체로 썼거나 두 어투를 섞어 썼습니다. techblog는 Casual 글을 해요체로만 씁니다.

Casual 글은 Default 초안의 문장 끝만 바꿔서 만들기 때문에 한 번 실행해서 나온 두 글의 내용은 같습니다. `--retone`으로 이미 쓴 글의 어투를 바꿀 때도 내용은 그대로입니다. 다만 같은 자료로 skill을 두 번 따로 실행하면 모델이 매번 다르게 글을 쓰기 때문에 두 글의 내용이 다를 수 있습니다.

### 평가 기준

평가 기준(rubric) 전체는 [`skills/techblog/references/rubric.md`](skills/techblog/references/rubric.md)에 있습니다. 기준은 Gate, 자동 측정 항목, 점검 후보, 판정 항목으로 나뉩니다.

Gate는 한 번이라도 어기면 불합격인 항목입니다. 자료에 없는 사실, 겪지 않은 경험, 챗봇 응답 흔적("물론입니다", "요청하신 글입니다"), 어투 혼용, 문장 첫머리의 접속부사("그러나", "그래서" 같은 말) 뒤 쉼표, "단순한 X를 넘어" 같은 표현이 Gate에 속합니다. 가운뎃점, em dash와 en dash(영어 문장에 사용하는 긴 줄표와 짧은 줄표), 빼기 기호 문자 `−`, 숫자 뒤 조사 오류("0.7717예요"), 맞춤법 오류("되요", "몇일")도 Gate입니다. 음수는 하이픈 `-`으로 표기합니다. 줄표 대신 띄어 쓴 하이픈(`1단계 - 설정`)도 Gate이므로, 이름과 내용을 가르는 라벨 구분자에는 콜론(`1단계: 설정`)을 사용합니다. 코드와 수식 안의 기호는 세지 않습니다.

자동 측정 항목은 검사 스크립트가 세고 PASS(통과), WARN(경고), FAIL(불합격) 중 하나로 판정합니다. 부정 대구("X가 아니라 Y"), 쉼표, 강조 문장, 문단 끝 교훈, 과사용 어휘, Claude가 영어 표현을 그대로 옮긴 번역투, 추정 표현 중첩, 문장 길이와 종결어미의 분포, 문단 길이가 자동 측정 항목입니다. 기준치는 사람 글의 분포에서 정했고, 기준치 계산에 사용하지 않은 사람 글(holdout) 22편 중 19편(86%)이 이 기준을 통과합니다. 사용자 검토에서 정한 형태 가운데 다섯 가지는 1회부터 FAIL입니다. 범위를 "창"으로 나타낸 말, 따옴표 친 영어 낱말을 문장 성분으로 사용한 말, 자료의 말을 "쓰다", "적다"로 옮긴 문장("~고 써요"), 피동을 두 번 겹친 이중 피동("보여지다", "쓰여지다"), 문제나 질문을 주어나 목적어로 삼아 열다, 닫다로 나타낸 문장("새로운 문제가 열렸다", "문제가 닫혔다")이 이 다섯 가지입니다. 이 가운데 이중 피동은 사람 글에도 나왔지만 걸린 문장이 모두 실제 오류였고, 나머지 네 가지는 사람 글에 나오지 않았습니다. 열다, 닫다로 나타낸 문장은 측정한 224편 가운데 원문을 다시 받을 수 있었던 222편으로 확인했습니다. 예스러운 말("옛", "제시된")은 한 번 나오면 WARN이고 두 번부터 FAIL입니다. 따옴표로 옮긴 말 뒤에는 "라고"와 "고"를 모두 사용합니다.

점검 후보는 판정에 넣지 않고 다시 읽을 문장만 보여 줍니다. 앞 문장에 기대야 뜻이 통하는 문장, 직역 후보("변화가 남아 있다"), "모든 X가 ~지 않았다"처럼 부정이 걸리는 범위가 둘로 읽히는 문장, 한 개념을 두 표기로 쓴 곳이 점검 후보입니다. "모든 X가 ~지 않았다"는 어느 X도 ~하지 않았다는 전부 부정인지, X가 모두 ~한 것은 아니라는 일부 부정인지 문장만으로 정할 수 없습니다. 여러 연구를 인용한 글에서 어느 연구인지 밝히지 않은 주어("저자들은", "세 저자는")가 있는 문장도 보여 줍니다. 학명, 약어, fact sheet 용어 표의 용어는 처음 나온 문장을 보여 주고, 그 자리에 무엇인지 밝힌 설명이 있는지는 skill이 5단계와 6단계에서 그 문장을 읽어 판단합니다. 문제와 질문 밖의 말에 열다, 닫다를 비유로 붙인 말("격차를 닫았다", "새 구간이 열리면")과 "열린 질문"처럼 꾸미는 말로 나타낸 형태도 점검 후보입니다. 면담 방법의 열린 질문이나 수학의 열린 구간처럼 그 분야에서 굳은 용어면 그대로 둡니다. 점검 후보 가운데 한국어 표현에 관한 후보는 검사 스크립트가 "한국어 점검 후보"로 묶어 보여 줍니다. "~하다"로 써도 되는 "~시키다"(필요 없는 사동), "약 N 정도"처럼 같은 뜻이 두 번 들어간 겹말, 짝이 없는 부사("만약" 뒤에 "~면"이 없는 문장)가 이 묶음에 듭니다.

판정 항목은 0~2점으로 매기는 항목입니다. 평가에서는 사람이나 judge 모델이 매기고, 5단계에서는 skill이 초안을 직접 읽고 매깁니다. 자료의 핵심을 빠짐없이 다뤘는지, 주장마다 수치와 근거가 있는지, 문장을 따로 읽어도 무엇에 대한 말인지 알 수 있는지, 한국어가 자연스러운지를 봅니다. 한국어 자연스러움(J5)은 문장마다 판정해 1,000자당 어색한 문장 수를 사람 글과 비교합니다.

5단계에서 점검하는 초안의 합격 조건은 Gate 위반 0, 자동 측정 FAIL 0, WARN 3개 이하이고, 판정 항목은 평균 1.6점 이상이면서 0점이 없어야 합니다. 6단계를 마친 최종 글은 Gate 위반과 FAIL이 없어야 하고, 6단계의 수정 때문에 AI 문체 항목(부정 대구, 쉼표, 강조 문장처럼 문장과 문단의 분포가 아닌 자동 측정 항목)의 판정이 초안보다 나빠지면 안 됩니다. 문장과 문단의 분포 항목(문장 길이, 종결 분포, 문단 길이, 목록, 자료를 주어로 삼은 문장 비율)의 WARN은 후처리에서 그 글에 맞는 형태로 선택한 결과면 남기고, 그 이유를 보고합니다.

### 평가 결과 요약

아래 결과는 skill로 쓴 글을 skill 없이 쓴 글과 비교하거나, 기능을 넣기 전과 넣은 뒤의 skill로 같은 자료를 정리해 비교한 것입니다. 대부분 자료마다 한 번 실행한 결과이고, 실행 조건과 버전은 [`EVALUATION.md`](EVALUATION.md)에 있습니다.

skill로 쓴 글은 같은 자료 7건에서 skill 없이 쓴 글과 비교했습니다. judge는 두 글을 순서를 바꿔 두 번 읽었고, 7쌍 중 6쌍에서 두 번 모두 skill로 쓴 글을 선택했습니다. 나머지 1쌍은 보여 주는 순서에 따라 판정이 갈렸습니다.

문장마다 무엇에 대한 말인지 드러나게 쓰는 규칙의 효과는 같은 자료 4건으로 측정했습니다. 앞 문장을 읽어야 이해되거나 앞 문장을 읽어도 이해되지 않는 문장의 비율은 규칙을 넣기 전 21.3%에서 13.5%로 낮아졌습니다. 사람이 쓴 기술 블로그 글 6편에서 같은 비율은 17.4%였습니다. 규칙을 넣은 뒤의 글은 넣기 전에 같은 자료로 쓴 글과의 비교에서 4쌍 중 3쌍을 이겼고 1쌍을 졌습니다.

영어 자료를 옮긴 문장의 한국어 표현을 점검하는 기능(초안 규칙, 검사 스크립트의 한국어 항목, 6단계의 한국어 문장 점검)은 사용자 검토 노트와 같은 분야의 신경과학 논문 한 편으로 효과를 측정했습니다. 점검을 넣기 전에 쓴 글에는 "100초 창", "가설이 제시됐습니다", "high strength 우선 조절" 같은 표현과 en dash가 있어서 새 검사 스크립트를 통과하지 못했습니다. 점검을 넣은 뒤 같은 논문으로 쓴 글은 Claude Code와 Codex 모두 검사를 통과했습니다. judge가 어색하다고 판정한 문장은 1,000자당 0.44(Claude Code)와 1.20(Codex)에서 둘 다 0.31로 줄었고, 6단계의 한국어 문장 점검은 시험한 글마다 2~21곳을 수정했습니다.

용어 설명, 인용 동사, 한 낱말 한 뜻 규칙은 이 skill로 쓴 학습 노트 14편으로 확인했습니다. 노트 14편은 한 편도 새 검사 스크립트를 통과하지 못했고, 걸린 형태는 자료의 말을 "쓰다", "적다"로 옮긴 문장 87곳과 따옴표 뒤의 "고" 84곳이었습니다. 따옴표 뒤의 "고"는 사용자가 자연스러운 말이라고 판단해서 나중에 검사 항목에서 뺐습니다. 노트 가운데 한 편의 주 자료인 논문을 새 규칙으로 쓴 글은 검사를 통과했고 두 형태가 없었습니다. 새 글의 첫 문장은 "C. elegans(예쁜꼬마선충)는 뉴런이 302개인 선충(실처럼 가늘고 긴 작은 벌레)이에요"였고, judge가 어색하다고 판정한 문장은 1,000자당 그 노트의 0.90에서 새 글의 0.27로 줄었습니다. 그 노트는 노트를 모아 둔 StudyNote 프로젝트의 노트 작성 가이드와 구성 문서도 따랐고 자료도 여러 개였습니다. 그래서 그 노트와 새 글의 차이를 규칙의 차이로만 읽을 수는 없습니다.

독자를 자료 분야의 지식이 없을 수 있는 사람으로 정하고 자료를 읽지 않은 subagent의 독자 점검을 넣은 뒤에는 설명이 빠진 말이 줄었습니다. 앞 문단에서 새 규칙으로 쓴 글(이 기능을 넣기 전의 글)과, 같은 논문을 이 기능을 넣은 뒤의 skill로 정리한 글을 비교하면 judge가 두 번 모두 설명이 빠진 말로 꼽은 말은 17개(pyloric 리듬, gastric mill 리듬, amacrine 세포 같은 신경과학 용어)에서 3개가 됐습니다. LLM이 여러 요청에 동시에 답할 때 메모리를 관리하는 방법을 제안한 PagedAttention 논문을 정리한 글에서 judge가 두 번 모두 설명이 빠진 말로 꼽은 말은 한국어 문장 점검과 용어 설명 규칙을 넣기 전에 `examples/`에 있던 예전 예시 글에서 50개였고, 이 기능을 넣은 뒤의 실행에서 나와 지금 `examples/`에 있는 글에서 0개였습니다. 이 50개와 0개의 차이에는 그 사이에 넣은 다른 기능의 효과도 들어 있습니다. 독자 점검을 넣을 때 정보 전달 글에 맞는 동사를 선택하는 기준도 함께 넣었습니다. 2022-11-30 이전 합니다체 사람 글 57편은 "사용하다"를 모든 뜻의 "쓰다"를 합친 횟수의 13배 많이 사용했고, 같은 글에 "재다"는 한 번도 나오지 않았습니다. 동사 기준을 넣은 뒤의 글에서 '사용' 뜻의 "쓰다"와 "재다", 판단을 옮기는 "~라고 봅니다"가 나온 빈도는 사람 글 수준이었습니다. pairwise judge는 두 자료 모두 순서를 바꾼 두 번의 판정에서 비교한 이전 글보다 이 기능을 넣은 뒤의 글을 선택했습니다.

서술어 점검은 서술어 직역 15문장과 그대로 두어야 할 대조 문장 8개를 일부러 넣은 초안으로 시험했습니다. 점검을 넣기 전과 뒤의 skill을 한 번씩 실행했더니 두 버전 모두 15문장을 자료가 밝힌 일에 맞게 수정했습니다. 대조 문장은 점검을 넣은 버전이 8개 모두, 넣기 전 버전이 6개를 그대로 두었습니다. 영어 비유 동사가 많은 자료로 새 글을 만든 실행에서는 자료의 영어 동사 14곳을 fact sheet, 6단계 전 초안, 최종 글에서 각각 판정한 결과 세 파일 모두 직역이 없었습니다.

### 예시

[`examples/`](examples/) 폴더에는 PagedAttention 논문(SOSP 2023, CC BY 4.0)을 정리한 Default 글과 Casual 글이 한 편씩 있습니다. SOSP 2023은 이 논문이 발표된 2023년의 운영체제 분야 학회이고, CC BY 4.0은 출처를 밝히면 복제, 배포, 변형을 허락하는 라이선스입니다. 예시 글 두 편은 techblog를 한 번 실행해서 나왔기 때문에 문장의 순서와 수치가 같고 문장 끝만 다릅니다. 이 실행에 사용한 techblog는 Skill-Techblog에서 독자 점검과 정보 전달 글의 동사 기준을 넣은 때의 버전입니다. 그 뒤에 넣은 다섯 가지 기능(6단계의 수정 후 검토, 이웃한 서술어 반복 점검, 가리키는 대상이 없는 구절의 점검, 주어나 목적어가 빠진 곳의 점검, 위 "평가 결과 요약" 절의 서술어 점검)은 예시 글에 들어 있지 않습니다.

### 한계

검사 스크립트는 형태소 분석기(문장을 뜻을 가진 가장 작은 말의 단위인 형태소로 나누는 프로그램) 없이 정규식으로 표현을 셉니다. 정규식은 사람 글의 일부 표현도 잘못 잡기 때문에, 기준치는 사람 글에 같은 스크립트를 실행해서 얻은 값으로 정했습니다. 사람 글 기준은 토스, 카카오, 당근 세 회사의 기술 블로그 글로만 만들었습니다.

평가에 사용한 judge 모델은 Claude Sonnet입니다. Claude가 쓴 글을 같은 계열의 모델이 판정했으므로 사람 독자의 평가와 다를 수 있습니다. 결과 글은 직접 읽어 확인해야 합니다.

자료와 다른 내용이 글에 들어가지 않는다는 것은 한 번의 실행으로 보장되지 않습니다. 같은 Discord 블로그 글을 두 번 정리하게 했을 때 fidelity judge가 찾은 문제는 0건과 6건이었고, 6건 중 3건이 글의 실제 오류였습니다. 실제 오류는 자료에 없는 "수십만 명"이라는 수치, 초안을 쓴 agent의 추론을 사실처럼 단정한 문장, 두 수치의 기준을 혼동한 문장이었습니다. 후처리는 수정한 문장과 초안에서 agent가 계산한 값만 원문으로 다시 확인하므로, 초안 단계에서 생긴 사실 오류는 후처리 뒤에도 남을 수 있습니다. 글을 공개하기 전에 수치와 고유명사를 원문과 대조해야 합니다.

초안 규칙은 수치가 든 문장마다 무엇과 비교한 값인지 밝히게 합니다. 이 규칙을 처음 넣었을 때는 수치가 많은 글이 "무작위 추측 정확도 20%보다" 같은 비교 기준을 문단마다 되풀이했습니다. 후처리는 이런 반복을 찾아 줄이도록 만들었지만, 후처리 평가에 사용한 초안 9건에서는 이 반복이 다시 나오지 않아서 효과를 확인하지 못했습니다.

검사 스크립트의 한국어 항목은 사용자가 수정한 문장 447개 중 16곳에만 걸립니다. 나머지는 6단계에서 subagent가 문장마다 읽어서 찾기 때문에 실행마다 찾는 문장이 다릅니다. 시험 실행에서도 "역시간 상수"(inverse time constant), "색 지도"(color map) 같은 표현이 점검 뒤에 남았습니다. 주어, 목적어와 어울리지 않는 서술어도 검사 스크립트는 열다, 닫다가 든 형태만 셉니다. 다른 동사의 짝("오버헤드를 도입한다", "Redis에 산다")은 6단계에서 subagent가 문장을 읽어 찾습니다.

문장 단위 J5 judge는 사용자 검토 노트 2편에서 사용자가 수정한 문장의 26.9%와 22.5%만 어색하다고 판정했습니다. 그래서 J5는 같은 자료로 쓴 글을 비교할 때만 사용합니다. 검사 스크립트의 용어 설명 점검 후보는 학명과 약어가 처음 나온 문장을 보여 줄 뿐, 그 자리에 무엇인지 밝힌 설명이 있는지는 판단하지 못합니다. 이 판단은 skill이 5단계와 6단계에서 문장을 읽어 하고, 평가에서는 judge가 판정 항목 J10(용어 설명을 0~2점으로 매기는 항목)으로 점수를 매깁니다. 같은 글을 다시 판정했을 때 J10 점수는 0점과 2점으로 갈렸습니다. 다의어(뜻이 여럿인 낱말) 검사가 보는 말은 "쓰다"와 "X를 Y로 적다"뿐입니다.

Claude Code로 수행한 후처리 평가에서는 후처리로 실행 시간이 4~6분 늘었고 한 번 실행하는 데 12~17분이 걸렸습니다. 6단계에 한국어 문장 점검 subagent를 하나 더 띄운 뒤로는 한국어 표현 점검의 효과를 측정한 신경과학 논문을 정리하는 Claude Code 실행의 시간과 비용이 16.9분, $5.30에서 28.1분, $9.18로 늘었습니다. Codex 실행 시간은 [`dev/codex/REPORT.md`](dev/codex/REPORT.md)에 기록했습니다.

Windows에서 `claude plugin eval`(plugin의 평가 케이스를 skill이 있을 때와 없을 때로 나눠 실행하고 채점하는 Claude Code 명령)을 실행하면 eval 안에서 Bash를 사용할 수 없습니다. 그래서 Windows에서 eval을 실행할 때 skill은 검사 스크립트 대신 평가 기준 문서(`rubric.md`)를 읽고 직접 점검합니다. techblog는 글에 넣을 이미지나 독자가 누르거나 조작하면 반응하는 웹 페이지 요소(상호작용하는 컴포넌트)를 만들지 않습니다.

## 설치

K-Writer 저장소는 marketplace(설치할 수 있는 plugin의 목록)를 함께 담고 있어서, 저장소 이름으로 marketplace를 등록한 뒤 plugin을 설치합니다.

### Claude Code: plugin marketplace

Claude Code 세션에서 아래 두 명령을 차례로 실행합니다.

```
/plugin marketplace add KANG-YEONWOOK/K-Writer
/plugin install k-writer@k-writer
```

터미널에서 설치할 때는 아래 명령을 사용합니다.

```bash
claude plugin marketplace add KANG-YEONWOOK/K-Writer
claude plugin install k-writer@k-writer
```

설치한 뒤에는 `/techblog` 명령으로 skill을 실행하고, 다른 plugin이나 skill에 같은 이름의 명령이 있으면 `/k-writer:techblog`를 사용합니다. 새 버전은 marketplace와 설치본을 차례로 갱신한 뒤 Claude Code를 다시 시작해 적용합니다.

```bash
claude plugin marketplace update k-writer
claude plugin update k-writer@k-writer --scope user
```

### Claude Code: 직접 설치

이 저장소의 `skills/techblog` 폴더를 Claude Code의 개인 skill 폴더(`~/.claude/skills/`)에 복사해도 같은 skill을 사용할 수 있습니다.

macOS와 Linux에서는 아래 명령을 실행합니다.

```bash
git clone https://github.com/KANG-YEONWOOK/K-Writer.git
mkdir -p ~/.claude/skills
cp -r K-Writer/skills/techblog ~/.claude/skills/
```

Windows PowerShell에서는 아래 명령을 실행합니다.

```powershell
git clone https://github.com/KANG-YEONWOOK/K-Writer.git
New-Item -ItemType Directory -Force "$HOME\.claude\skills" | Out-Null
Copy-Item -Recurse K-Writer\skills\techblog "$HOME\.claude\skills\techblog"
```

### Codex: plugin marketplace

Codex CLI에서 다음 명령을 실행합니다. `codex plugin add`가 있는 CLI가 필요합니다. 버전별 검증 환경과 결과는 [`dev/codex/REPORT.md`](dev/codex/REPORT.md)에 기록합니다.

```bash
codex plugin marketplace add KANG-YEONWOOK/K-Writer
codex plugin add k-writer@k-writer
```

설치한 뒤 새 세션에서 skill 선택기의 techblog를 선택하거나 `$k-writer:techblog`로 명시적으로 호출합니다. plugin 화면에서도 `k-writer` marketplace의 K-Writer를 확인할 수 있습니다. `$techblog`와 자연어 요청도 사용할 수 있지만, plugin으로 설치한 skill을 확실히 지정하려면 선택기를 사용합니다. 업데이트할 때는 다음 명령을 실행하고 새 세션을 엽니다.

```bash
codex plugin marketplace upgrade k-writer
codex plugin add k-writer@k-writer
```

저장소의 수정본을 시험할 때는 GitHub 주소 대신 로컬 저장소 경로를 등록합니다.

```bash
codex plugin marketplace add /absolute/path/to/K-Writer
codex plugin add k-writer@k-writer
```

### Codex: 직접 설치

Codex 대화에서 기본 제공 설치 skill에 아래처럼 요청할 수 있습니다.

```text
$skill-installer KANG-YEONWOOK/K-Writer 저장소의 skills/techblog 스킬을 설치해줘.
```

직접 복사하려면 macOS와 Linux에서 다음 명령을 실행합니다. 목적지에 techblog가 없는 첫 설치를 기준으로 한 명령입니다.

```bash
git clone https://github.com/KANG-YEONWOOK/K-Writer.git
mkdir -p "$HOME/.agents/skills"
cp -R K-Writer/skills/techblog "$HOME/.agents/skills/techblog"
```

Windows PowerShell에서는 아래 명령을 실행합니다.

```powershell
git clone https://github.com/KANG-YEONWOOK/K-Writer.git
New-Item -ItemType Directory -Force "$HOME\.agents\skills" | Out-Null
Copy-Item -Recurse K-Writer\skills\techblog "$HOME\.agents\skills\techblog"
```

특정 프로젝트에서만 사용할 때는 그 프로젝트의 `.agents/skills/techblog`에 복사합니다. `$skill-installer`가 사용하는 `~/.codex/skills`도 지원되는 설치 위치입니다. 직접 설치와 plugin 설치 중 하나만 선택하면 skill이 중복으로 표시되지 않습니다. 직접 복사한 skill은 clone한 K-Writer 저장소를 `git pull`로 업데이트한 뒤 기존 skill 폴더를 백업하고 새 `skills/techblog` 폴더로 교체합니다. 설치나 업데이트가 표시되지 않으면 새 Codex 세션을 엽니다.

### 필요한 환경

- Claude Code 또는 Codex가 필요합니다.
- Python 3.8 이상이 설치돼 있으면 skill이 검사 스크립트(`lint_ko.py`, `revise_ko.py`, `tone_check.py`)를 실행합니다. Python이나 셸이 없으면 같은 기준을 문서로 읽고 직접 점검하며 자동 검사를 하지 못했다고 보고합니다. 검사 스크립트는 외부 패키지를 사용하지 않습니다.
- Claude Code는 PDF를 Read로 읽습니다. Codex에 PDF 읽기 기능이 없으면 PDF를 처리하는 오픈소스 라이브러리 Poppler의 `pdftotext`(텍스트 추출)와 `pdftoppm`(쪽을 이미지로 변환)을 사용합니다. 읽기에 필요한 도구가 없으면 읽을 수 있는 원문을 요청합니다. skill이 도구를 자동으로 설치하지는 않습니다.
- 6단계의 점검과 후처리는 독립 subagent가 제공되면 그 기능을 사용합니다. 사용할 수 없으면 상위 agent가 같은 지침을 직접 수행하고 그 사실을 보고합니다.

### Codex에서 `SKILL.md`가 잘렸다는 경고가 나올 때

`Skill k-writer:techblog exceeded the main prompt context limit and was truncated` 경고는 plugin의 skill을 프롬프트에 넣을 때 `SKILL.md`의 내용이 잘렸다는 뜻입니다. `SKILL.md`는 skill을 실행할 때 가장 먼저 내용 전체가 프롬프트에 들어가는 진입점 파일이고, 맨 앞의 frontmatter(`---` 사이에 skill의 이름과 설명을 적은 부분)와 그 뒤의 지침 본문으로 이루어집니다. Codex 0.155.1과 0.162.1에서 프롬프트에 넣을 수 있는 `SKILL.md`의 크기 한도는 frontmatter를 포함한 파일 전체를 UTF-8(유니코드 글자를 바이트로 저장하는 인코딩 방식)로 저장했을 때의 **8,000바이트**입니다. 한국어 글자 수나 토큰 수로 세지 않습니다.

techblog의 진입점 `SKILL.md`는 한때 24,394바이트였고, 1~8단계 지침을 참조 문서로 옮겨 진입점을 줄였습니다. 각 단계에서 필요한 문서를 읽으므로 글쓰기 규칙, 검사 기준, 어투 변환은 그대로입니다. 경고가 나오면 plugin을 업데이트하고 새 세션에서 skill을 다시 선택합니다. 직접 설치했다면 `SKILL.md` 하나가 아니라 `skills/techblog` 폴더 전체를 교체해야 합니다. 원인과 검증 범위는 [검증 기록](dev/codex/REPORT.md)에 있습니다.

### 이전 plugin에서 옮기기

이전 저장소 Skill-Techblog의 plugin(`techblog@skill-techblog`)을 설치했다면 그 plugin을 지운 뒤 K-Writer를 설치합니다. 두 plugin은 이름이 같은 techblog skill을 담고 있어서, 함께 설치하면 techblog가 두 개 보입니다.

Claude Code에서는 아래 명령으로 이전 plugin과 marketplace를 지우고 K-Writer를 설치합니다.

```bash
claude plugin uninstall techblog@skill-techblog
claude plugin marketplace remove skill-techblog
claude plugin marketplace add KANG-YEONWOOK/K-Writer
claude plugin install k-writer@k-writer
```

Codex에서는 아래 명령을 실행합니다.

```bash
codex plugin remove techblog@skill-techblog
codex plugin marketplace remove skill-techblog
codex plugin marketplace add KANG-YEONWOOK/K-Writer
codex plugin add k-writer@k-writer
```

## 개발

```bash
python -m unittest discover tests        # 단위 테스트
claude plugin validate .                  # plugin manifest 검사
claude plugin eval . --allow-tools Write Edit --scaffold   # evals/ 케이스로 skill이 있을 때와 없을 때를 비교
```

- `dev/baseline/` 폴더에는 사람 글을 측정하는 스크립트(`measure.py`), 측정값으로 기준치를 만드는 스크립트(`calibrate.py`), 후처리 반복 후보가 사람 글에서 몇 개 나오는지 측정하는 스크립트(`repeats_stats.py`), 한국어 점검 항목이 사람 글과 수정 전후 글에서 얼마나 걸리는지 측정하는 스크립트(`ko_stats.py`), 이웃한 서술어 반복 후보를 측정하는 스크립트(`predicate_stats.py`)가 있습니다.
- `dev/dogfood/` 폴더에는 headless Claude Code로 skill을 실행하는 스크립트(`run.py`), 결과 글을 다시 검사하는 스크립트(`evaluate.py`), judge 모델로 결과 글을 평가하는 스크립트(`judge.py`)가 있습니다. `judge.py --within`은 같은 실행의 후처리 전 초안과 후처리를 마친 글을 비교하고, `judge.py`의 korean stage(한국어 판정 단계)는 글의 문장마다 한국어 자연스러움(J5)을 판정합니다. 실행 기록은 `REPORT.md`에 있습니다.
- `evals/` 폴더에는 `claude plugin eval`로 실행하는 평가 케이스가 있습니다.
- [`dev/codex/`](dev/codex/README.md)에는 Codex의 직접 설치, plugin 설치, 실제 글 작성을 검증하는 실행기가 있습니다. 임시 환경에서 실행하므로 개인 skill이나 plugin 설정을 바꾸지 않습니다. 검사 기준과 결과는 해당 문서에 기록합니다.

Codex 구성은 [공식 skill 문서](https://learn.chatgpt.com/docs/build-skills)와 [공식 plugin 문서](https://developers.openai.com/plugins/build/plugins)를 참고했습니다.
