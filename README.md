# K-Writer

K-Writer는 AI가 사람처럼 자연스러운 한국어 글을 쓰게 하는 Claude Code, Codex 플러그인입니다. 스킬은 세 가지입니다. write는 자료나 주제를 받아 사용자가 정한 목적, 분량, 어투에 맞는 글을 씁니다. techblog는 자료를 한국어 기술 블로그 글로 정리하고, brief는 자료를 요약합니다.

AI가 쓴 한국어 글은 문법에 맞아도 어색합니다. 사람이 쓴 글과 비교하면 다음과 같은 문제가 있습니다.

| 문제 | AI가 쓴 문장 | 수정한 문장 |
|---|---|---|
| 같은 문형과 상투적인 표현을 반복합니다 | "캐시 문제가 아니라 배치 크기 문제입니다. 핵심은 배치 크기입니다." | "배치 크기가 원인입니다." |
| 쉼표를 너무 많이 사용합니다 | "캐시를 비우고, 서버를 재시작했습니다." | "캐시를 비우고 서버를 재시작했습니다." |
| 영어 표현을 직역합니다 | "새로운 문제가 열렸습니다."(open) | "새로운 문제가 발생했습니다." |
| 사람이 그 의미로 사용하지 않는 단어를 선택합니다 | "이전 판을 시험했습니다.", "결과 표를 함께 냅니다." | "이전 버전을 테스트했습니다.", "결과 표를 함께 출력합니다." |
| 설명할 내용을 물건이나 몸동작에 비유합니다 | "동작을 못 박았습니다.", "기준은 둘로 갈립니다." | "동작을 명확히 정의했습니다.", "기준은 둘 중 하나입니다." |
| 처음 나온 용어를 설명하지 않습니다 | "write-back이라는 캐시를 사용합니다." | "write-back 캐시(쓰기를 캐시에만 먼저 반영하고 저장소에는 나중에 반영하는 캐시)를 사용합니다." |
| 수치가 무엇을 측정한 값인지 쓰지 않습니다 | "지연이 80% 줄었습니다." | "쓰기 비율이 30% 미만인 서비스에서 p99 지연이 4.2초에서 0.8초로 줄었습니다." |
| 무엇을 무엇으로 바꿨는지 쓰지 않습니다 | "실험 뒤에 배치 설정을 수정했습니다." | "실험 뒤에 무효화 메시지의 배치 크기를 100에서 10으로 바꿨습니다." |
| 값이 얼마이고 누가 정했는지 쓰지 않고 측정값이 아니라고만 합니다 | "타임아웃은 측정값이 아닙니다." | "승인 요청의 타임아웃 5초는 개발팀이 부하 테스트 없이 임시로 정한 값입니다." |
| 자료에 없는 내용을 지어냅니다 | "저희 팀이 직접 운영해 보니 지연이 줄었습니다." | 자료에 있는 사실만 씁니다 |

K-Writer는 세 단계를 거쳐 이런 문제를 줄입니다.

1. 모델이 글을 쓰기 전에 한국어 문장 규칙을 읽습니다. 규칙의 근거는 사람이 쓴 기술 블로그 글과 논문 초록에서 표현과 쉼표의 빈도, 문장 길이 등을 측정한 값과, K-Writer 개발자가 AI가 쓴 글을 다시 읽고 수정한 기록입니다.
2. 초안을 작성하면 검사 스크립트가 AI가 쓴 글에 자주 나오는 표현을 세어 기준치와 비교하고, 자료에 없는 수치를 찾습니다. 기준치는 토스, 카카오, 당근, 네이버 D2, 우아한형제들, NAVER CLOVA 기술 블로그에서 사람이 쓴 글 600편을 같은 스크립트로 측정해 정했습니다.
3. 초안을 작성하지 않은 subagent가 글을 다시 읽어 스크립트로 찾을 수 없는 직역과 어색한 문장, 설명이 빠진 용어를 찾습니다. 찾은 부분을 subagent가 수정하는지 글을 쓴 모델이 수정하는지는 스킬마다 다르고, write에서는 글의 길이에 따라서도 다릅니다. 스킬별 작성 과정은 아래 "스킬" 섹션의 표에 연결한 문서에 있습니다.

사람이 쓴 글에도 있는 표현을 모두 없애지는 않습니다. 표현의 빈도가 기준치 안으로 들어오면 수정을 멈춥니다. 글의 수치와 주장은 사용자가 제공한 자료와 사용자가 알려 준 내용에서만 가져오고, write가 자료 없이 주제만 받았을 때만 웹에서 출처를 확인한 일반 지식을 함께 사용합니다.

## 설치

### Claude Code

Claude Code 세션에서 marketplace(설치할 수 있는 플러그인의 목록)를 등록하고 플러그인을 설치합니다.

```
/plugin marketplace add KANG-YEONWOOK/K-Writer
/plugin install k-writer@k-writer
```

새 버전으로 업데이트하려면 아래 명령을 실행한 뒤 Claude Code를 다시 시작합니다.

```bash
claude plugin marketplace update k-writer
claude plugin update k-writer@k-writer --scope user
```

### Codex

`codex plugin add` 명령을 지원하는 Codex CLI에서 아래 명령을 실행합니다.

```bash
codex plugin marketplace add KANG-YEONWOOK/K-Writer
codex plugin add k-writer@k-writer
```

업데이트할 때는 아래 명령을 실행하고 새 세션을 엽니다.

```bash
codex plugin marketplace upgrade k-writer
codex plugin add k-writer@k-writer
```

### 스킬 폴더 직접 복사

플러그인을 설치하지 않고 `skills/` 아래의 스킬 폴더를 개인 스킬 폴더에 복사해도 같은 스킬을 사용할 수 있습니다. 개인 스킬 폴더는 Claude Code에서는 `~/.claude/skills/`, Codex에서는 `~/.agents/skills/`입니다. Codex에서 폴더를 직접 복사하고 플러그인도 설치하면 스킬이 두 번 표시되므로 둘 중 하나만 선택합니다.

```bash
git clone https://github.com/KANG-YEONWOOK/K-Writer.git
mkdir -p ~/.claude/skills && cp -r K-Writer/skills/* ~/.claude/skills/   # Claude Code
mkdir -p ~/.agents/skills && cp -r K-Writer/skills/* ~/.agents/skills/   # Codex
```

### 필요한 환경

Python 3.8 이상이 있으면 스킬이 검사 스크립트를 실행합니다. 검사 스크립트는 외부 패키지를 사용하지 않습니다. Python이 없으면 스킬은 검사 항목과 통과 조건을 정리한 문서를 읽어 글을 직접 점검한 뒤, 자동 검사를 실행하지 못했다고 보고합니다. 스킬마다 추가로 필요한 도구는 각 스킬의 README에 있습니다.

## 스킬

모든 스킬은 같은 한국어 문장 규칙, 어투 규칙, 검사 스크립트를 사용합니다. write는 글의 종류를 미리 정해 두지 않은 기본 스킬입니다. 자료나 주제, 목적, 분량, 어투를 모두 사용자에게 받고, 요청에 없는 값은 글을 쓰기 전에 묻습니다. techblog와 brief는 글의 목적과 구성을 미리 정해 둔 스킬이라 목적을 묻지 않습니다.

| 스킬 | 하는 일 | 사용자가 정하는 값 | 호출 | 문서 |
|---|---|---|---|---|
| write | 자료(파일, URL, 붙여넣은 텍스트)나 주제로 목적에 맞는 글을 씁니다. 공지, 보고, 제안, 소개 글처럼 기술 블로그 글이나 요약이 아닌 글을 쓸 때 사용합니다. | 자료나 주제, 목적, 분량, 어투(합니다체, 해요체, "~다"로 끝나는 해라체, 직접 입력) | Claude Code `/k-writer:write`, Codex `$k-writer:write` | [사용법과 작성 과정](skills/write/README.md) |
| techblog | 논문 PDF, 기술 문서, 웹 페이지, 붙여넣은 텍스트의 핵심 내용을 한국어 기술 블로그 글로 정리합니다. | 자료, 독자, 분량, 어투(합니다체, 해요체) | Claude Code `/k-writer:techblog`, Codex `$k-writer:techblog` | [사용법과 작성 과정](skills/techblog/README.md) |
| brief | 문서, 웹 페이지, 붙여넣은 텍스트, 대화 내용을 요약합니다. | 자료, 분량(한 줄, 한 문단, 자세히), 어투(합니다체, 해요체, 해라체, 직접 입력) | Claude Code `/k-writer:brief`, Codex `$k-writer:brief` | [사용법과 요약 과정](skills/brief/README.md) |

예를 들어 Claude Code에서 `/k-writer:brief report.pdf`를 실행하면 brief가 분량과 어투를 물은 뒤 보고서를 요약합니다. `/k-writer:write`만 실행하면 write가 어떤 자료나 주제로 글을 쓸지부터 묻습니다.

## 검사할 표현을 정한 근거

어떤 표현을 검사할지는 AI가 쓴 한국어 글을 분석한 연구와 측정 결과를 근거로 정했습니다.

- LLM(Claude 같은 대규모 언어 모델)과 관련된 문체 변화를 분석한 [Lee(2026)](https://arxiv.org/abs/2609.07447)에 따르면 한국어 학술지 초록 398,296건에서 "단순한 X를 넘어"가 들어간 초록의 비율은 2019년 0.12%, 2026년 4.93%였습니다.
- AI가 쓴 한국어 글의 표현을 분류하고 사람이 쓴 글과 비교한 GitHub 프로젝트 [im-not-ai](https://github.com/epoko77-ai/im-not-ai)에서 "A가 아니라 B입니다"처럼 한쪽을 부정한 뒤 다른 쪽을 말하는 문장(부정 대구)은 1,000자당 AI가 쓴 글에서 5.8회, 사람이 쓴 글에서 0.6회 나왔습니다.
- LLM이 생성한 한국어 글을 가려내는 연구 [KatFishNet](https://arxiv.org/abs/2503.00032)에서 쉼표가 있는 문장의 비율은 사람이 쓴 에세이가 26.3%, LLM이 생성한 글이 61.0%였습니다.
- 사람이 쓴 기술 블로그 글 600편에서 "버전"은 1,305번 나왔지만 version을 의미하는 "판"은 한 번도 나오지 않았습니다. K-Writer 개발자의 컴퓨터에 남은 작업 기록에서 Claude Opus 5.5가 스킬 없이 작성한 개발 문서와 대화 답변(한글 81만 자)에는 같은 의미의 "판"이 74번 나왔습니다. 이 글들은 개발자가 모든 작업에서 모델이 따르도록 설정한 지침(전역 지침)이 적용된 상태에서 작성됐고, 평가 기록 문서인 [`EVALUATION.md`](EVALUATION.md)는 이 점을 측정의 한계로 밝힙니다.

모델은 읽은 문서의 단어를 그대로 따라 사용합니다. K-Writer 0.3.1 스킬의 지침 문서에서 "낱말"을 107번 사용했더니 그 문서를 읽고 작성한 글 9편에도 "낱말"이 29번 나왔습니다. 사람이 쓴 기술 블로그 글 600편에서 "낱말"은 한 번도 나오지 않았습니다.

그래서 K-Writer 0.4.0부터는 스킬의 지침 문서도 사람이 쓴 글에서 사용하는 단어로 작성합니다. 글쓰기 평가에 사용하려고 만든 가상의 개발 노트 한 편을 K-Writer 0.3.1과 0.4.0의 techblog로 각각 정리했습니다. 두 최종 글 중 0.3.1의 글에는 version을 의미하는 "판"이 1번 나왔고, "낱말", "시험"처럼 사람이 쓴 글에서는 다른 단어를 사용하는 표현이 있는 문장이 14개 있었습니다. 0.4.0의 글에는 둘 다 없었습니다.

다만 이 비교에서는 버전마다 한 번씩만 실행했습니다. 가상 노트는 규칙을 만드는 과정에서도 사용한 자료라서 이 비교는 독립된 평가가 아닙니다. AI가 쓴 글의 단어 선택 문제를 다룬 문서의 목록과 측정값은 [`plain-terms.md`](dev/baseline/techblog/plain-terms.md)에 있습니다.

## 평가 결과

같은 자료로 스킬을 사용해 쓴 글과 스킬 없이 쓴 글을 비교한 평가는 K-Writer의 이전 저장소인 [Skill-Techblog](https://github.com/KANG-YEONWOOK/Skill-Techblog)에서 진행했습니다. K-Writer 0.1.0의 techblog는 Skill-Techblog 0.11.0과 같은 파일이고, 아래 결과는 그보다 이전 버전인 Skill-Techblog 0.2.0의 techblog로 쓴 글을 평가한 값입니다. 그 뒤의 버전으로 쓴 글은 대부분 이전 버전으로 쓴 글과 비교했고, 그 결과는 [`EVALUATION.md`](EVALUATION.md)에 있습니다.

평가에서는 Claude Opus 5.5가 Skill-Techblog 0.2.0의 techblog로 논문 PDF 5편, 영문 엔지니어링 블로그 글 1편, Python 기능 제안 문서(PEP) 1편을 정리한 글과, 같은 모델에 같은 자료를 스킬 없이 "한국어 기술 블로그 아티클로 정리해 달라"고 요청해 얻은 글을 비교했습니다. 이 평가의 judge 모델(글을 읽고 정해진 기준으로 판정하는 모델)은 Claude Sonnet입니다.

- 같은 자료로 쓴 두 글을 judge 모델에게 순서를 바꿔 두 번 보여 주고, 자연스러운 한국어인지, 자료의 핵심을 정확하게 전달하는지, 구조가 읽기 쉬운지를 기준으로 더 나은 글을 선택하게 했습니다. 자료 7건 중 6건에서 두 번 모두 스킬로 쓴 글을 선택했고 나머지 1건은 순서에 따라 판정이 달라졌습니다.
- 스킬 없이 쓴 글은 목록 비중, 1,000자당 굵은 글씨 수, 1,000자당 세 항목 나열 수, 연결어미 뒤 쉼표의 비율이 사람이 쓴 글의 중앙값과 비교해 지표에 따라 2~12배였습니다. 스킬로 쓴 글은 이 네 지표가 사람이 쓴 글의 중앙값과 비슷하거나 그보다 낮았습니다. 사람이 쓴 글의 값은 2025년 이전의 토스, 카카오, 당근 기술 블로그 글(합니다체 57편, 해요체 31편)의 중앙값입니다. 이 값은 K-Writer 0.2.0에서 표본을 600편으로 늘리기 전에 측정했습니다.
- 검사 스크립트를 통과한 글은 스킬 없이 쓴 글 7편 중 3편이었고, 스킬로 쓴 글은 합니다체 4편과 해요체 3편이 모두 통과했습니다.
- 글의 수치와 주장을 자료 원문과 대조한 judge 모델은 자료와 다르거나 근거가 없는 주장을 스킬 없이 쓴 글에서 글당 중앙값 2건 찾았고, 스킬로 쓴 글에서는 7편 중 1편에서 1건 찾았습니다.

문체를 0~2점으로 채점한 judge 모델의 평균 점수는 스킬 없이 쓴 글이 1.58점이었고 스킬로 쓴 글은 합니다체가 1.50점, 해요체가 1.58점으로 차이가 작았습니다. judge 모델과 글을 쓴 모델이 같은 Claude 계열이므로 이 평가의 판정은 사람 독자의 평가와 다를 수 있습니다.

K-Writer 0.5.1을 만들면서 0.5.0의 brief 8건과 write 4건을 `claude -p`로 한 번씩 실행했을 때, brief는 한 건에 5.0~13.2분이 걸렸고 비용은 1.69~3.61달러였습니다. write는 한 건에 13.1~20.6분이 걸렸고 비용은 4.01~5.66달러였습니다. 실행 조건은 EVALUATION.md의 K-Writer 0.5.1 섹션에 있습니다.

## 한계

검사 스크립트는 형태소 분석기 없이 정규식으로 표현을 세므로 잘못 검출하는 경우가 있습니다. 그래서 기준치도 사람이 쓴 글에 같은 스크립트를 실행해 얻은 값으로 정했습니다. 지금까지 측정한 표본은 사람이 쓴 기술 블로그 글 600편과 논문 초록 1,206편입니다. 초록은 brief의 분량 범위와 검사 항목을 사람이 쓴 요약과 대조하는 데 사용했고(한 문단 분량 범위, 바꾼 내용을 밝히지 않은 문장의 빈도, 해라체 종결 분포), 기준치는 기술 블로그 글에서 측정한 값으로만 정했습니다. 그래서 write와 brief는 부정 대구나 번역투처럼 특정 표현의 빈도를 세는 항목에 기술 블로그 글의 기준치를 가져와 사용하고, 문장 길이나 목록 비중처럼 글의 종류에 따라 달라지는 항목은 판정하지 않습니다.

문장 점검은 subagent가 글을 한 문장씩 읽어 문제를 찾는 방식이라 실행할 때마다 찾아내는 문장이 다릅니다. 스킬로 작성한 글에 자료와 다른 내용이 없다는 보장도 없으므로, 글을 공개하기 전에 수치와 고유명사를 자료 원문과 대조해야 합니다.

## 개발

저장소의 구조와 스킬을 추가하는 방법은 [`ARCHITECTURE.md`](ARCHITECTURE.md)에 있습니다. 이 저장소의 README, 스킬의 지침 문서, 커밋 메시지 같은 한국어 글도 플러그인의 검사와 점검 절차를 거쳐 작성합니다. 작업 규칙은 [`AGENTS.md`](AGENTS.md)에 있습니다.

```bash
python -m unittest discover tests        # 단위 테스트
python dev/sync_core.py --check           # 스킬 폴더의 core 복사본이 원본과 같은지 확인
python dev/borrow_thresholds.py --check   # write와 brief가 가져온 기준치가 techblog의 값과 같은지 확인
claude plugin validate .                  # 플러그인 manifest 검사
claude plugin eval . --allow-tools Write Edit --scaffold   # evals/ 케이스로 스킬이 있을 때와 없을 때를 비교
```
