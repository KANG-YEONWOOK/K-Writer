# write

write는 사용자가 전달한 자료나 주제로 한국어 글을 쓰는 K-Writer의 기본 스킬입니다. 글의 종류를 미리 정해 두지 않고, 글의 목적과 분량, 어투를 사용자에게 받아 그에 맞게 작성합니다. 기술 블로그 글을 작성하는 techblog와 요약을 작성하는 brief는 글의 목적과 구성을 미리 정해 둔 스킬입니다. 설치 방법과 K-Writer 전체 소개는 [저장소 README](https://github.com/KANG-YEONWOOK/K-Writer#readme)에 있습니다.

## 사용법

Claude Code:

```
/write
/write meeting-notes.md 팀에 공유할 회의 정리 글로 써줘
/write 사내 스터디 모집 공지, 해요체로 500자 안팎
/write plain https://example.com/report.pdf -o report-intro.md --defaults
```

Codex:

```text
$write
$write meeting-notes.md 팀에 공유할 회의 정리 글로 써줘
$write 사내 스터디 모집 공지, 해요체로 500자 안팎
$write plain https://example.com/report.pdf -o report-intro.md --defaults
```

다른 플러그인이나 스킬에 같은 이름의 명령이 있으면 Claude Code에서는 `/k-writer:write`, Codex에서는 `$k-writer:write`로 호출합니다. 셸에서 `codex exec`로 실행할 때는 셸이 `$write`를 변수로 해석하지 않도록 명령 전체를 작은따옴표로 감쌉니다.

## 글을 쓰기 전에 정하는 네 가지

write는 아래 네 가지를 모두 정한 뒤에 글을 쓰기 시작합니다. 요청에 이미 적은 값은 다시 묻지 않습니다.

| 값 | 설명 | 요청에 없을 때 |
|---|---|---|
| 자료나 주제 | 글의 바탕이 되는 파일, URL, 붙여넣은 텍스트입니다. 자료가 없으면 주제만 적어도 됩니다. | 어떤 자료나 주제로 글을 쓸지 묻고 답을 기다립니다. 기본값이 없습니다. |
| 목적 | 글을 읽을 사람과, 그 사람이 글을 읽은 뒤 알게 될 내용이나 하게 될 일입니다. 설명, 설득, 안내, 기록 중에서 선택하거나 "협력사에 보내는 일정 변경 메일"처럼 직접 적습니다. | 선택지를 보여 주고 묻습니다. 기본값은 설명입니다. |
| 분량 | 짧게(공백 제외 500자 안팎), 보통(1,500자 안팎), 길게(3,000자 이상) 중에서 선택하거나 "A4 한 장"처럼 직접 적습니다. | 선택지를 보여 주고 묻습니다. 기본값은 목적을 이루는 데 필요한 내용을 모두 쓰는 분량이고 글자 수 상한이 없습니다. |
| 어투 | 합니다체, 해요체, 해라체("~다"로 끝나는 문장) 중에서 선택하거나 "반말로"처럼 직접 적습니다. | 선택지를 보여 주고 묻습니다. 기본값은 합니다체입니다. |

요청에 "공지문", "회의 정리"처럼 글의 종류를 적으면 write는 그 종류에 맞는 목적(공지문은 안내, 회의 정리는 기록)을 정하고 목적을 다시 묻지 않습니다. 주제만 적었는데 모집 기간이나 장소처럼 글에 꼭 필요한 사실이 없으면 그 사실도 함께 묻습니다. 사용자가 알려 주지 않은 사실은 지어내지 않고, 글에서 제외한 뒤 결과 보고에 적습니다.

`claude -p`나 `codex exec`처럼 질문에 답할 사람이 없는 환경에서는 요청에 네 값을 모두 적거나 `--defaults`를 붙입니다. `--defaults`를 붙이면 목적, 분량, 어투 중 요청에 없는 값에 기본값을 사용합니다. 자료나 주제는 이때도 요청에 있어야 합니다.

| 인자 | 설명 |
|---|---|
| `default`, `casual`, `plain` | 글의 어투입니다. 차례로 합니다체, 해요체, 해라체이고 `합니다체`, `해요체`, `해라체`라고 써도 됩니다. |
| 자료 | 글의 바탕이 될 파일(PDF, 마크다운, 텍스트)의 경로나 URL입니다. 대화에 붙여넣은 텍스트도 자료로 사용합니다. |
| `-o <경로>` | 글을 저장할 경로입니다. 생략하면 글 주제를 나타내는 영문 이름으로 현재 폴더에 저장합니다. |
| `--keep-work` | fact sheet(자료의 사실을 모아 둔 파일)와 점검 전 초안 같은 작업 파일을 삭제하지 않습니다. |
| `--defaults` | 목적, 분량, 어투 중 요청에 없는 값을 묻지 않고 기본값을 사용합니다. |
| 추가 지시 | "신입 사원이 읽을 안내문"처럼 문장으로 덧붙입니다. 여기에 적은 값은 다시 묻지 않습니다. |

## 필요한 환경

Python 3.8 이상이 필요합니다. Codex에 PDF를 읽는 기능이 없으면 write는 오픈소스 PDF 라이브러리 Poppler의 `pdftotext`와 `pdftoppm`을 사용합니다. write는 필요한 도구를 자동으로 설치하지 않습니다.

## 목적에 따라 달라지는 것

목적은 글의 구성을 정합니다. 요청에 독자가 없으면 목적에 따라 독자도 가정합니다. 어느 목적이든 글의 핵심을 첫 문단에서 먼저 밝힙니다.

| 목적 | 첫 문단에 쓰는 내용 | 이어지는 내용 |
|---|---|---|
| 설명 | 무엇에 대한 글이고 독자가 무엇을 알게 되는지 | 배경과 문제, 핵심 내용, 근거, 한계와 조건 |
| 설득 | 제안이나 주장 한 문장 | 지금의 문제, 제안 내용, 근거, 비용과 위험, 독자가 결정할 일 |
| 안내 | 독자가 할 일과 기한 | 대상, 일정과 방법, 예외와 주의할 점, 문의할 곳 |
| 기록 | 무슨 일이 있었고 결과가 무엇인지 | 경과, 결정한 것과 남은 일, 원인과 다음에 바꿀 것 |

자료가 사용자나 사용자의 조직이 한 일을 담고 있으면 글에서도 "우리 팀은"처럼 그 조직을 주어로 사용합니다. 논문이나 기사처럼 다른 사람이 작성한 자료를 정리하는 글에서는 자료의 내용을 직접 겪은 일처럼 서술하지 않습니다. 구성의 자세한 규칙은 [`genre.md`](references/genre.md)에 있습니다.

## 글을 쓰는 순서

1. 자료를 끝까지 읽습니다. 주제만 받았으면 사용자가 알려 준 사실과, 웹에서 출처를 확인한 일반 지식을 모읍니다.
2. 자료에서 글에 사용할 사실과 주장을 골라 fact sheet에 정리합니다. 글의 사실은 fact sheet에서만 가져옵니다.
3. 한국어 문장 규칙([`style-guide.md`](references/style-guide.md))과 목적별 구성 지침을 읽고 개요를 작성합니다.
4. 어떤 어투로 요청받아도 먼저 합니다체로 초안을 작성합니다.
5. 검사 스크립트 `lint_ko.py`로 초안을 검사해 불합격으로 판정된 항목의 문장을 수정하고, 글의 수치와 날짜를 fact sheet와 대조합니다. "배치 설정을 수정했습니다"처럼 무엇을 바꾸거나 정했다고 전하는 문장에는 무엇을 무엇으로 바꿨는지, 누가 어떤 값으로 정했는지를 썼는지 확인합니다. 독자가 이 글만 읽고 목적을 이룰 수 있는지도 확인합니다.
6. 초안을 작성한 대화의 내용을 모르는 subagent가 글을 다시 읽습니다.
   - 독자 점검: 자료를 읽지 않은 subagent가 글만 읽고, 무엇인지 알 수 없는 용어와 글에 빠진 정보를 적습니다.
   - 후처리: 독자 점검이 찾은 부분에 설명과 빠진 정보를 추가하고 필요 없는 반복을 줄입니다.
   - 한국어 문장 점검: 다른 subagent가 글을 한 문장씩 읽고 주어와 어울리지 않는 서술어나 직역 같은 어색한 표현과 두 가지 의미로 읽히는 문장을 수정합니다.
   - 수정 후 검토: 점검에서 바뀐 문장과 앞뒤 문맥을 다시 읽어 수치와 조건이 그대로인지 확인합니다.
7. 합니다체가 아닌 어투로 요청했으면 점검을 마친 초안의 문장 끝만 그 어투로 바꾸고, `tone_check.py`로 두 글의 문장 수와 수치가 같은지 확인합니다.
8. 작업 파일을 삭제하고 저장 경로와 검사 결과, 사용자가 채워야 할 사실을 보고합니다.

본문이 공백 제외 1,500자 이상인 글은 6단계의 네 점검을 모두 subagent에게 맡깁니다. 그보다 짧은 글은 독자 점검과 한국어 문장 점검만 subagent에게 맡기고 나머지 두 점검은 write를 실행한 agent가 직접 합니다. subagent를 실행할 도구가 없으면 네 점검을 모두 직접 하고 그 사실을 보고합니다.

## 검사 기준

write는 techblog와 같은 검사 스크립트 `lint_ko.py`를 사용합니다. techblog는 사람이 쓴 기술 블로그 글 600편에서 측정한 기준치로 항목을 판정하지만, write에는 사람이 쓴 글을 측정한 값이 아직 없어서 항목의 종류에 따라 기준을 다르게 적용합니다.

- 한 번만 나와도 불합격인 항목은 techblog와 똑같이 적용합니다. "단순한 X를 넘어" 같은 상투적인 표현, 가운뎃점과 em dash, 맞춤법 오류, 이중 피동, version을 "판"으로 옮긴 표현이 여기에 해당합니다.
- 특정 표현이 얼마나 자주 나오는지 세는 항목 15개는 techblog의 기준치를 가져와 판정합니다. 부정 대구("A가 아니라 B입니다"처럼 한쪽을 부정한 뒤 다른 쪽을 말하는 문장), 강조 문장("핵심은 ~입니다"), 번역투, 연결어미 뒤 쉼표가 여기에 해당합니다. 이런 표현의 빈도는 글의 종류와 관계가 적다고 가정한 임시 기준입니다.
- 문장 길이, 문단 길이, 목록 비중처럼 글의 종류에 따라 달라지는 항목은 값만 보여 주고 판정하지 않습니다.
- 본문이 공백 제외 1,500자 미만인 글에는 짧은 글 기준을 적용합니다. 이 기준은 번역투와 과사용 어휘(AI 글에 지나치게 자주 나오는 단어) 같은 네 항목을 1,000자당 비율 대신 개수로 판정하고, 문장 수가 적으면 문장 하나로 값이 크게 달라지는 항목을 제외합니다.

techblog에서는 "직접 운영해 보니"처럼 겪은 일을 말하는 표현이 불합격입니다. write는 이런 표현이 있는 문장을 그 경험이 자료에 있는지 확인할 후보로 보여 주고, "궁금한 점이 있으면 문의해 주세요"처럼 독자에게 하는 말도 허용합니다. 항목의 정의는 [`rubric.md`](references/rubric.md)에 있습니다.

## 한계

write의 목적별 구성은 글쓰기에서 일반적으로 사용하는 구성이고, 표현의 빈도를 판정하는 기준치도 기술 블로그 글에서 측정한 값이라 공지나 메일 같은 글에는 맞지 않을 수 있습니다.

사용자가 직접 정한 어투(반말, 개조식 등)는 검사 스크립트가 문장 끝을 판정하지 못합니다. 이 경우에는 write가 변환한 문장을 모두 읽어 문장 끝이 그 어투로 이어지는지 확인합니다.

주제만 받은 경우에는 사용자가 알려 준 사실과 웹에서 확인한 일반 지식으로 글을 씁니다. 글을 공개하기 전에 보고의 "채워야 할 사실"과 글의 날짜와 수치를 직접 확인해야 합니다.
