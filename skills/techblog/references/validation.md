# 점검과 마무리: 5~8단계

Default 초안을 작성한 뒤 이 문서와 [checking.md](checking.md)를 읽고 5~8단계를 수행한다. 검사 명령, 검사 결과를 수정하는 방법, 독립 점검의 prompt, 지적을 반영하는 방법, 어투를 적용하는 방법은 checking.md에 있다. 이 문서는 techblog에서 따로 확인할 항목과 보고 형식을 정한다. 점검 대상은 합니다체 글이다. Default 글이면 출력 파일 `<이름>.md`, Casual 글이면 Default 초안 `<이름>.draft.md`다.

4단계에서 문장과 단위를 이미 점검했으므로 5단계부터는 글 전체를 점검한다. 글 전체를 확인하는 점검은 5단계의 검사와 자료 대조, 6단계의 독립 점검이고 각각 한 번만 한다. 그 뒤에는 검사 명령이 출력하는 수정한 부분과 그 앞뒤 세 문장씩만 다시 확인한다.

### 5. 검사하고 자료와 대조하기

1. 검사 명령을 실행하고 checking.md의 "검사 결과 수정하기"대로 수정한다. 검사 명령은 설계 문서(`<이름>.plan.md`)를 찾아 글과 대조한 "설계 대조"도 함께 출력한다. techblog에서는 아래 항목을 이렇게 처리한다.
   - "설계 대조"의 글에서 찾지 못한 계획 문장과 글에 없는 수치: 4단계에서 줄여 쓰거나 빠뜨린 내용이다. 설계의 위치에 다시 쓴다. 쓰지 않기로 했으면 설계 문서에서 삭제하고 "제외한 사실"에 적는다.
   - "설계 대조"의 설계에 없는 문장과 "문장 연결과 주제 점검 후보": 그 문장이 섹션의 전할 내용을 설명하는지, 그 문단이 핵심 주제를 설명하는지 확인하고 설명하지 않으면 삭제한다. 그림, 표, 코드를 소개하는 문장과 용어를 설명하는 문장은 그대로 둔다.
   - 문장 부호 정책(G6)에 따라 영어 인용문 안의 em dash를 쉼표 한 쌍으로 바꾸는 것은 인용을 바꾸지 않는다는 규칙의 예외다. 쉼표로 바꾼 쌍이 나열로 읽히지 않는지 바꾼 문장을 다시 읽는다.
   - "단독 읽기 점검 후보"의 `A18.bare_author`는 글이 연구를 둘 이상 인용하는데 어느 연구인지 밝히지 않은 주어다. 주장과 인용을 옮기는 문장에는 연구 이름을 쓴다. 새로 쓰는 주어는 기술, 설정, 지표의 이름으로 쓴다.
   - "용어 설명 점검 후보"(A20)는 앞의 몇 건만 문장 전체로 출력되고 나머지는 "나머지 N개 항목"에 줄 번호로 출력된다. 그 줄도 읽는다. 용어 표에 없는 용어(`A20.untabled`)는 독자가 모를 용어면 용어 표에 추가하고 설명을 쓴다. 여러 용어를 묶은 행(`A20.table_combined_row`)은 용어마다 나눈다.
   - `A8.same_predicate_adjacent`는 앞뒤 문장을 함께 읽는 후보다. 자연스러운 반복은 그대로 둔다. `A8.ending_run4`는 참고값이므로 값을 낮추려고 동사나 시제를 바꾸지 않는다.
   - `A22.heading_sentence`(문장으로 끝난 제목과 헤딩)는 style-guide.md의 "제목과 헤딩"대로 명사나 명사형으로 끝낸다.
2. 글을 처음부터 끝까지 한 번 읽으면서 수치, 인과, 범위를 말하는 문장을 fact sheet와 대조한다.
   - 수치와 조건: 값, 단위, 비교 기준("~의 20%"와 "~보다 20%")이 원문 표현과 같은가. 수치마다 무엇을 센 값인지, 기간, 제외한 것과 예외, 판단 기준이 fact sheet의 행과 같은가. 줄여 옮기면서 조건 하나가 빠지면 다른 사실이 된다
   - 같은 사실의 다른 위치: 같은 수치, 같은 이름, 같은 규칙을 쓴 문장이 모두 같은 대상과 조건을 말하는가. 여러 대상을 묶어 부른 이름이 다른 묶음의 이름과 겹치지 않는가
   - 열거와 합계: 목록과 합계를 함께 쓴 문장에서 목록이 전체인지 예인지 드러나는가. 합계를 부르는 이름이 합계의 항목 모두에 맞는가
   - 인과와 일반화: "~때문에"는 자료가 설명한 원인인가. "~할수록 ~하다" 같은 법칙 문장이 자료에 있는가. 자료가 예시 하나만 들었으면 그 예시로 쓰거나 추론임을 드러낸다
   - 서술어가 말하는 일: 해결, 미해결, 공개, 종료, 감소처럼 서술어가 말하는 일이 자료와 같은가. 영어 closed를 근거 없이 "해결됐다"로, 줄어든 차이를 "없어졌다"로 쓰지 않았는가
   - 범위와 빈도: "모두", "~뿐", "항상", "자주"가 자료의 표현인가. 도입과 적용 섹션은 자료의 문장을 옮기지 않고 풀어 쓰는 부분이라 이런 표현이 덧붙기 쉽다
   - 방법의 세부: 토큰화 방식, 단위, 설정값처럼 방법을 설명하는 세부 사항이 자료에 있는가
   - 추정과 출처: 자료가 "likely", "may", "suggest"로 쓴 주장이 fact sheet의 한국어 추정 표현으로 쓰였는가. 자료의 말을 옮긴 문장마다 누구의 말인지가 fact sheet의 "인용할 문장"과 같고 동사가 그 문장이 하는 일(주장, 결론, 결과 보고, 추정)과 강도에 맞는가
   - 용어: 글의 표기가 fact sheet 용어 표의 "글에 쓸 표기"와 같고 제목, 헤딩, 본문, 표가 한 개념을 같은 표기로 쓰는가. 용어 설명에 쓴 사실이 자료에 있거나 용어 표에 확인한 출처를 적은 일반 지식인가
3. 같은 읽기에서 아래 문장을 그 바로 앞 문장과 함께 읽고 무엇에 대한 내용인지, 누구의 말인지, 수치가 무엇을 측정한 값이고 무엇과 비교한 값인지 답한다. 답할 수 없으면 빠진 주어, 측정 대상, 비교 기준, 연구 이름을 fact sheet에서 찾아 그 문장에 쓴다.
   - 섹션과 문단의 첫 문장, 수치가 포함된 문장
   - "바꿨다", "정했다", "수정했다"로 끝나는 문장, 개수나 여러 항목을 묶어 부르는 명사만 쓴 문장. 무엇을 무엇에서 무엇으로 바꿨는지, 누가 어떤 값으로 정했는지, 그 항목이 무엇인지가 그 문장이나 바로 앞뒤 문장에 있어야 한다(style-guide.md의 "바꾼 일과 정한 값의 내용 쓰기"). fact sheet와 자료에도 답이 없으면 그 문장을 글에서 제외하고 보고에 적는다
4. 구성을 확인한다.
   - fact sheet 맨 위의 핵심 주제를 다시 읽고 제목과 도입이 핵심 주제를 드러내는지, 섹션마다 핵심 주제의 어느 부분을 설명하는지 확인한다. 섹션의 순서가 설계 문서의 순서와 같고 섹션과 문단마다 설계에 적은 "전할 내용"을 전하는지 확인한다. 핵심 주제를 설명하지 않는 문단과 세부 사항은 삭제하고 설계 문서에도 반영한다.
   - fact sheet의 중심 대상마다 정한 위치(도입이나 첫 섹션의 첫 문단)에 정의가 있는지, 정의가 여러 섹션에 흩어져 있지 않은지 확인한다.
   - 자료의 문제, 방법, 결과, 한계가 글에 모두 있는지 확인한다.
5. 기존 글의 일부를 수정하는 작업이면 수정하기 전에 검사 명령을 한 번 실행해 기존 글을 검사한 글로 저장한다. 수정한 뒤 검사 명령을 다시 실행하면 바뀐 문장만 출력되므로 출력된 문장마다 2와 3을 수행한다.
6. 2~4에서 글을 수정했으면 검사 명령을 다시 실행한다. 이번 출력에는 수정한 부분만 나온다.

### 6. 독립 점검과 수정한 부분 확인

1. checking.md의 "독립 점검"대로 subagent 하나에게 글을 맡긴다. prompt의 독자에는 fact sheet의 "독자" 줄을 그대로 넣는다. 목적에는 "자료를 읽지 않은 독자가 이 글만 읽고 자료의 문제, 방법, 결과, 한계를 이해하는 것"을, 기준 글에는 "사람이 쓴 한국어 기술 블로그 글"을 넣는다.
2. 요청에 `--quick`이 있거나 사용자가 빠르게 써 달라고 했으면 독립 점검을 생략하고 8단계 보고에 적는다.
3. checking.md의 "지적 반영하기"대로 보고의 문단별 내용을 설계 문서의 섹션과 문단마다 적은 "전할 내용"과 비교하고, 표의 행마다 수정할지 정해 수정한다. 용어 설명을 추가할 때는 fact sheet 용어 표의 설명을 사용하고, 일반 지식으로 쓴 설명은 확인한 출처를 용어 표에 적는다. 위치와 순서를 설명하는 그림이나 표를 수정했으면 본문의 이름, 순서, 값과 대조한다.
4. checking.md의 "수정한 부분 확인하기"대로 검사 명령을 실행하고 출력된 부분만 다시 읽는다. 5단계 통과나 Gate 0만으로 이 확인을 생략하지 않는다.

### 7. 어투 적용 (Casual일 때, `--retone`일 때)

- 새 Casual 글은 checking.md의 "어투 적용하기"대로 점검을 마친 Default 초안(`<이름>.draft.md`)의 종결부만 바꿔 출력 파일에 저장하고 어투 검사를 실행한다. "~입니다" 앞이 숫자, 영어, 기호면 tone.md의 "숫자, 영어, 기호 뒤 조사"로 "~이에요"와 "~예요"를 선택한다.
- `--retone`이면 입력 파일은 완성된 글이다. Casual을 Default로 바꿀 때는 tone.md의 대응표를 반대로 적용하고, 어투 검사의 인자 순서는 항상 Default 글, Casual 글로 유지한다. 입력 파일을 수정하거나 작업 파일로 취급해 삭제하지 않는다. 원문의 어투 외 검사 항목(입력에 원래 있던 문장 부호, 숫자 뒤 조사, 주어나 목적어와 어울리지 않는 서술어 포함)은 보고만 하고 내용은 바꾸지 않는다. 바꾼 종결부에서 생긴 숫자 뒤 조사(G10)는 수정한다. 이 모드에서는 fact sheet를 만들지 않는다.

### 8. 정리하고 보고하기

- `--keep-work`가 없으면 checking.md의 "작업 파일 정리하기"대로 이번 실행에서 만든 작업 파일만 삭제한다. 입력 자료와 `--retone` 입력은 작업 파일이 아니다.
- 보고도 사용자가 읽는 한국어 글이다. 요청받은 어투와 관계없이 합니다체로 쓰고 글과 같은 단어를 사용한다(style-guide.md의 "정보 전달 글의 동사", "같은 대상을 부르는 말"). 문장을 바꾼 일은 "수정했습니다", 내용을 글에 쓰지 않은 일은 "제외했습니다", 파일이나 문장을 없앤 일은 "삭제했습니다", 검사 스크립트가 찾은 표현은 "검출된 표현"으로 쓴다. "고쳤습니다", "뺐습니다", "지웠습니다", "짚었습니다", "공백 빼고"는 보고에 사용하지 않는다.
- 사용자에게 짧게 보고하고 글 본문은 대화에 다시 붙여넣지 않는다. 보고에는 아래 내용을 쓴다.
  - 저장 경로, 사용한 자료, 설정값(독자, 어투, 분량)과 값마다 출처(요청, 사용자 선택, 기본값), 본문 글자 수
  - 최종 글의 검사 판정(Gate, FAIL, WARN 수)과 남긴 WARN의 이유, Casual이면 어투 검사 결과
  - 설계: 단위와 문장의 수, 마지막 검사의 "설계 대조"에 남은 항목과 남긴 이유, 설계 문서의 "제외한 사실"에 적은 항목
  - 독립 점검: 사용한 방식(독립 subagent, 직접 점검, 생략), 지적된 행 수와 수정한 수, 수정하지 않은 지적과 이유
  - 일반 지식으로 설명한 용어와 확인한 출처, 확인하지 못해 자료의 설명만 쓴 용어, 자료에 답이 없어서 해결하지 못한 지적
- 최종 글의 조건은 Gate 위반 0, FAIL 0이다. 문장과 문단의 분포 항목(A8, A9, A16, A17)의 WARN은 의도한 형태면 남길 수 있다. 점검 후보(CHECK)를 읽지 않은 채 점검을 마쳤다고 보고하지 않는다.
