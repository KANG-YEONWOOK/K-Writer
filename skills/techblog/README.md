# techblog

techblog는 논문 PDF, 기술 문서, 웹 페이지, 붙여넣은 텍스트의 핵심 내용을 한국어 기술 블로그 글로 정리하는 K-Writer 스킬입니다. 자료를 짧게 요약할 때는 brief 스킬을, 기술 블로그가 아닌 글을 쓸 때는 write 스킬을 사용합니다. 설치 방법과 K-Writer 전체 소개는 [저장소 README](https://github.com/KANG-YEONWOOK/K-Writer#readme)에 있습니다.

## 사용법

Claude Code:

```
/techblog paper.pdf
/techblog casual https://arxiv.org/pdf/2309.06180 -o paged-attention.md --defaults
/techblog default design-doc.md 독자는 백엔드 개발자, 분량은 5,000자 안팎
/techblog casual --retone paged-attention.md
```

Codex:

```text
$techblog paper.pdf
$techblog casual https://arxiv.org/pdf/2309.06180 -o paged-attention.md --defaults
$techblog default design-doc.md 독자는 백엔드 개발자, 분량은 5,000자 안팎
$techblog casual --retone paged-attention.md
```

다른 플러그인이나 스킬에 같은 이름의 명령이 있으면 Claude Code에서는 `/k-writer:techblog`, Codex에서는 `$k-writer:techblog`로 호출합니다. 셸에서 `codex exec`로 실행할 때는 셸이 `$techblog`를 변수로 해석하지 않도록 명령 전체를 작은따옴표로 감쌉니다(`codex exec '$techblog default design-doc.md --defaults'`).

요청에 독자, 어투, 분량이 없으면 글을 쓰기 전에 이 값을 묻습니다. 기본값은 사전 지식이 없는 독자, Default 어투, 자료 크기에 맞춘 분량(논문 한 편이면 공백 제외 5,000~10,000자)입니다. `claude -p`나 `codex exec`처럼 질문에 답할 사람이 없는 환경에서 실행할 때는 `--defaults`를 붙입니다.

| 인자 | 설명 |
|---|---|
| `default`, `casual` | 글의 어투입니다. `합니다체`, `해요체`라고 써도 됩니다. |
| 자료 | 정리할 파일(PDF, 마크다운, 텍스트)의 경로나 URL입니다. 생략하면 대화에 붙여넣은 텍스트를 사용합니다. |
| `-o <경로>` | 글을 저장할 경로입니다. 생략하면 글 주제를 나타내는 영문 이름으로 현재 폴더에 저장합니다. |
| `--retone` | 이미 작성한 글의 어투만 바꿉니다. 문장 순서, 수치, 고유명사는 바꾸지 않습니다. |
| `--keep-work` | fact sheet와 후처리 전 초안 같은 작업 파일을 삭제하지 않습니다. |
| `--defaults` | 설정값을 묻지 않고 기본값을 사용합니다. |
| 추가 지시 | "독자는 백엔드 개발자"처럼 문장으로 덧붙입니다. 여기에 적은 값은 다시 묻지 않습니다. |

어투는 Default(합니다체)와 Casual(해요체) 중에서 선택합니다. Casual 글은 "~더라고요", "~네요" 같은 어미를 사용하지 않고 정중한 해요체로만 문장을 끝냅니다. Casual로 요청하면 먼저 Default 글을 완성한 뒤 문장 끝만 바꿔 Casual 글을 만듭니다. 그래서 두 글은 문장 끝만 다르고 내용은 같습니다. 이때 Default 글은 작업 파일이므로 `--keep-work`를 붙이지 않으면 Casual 글을 만든 뒤 삭제합니다.

[`examples/`](https://github.com/KANG-YEONWOOK/K-Writer/tree/main/examples) 폴더에는 LLM이 여러 요청에 동시에 답할 때 메모리를 관리하는 방법을 제안한 PagedAttention 논문(SOSP 2023, CC BY 4.0)을 techblog로 정리한 Default 글과 Casual 글이 있습니다.

## 필요한 환경

Python 3.8 이상이 필요합니다. Codex에 PDF를 읽는 기능이 없으면 techblog는 오픈소스 PDF 라이브러리 Poppler의 `pdftotext`(텍스트 추출)와 `pdftoppm`(페이지를 이미지로 변환)을 사용합니다. techblog는 필요한 도구를 자동으로 설치하지 않습니다.

## 글을 쓰는 순서

1~5단계에서는 모든 글에 같은 규칙과 기준치를 적용해 초안을 작성하고 점검합니다. 6단계에서는 초안을 작성한 대화의 내용을 모르는 subagent 네 개가 차례로 글을 다시 읽습니다.

1. 자료를 끝까지 읽습니다.
2. 자료의 수치, 주장, 한계를 fact sheet에 정리하고 글에 사용할 용어의 표기와 설명도 함께 적습니다. fact sheet는 자료의 사실을 모아 두는 작업 파일이고, 글의 수치와 주장은 fact sheet에서만 가져옵니다.
3. 한국어 문장 규칙([`style-guide.md`](references/style-guide.md))과 기술 블로그 글의 구성 지침([`genre.md`](references/genre.md))을 읽고 제목과 섹션 구성을 정합니다.
4. 합니다체로 초안을 작성합니다. 문장마다 무엇에 대한 말인지 밝히고, 수치가 있는 문장에는 무엇을 측정해 무엇과 비교한 값인지 함께 씁니다. 처음 나오는 용어는 바로 설명하고 한 글에서 한 단어는 한 의미로만 사용합니다.
5. `lint_ko.py`로 초안을 검사합니다. `lint_ko.py`는 fact sheet에 없는 수치도 찾습니다. Gate와 불합격 항목은 반드시 수정하고, 경고 항목은 삭제해도 정보가 줄지 않는 구절이 있을 때만 수정합니다. 어느 항목이든 기준치 안으로 들어오면 수정을 멈춥니다. 이어서 문장을 하나씩 따로 읽어 무엇에 대한 말인지 알 수 있는지 확인합니다. `lint_ko.py`가 보여 준 점검 후보 문장을 읽고 글의 수치와 주장을 fact sheet와 대조합니다. 마지막으로 아래 표의 판정 항목에 0~2점을 매깁니다.
6. subagent 네 개가 차례로 글을 점검합니다.
   - 독자 점검: 자료와 fact sheet를 읽지 않은 subagent가 글만 읽고, 글의 설명만으로는 무엇인지, 무엇을 하는지 답할 수 없는 용어를 적습니다. 상위 agent(techblog를 실행하고 subagent에게 점검을 맡기는 agent)는 자료를 읽고 1~5단계를 수행했기 때문에 글에 설명이 빠져 있어도 이미 아는 내용으로 이해합니다. 그래서 이 점검은 subagent에게 맡깁니다.
   - 후처리: 초안을 작성하지 않은 subagent가 글 전체를 처음부터 읽은 뒤 필요한 부분만 수정합니다. 수치가 있는 문장마다 반복된 비교 기준을 삭제하고 독자 점검이 찾은 용어에 설명을 추가합니다. 설명을 추가하지 않은 용어는 이유를 보고합니다. 상위 agent가 초안에서 계산한 차이와 비율은 자료 원문으로 다시 확인합니다. 어떤 형태가 읽기 쉬운지는 글마다 다르므로, 수정 여부는 "이 구절을 삭제하면 독자가 잃는 정보가 있는가" 같은 질문으로 판단합니다. 글을 처음부터 다시 쓰지는 않습니다.
   - 한국어 문장 점검: 또 다른 subagent가 글을 한 문장씩 읽고 영어 동사의 직역, 그 분야에서 사용하지 않는 번역어, 주어와 어울리지 않는 서술어 같은 21가지 유형에 해당하는 문장만 수정합니다. 이 subagent가 수치나 사실을 바꿨으면 상위 agent가 그 수정을 되돌립니다.
   - 수정 후 검토: 마지막 subagent가 초안과 수정한 글을 대조해 수정한 문장 앞뒤의 문단과 결론에서 주체, 조건, 추정의 강도가 그대로인지 검토합니다. 이 subagent는 문제를 보고만 하고, 수정은 상위 agent가 합니다.
7. Casual(해요체)로 요청했으면 6단계를 마친 Default(합니다체) 글의 문장 끝만 해요체로 바꾸고, `tone_check.py`로 두 글의 문장 수와 수치가 같은지 확인합니다.
8. 작업 파일을 삭제하고 저장 경로와 검사 결과를 보고합니다.

subagent를 실행할 도구가 없거나 사용자가 subagent를 사용하지 말라고 하면 상위 agent가 6단계의 네 가지 점검을 차례로 직접 수행하고 그 사실을 보고합니다.

## 기준치

검사 스크립트 `lint_ko.py`는 부정 대구("A가 아니라 B입니다"처럼 한쪽을 부정한 뒤 다른 쪽을 말하는 문장)와 쉼표 같은 항목의 수를 세고 문장과 문단의 길이를 측정한 뒤, 항목마다 기준치와 비교해 통과, 경고, 불합격으로 판정합니다.

기준치는 토스, 카카오, 당근, 네이버 D2, 우아한형제들, NAVER CLOVA 기술 블로그에서 사람이 쓴 글 600편(이하 사람 글)을 `lint_ko.py`로 측정해 정했습니다. 쉼표처럼 많을수록 나쁜 항목 대부분은 사람 글의 p95(글의 95%가 넘지 않는 값) 이하이면 통과, p99.5에 여유를 더한 값 이하이면 경고, 그보다 크면 불합격입니다. 항목별 계산 방식은 [`rubric.md`](references/rubric.md)에 있습니다. 저장소에는 원문을 저장하지 않고 URL 목록과 측정값만 저장합니다.

측정한 글에는 발행 시기에 따라 가중치를 줍니다. 글쓰기에 AI를 사용한 비중이 낮은 2018-01-01~2022-11-30(기준 기간)의 글은 1.0, 2022-12-01~2024-12-31의 글은 0.5, 2025년 이후의 글은 0입니다. 부정 대구와 쉼표 같은 항목의 기준치는 기준 기간의 글로만 계산하고, 가중치 0.5는 문장 길이와 문단 길이 같은 나머지 항목에만 적용합니다. 2025년 이후의 글에 가중치를 주지 않는 이유는 부정 대구처럼 AI 글에 자주 나오는 표현이 기준 기간의 글보다 많기 때문입니다. 예를 들어 합니다체 글 한 편에 나오는 부정 대구 문장 수의 중앙값은 2025년 이후의 글이 3.0, 기준 기간의 글이 1.0이었습니다.

기준치를 계산할 때 제외한 기준 기간의 사람 글 31편(holdout)으로 이 기준치가 사람 글을 얼마나 통과시키는지 확인합니다. techblog는 초안의 `lint_ko.py` 결과에 아래 표의 Gate에 해당하는 표현과 불합격 항목이 없고 경고가 3개 이하이면 통과로 판정합니다. 이 조건으로 판정하면 31편 중 28편(90%)이 통과합니다. 목표는 85% 이상입니다. 어투 혼용과 맞춤법처럼 techblog의 글에만 적용하는 규칙은 이 판정에서 제외했습니다.

`lint_ko.py`가 경고나 불합격으로 판정한 항목만 수정하고, 그 항목이 기준치 안으로 들어오면 멈춥니다. 사람 글에도 있는 표현을 0으로 만들 필요는 없습니다. [Boggia(2026)](https://arxiv.org/abs/2607.21498) 논문은 AI 모델이 쓴 글과 사람 글의 부정 대구를 비교한 뒤, 모델에게 초안을 완성한 다음 다시 작성하게 하면 모든 장르에서 부정 대구가 0이 되어 빈도 분포가 사람 글과 달라진다고 보고했습니다.

## 검사 항목

평가 기준 문서 [`rubric.md`](references/rubric.md)는 검사 항목을 네 종류로 나누고 항목마다 근거 자료를 적어 둡니다.

| 종류 | 판정 | 예 |
|---|---|---|
| Gate | 한 번만 나와도 불합격입니다. 정해진 형태는 `lint_ko.py`가 세고, 자료에 없는 사실은 techblog가 글과 자료를 대조해 찾습니다 | 자료에 없는 사실, 글쓴이가 직접 겪은 것처럼 꾸민 경험, "물론입니다" 같은 챗봇 응답 흔적, 어투 혼용, "단순한 X를 넘어", 가운뎃점(`·`), em dash(영어 문장에서 사용하는 긴 줄표 `—`), 맞춤법 오류 |
| 자동 측정 항목 | `lint_ko.py`가 기준치와 비교해 통과, 경고, 불합격으로 판정합니다 | 부정 대구, 쉼표, 강조 문장("핵심은 ~입니다" 같은 문장), 번역투("~에 의해", "중요한 역할을 하다" 같은 표현), 굵은 글씨와 목록 비중, 문장 길이와 문단 길이 분포 |
| 점검 후보 | `lint_ko.py`는 판정하지 않고 다시 읽을 문장만 보여 줍니다. 5단계에서 techblog가 읽고 수정 여부를 정합니다 | 직역 후보("변화가 남아 있다"), 사람 글에서는 다른 단어를 사용하는 표현("낱말"), 물건이나 몸동작에 비유한 표현("행동을 못 박았습니다"), 부정이 걸리는 범위가 둘로 읽히는 문장, 처음 나온 용어 |
| 판정 항목 | 5단계에서 techblog가 초안을 읽고 항목마다 0~2점을 매깁니다 | 문장을 따로 읽어도 무엇에 대한 말인지 알 수 있는가, 한국어가 자연스러운가 |

초안은 Gate 위반과 불합격 항목이 없고 경고가 3개 이하이며, 판정 항목의 평균이 1.6점 이상이고 0점이 없어야 합격입니다. 6단계를 마친 최종 글은 Gate 위반과 불합격 항목이 없어야 하고, 6단계의 수정으로 Gate와 자동 측정 항목의 판정이 초안보다 나빠지면 안 됩니다. 다만 문장 길이, 문단 길이, 목록 비중처럼 문장과 문단의 분포를 측정하는 항목의 경고는 후처리에서 그 글의 독자에게 더 읽기 쉬운 형태를 선택한 결과라면 남길 수 있습니다. 그래서 최종 글의 경고는 3개를 넘을 수 있고, techblog는 남긴 경고를 이유와 함께 사용자에게 보고합니다.

사전에서 맞는 단어를 골라도 사람 글에 나오지 않는 단어이면 글이 어색합니다. `lint_ko.py`는 version을 의미하는 "판"이 한 번만 나와도 불합격으로 판정합니다. "낱말", "시험", "사본"처럼 사람 글에서는 다른 단어를 사용하는 표현은 사람 글에 나오는 비율을 넘으면 경고나 불합격으로 판정하고, 판정과 상관없이 해당 문장을 점검 후보로 보여 줍니다. 측정값은 [`plain-terms.md`](https://github.com/KANG-YEONWOOK/K-Writer/blob/main/dev/baseline/techblog/plain-terms.md)에 있습니다.

AI 글에 자주 나오는 표현의 목록([`ai-patterns.md`](references/ai-patterns.md))은 초안을 작성한 뒤에만 읽습니다. 언어 모델이 반복하는 상투적인 표현(slop)을 찾아 없애는 방법을 다룬 연구 [Antislop(2025)](https://arxiv.org/abs/2510.15061)은 피할 표현의 목록을 초안 작성 전에 보여 주면 그 표현이 오히려 늘 수 있다고 지적했습니다.

`lint_ko.py`는 정규식으로 표현을 셉니다. 직역, 그 분야에서 사용하지 않는 번역어, 주어와 어울리지 않는 서술어 중 정규식으로 셀 수 있는 형태는 위 표의 번역투와 직역 후보 같은 일부뿐입니다. 나머지는 6단계의 한국어 문장 점검에서 subagent가 글을 한 문장씩 읽어 찾습니다. 이 점검의 21가지 유형은 K-Writer 개발자가 techblog로 쓴 글을 다시 읽고 수정한 기록과, 피동을 두 번 겹친 표현이나 같은 의미를 두 번 쓴 겹말처럼 글쓰기에서 일반적으로 점검하는 표현을 바탕으로 정했습니다.

## 한계

기준 기간의 해요체 사람 글 15편은 모두 당근 글이라서 해요체 글로만 계산하는 기준치는 대부분 당근 글의 값으로 정해집니다.

후처리는 수정한 문장과, 상위 agent가 초안에서 자료의 값으로 계산한 차이와 비율만 자료 원문에서 다시 확인합니다. 그래서 초안 단계에서 생긴 사실 오류는 후처리 뒤에도 남을 수 있습니다. 글을 공개하기 전에 수치와 고유명사를 자료 원문과 대조해야 합니다.
