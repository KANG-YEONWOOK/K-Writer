## 모바일 앱 성능 개선 프로젝트 결과 공유
### 12주 동안 앱 시작 시간을 절반으로 줄인 과정과 성과
- 기간: 2026년 7월~9월(12주)
- 참여: iOS 3명, Android 3명, 백엔드 2명, QA 1명, 데이터 분석 1명
- 핵심 결과: 콜드 스타트 3.8초 → 1.9초, 크래시 없는 세션 비율 99.1% → 99.8%
- 발표 순서: 배경, 목표, 진단, 개선 내용, 성과, 다음 단계

## 프로젝트 배경
### 느린 앱이 이탈과 낮은 평점으로 이어지고 있었다
- 2분기 스토어 리뷰의 38%가 "느리다", "멈춘다"를 언급
- 앱 시작에 3초 넘게 걸린 세션은 3초 이하 세션보다 첫 화면 이탈률이 2.3배 높았음
- 스토어 평점이 1년 사이 4.4에서 4.1로 하락
- 기능 출시를 우선하면서 성능 점검이 2년간 뒤로 밀려 있었음

## 목표와 측정 기준
### 네 가지 지표에 목표값을 정하고 실제 사용자 데이터로 측정했다
- 콜드 스타트(중앙값): 3.8초 → 2.0초 이하
- 홈 피드 로딩(P95, 전체 세션의 95%가 이 시간 안에 완료): 2.4초 → 1.2초 이하
- 크래시 없는 세션 비율: 99.1% → 99.7% 이상
- 설치 용량: 86MB → 65MB 이하
- 측정 방식: 테스트 기기가 아닌 실제 사용자 세션 기준, 보급형 기기는 별도 집계

## 진단 결과
### 병목은 앱 시작, 렌더링, 네트워크, 용량 네 영역에 있었다
- 앱 시작: 시작 시점에 초기화하는 SDK 23개 중 14개는 첫 화면에 필요 없었음
- 렌더링: 홈 피드 스크롤 시 느린 프레임 비율이 14%였고, 원인은 원본 크기 이미지 디코딩과 깊은 레이아웃 중첩
- 네트워크: 홈 화면 진입에 API를 11회 호출했고 대부분 순차 실행
- 용량: 미사용 리소스와 중복 라이브러리가 설치 용량의 약 22%를 차지

## 개선 1: 앱 시작 속도
### 첫 화면에 필요 없는 작업을 뒤로 미뤄 시작 시간을 절반으로 줄였다
- SDK 14개를 지연 초기화로 전환해 시작 시점에는 9개만 실행
- 첫 화면은 로컬 캐시로 먼저 표시하고, 최신 데이터가 도착하면 교체
- Android는 Baseline Profile을 적용하고, iOS는 동적 라이브러리 31개를 6개로 통합
- 결과: 콜드 스타트 중앙값 3.8초 → 1.9초(50% 단축)

## 개선 2: 화면 렌더링과 안정성
### 이미지와 레이아웃을 정리해 스크롤 끊김과 크래시를 함께 줄였다
- 이미지를 표시 크기에 맞춰 서버에서 리사이즈하고 WebP로 전환
- 피드 셀의 레이아웃 중첩을 7단계에서 3단계로 축소
- 메인 스레드에서 하던 JSON 파싱과 이미지 디코딩을 백그라운드로 이동
- 결과: 느린 프레임 비율 14% → 5%, ANR(앱 응답 없음) 발생률 0.62% → 0.21%
- 결과: 이미지 메모리 사용량 감소와 상위 크래시 10건 수정으로 크래시 없는 세션 비율 99.1% → 99.8%

## 개선 3: 네트워크와 앱 용량
### 호출 횟수와 설치 용량을 함께 줄였다
- 홈 화면 진입 시 API 호출을 11회에서 3회로 통합하고, 서로 의존하지 않는 호출은 병렬로 실행
- 응답 압축과 캐시 정책을 적용해 API 응답 시간(P95) 820ms → 410ms
- 결과: 홈 피드 로딩(P95) 2.4초 → 1.1초
- 미사용 리소스 제거, 중복 라이브러리 정리, 일부 기능의 주문형 다운로드 전환
- 결과: 설치 용량 86MB → 61MB(29% 감소)

## 성과 요약
### 네 가지 목표를 모두 달성했다
- 콜드 스타트(중앙값): 3.8초 → 1.9초(목표 2.0초 이하)
- 홈 피드 로딩(P95): 2.4초 → 1.1초(목표 1.2초 이하)
- 크래시 없는 세션 비율: 99.1% → 99.8%(목표 99.7% 이상)
- 설치 용량: 86MB → 61MB(목표 65MB 이하)
- 보급형 기기의 콜드 스타트도 6.1초에서 3.2초로 단축

## 사용자와 비즈니스 영향
### 성능 개선 이후 평점, 재방문, 구매 전환이 함께 올랐다
- 스토어 평점: 4.1 → 4.5(출시 후 6주 기준)
- "느리다" 관련 리뷰 비중: 38% → 9%
- 7일 차 재방문율: 31.2% → 34.0%(+2.8%p)
- 구매 전환율: 2.6% → 3.0%(+0.4%p)
- 같은 기간에 가을 프로모션이 있었으므로, 전환율 상승분 전체를 성능 개선 효과로 보기는 어려움

## 배운 점과 다음 단계
### 성능을 일회성 프로젝트가 아닌 상시 관리 대상으로 전환한다
- 배운 점: 개선 효과의 대부분은 새 기술 도입이 아니라 불필요한 작업 제거에서 나왔음
- 배운 점: 실제 사용자 데이터와 보급형 기기 기준으로 봐야 우선순위가 정확해짐
- 다음 단계: 성능 예산(콜드 스타트 2.0초, 용량 65MB)을 정하고, 초과하는 빌드는 배포 전에 자동 차단
- 다음 단계: 주간 성능 대시보드를 전 팀에 공유하고, 4분기에는 검색과 결제 화면으로 범위 확대
- 요청 사항: 신규 SDK를 도입할 때 성능 검토 절차를 거치도록 각 팀의 협조 필요
