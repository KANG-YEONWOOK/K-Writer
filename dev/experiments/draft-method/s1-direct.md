# 공개 API rate limiter를 고정 윈도우에서 토큰 버킷으로 변경한 결과

우리 팀은 공개 API에서 클라이언트별 요청 수를 제한하는 rate limiter를 고정 윈도우(fixed window) 방식에서 토큰 버킷(token bucket) 방식으로 변경했습니다. 고정 윈도우는 시간을 윈도우라는 일정한 길이의 구간으로 나누고 윈도우마다 정해진 수까지 요청을 허용하는 방식입니다. 토큰 버킷은 버킷에 일정한 속도로 채워지는 토큰을 요청마다 차감하고 토큰이 없으면 요청을 거부하는 방식입니다. 토큰 버킷 방식을 배포하고 2주 뒤 같은 트래픽 수준에서 측정했을 때 게이트웨이의 p99 지연 시간은 1,850ms에서 420ms로 줄었습니다.

기존 고정 윈도우 방식에서는 클라이언트마다 60초 윈도우 하나에 요청을 600건까지 보낼 수 있었습니다. 한도를 넘어 요청이 거부된 클라이언트들은 윈도우가 시작할 때마다 같은 순간에 재시도했습니다.

평균 부하는 초당 요청 900건이었는데 윈도우의 첫 1초에는 요청이 초당 최대 4,800건까지 몰렸습니다. 이렇게 몰린 요청 때문에 게이트웨이의 p99 지연 시간은 1,850ms까지 늘었습니다.

토큰 버킷 방식에서는 클라이언트마다 버킷을 하나씩 사용합니다. 버킷 하나에는 토큰이 100개까지 담기고 토큰은 초당 10개씩 채워지므로 장기적인 한도는 기존과 같은 분당 600건으로 유지됩니다.

버킷의 상태는 Redis에 저장합니다. 토큰이 남았는지 확인하고 차감하는 동작은 Lua 스크립트가 원자적으로 실행하므로 게이트웨이 인스턴스 두 대가 같은 토큰을 사용할 수 없습니다. 요청을 거부할 때는 다음 토큰이 채워질 때까지 남은 시간으로 계산한 Retry-After 헤더를 응답에 포함합니다.

토큰 버킷 방식을 배포하고 2주 뒤 같은 트래픽 수준에서 측정한 결과, 초당 요청 수의 최댓값은 4,800건에서 1,400건으로, 게이트웨이의 p99 지연 시간은 1,850ms에서 420ms로 줄었습니다.

같은 측정에서 거부된 요청의 비율은 2.1%에서 2.6%로 늘었습니다. 고정 윈도우에서는 클라이언트가 윈도우 경계에서 한도보다 많은 요청을 보낼 수 있었는데 토큰 버킷에서는 그럴 수 없기 때문입니다. Redis의 CPU 사용률도 8%p 늘었습니다.

토큰 버킷은 서로 다른 클라이언트 여러 개가 같은 순간에 요청을 보내기 시작할 때는 요청이 몰리는 것을 막지 못해서 배포 뒤에는 지금도 짧은 시간 동안 요청이 몰립니다. Retry-After 헤더를 무시하는 클라이언트는 지금도 요청이 거부되면 즉시 재시도합니다. 우리 팀은 활성 클라이언트가 50,000개를 넘는 조건에서는 토큰 버킷 설계를 테스트하지 않았습니다.
