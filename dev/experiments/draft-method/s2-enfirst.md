# 검색 인덱서에 배치 처리를 적용한 이유와 결과

검색 인덱서는 판매자가 업로드한 상품 정보 하나하나를 검색 인덱스의 항목으로 만드는 프로그램이고 검색 인프라팀이 담당합니다. 인덱서는 상품 정보 하나를 문서 하나로 다루는데 4월까지는 문서를 한 번에 하나씩 처리했습니다. 지금은 문서 여러 개를 묶어 한 번에 저장하는 배치 처리(batching)를 사용합니다. 그 결과 부산 클러스터에서는 업로드한 상품 정보가 검색되기까지 걸리는 시간이 9분에서 2분으로 줄었습니다.

인덱서를 변경한 이유는 문서가 큐에서 대기하는 시간이 인덱스 지연(index lag)의 70%를 차지했기 때문입니다. 인덱스 지연은 판매자가 상품 정보를 업로드한 때부터 그 상품 정보가 검색되기 시작할 때까지 걸리는 시간입니다. 인덱스 상태는 오브젝트 스토리지에 저장돼 있는데 변경 전 인덱서는 문서를 하나 처리할 때마다 오브젝트 스토리지에 쓰기 요청을 따로 보내야 했습니다.

변경 후 인덱서는 문서를 최대 200개까지 배치 하나로 묶어 오브젝트 스토리지에 쓰기 요청 한 번으로 저장합니다. 워커는 CPU 시간의 60%를 문서의 압축을 푸는 데 사용하고 배치를 압축할 때는 문서 하나당 약 3 ms의 오버헤드가 생깁니다.

배치 처리를 적용한 뒤에는 배치 안의 문서 하나가 검증에 실패하면 배치 전체가 거부되는 문제가 새로 발생했습니다. 이 문제는 SEARCH-311 티켓으로 관리했고 검증에 실패한 문서만 재시도하도록 수정했습니다. 수정한 내용이 v4.1에 반영된 뒤 문제가 해결되어 SEARCH-311 티켓을 종료했습니다.

v4.1은 6월에 배포됐습니다. v4.1에 추가된 스키마 레지스트리 덕분에 예전 상품 정보 형식의 마이그레이션 중 남아 있던 작업도 진행할 수 있게 됐습니다.

판매자가 상품 정보를 업로드할 때 사용하는 업로드 클라이언트는 리스팅팀이 담당합니다. 새 업로드 클라이언트는 인덱싱 오류를 판매자에게 보여 주므로, 판매자는 어느 상품 정보의 인덱싱이 왜 실패했는지 확인할 수 있습니다.

SEARCH-327 티켓은 인덱스에 중복 문서가 있다는 보고였지만 수정하지 않기로 하고 종료했습니다. 수정하지 않기로 한 이유는 중복 문서가 검색 쿼리의 0.01% 미만에서 나타났고 다음 전체 재인덱싱에서 삭제되기 때문입니다.

배치 처리를 적용한 뒤 부산 클러스터의 인덱스 지연은 9분에서 2분으로 줄었습니다. 서울 클러스터의 인덱스 지연은 배치 처리 전과 같은 1.5분이어서, 두 클러스터의 인덱스 지연 차이는 대부분 없어졌습니다. 오브젝트 스토리지에 보내는 쓰기 요청 수의 최대치도 85% 줄었습니다.

5 MB보다 큰 이미지가 포함된 상품 정보에서도 배치 처리가 잘 동작하는지는 아직 확인하지 않았습니다. 지금까지 배치 처리는 이미지가 없는 상품 정보로만 테스트했습니다. 급하게 처리해야 하는 상품 정보에는 배치 하나에 묶는 문서 수인 배치 크기를 더 작게 설정하는 방안을 선택지로 남겨 두었습니다.
