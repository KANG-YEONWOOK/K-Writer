# 공개 API rate limiter를 고정 윈도우에서 토큰 버킷으로 변경한 방법과 결과

우리 팀은 공개 API의 rate limiter를 고정 윈도우(fixed window) 방식에서 토큰 버킷(token bucket) 방식으로 변경했습니다. 고정 윈도우는 정해진 길이의 구간마다 클라이언트가 보낼 수 있는 요청 수를 제한하는 방식이고, 토큰 버킷은 토큰이 남아 있을 때만 요청을 허용하고 토큰을 일정한 속도로 다시 채우는 방식입니다. 토큰 버킷 방식을 배포하고 2주 뒤 변경 전과 같은 트래픽 수준에서 게이트웨이의 p99 지연 시간은 1,850ms에서 420ms로 줄었습니다.

변경 전에는 클라이언트 하나가 60초 구간마다 요청을 600건까지 보낼 수 있었습니다. 새 구간이 시작될 때마다 요청이 거부됐던 클라이언트들이 동시에 재시도했습니다. 평균 부하는 초당 900건이었지만 구간의 첫 1초에는 요청이 초당 4,800건까지 몰렸고, 이렇게 몰린 요청 때문에 게이트웨이의 p99 지연 시간이 1,850ms까지 늘었습니다.

토큰 버킷 방식에서는 클라이언트마다 버킷이 하나씩 있습니다. 요청 한 건은 그 버킷의 토큰을 하나 사용하고 버킷에 토큰이 없으면 요청이 거부됩니다. 버킷 하나에는 토큰이 100개까지 들어가고 초당 10개씩 다시 채워지므로 장기적인 한도는 변경 전과 같은 분당 600건입니다.

버킷의 상태는 Redis에 저장하고, 토큰이 남았는지 확인해 하나를 차감하는 작업은 Lua 스크립트가 원자적으로 실행합니다. 그래서 게이트웨이 인스턴스 두 개가 같은 토큰을 사용하는 일은 생기지 않습니다. 요청이 거부되면 응답에 Retry-After 헤더가 포함되고 헤더의 값은 다음 토큰이 채워질 때까지 남은 시간으로 계산합니다.

결과는 토큰 버킷 방식을 배포하고 2주 뒤 변경 전과 같은 트래픽 수준에서 비교했습니다. 1초 단위로 측정한 최대 부하는 초당 4,800건에서 1,400건으로 줄었고 게이트웨이의 p99 지연 시간은 1,850ms에서 420ms로 줄었습니다.

같은 조건에서 거부된 요청의 비율은 2.1%에서 2.6%로 늘었습니다. 고정 윈도우 방식에서는 구간이 바뀌는 시점 앞뒤로 클라이언트가 한도보다 많은 요청을 보낼 수 있었지만 토큰 버킷 방식에서는 그렇게 보낼 수 없기 때문입니다. Redis의 CPU 사용률도 8%p 늘었습니다.

서로 다른 클라이언트 여럿이 동시에 요청을 보내기 시작하는 경우에는 토큰 버킷이 도움이 되지 않아서, 배포 직후에는 요청이 짧은 시간 동안 몰리는 현상이 지금도 나타납니다. Retry-After 헤더를 무시하는 클라이언트는 지금도 요청이 거부되면 바로 재시도합니다. 우리 팀은 활성 클라이언트가 50,000개보다 많은 조건에서는 토큰 버킷 설계를 테스트하지 않았습니다.
