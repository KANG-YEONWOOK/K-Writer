## 한 줄 요약

공개 API의 rate limiter를 **fixed window(60초당 600건)에서 클라이언트별 token bucket으로 바꿨습니다.** 매 윈도우 시작마다 트래픽이 몰려 게이트웨이 지연이 튀던 문제를 없애려는 목적이었습니다. 바꾼 뒤 피크 부하와 p99 지연은 크게 줄었습니다. 대신 거절 비율과 Redis CPU 사용량이 조금 올랐습니다.

## 왜 바꿨나

- 기존 방식에서는 제한에 걸린 클라이언트들이 **새 윈도우가 열리는 순간 다 같이 재시도했습니다.**
- 그래서 평균 부하는 초당 900건인데, 윈도우 첫 1초에는 **초당 최대 4,800건**까지 몰렸습니다. 평균의 5배가 넘습니다.
- 이 버스트 때문에 게이트웨이 **p99 지연이 1,850ms**까지 올라갔습니다.

## 무엇을 바꿨나

- **클라이언트마다 bucket을 하나씩 둡니다.** 최대 100개 토큰을 담고, 초당 10개씩 다시 채워집니다. 장기적으로 보면 기존과 같은 분당 600건 제한입니다.
- **상태는 Redis에 저장합니다.** 확인하고 차감하는 동작을 Lua 스크립트로 원자적으로 처리합니다. 그래서 게이트웨이 인스턴스가 여러 대여도 같은 토큰을 두 번 쓰지 못합니다.
- **거절 응답에는 `Retry-After` 헤더를 넣습니다.** 값은 다음 토큰이 생길 때까지 남은 시간으로 계산합니다.

## 바뀐 뒤 결과 (롤아웃 2주 후, 같은 트래픽 수준)

| 지표 | 이전 | 이후 |
|---|---|---|
| 1초 단위 피크 부하 | 4,800 req/s | 1,400 req/s |
| 게이트웨이 p99 지연 | 1,850 ms | 420 ms |
| 거절된 요청 비율 | 2.1% | 2.6% |
| Redis CPU | — | +8 %p |

- 거절 비율이 오른 건 의도된 결과입니다. 노트에 따르면 이제 **윈도우 경계를 이용해 제한을 넘는 요청이 불가능해졌기 때문**입니다.
- Redis CPU는 8% 증가가 아니라 **8%p(퍼센트포인트) 증가**입니다.

## 아직 남은 한계 (노트에 적힌 것)

1. **서로 다른 클라이언트 여러 개가 동시에 시작하면 효과가 없습니다.** bucket이 클라이언트별이라서, 배포 직후 같은 상황에서는 아직 짧은 버스트가 생깁니다.
2. **활성 클라이언트 5만 명 이상에서는 테스트하지 않았습니다.**
3. **`Retry-After`를 무시하는 클라이언트**는 여전히 즉시 재시도합니다.

## 참고: 노트를 읽으며 제가 따로 짚은 점

아래는 노트에 직접 쓰여 있지 않고, 노트에 나온 숫자로 제가 해석한 내용입니다.

- **피크가 줄어든 이유:** 기존에는 클라이언트 하나가 윈도우 시작 순간에 600건을 한꺼번에 보낼 수 있었습니다. 이제는 한 번에 최대 100건이고, 그다음은 초당 10건으로 고르게 퍼집니다. 클라이언트 하나가 낼 수 있는 순간 버스트가 1/6로 줄어든 셈입니다.
- **"분당 600건"은 장기 평균입니다.** bucket이 가득 찬 상태에서 시작하면 어떤 60초 구간에는 최대 약 700건(100 + 10×60)까지 통과할 수 있습니다. 엄격한 분당 600건을 전제로 하는 코드나 문서가 있다면 확인해 보는 게 좋습니다. 참고로 기존 fixed window도 경계를 걸치면 60초 안에 최대 1,200건이 가능했으니, 지금이 더 엄격합니다.
- **노트에서 다루지 않는 부분:**
  - Redis 장애 시 fail-open인지 fail-closed인지
  - 현재 활성 클라이언트 수가 5만 명에 얼마나 가까운지
  - 배포 후 버스트에 대한 후속 대책
