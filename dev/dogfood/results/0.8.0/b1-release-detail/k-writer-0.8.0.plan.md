# 설계

- 핵심 주제: K-Writer 0.5.0은 자료를 한국어로 요약하는 brief 스킬과 자료나 주제, 목적, 분량, 어투를 받아 글을 쓰는 write 스킬을 추가하고 techblog의 short 모드를 삭제했다.
- 전개 순서: 요약 → 스킬의 동작 → core와 lint의 변경 → lint 출력 비교 → 테스트 실행 결과와 수정 → 한계

## 단위 1. 요약
- 형태: 문단
- 전할 내용: K-Writer 0.5.0은 brief와 write 스킬을 추가하고 techblog의 short 모드를 삭제했으며 새 스킬은 테스트 실행으로만 확인했다.
- 전개: 핵심 → 근거 → 결정 → 한계

1. [핵심] K-Writer 0.5.0은 자료를 한국어로 요약하는 brief 스킬과 자료나 주제, 목적, 분량, 어투를 사용자에게 받아 글을 쓰는 write 스킬을 추가했다. (사실 2, 사실 3)
2. [근거] 두 스킬을 요청한 사용자는 write가 기본 스킬이고 다른 스킬은 글의 목적, 문체, 구성을 미리 정해 둔 스킬이라고 설명했다. (사실 4)
3. [결정] techblog의 short 모드는 삭제하고 짧은 글은 brief로 작성하기로 했다. (사실 5)
4. [한계] 새 스킬은 스킬 문서를 작성하지 않은 subagent에게 스킬 문서만 주고 사용자 요청을 실행하게 하는 테스트 실행으로 확인했고 claude plugin eval과 dogfood는 실행하지 않았다. (사실 26, 사실 44)

## 단위 2. 새 스킬의 동작
- 형태: 문단
- 전할 내용: write는 자료나 주제와 요청에 없는 설정값을 먼저 묻고 brief는 분량과 어투만 묻는다.
- 전개: write가 묻는 값 → brief가 묻는 값과 저장

5. [방법] write는 자료나 주제가 없으면 대화에서 먼저 요청하고 목적(설명, 설득, 안내, 기록, 직접 입력), 분량, 어투 중 요청에 없는 값을 한 번에 묻는다. (사실 6)
6. [방법] brief는 분량(한 줄, 한 문단, 자세히)과 어투만 묻고 -o가 있으면 요약을 파일에도 저장한다. (사실 9, 사실 10)

## 단위 3. core와 lint의 변경
- 형태: 문단
- 전할 내용: core에 해라체와 사용자가 정한 어투, 짧은 글 기준을 추가했고 write와 brief의 lint 기준치 15개를 techblog에서 가져왔다.
- 전개: 어투 추가 → 짧은 글 기준 이동 → 기준치를 가져온 이유와 범위

7. [방법] core의 어투에는 해라체(Plain)와 사용자가 직접 정한 어투를 추가해 lint_ko.py와 tone_check.py의 --tone이 plain과 free를 받는다. (사실 12)
8. [방법] 짧은 글 기준은 core의 rules.json으로 옮겼고 lint_ko.py --short와 revise_ko.py의 check --short, audit --short가 이 기준을 적용한다. (사실 14)
9. [이유] write와 brief는 기준 글 표본이 없어 부정 대구나 번역투도 판정하지 못하므로 특정 표현의 빈도를 세는 lint 항목 15개는 techblog의 기준치를 가져와 사용한다. (사실 17)

## 단위 4. lint 출력 비교
- 형태: 문단
- 전할 내용: 0.5.0의 수정 뒤에도 lint의 항목 값과 판정은 수정 전과 같았다.
- 전개: 수정 전후 출력 비교 방법 → 비교 결과

10. [방법] 수정 전후의 lint_ko.py를 예시 글, eval 글, 평가 기록의 글 34개에 --tone default와 --tone casual로 실행해 출력 68개를 비교했다. (사실 22)
11. [결과] 달라진 부분은 이번에 문구를 바꾼 G4.off_tone의 수정 방향 한 줄뿐이고 항목의 값과 판정은 모두 같았다. (사실 23)

## 단위 5. 테스트 실행 결과와 수정
- 형태: 문단
- 전할 내용: 테스트 실행에서 brief 요약이 길어지고 write 글에 "저희"와 해라체가 섞여서 기본 독자, 독립 점검, 조직 주어 규칙을 수정했다.
- 전개: brief 요약의 길이 변화 → 길어진 원인 → 원인에 따른 수정 → write 글의 문제 → 수정

문단 1: brief 요약이 길어진 원인과 수정
12. [결과] 테스트 실행에서 영어 엔지니어링 노트를 한 문단, 합니다체로 요약한 brief의 요약은 첫 실행에서 5문장 590자였고 문서를 수정한 뒤의 두 번째 실행에서 4문장 296자였다. (사실 27, 사실 28)
13. [원인] 첫 실행의 요약이 길어진 원인은 기본 독자를 자료 분야의 지식이 없을 수 있는 사람으로 정해 용어마다 설명이 붙은 것과 독립 점검 단계에서 독자 점검이 낸 질문마다 요약에 설명을 추가한 것이었다. (사실 33, 사실 34)
14. [결정] 그래서 기본 독자를 자료가 대상으로 삼은 독자와 같은 수준의 사람으로 바꿨다. (사실 35)
15. [결정] 독립 점검은 요약만 읽는 subagent가 읽다가 멈춘 부분을 보고하면 상위 agent가 분량 안에서 수정하는 방식으로 바꿨다. (사실 36)
문단 2: write 글의 "저희" 문제와 수정
16. [결과] write의 두 번째 실행에서 해라체로 쓴 기록에는 어투 변환이 합니다체 초안의 종결부만 바꾸는 탓에 "저희"와 해라체가 함께 쓰인 문장이 6개 있었다. (사실 32, 사실 39, 사실 13)
17. [결정] 그래서 조직을 주어로 쓸 때 "우리 팀은"이나 조직의 이름을 쓰도록 genre.md, drafting.md, tone.md를 수정했다. (사실 40)

## 단위 6. 한계
- 형태: 문단
- 전할 내용: 새 eval 케이스와 두 번째 실행 뒤의 수정, 설정을 묻는 흐름은 실행해 확인하지 않았고 write와 brief의 분량 범위는 측정값이 아니다.
- 전개: 실행하지 않은 eval과 비교 → 다시 확인하지 않은 수정 → 실행하지 못한 흐름 → 측정하지 않은 값

18. [한계] 새로 작성한 eval 케이스 4개는 실행하지 않았고 스킬 없이 쓴 글이나 사람이 쓴 글과 비교한 결과도 없다. (사실 45, 사실 46)
19. [한계] 테스트의 두 번째 실행 뒤에 수정한 "저희" 규칙, 사실 표의 열, brief의 출력 파일 조립은 다시 실행해 확인하지 않았다. (사실 47)
20. [한계] 테스트 실행을 subagent 안에서 해서 AskUserQuestion으로 설정을 묻는 흐름과 대화에서 자료나 주제를 요청하는 흐름은 실행해 보지 못했다. (사실 48)

## 제외한 사실
- 분량을 글자 수 범위로 정해 넘기지 않게 한 일(사실 35): 자료에 정한 범위의 값이 없어서 제외했다.
- 테스트 실행이 설정마다 한 번이었다는 한계(사실 47): brief는 같은 설정으로 두 번 실행했으므로 "설정마다 한 번"이 무엇을 뜻하는지 자료에서 정할 수 없어 제외했다.
- short 모드와 함께 삭제한 파일과 옵션 목록(사실 11): 분량 때문에 제외했다. short 모드 삭제는 단위 1에 있다.
- lint_ko.py의 정규식 두 개를 뒤의 정의와 같게 맞춘 일(사실 20, 사실 21): 분량 때문에 제외했다. 수정 전후 출력이 같다는 결과는 단위 4에 있다.
- write와 brief의 구성과 분량 범위가 측정값이 아니라는 한계(사실 51): 자료에 그 범위의 값이 없어서 값을 쓸 수 없으므로 제외했다.
- 분포 항목의 기준치는 가져오지 않은 일(사실 18): 분량 때문에 제외했다. 가져온 항목이 빈도를 세는 15개라는 것은 문장 9에 있다.
- --tone auto가 해라체 문서 7개를 plain으로 인식해 출력이 달라진 일(사실 24): 분량 때문에 제외했다.
- revise_ko.py의 check와 audit가 짧은 글 기준을 적용하지 않던 문제(사실 37, 사실 38): 분량 때문에 제외했다. 수정한 결과는 문장 8에 있다.
