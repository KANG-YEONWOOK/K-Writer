PEP 659의 인터프리터는 함수를 실행하는 동안 바이트코드 명령 하나하나를 그 명령이 실제로 만난 객체 타입에 맞는 전용 명령으로 바꿔 끼웁니다. 예상과 다른 타입이 계속 들어오면 그 명령을 다시 적응형 명령으로 되돌리고 새 타입에 맞는 전용 명령을 찾습니다. 이 인터프리터는 Python 3.11에 들어갔습니다. 아래 설명은 PEP 본문을 따르고 실행 예시는 이 환경의 Python 3.13.5에서 직접 실행한 결과입니다.

## 바이트코드와 명령

Python은 함수를 실행하기 전에 소스 코드를 바이트코드로 컴파일합니다. 바이트코드는 인터프리터가 하나씩 읽어 실행하는 명령의 목록입니다. 명령 하나는 16비트입니다. 앞의 8비트 opcode는 어떤 동작을 할지 나타내고 뒤의 8비트 operand는 그 동작의 대상을 가리킵니다. 표준 라이브러리의 `dis` 모듈로 함수의 바이트코드를 출력할 수 있습니다.

```python
def get_x(p):
    return p.x
```

```
LOAD_FAST                0 (p)
LOAD_ATTR                0 (x)
RETURN_VALUE
```

출력에서는 이 설명에 필요한 줄만 남겼습니다. `LOAD_FAST`는 지역 변수 `p`를 읽습니다. `LOAD_ATTR`는 그 객체에서 이름이 `x`인 속성을 꺼내고 `RETURN_VALUE`는 꺼낸 값을 반환합니다.

## 명령을 바꾸는 이유

`LOAD_ATTR`는 `p`가 어떤 객체든 처리해야 합니다. PEP에 따르면 속성은 일반 인스턴스, 클래스, 모듈이나 그 밖의 여러 특수한 경우에 속할 수 있습니다. 그래서 `LOAD_ATTR` 하나가 이 모든 경우를 처리하는 코드를 갖춰야 합니다.

**특수화**(specialization)는 명령을 지금 다루는 타입에만 맞춘 전용 명령으로 바꾸는 최적화입니다. 전용 명령은 입력이 예상한 타입이면 같은 동작을 훨씬 빠르게 수행합니다. 특수화는 보통 JIT 컴파일러가 기계어를 만들면서 하는 일입니다. PEP 659는 기계어를 만들지 않고 인터프리터 안에서 바이트코드 명령을 바꿔서 특수화합니다.

PEP는 특수화를 일찍 하는 쪽을 택했습니다. 가상 머신의 일반적인 최적화는 비용이 커서 그 비용을 치를 가치가 있다고 확신할 때까지 긴 준비 시간(warm-up)을 둡니다. PEP 659의 인터프리터는 함수를 몇 번만 실행해도 지금 본 타입이 계속 들어온다고 추측하고 특수화합니다. 이 추측은 틀릴 수 있으므로 인터프리터는 특수화와 되돌리기를 계속 반복할 수 있을 만큼 싸게 해야 합니다.

## 명령 계열

PEP는 특수화로 이득을 보는 명령마다 명령 계열(family)을 만듭니다. PEP가 꼽은 대상은 `CALL`, `LOAD_ATTR`, `LOAD_GLOBAL`, `BINARY_ADD`입니다. 계열 하나에는 적응형 명령 하나와 특수화 명령 여러 개가 들어갑니다. 적응형 명령은 카운터를 두고 자신을 특수화 명령으로 바꾸려고 주기적으로 시도합니다. 특수화 명령은 한 가지 경우만 처리합니다. PEP가 예로 든 `LOAD_ATTR` 계열은 다음과 같습니다.

| 명령 | 역할 |
|---|---|
| `LOAD_ATTR_ADAPTIVE` | 적응형 명령입니다. 실행 횟수를 세다가 특수화를 시도합니다. |
| `LOAD_ATTR_INSTANCE_VALUE` | 인스턴스의 값 배열에 저장된 속성을 읽습니다. 같은 이름의 디스크립터(예: property)가 그 속성을 가리지 않을 때 사용합니다. |
| `LOAD_ATTR_MODULE` | 모듈의 속성을 읽습니다. |
| `LOAD_ATTR_SLOT` | `__slots__`를 정의한 클래스의 객체에서 속성을 읽습니다. |

## 명령이 바뀌는 과정

PEP는 느린 명령을 더 빠른 변형으로 바꾸는 과정을 퀵닝(quickening)이라고 부릅니다. 퀵닝한 코드는 실행 중에 바꿀 수 있고 원래 바이트코드와 같은 16비트 명령 형식을 유지합니다. `LOAD_ATTR` 하나가 바뀌는 순서는 다음과 같습니다.

1. 인터프리터가 `LOAD_ATTR`를 적응형 명령인 `LOAD_ATTR_ADAPTIVE`로 바꿉니다.
2. `LOAD_ATTR_ADAPTIVE`는 실행될 때마다 카운터를 줄입니다. 카운터가 0이 되기 전에는 모든 경우를 처리하는 원래 `LOAD_ATTR`의 일반 동작으로 속성을 읽습니다.
3. 카운터가 0이 되면 `LOAD_ATTR_ADAPTIVE`는 내부 함수 `_Py_Specialize_LoadAttr`를 호출합니다. 이 함수는 지금 읽는 속성의 종류를 조사하고 맞는 특수화 명령이 있으면 그 자리의 `LOAD_ATTR_ADAPTIVE`를 그 명령으로 바꿉니다. 맞는 명령이 없으면 적응형 명령으로 남아 나중에 다시 시도합니다.
4. 특수화 명령은 실행할 때마다 먼저 입력이 예상과 같은지 확인합니다. 입력이 예상과 같으면 빠른 경로로 속성을 읽고 카운터를 올립니다. 입력이 예상과 다르면 카운터를 내리고 일반 동작으로 속성을 읽습니다. 어느 경로로 읽든 결과는 같습니다.
5. 카운터가 최솟값에 닿으면 인터프리터는 그 명령의 opcode만 적응형 명령으로 바꿉니다. PEP는 이 단계를 되돌리기(de-optimization)라고 부릅니다. 되돌린 명령은 2단계부터 다시 진행합니다.

4단계의 카운터는 포화 카운터(saturating counter)입니다. 포화 카운터는 정해진 최댓값과 최솟값을 넘어가지 않는 카운터입니다. 이 카운터는 최댓값에서 더 올라가지 않습니다. 그래서 오래 예상이 맞아 온 명령도 예상과 다른 입력이 계속 들어오면 정해진 횟수 안에 최솟값에 닿아 되돌려집니다.

되돌리기가 opcode 하나만 바꾸면 끝나는 이유는 PEP가 명령 하나 단위로 특수화하기 때문입니다. 학계에서 제안된 방법은 대부분 여러 명령으로 이루어진 구간을 한꺼번에 최적화합니다. 그런 방법에서는 구간 중간에서 되돌려야 하는 경우를 처리하는 코드가 따로 필요합니다. 명령 하나 단위로 특수화하면 되돌리기가 구간 중간에서 일어날 수 없습니다. 이 덕분에 프로그램이 다루는 타입이 바뀌어도 인터프리터가 적은 비용으로 빠르게 따라갑니다.

## 인라인 데이터 캐시

특수화 명령은 대부분 8비트 operand에 담을 수 없는 정보가 필요합니다. 예를 들어 `LOAD_GLOBAL_MODULE`은 전역 이름공간에서 값이 있는 위치(인덱스)를 기억해야 합니다. PEP는 이런 정보를 명령 바로 뒤에 붙은 16비트 항목 여러 개에 저장합니다. 이 항목들은 명령 옆에 붙어 있는 캐시라서 인라인 데이터 캐시(inline data cache)라고 부릅니다. 적응형 명령은 이 캐시의 첫 항목을 2단계의 카운터로 사용하고 나머지 항목은 건너뜁니다.

## 실행 예: LOAD_ATTR

`dis` 모듈에 `adaptive=True`를 전달하면 특수화한 뒤의 명령을 볼 수 있습니다. 아래 코드는 `get_x`를 `Point` 객체로 100번 호출한 다음 `Slotted` 객체로 100번 호출합니다. 코드는 호출할 때마다 `LOAD_ATTR` 자리의 명령 이름을 확인하고 이름이 바뀌면 출력합니다.

```python
import dis

class Point:
    def __init__(self, x):
        self.x = x

class Slotted:
    __slots__ = ("x",)
    def __init__(self, x):
        self.x = x

def get_x(p):
    return p.x

def attr_op():
    for ins in dis.get_instructions(get_x, adaptive=True):
        if ins.opname.startswith("LOAD_ATTR"):
            return ins.opname

print("호출 전:", attr_op())
prev = attr_op()
for cls in (Point, Slotted):
    for i in range(1, 101):
        get_x(cls(1))
        if attr_op() != prev:
            prev = attr_op()
            print(f"{cls.__name__} 객체로 {i}번째 호출한 뒤:", prev)
```

```
호출 전: LOAD_ATTR
Point 객체로 2번째 호출한 뒤: LOAD_ATTR_INSTANCE_VALUE
Slotted 객체로 53번째 호출한 뒤: LOAD_ATTR_SLOT
```

`LOAD_ATTR`는 `Point` 객체로 두 번째 호출한 뒤에 `LOAD_ATTR_INSTANCE_VALUE`로 바뀌었습니다. 이 결과는 PEP의 설명대로 함수를 몇 번만 실행해도 특수화한다는 것을 보여 줍니다. `Slotted` 객체로 바꾼 뒤에는 명령이 바로 바뀌지 않았습니다. 명령은 53번째 호출 뒤에 `LOAD_ATTR_SLOT`으로 바뀌었습니다. 이 지연은 4단계에서 카운터가 최솟값까지 내려가고 2단계에서 카운터가 다시 0이 될 때까지 기다려야 하기 때문으로 보입니다. 그 사이의 52번 호출도 일반 동작으로 올바른 값을 반환했습니다.

실제 3.13은 PEP의 설계와 이름이 조금 다릅니다. 3.13에는 `LOAD_ATTR_ADAPTIVE`라는 명령이 없고 출력에서도 특수화 전 명령이 `LOAD_ATTR`로 나옵니다. PEP는 세부 구현이 바뀔 수 있다고 밝혔고 3.13에서는 `LOAD_ATTR`가 적응형 명령의 역할까지 맡는 것으로 보입니다. 3.13의 `LOAD_ATTR` 계열에는 PEP가 예로 든 세 명령을 포함해 특수화 명령이 12개 있습니다.

## 실행 예: LOAD_GLOBAL

`LOAD_GLOBAL`은 전역 이름공간에서 이름을 찾고 없으면 내장 이름공간(builtins)에서 찾는 명령입니다. PEP는 `LOAD_GLOBAL`에 다음 두 특수화 명령을 둡니다.

- `LOAD_GLOBAL_MODULE`은 값이 전역 이름공간에 있을 때 사용합니다. 이 명령은 전역 이름공간의 키가 바뀌지 않았는지 확인한 뒤 저장해 둔 인덱스에서 값을 읽습니다.
- `LOAD_GLOBAL_BUILTIN`은 값이 내장 이름공간에 있을 때 사용합니다. 이 명령은 전역 이름공간에 키가 추가되지 않았는지와 내장 이름공간이 바뀌지 않았는지 확인합니다.

두 명령은 전역 변수의 값이 바뀌었는지는 확인하지 않고 키만 확인합니다. `LOAD_GLOBAL_MODULE`은 값이 아니라 값이 있는 위치를 기억하므로 `g = 20`처럼 값만 바뀌면 같은 위치에서 새 값을 읽습니다. `LOAD_GLOBAL_BUILTIN`이 키 추가를 확인하는 이유는 전역에 `len`이라는 이름이 새로 생기면 `len`이 가리키는 대상이 내장 함수에서 그 전역 변수로 바뀌기 때문입니다. 3.13.5에서 아래 함수를 100번 호출하자 `len`은 `LOAD_GLOBAL_BUILTIN`으로, `g`는 `LOAD_GLOBAL_MODULE`로 바뀌었습니다.

```python
g = 10
def use_globals():
    return len("ab") + g
```

## 사용자에게 보이는 변화

이 인터프리터는 언어, 라이브러리, API를 바꾸지 않습니다. PEP에 따르면 사용자는 실행 시간을 재거나 디버깅 도구를 쓰거나 메모리 사용량을 측정해야 새 인터프리터를 알아챌 수 있습니다. 앞에서 사용한 `dis`의 `adaptive=True` 옵션이 디버깅 도구로 확인하는 방법에 해당합니다. PEP는 특수화의 효과가 다른 최적화에 따라 달라져 정확히 측정하기 어렵다고 밝히면서 속도 향상을 10~60%로 추정합니다. 향상의 대부분은 특수화에서 나오고 가장 크게 기여하는 부분은 속성 조회, 전역 변수 조회, 함수 호출입니다.
