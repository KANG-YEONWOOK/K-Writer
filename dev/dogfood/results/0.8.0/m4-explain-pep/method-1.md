PEP 659의 인터프리터는 함수를 실행하는 동안 바이트코드 명령어를 그 자리에서 실제로 들어온 타입 전용 명령어로 바꿉니다. 예상과 다른 타입이 계속 들어오면 그 명령어를 원래 형태로 되돌립니다. 이 PEP는 Python 3.11에 적용되었습니다.

## 바이트코드와 범용 명령어

Python은 함수 본문을 바이트코드로 컴파일하고 CPython 인터프리터는 이 바이트코드를 명령어 하나씩 읽어 실행합니다. 명령어 하나는 16비트 값입니다. 앞 8비트는 명령어 종류를 나타내는 **opcode**이고 뒤 8비트는 피연산자입니다. 예를 들어 `p.x`는 `LOAD_ATTR` 명령어로 컴파일됩니다. `LOAD_ATTR`은 스택 맨 위의 객체에서 `x` 속성을 읽어 그 객체 자리에 넣습니다.

`LOAD_ATTR`은 모든 경우를 처리하는 범용 명령어입니다. 속성은 일반 인스턴스, 클래스, 모듈, `__slots__`를 정의한 객체 등 여러 곳에 있을 수 있습니다. 그래서 범용 명령어는 실행할 때마다 지금 어느 경우인지 확인한 뒤 그 경우에 맞는 방법으로 속성을 찾습니다. 실행 중에 코드를 실제로 들어오는 타입과 값에 맞춰 바꾸는 최적화를 특수화(specialization)라고 합니다. PEP 659는 이 특수화를 인터프리터 안에서 수행합니다.

## 명령어 하나 단위로 바꾸는 이유

PEP에 따르면 일반적인 가상 머신 최적화는 비용이 큽니다. 그래서 최적화할 가치가 있다고 확신하기까지 긴 워밍업 시간이 필요합니다. PEP 659는 워밍업 없이 빨라지도록 함수가 몇 번만 실행되어도 특수화합니다. 추측이 틀리면 적은 비용으로 되돌립니다. 특수화한 명령어를 되돌리는 일을 역최적화(de-optimization)라고 합니다.

역최적화 비용을 낮추려고 PEP 659는 특수화 범위를 명령어 하나로 제한합니다. 여러 명령어를 묶어 최적화하면 묶음 중간에서 되돌리는 코드가 필요합니다. 명령어 하나만 특수화하면 그 명령어의 opcode를 다시 바꾸는 것으로 역최적화가 끝납니다.

## 명령어 패밀리와 퀵닝

PEP는 특수화할 범용 명령어마다 명령어 패밀리(family)를 정의합니다. `LOAD_ATTR` 패밀리는 다음 명령어로 구성됩니다.

- 범용 명령어 `LOAD_ATTR`은 모든 경우의 속성 읽기를 처리합니다.
- 적응형(adaptive) 명령어 `LOAD_ATTR_ADAPTIVE`는 카운터를 가지고 있습니다. 카운터가 0이 되면 자기 자신을 특수화하려고 시도합니다.
- 특수화된 명령어는 한 가지 경우만 빠르게 처리합니다. `LOAD_ATTR_INSTANCE_VALUE`는 인스턴스 자체에 저장된 속성을 읽습니다. `LOAD_ATTR_MODULE`은 모듈의 속성을 읽고 `LOAD_ATTR_SLOT`은 `__slots__`를 정의한 클래스 객체의 속성을 읽습니다.

PEP는 느린 명령어를 더 빠른 변형으로 바꾸는 일을 퀵닝(quickening)이라고 부릅니다. 퀵닝은 실행 중에 고칠 수 있는 별도의 코드를 바꿉니다. 사용자에게 보이는 원래 바이트코드는 바뀌지 않습니다.

## 바이트코드가 바뀌는 과정

`LOAD_ATTR` 명령어 하나는 실행 중에 다음 순서로 바뀝니다.

1. 인터프리터가 퀵닝 단계에서 `LOAD_ATTR`을 적응형 명령어 `LOAD_ATTR_ADAPTIVE`로 바꿉니다.
2. `LOAD_ATTR_ADAPTIVE`는 실행될 때마다 카운터를 줄입니다. 속성은 원래 `LOAD_ATTR`과 같은 방법으로 읽습니다.
3. 카운터가 0이 되면 `LOAD_ATTR_ADAPTIVE`가 내부 함수 `_Py_Specialize_LoadAttr`를 호출합니다. 이 함수는 지금 읽는 속성의 종류를 확인합니다. 맞는 특수화된 명령어가 있으면 `LOAD_ATTR_ADAPTIVE`를 그 자리에서 그 명령어로 교체합니다. 예를 들어 일반 인스턴스의 속성이면 `LOAD_ATTR_INSTANCE_VALUE`로 바뀝니다.
4. 특수화된 명령어는 실행할 때마다 입력이 예상과 같은지 먼저 확인합니다. 입력이 예상과 같으면 빠른 경로로 속성을 읽고 포화 카운터를 늘립니다. 입력이 예상과 다르면 포화 카운터를 줄이고 범용 방식으로 속성을 읽습니다. 포화 카운터(saturating counter)는 최댓값과 최솟값을 넘어가지 않는 카운터입니다.
5. 포화 카운터가 최솟값에 도달하면 인터프리터가 이 명령어의 opcode를 `LOAD_ATTR_ADAPTIVE`로 되돌립니다. 그 뒤로는 2단계부터 다시 진행합니다. 그래서 이 명령어는 새로 들어오는 타입에 맞는 특수화된 명령어로 다시 바뀝니다.

이 과정에서 바뀌는 것은 명령어 하나의 opcode뿐입니다. 프로그램이 다루는 타입이 바뀌어도 잘못 특수화된 명령어의 추가 비용은 정해져 있습니다. 카운터가 최솟값에 닿을 때까지 입력을 확인하고 범용 방식으로 실행하는 비용이 전부입니다.

## 인라인 캐시

특수화된 명령어는 대부분 8비트 피연산자에 다 들어가지 않는 정보가 필요합니다. PEP 659는 이 정보를 명령어 바로 뒤에 붙은 16비트 항목 여러 개에 저장합니다. 이 항목들을 인라인 데이터 캐시(inline data cache)라고 부릅니다. 특수화되기 전의 적응형 명령어는 이 캐시의 첫 항목을 카운터로 사용하고 나머지 항목은 건너뜁니다.

전역 변수를 읽는 `LOAD_GLOBAL` 패밀리를 보면 이 정보가 어떻게 쓰이는지 알 수 있습니다. `LOAD_GLOBAL_MODULE`은 모듈의 전역 네임스페이스에서 값을 읽을 때 쓰는 특수화된 명령어입니다. 이 명령어는 먼저 전역 네임스페이스의 키가 바뀌지 않았는지 확인합니다. 키가 그대로면 저장해 둔 인덱스에서 값을 바로 읽습니다. 전역 변수의 값만 바뀌고 키가 그대로라면 이 확인은 통과합니다. 같은 인덱스에서 새 값을 읽기 때문입니다.

PEP 계산에 따르면 64비트 기기에서 3.11은 명령어당 6바이트를 사용합니다. 명령어 자체가 2바이트이고 캐시가 4바이트입니다. 같은 기준으로 3.10은 실행 횟수가 약 2000번이 되기 전까지 명령어당 2바이트를 사용했고 그 뒤로는 7.8바이트를 사용했습니다. 그래서 PEP는 거의 실행되지 않는 함수가 많은 대부분의 애플리케이션에서 3.11이 3.10보다 메모리를 조금 더 사용한다고 결론 내렸습니다.

## Python 3.13에서 확인한 변화

로컬 Python 3.13.5에서 `dis.dis(함수, adaptive=True)`로 인터프리터가 실제로 실행하는 바이트코드를 출력했습니다. `adaptive=True`를 빼면 `dis`는 바뀌기 전의 원래 바이트코드를 출력합니다.

```python
import dis

class Point:
    def __init__(self, x):
        self.x = x

class Other:
    __slots__ = ("x",)
    def __init__(self, x):
        self.x = x

def get_x(p):
    return p.x

dis.dis(get_x, adaptive=True)   # 실행 전
for _ in range(1000):
    get_x(Point(1))
dis.dis(get_x, adaptive=True)   # Point로 1000번 호출한 뒤
for _ in range(1000):
    get_x(Other(1))
dis.dis(get_x, adaptive=True)   # Other로 1000번 더 호출한 뒤
```

| 시점 | `p.x` 위치의 명령어 |
|---|---|
| 실행 전 | `LOAD_ATTR` |
| `Point`로 1000번 호출한 뒤 | `LOAD_ATTR_INSTANCE_VALUE` |
| `Other`로 1000번 더 호출한 뒤 | `LOAD_ATTR_SLOT` |

`Point` 인스턴스로 호출하는 동안 `LOAD_ATTR`은 인스턴스 속성 전용인 `LOAD_ATTR_INSTANCE_VALUE`로 바뀌었습니다. 그다음 `__slots__`를 정의한 `Other` 인스턴스를 넘기자 `LOAD_ATTR_INSTANCE_VALUE`의 예상이 계속 틀렸습니다. 그러자 같은 위치의 명령어가 `LOAD_ATTR_SLOT`으로 다시 특수화되었습니다. 함수 시작을 표시하는 `RESUME`도 같은 방식으로 `RESUME_CHECK`로 바뀌었습니다. `show_caches=True`를 추가하면 `LOAD_ATTR` 뒤에 인라인 캐시 항목 `CACHE` 9개가 출력됩니다. 이 항목에는 카운터(`counter`)와 타입 버전(`version`) 같은 값이 들어 있습니다.

3.13의 출력에는 `LOAD_ATTR_ADAPTIVE`가 나오지 않습니다. 3.13의 `dis.opmap`에는 이름에 `ADAPTIVE`가 들어간 명령어가 하나도 없습니다. 3.13에서는 특수화 전의 `LOAD_ATTR`이 캐시 첫 항목에 카운터를 두고 적응형 명령어 역할을 합니다. PEP는 특수화를 관리하는 방식만 정하고 세부 구현은 바뀔 수 있다고 밝혔습니다. 그래서 명령어 이름은 버전마다 다를 수 있습니다.

## 사용자 입장에서 달라지는 점

이 인터프리터 때문에 Python 언어, 라이브러리, API가 바뀌지는 않습니다. 사용자는 실행 시간, 디버깅 도구, 메모리 사용량으로만 이 변화를 알아챌 수 있습니다. PEP는 특수화로 얻는 속도 향상을 10~60%로 추정합니다. 그중 가장 큰 부분은 속성 조회, 전역 변수, 함수 호출을 특수화해서 얻습니다.
