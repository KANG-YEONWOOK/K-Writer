PEP 659가 하는 일은 한 문장으로 요약됩니다. **인터프리터가 실행 중에 바이트코드 명령어를 하나씩 "이 상황 전용" 명령어로 바꿔 끼우고, 추측이 틀리면 다시 원래대로 되돌립니다.** 이 방식은 Python 3.11부터 CPython의 기본 인터프리터에 들어갔습니다. 아래에서 순서대로 설명하겠습니다.

---

## 0. 먼저 알아둘 것: 바이트코드

Python 함수는 실행 전에 **바이트코드**라는 작은 명령어 목록으로 컴파일됩니다.

```python
def get_x(p):
    return p.x
```
```
LOAD_FAST   p      # 지역변수 p를 스택에 올림
LOAD_ATTR   x      # 스택 위 객체에서 속성 x를 꺼냄
RETURN_VALUE
```

문제는 `LOAD_ATTR` 같은 명령어가 아주 **범용적**이라는 점입니다. `p`는 일반 인스턴스일 수도, 모듈이나 클래스일 수도, `__slots__`를 쓰는 객체일 수도 있습니다. 그래서 `p.x`를 실행할 때마다 "타입이 뭐지? 디스크립터(property 등)가 있나? `__dict__`는 어디 있지?"를 처음부터 다시 따집니다. 그런데 실제 프로그램에서는 한 줄의 `p.x`에 거의 늘 **같은 종류의 객체**가 들어옵니다. PEP 659는 바로 이 점을 이용합니다.

## 1. 명령어가 거치는 단계

PEP의 `Specialization` 절에 나오는 내용을 그림으로 그리면 이렇습니다.

```
LOAD_ATTR                        ← 컴파일러가 만든 원래 명령어
   │ ① 퀵닝(quickening)
   ▼
LOAD_ATTR_ADAPTIVE               ← "적응형": 일반 방식으로 실행하며 카운터를 줄여 감
   │ ② 카운터가 0이 되면 지금 들어온 값을 보고 특화를 시도
   ▼
LOAD_ATTR_INSTANCE_VALUE         ← "특화형": 예상한 입력이면 빠른 경로로 처리
   │    예상대로면 카운터 +1, 예상 밖이면 카운터 -1 하고 일반 방식으로 처리
   │ ③ 카운터가 최솟값에 닿으면 탈최적화(de-optimization)
   └──────▶ LOAD_ATTR_ADAPTIVE로 복귀한 뒤 다시 관찰하고 재특화
```

### ① 퀵닝: 바꿔 끼울 수 있는 상태로 만들기
특화해서 이득을 볼 만한 명령어(`LOAD_ATTR`, `LOAD_GLOBAL`, `CALL`, 이항 연산 등)를 "적응형" 버전으로 바꿉니다. 이렇게 실행 중에 명령어를 더 빠른 변형으로 바꾸는 과정 전체를 PEP는 **quickening**이라고 부릅니다.

### ② 적응형 명령어: 관찰하다가 특화하기
적응형 명령어는 실행될 때마다 **카운터**를 하나씩 줄입니다. 그동안에는 원래의 범용 방식으로 일합니다. 카운터가 0이 되면 지금 들어온 값의 종류를 살펴봅니다. 맞는 특화 명령어가 있으면 **자기 자신의 opcode를 그 자리에서 덮어씁니다.** 특화에 실패하면 카운터를 다시 채우고 나중에 또 시도합니다.

PEP는 이 "몇 번 지켜보는" 기간을 아주 짧게 잡습니다. 기존 JIT는 수천 번 실행을 지켜본 뒤에야 최적화하는데(warm-up), 이 PEP는 몇 번만 실행돼도 과감하게 추측합니다. 틀렸을 때 되돌리는 비용이 아주 싸기 때문에 가능한 선택입니다.

### ③ 특화 명령어: 빠른 경로와 안전장치
특화 명령어는 실행할 때마다 먼저 **"입력이 내가 예상한 그 종류가 맞나?"를 값싸게 확인**합니다(이런 확인을 보통 가드라고 부릅니다).
- **맞으면** 빠른 경로로 바로 처리하고 카운터를 올립니다.
- **틀리면** 그 한 번은 범용 방식으로 올바르게 처리하고 카운터를 내립니다.
- 카운터가 바닥나면 **opcode만 적응형으로 되돌립니다.** 탈최적화는 이게 전부입니다.

이 카운터는 **포화 카운터(saturating counter)** 입니다. 최댓값과 최솟값에서 더 늘거나 줄지 않고 멈춥니다. 그래서 가끔 한 번 빗나간다고 바로 되돌아가지 않고, 계속 빗나갈 때만 되돌아갑니다.

## 2. 데이터는 어디에 저장하나: 인라인 캐시

특화 명령어는 "어느 타입을 기대하는지", "값이 몇 번째 칸에 있는지" 같은 정보를 기억해야 합니다. 명령어 한 개는 8비트 opcode와 8비트 인자, 합쳐서 16비트뿐이라 그 안에는 다 들어가지 않습니다. 그래서 **명령어 바로 뒤에 16비트 칸 몇 개를 덧붙여** 거기에 적어 둡니다. PEP는 이것을 "inline data cache"라고 부릅니다. 적응형 명령어는 이 캐시의 첫 칸을 카운터로 쓰고 나머지 칸은 건너뜁니다.

로컬 Python 3.13에서 확인해 보면 이렇습니다.

```
LOAD_GLOBAL_BUILTIN   (len)
CACHE   (counter)
CACHE   (index)
CACHE   (module_keys_version)
CACHE   (builtin_keys_version)
```

명령어 뒤에 붙은 4칸이 이 명령어 전용 메모장입니다.

## 3. PEP의 두 가지 예시

### `LOAD_ATTR` (속성 읽기 `obj.x`)
PEP가 예로 드는 특화형은 다음과 같습니다.
- `LOAD_ATTR_INSTANCE_VALUE`: 일반 인스턴스이고, 속성이 객체의 값 배열에 들어 있으며, 덮어쓰는 디스크립터가 없는 흔한 경우
- `LOAD_ATTR_MODULE`: 모듈의 속성(`math.pi` 같은 것)
- `LOAD_ATTR_SLOT`: `__slots__`를 쓰는 클래스의 속성

직접 실행해서 명령어가 바뀌는 모습을 확인했습니다(출력 일부).

```python
dis.dis(get_x, adaptive=True)   # 실행 전            → LOAD_ATTR
for _ in range(1000): get_x(Point(1))
dis.dis(get_x, adaptive=True)   # 인스턴스로 실행 후  → LOAD_ATTR_INSTANCE_VALUE
for _ in range(2000): get_x(some_module)
dis.dis(get_x, adaptive=True)   # 모듈로 실행 후      → LOAD_ATTR_MODULE
```

세 번째 결과가 위 그림의 ③단계를 실제로 보여 줍니다. 인스턴스 전용으로 특화된 명령어에 모듈이 계속 들어오자 가드가 계속 실패했습니다. 그래서 카운터가 바닥나 적응형으로 되돌아갔고, 다시 관찰한 뒤 모듈 전용으로 재특화됐습니다. 소스 코드는 그대로인데 **같은 줄의 명령어가 실행 패턴에 따라 바뀐** 것입니다.

### `LOAD_GLOBAL` (전역/내장 이름 읽기, 예: `len`)
- `LOAD_GLOBAL_MODULE`: 값이 전역 네임스페이스에 있는 경우입니다. 전역 dict의 **키 구성이 바뀌지 않았는지**만 확인하고, 기억해 둔 위치(index)에서 값을 바로 꺼냅니다.
- `LOAD_GLOBAL_BUILTIN`: 값이 내장 네임스페이스에 있는 경우입니다. **전역에 새 키가 추가되지 않았는지** 확인합니다. 누군가 전역에 `len = ...`을 정의해서 내장 `len`을 가리면 안 되기 때문입니다. 그리고 내장 네임스페이스가 바뀌지 않았는지도 확인합니다.

PEP는 "전역 변수의 **값**이 바뀌는 건 상관없고 **키**만 본다"고 강조합니다. 캐시가 저장하는 건 값 자체가 아니라 "몇 번째 칸에 있는지"입니다. 키 구성이 그대로면 그 칸 번호는 여전히 유효하고, 값은 매번 그 칸에서 새로 읽습니다. 그래서 값이 바뀌어도 틀린 결과가 나오지 않습니다.

## 4. 왜 명령어 하나 단위인가

학계의 다른 방법들은 여러 명령어를 묶은 큰 영역을 한꺼번에 최적화합니다. 그러면 영역 **중간에서** 가정이 깨졌을 때 지금까지의 상태를 원래 형태로 복원하는 복잡한 코드가 필요합니다. PEP 659는 최적화 범위를 **명령어 하나**로 제한합니다. 그래서 "중간"이라는 게 생기지 않고, 탈최적화는 opcode 하나를 바꿔 쓰는 것으로 끝납니다(PEP 표현으로 "trivial"). 큰 범위의 최적화는 포기했지만, 그 대가로 공격적으로 추측해도 틀렸을 때 손해가 아주 작습니다.

## 5. Python 사용자 입장에서 달라지는 것

- **언어, 라이브러리, API는 바뀌지 않습니다.** 차이는 실행 속도, 디버깅 도구, 메모리 사용량으로만 드러납니다.
- **디버거와 커버리지 도구도 그대로 동작합니다.** 퀵닝된 코드도 원래 바이트코드와 같은 16비트 형식을 유지합니다. 그래서 추적(tracing)이 필요하면 원래 바이트코드로 쉽게 되돌아갈 수 있습니다.
- **성능**: PEP는 10–60% 향상을 추정하고, 가장 큰 이득은 속성 접근, 전역 변수 접근, 함수 호출에서 나온다고 합니다.
- **메모리**: 명령어당 약 6바이트를 씁니다. 3.10은 덜 실행된 코드가 2바이트, 자주 실행된 코드가 7.8바이트였으므로, 함수 상당수가 거의 안 쓰이는 일반적인 앱에서는 메모리가 조금 늘어납니다. PEP의 결론은 "늘긴 하지만 많이는 아니다"입니다.

## 6. PEP 문서와 실제 CPython의 차이

PEP도 "세부 사항은 바뀔 수 있다"고 적어 두었고, 실제로 몇 가지가 달라졌습니다.
- 위 실행 결과에서 실행 전 명령어가 `LOAD_ATTR_ADAPTIVE`가 아니라 그냥 `LOAD_ATTR`로 나온 것을 볼 수 있습니다. 3.12부터는 별도의 `_ADAPTIVE` 명령어를 없애고, 원래 명령어가 카운터를 관리하는 적응형 역할까지 맡습니다.
- PEP에 나오는 `BINARY_ADD`는 3.11에서 `BINARY_OP`로 통합됐습니다.

**관찰 → 특화 → 확인 → 틀리면 되돌리기**라는 기본 구조는 그대로입니다.

Python 3.11 이상에서 `dis.dis(함수, adaptive=True)`를 쓰면, 함수를 몇 번 실행한 뒤 명령어가 어떻게 바뀌었는지 직접 볼 수 있습니다.
