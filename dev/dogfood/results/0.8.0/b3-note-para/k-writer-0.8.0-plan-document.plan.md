# 설계

- 핵심 주제: 공개 API의 처리율 제한 방식을 고정 윈도우에서 클라이언트별 토큰 버킷으로 바꾸자 배포 2주 뒤 같은 트래픽 수준에서 게이트웨이의 p99 지연이 1,850ms에서 420ms로 줄었다.
- 전개 순서: 한 문단 요약

## 단위 1. 처리율 제한 방식 변경과 결과
- 형태: 문단
- 전할 내용: 처리율 제한 방식을 고정 윈도우에서 토큰 버킷으로 바꾸자 구간 시작 때의 요청 몰림이 줄어 게이트웨이의 p99 지연이 줄었고, 동시에 시작하는 클라이언트의 몰림은 남았다.
- 전개: 핵심 → 근거 → 조건이나 한계

1. [핵심] 공개 API의 처리율 제한을 고정 윈도우에서 클라이언트별 토큰 버킷으로 바꾸자 배포 2주 뒤 같은 트래픽 수준에서 게이트웨이의 p99 지연이 1,850ms에서 420ms로 줄었다. (사실 5, 사실 9, 사실 11)
2. [원인] 고정 윈도우에서는 60초 구간이 시작될 때마다 제한에 걸렸던 클라이언트들이 동시에 재시도해 요청이 몰렸다. (사실 1, 사실 2)
3. [방법] 토큰 버킷은 토큰을 최대 100개 담고 초당 10개씩 채워 기존과 같은 분당 600건 한도를 유지한다. (사실 6)
4. [결과] 배포 2주 뒤 1초 동안의 최대 요청 수는 4,800건에서 1,400건으로 줄었다. (사실 10)
5. [한계] 배포 직후처럼 서로 다른 클라이언트 여러 개가 같은 순간에 요청을 시작하면 짧은 몰림이 여전히 생기고 활성 클라이언트가 50,000개를 넘는 환경에서는 테스트하지 않았다. (사실 14, 사실 15)

## 제외한 사실
- 고정 윈도우에서 평균 부하가 초당 900건이었다(사실 3): 최대 부하의 변화는 4번 문장의 4,800건과 1,400건으로 전하고 한 문단 분량 300자 안에 넣을 수 없다.
- 거절된 요청의 비율이 2.1%에서 2.6%로 늘었다(사실 12): 결론의 범위를 바꾸지 않는 결과이고 이 사실을 넣으면 본문이 300자를 넘는다.
- Redis의 CPU 사용률이 8%p 늘었다(사실 13): 결론의 범위를 바꾸지 않는 비용이고 한 문단 분량 300자 안에 넣을 수 없다.
