# API rate limiter를 token bucket으로 바꿔 게이트웨이 p99 latency를 1,850ms에서 420ms로 줄인 방법

공개 API(외부 프로그램이 서비스의 기능을 요청할 때 사용하는 인터페이스)를 운영하는 서비스는 API를 호출하는 클라이언트 프로그램 하나가 정해진 시간 동안 보낼 수 있는 요청 수를 제한하기도 합니다. 이렇게 요청 수를 제한하고 한도를 넘은 요청을 거부하는 장치를 rate limiter라고 부릅니다. 한도를 넘어 요청을 거부당한 클라이언트는 다시 요청하므로, 보낼 수 있는 요청 수가 모든 클라이언트에게 같은 시각에 다시 채워지면 거부당했던 클라이언트들의 재시도 요청이 그 시각에 한꺼번에 몰립니다.

한 회사의 엔지니어링 팀이 2026년에 작성한 사내 노트는 공개 API의 rate limiter를 fixed window 방식에서 token bucket 방식으로 바꾼 이유와 바꾼 뒤 측정한 결과를 기록했습니다. fixed window 방식은 모든 클라이언트가 보낼 수 있는 요청 수를 정해진 시각에 한꺼번에 다시 채우고 token bucket 방식은 클라이언트마다 일정 속도로 조금씩 다시 채웁니다.

이 글에서는 rate limiter 방식을 바꾼 뒤 재시도 요청이 한꺼번에 몰리는 정도와 API의 응답 시간이 어떻게 달라졌는지 정리합니다.

## fixed window에서 재시도 요청이 몰린 원인

fixed window 방식은 시간을 같은 길이의 구간으로 나누고 구간마다 클라이언트의 요청 수를 세어 한도를 넘은 요청을 거부하는 rate limiter 방식입니다. 요청 수를 세는 이 고정된(fixed) 시간 구간을 window라고 부릅니다. 노트를 작성한 팀의 공개 API는 클라이언트마다 60초 window 하나에 요청을 600건까지 허용했습니다.

새 window가 시작될 때마다 앞 window에서 요청을 거부당한 클라이언트들은 같은 순간에 재시도했습니다. fixed window 방식에서는 한도에 걸린 클라이언트가 모두 다음 window가 시작되는 같은 시각에 다시 요청을 보낼 수 있게 되므로 재시도 시각도 그 시각으로 모입니다.

fixed window를 사용하던 기간에는 window가 시작된 첫 1초 동안 들어온 요청이 최대 4,800건이었습니다. 이 4,800건은 평균 요청 수인 초당 900건의 약 5.3배였습니다.

게이트웨이는 클라이언트의 요청을 먼저 받아 뒤쪽 서버로 전달하는 서버입니다. 이 공개 API의 rate limiter는 게이트웨이에서 요청을 검사합니다. window 시작 직후에 몰린 요청 때문에 게이트웨이의 p99 latency는 1,850ms에 이르렀습니다. p99 latency는 요청 100건 중 99건이 그 시간 안에 응답을 받는 지연 시간이므로 1,850ms는 가장 느린 1%의 요청이 1.85초 이상 기다렸다는 의미입니다.

## token bucket이 요청을 허용하는 방식

token bucket 방식은 클라이언트마다 토큰을 담는 저장 공간을 두고 요청 하나를 허용할 때마다 토큰 하나를 사용하는 rate limiter 방식입니다. 토큰은 요청 하나를 보낼 수 있는 권한 한 단위이고 클라이언트 하나의 토큰을 담는 저장 공간을 bucket이라고 부릅니다. bucket에는 정해진 속도로 토큰이 다시 채워지고 bucket에 토큰이 하나도 없으면 rate limiter는 요청을 거부합니다.

token bucket 방식으로 바꾼 새 rate limiter는 클라이언트마다 token bucket을 하나씩 두고 bucket 하나에 토큰을 최대 100개까지 담습니다. 각 bucket에는 초당 토큰 10개가 다시 채워집니다. 초당 10개는 1분에 600개이므로 긴 기간의 평균으로 계산하면 클라이언트 하나가 보낼 수 있는 요청은 기존 fixed window와 같은 분당 600건입니다.

아래 표는 노트에 적힌 두 rate limiter 설정을 보낼 수 있는 요청 수가 다시 채워지는 방식과 한꺼번에 보낼 수 있는 요청 수로 비교한 것입니다.

| 항목 | fixed window | token bucket |
|---|---|---|
| 장기 평균 한도 | 분당 600건 | 분당 600건 |
| 보낼 수 있는 요청 수가 다시 채워지는 방식 | 다음 window 시작 시각에 600건이 한꺼번에 | 초당 10건씩(토큰 10개) |
| 한 window 안에서, 또는 bucket이 가득 찬 상태에서 한꺼번에 보낼 수 있는 요청 수 | 600건 | 100건 |

fixed window와 token bucket은 장기 평균 한도가 분당 600건으로 같고 보낼 수 있는 요청 수가 다시 채워지는 방식과 한꺼번에 보낼 수 있는 요청 수가 다릅니다.

token bucket에서는 토큰이 초당 10개씩 채워지므로 거부당한 클라이언트가 다시 보낼 수 있는 요청 수도 초당 10건씩 늘어납니다. bucket의 최대 토큰 수 100개는 클라이언트 하나가 한꺼번에 보낼 수 있는 요청을 100건으로 제한합니다. 반면 fixed window에서는 다음 window가 시작되는 시각에 클라이언트마다 600건이 한꺼번에 다시 채워졌고 클라이언트는 이 600건을 window 시작 직후에 한꺼번에 보낼 수 있었습니다.

## 게이트웨이 인스턴스 여러 개가 같은 토큰을 사용하지 않게 하는 방법

token bucket rate limiter는 클라이언트마다 남은 토큰 수 같은 bucket 상태를 Redis에 저장합니다. Redis는 데이터를 메모리에 저장하는 키-값 저장소로, 키 하나에 값 하나를 짝지어 저장하고 키로 값을 찾습니다.

게이트웨이(클라이언트의 요청을 먼저 받아 뒤쪽 서버로 전달하는 서버)는 같은 프로그램을 여러 서버에서 실행할 수 있고 이렇게 실행한 하나하나를 게이트웨이 인스턴스라고 부릅니다. 노트가 설명하는 게이트웨이는 인스턴스 여러 개로 실행됩니다. bucket 상태를 인스턴스마다 따로 저장하면 같은 클라이언트가 요청을 여러 인스턴스에 나눠 보낼 때 인스턴스마다 토큰을 따로 사용하게 되므로 클라이언트 하나에 정한 한도보다 많은 요청이 허용될 수 있습니다. bucket 상태를 Redis 한 곳에 저장하면 어느 인스턴스가 요청을 받아도 같은 클라이언트의 같은 bucket에서 토큰을 차감합니다.

rate limiter는 요청이 들어올 때마다 남은 토큰이 있는지 확인하고 토큰이 있으면 하나를 차감합니다. 이 토큰 확인과 차감을 두 단계로 따로 실행하면 한 인스턴스가 확인을 마치고 차감하기 전에 다른 인스턴스의 확인이 끼어들 수 있습니다. 이때 남은 토큰이 하나뿐이었다면 두 인스턴스는 모두 토큰이 남아 있다고 판단해 요청 두 건을 허용합니다.

Lua 스크립트는 프로그래밍 언어 Lua로 작성해 Redis 안에서 실행하는 프로그램입니다. Redis는 스크립트 하나를 실행하는 동안 다른 명령을 처리하지 않습니다. token bucket rate limiter는 Lua 스크립트로 토큰 확인과 차감을 원자적으로(중간에 다른 명령이 끼어들지 못하게 한 번에) 실행합니다. 토큰 확인과 차감이 한 번에 실행되므로 두 게이트웨이 인스턴스가 같은 토큰 하나를 함께 사용하는 일은 생기지 않습니다.

## 거부 응답에 넣은 Retry-After 헤더

Retry-After 헤더는 서버가 응답에 넣어 클라이언트에게 얼마 뒤에 다시 요청하라고 알려 주는 HTTP 응답 헤더(응답 본문과 함께 보내는 부가 정보)입니다. token bucket rate limiter는 요청을 거부할 때 응답에 Retry-After 헤더를 넣고 헤더 값을 다음 토큰이 채워질 때까지 남은 시간으로 계산합니다.

Retry-After 헤더의 값만큼 기다렸다가 재시도한 클라이언트의 요청은 그 클라이언트의 bucket에 다음 토큰이 채워진 뒤에 도착합니다. 같은 클라이언트의 다른 요청이 그 토큰을 먼저 사용하지 않았다면 이 재시도 요청은 토큰이 없다는 이유로 다시 거부되지 않습니다.

## 배포 2주 뒤에 측정한 수치

token bucket rate limiter의 결과는 배포하고 2주 뒤에 변경 전과 같은 트래픽(서비스에 들어오는 요청의 양) 수준에서 측정한 값입니다. 아래 표는 rate limiter를 바꾸기 전과 바꾼 뒤의 지표 네 개를 비교한 것입니다.

| 지표 | 변경 전(fixed window) | 변경 후(token bucket) |
|---|---|---|
| 초당 최대 요청 수 | 4,800건 | 1,400건 |
| 게이트웨이 p99 latency | 1,850ms | 420ms |
| 거부된 요청 비율 | 2.1% | 2.6% |
| Redis CPU 사용률 | 노트에 값 없음 | 변경 전보다 8퍼센트포인트 증가 |

초당 최대 요청 수(1초 단위로 센 요청 수의 최댓값)는 4,800건에서 1,400건으로 줄어 변경 전의 약 29%가 됐습니다. 게이트웨이 p99 latency는 1,850ms에서 420ms로, 변경 전의 약 23% 수준까지 낮아졌습니다.

노트에는 변경 후의 평균 요청 수가 없지만 트래픽 수준이 같다고 했으므로 변경 전 평균인 초당 900건을 그대로 기준으로 삼으면 초당 최대 요청 수는 평균의 약 5.3배에서 약 1.6배로 줄었습니다.

전체 요청 중 거부된 요청의 비율은 2.1%에서 2.6%로 0.5퍼센트포인트 늘었습니다. 노트를 작성한 팀은 window 경계에서 한도보다 많이 보내던 요청이 이제 거부되는 것을 거부 비율이 늘어난 원인으로 설명합니다.

fixed window 방식에서는 클라이언트가 앞 window의 끝에 600건, 다음 window의 시작에 600건을 몰아 보내면 짧은 시간 동안 60초 한도인 600건보다 많은 요청을 보낼 수 있었습니다. token bucket 방식에서는 이렇게 짧은 시간에 몰아 보낸 요청 중 bucket에 토큰이 없을 때 도착한 요청이 거부됩니다.

Redis CPU 사용률은 변경 전보다 8퍼센트포인트 늘었습니다. token bucket rate limiter는 요청마다 Redis에서 Lua 스크립트를 실행하므로 이 실행 비용이 늘어난 사용률의 원인일 수 있습니다. 다만 노트는 원인도, 변경 전후의 사용률 값도, 변경 전에 Redis를 무엇에 사용했는지도 밝히지 않았습니다.

## token bucket으로 해결되지 않은 문제와 테스트하지 않은 범위

token bucket 방식은 클라이언트별로 요청 수를 제한하므로 서로 다른 클라이언트 여러 개가 같은 순간에 요청을 시작하는 경우에는 요청이 몰리는 것을 막지 못합니다. 노트에 따르면 배포 직후에는 짧은 시간 동안 요청이 몰리는 현상이 아직 나타납니다.

Retry-After 헤더를 무시하는 클라이언트는 token bucket으로 바꾼 뒤에도 거부당한 직후에 바로 재시도합니다.

이 설계는 활성 클라이언트가 50,000개를 넘는 환경에서 테스트되지 않았습니다. 활성 클라이언트는 일정 기간 안에 실제로 요청을 보내는 클라이언트를 가리키며 그 기간은 노트에 나와 있지 않습니다.

## 마치며

token bucket으로 바꾼 뒤에도 클라이언트 하나의 장기 평균 한도는 분당 600건 그대로였고 바뀐 것은 요청이 들어오는 시점의 분포였습니다. 초당 최대 요청 수와 게이트웨이 p99 latency가 줄어든 결과는 배포 2주 뒤에 변경 전과 같은 트래픽 수준에서 측정한 값입니다.

token bucket을 도입하려는 서비스라면 초당 최대 요청 수와 p99 latency뿐 아니라 이 노트에서 함께 늘어난 거부 비율과 Redis CPU 사용률도 배포 전후로 비교해야 합니다. 이 설계는 활성 클라이언트가 50,000개를 넘는 환경에서 테스트되지 않았고 bucket 상태는 클라이언트마다 하나씩 Redis에 저장됩니다. 그래서 활성 클라이언트가 50,000개를 넘는 서비스라면 token bucket을 적용하기 전에 Redis의 메모리 사용량과 CPU 사용률부터 측정할 필요가 있습니다.

Redis CPU 사용률의 절대값과 배포 직후에 몰리는 요청의 크기는 노트에 나와 있지 않습니다. 그래서 노트의 결과만으로는 token bucket을 적용한 뒤 Redis에 여유가 얼마나 남는지와 배포 직후에 요청이 얼마나 몰리는지 판단할 수 없습니다.
