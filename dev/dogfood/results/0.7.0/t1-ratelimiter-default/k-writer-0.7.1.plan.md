# 설계

- 핵심 주제: 공개 API의 rate limiter를 fixed window 방식에서 클라이언트별 token bucket 방식으로 바꾸자 window 경계에서 몰리던 재시도 요청이 분산돼 게이트웨이의 초당 최대 요청 수와 p99 latency가 줄었고, 그 대가로 거부 비율과 Redis CPU 사용률이 늘었으며 해결하지 못한 문제가 남았다.
- 전개 순서: 도입(재시도가 한 순간에 몰리는 장면, rate limiter 정의, 노트 소개, 핵심 결과) → fixed window에서 재시도가 몰린 원인 → token bucket의 동작과 설정 → Redis와 Lua 스크립트로 토큰을 차감하는 방법 → Retry-After 헤더 → 배포 후 2주 동안의 결과 → 해결하지 못한 문제 → 마치며(적용 기준) → 참고자료

## 단위 1. 도입
- 형태: 제목과 첫 문단
- 전할 내용: 한도가 풀리는 순간이 모든 클라이언트에게 같으면 거부당한 클라이언트의 재시도가 한 순간에 몰리고, 한 사내 노트는 rate limiter 방식을 바꿔 이 문제를 줄였다.
- 전개: 구체 장면 → 중심 대상 rate limiter 정의 → 노트 소개 → 두 방식의 차이를 한 문장으로 정의 → 이 글에서 다룰 내용

- [제목] API rate limiter를 token bucket으로 바꿔 게이트웨이 p99 latency를 1,850ms에서 420ms로 줄인 방법
문단 1: 요청 수 제한의 배경, rate limiter의 정의, 재시도가 한 시각에 몰리는 장면
1. [배경] 공개 API를 운영하는 서비스는 클라이언트 프로그램 하나가 정해진 시간 동안 보낼 수 있는 요청 수를 제한하기도 한다. (문제와 배경, 용어: API, client, rate limiter)
2. [정의] 이렇게 요청 수를 제한하고 한도를 넘은 요청을 거부하는 장치를 rate limiter라고 부른다. (중심 대상: rate limiter, 용어: rate limiter)
3. [장면] 거부당한 클라이언트는 다시 요청하므로 보낼 수 있는 요청 수가 모든 클라이언트에게 같은 시각에 다시 채워지면 재시도 요청이 그 시각에 한꺼번에 몰린다. (문제와 배경)
문단 2: 노트 소개와 두 방식의 차이
4. [소개] 한 회사의 엔지니어링 팀이 2026년에 작성한 사내 노트는 공개 API의 rate limiter를 fixed window 방식에서 token bucket 방식으로 바꾼 이유와 바꾼 뒤 측정한 결과를 기록했다. (자료 정보)
5. [정의] fixed window 방식은 모든 클라이언트가 보낼 수 있는 요청 수를 정해진 시각에 한꺼번에 다시 채우고 token bucket 방식은 클라이언트마다 일정 속도로 조금씩 다시 채운다. (중심 대상: fixed window 방식, token bucket 방식)
문단 3: 이 글이 다룰 내용
6. [핵심] 이 글에서는 rate limiter 방식을 바꾼 뒤 재시도 요청이 한꺼번에 몰리는 정도와 API의 응답 시간이 어떻게 달라졌는지 정리한다. (핵심 주제)

## 단위 2. fixed window에서 재시도가 몰린 원인
- 형태: 섹션 "fixed window에서 재시도 요청이 몰린 원인"
- 전할 내용: fixed window 방식은 모든 클라이언트의 한도를 같은 시각에 다시 채우므로 거부당한 클라이언트의 재시도가 window 시작 직후에 몰렸고 이 요청이 게이트웨이 p99 latency를 1,850ms까지 늘렸다.
- 전개: fixed window 정의 → 이 팀의 설정 → 현상(window 시작마다 재시도) → 원인이 몰림을 만드는 과정(분석) → 수치(4,800 대 900) → 결과(게이트웨이 정의, p99 latency 정의, 1,850ms)

문단 1: fixed window 방식의 정의와 설정
7. [정의] fixed window 방식은 시간을 같은 길이의 구간으로 나누고 구간마다 클라이언트의 요청 수를 세어 한도를 넘은 요청을 거부하는 rate limiter 방식이다. (용어: fixed window, window)
8. [풀이] 이 방식에서 요청 수를 세는 고정된 시간 구간을 window라고 부른다. (용어: window)
9. [설정] 노트를 작성한 팀의 공개 API는 클라이언트마다 60초 window 하나에 요청을 600건까지 허용했다. (수치: fixed window 한도)
문단 2: 재시도가 window 시작 시각에 모이는 과정
10. [현상] 새 window가 시작될 때마다 앞 window에서 요청을 거부당한 클라이언트들이 같은 순간에 재시도했다. (문제와 배경, 의미(주장) 1)
11. [분석] fixed window 방식에서는 한도에 걸린 클라이언트가 모두 다음 window가 시작되는 같은 시각에 한도를 다시 받으므로 재시도 시각도 그 시각으로 모인다. (분석 후보 1)
문단 3: 몰린 요청의 크기
12. [근거] window가 시작된 첫 1초에 들어온 요청은 최대 초당 4,800건까지 측정됐고 같은 기간의 평균 요청 수는 초당 900건이었다. (수치: window 첫 1초의 순간 요청량, 평균 부하)
13. [분석] 4,800건은 평균 요청 수 900건의 약 5.3배이므로 window가 시작되는 1초 동안 게이트웨이는 평소의 다섯 배가 넘는 요청을 받았다. (수치: 평균 부하의 계산값)
문단 4: 게이트웨이 p99 latency에 준 영향
14. [정의] 게이트웨이는 클라이언트의 요청을 먼저 받아 뒤쪽 서버로 전달하는 서버이고 이 팀의 rate limiter는 게이트웨이에서 요청을 검사한다. (용어: gateway)
15. [결과] window 시작 직후에 몰린 요청 때문에 게이트웨이의 p99 latency는 1,850ms까지 늘었다. (수치: 변경 전 게이트웨이 p99 latency)
16. [정의] p99 latency는 요청 100건 중 99건이 그 시간 안에 응답을 받는 지연 시간이므로 1,850ms는 가장 느린 1% 요청이 약 1.85초 넘게 기다렸다는 의미다. (용어: p99 latency, 수치: 변경 전 게이트웨이 p99 latency)

## 단위 3. token bucket의 동작과 설정
- 형태: 섹션 "token bucket이 요청을 허용하는 방식"
- 전할 내용: token bucket 방식은 클라이언트마다 토큰을 일정 속도로 채우므로 분당 한도는 600건으로 유지하면서 한도가 한 시각에 한꺼번에 생기지 않게 한다.
- 전개: token bucket 정의 → 토큰과 bucket 풀이 → 이 팀의 설정 → 장기 한도가 같다는 계산 → 표로 두 방식 비교 → 설계 이유(분석)

문단 1: token bucket의 정의
17. [정의] token bucket 방식은 클라이언트마다 토큰을 담는 저장 공간을 두고 요청 하나를 허용할 때마다 토큰 하나를 사용하는 rate limiter 방식이다. (중심 대상: token bucket, 용어: token bucket)
18. [풀이] 토큰은 요청 하나를 보낼 수 있는 권한 한 단위이고 클라이언트 하나의 토큰을 담는 저장 공간을 bucket이라고 부른다. (용어: token, bucket)
19. [과정] bucket에는 정해진 속도로 토큰이 다시 채워지고 bucket에 토큰이 하나도 없으면 rate limiter는 요청을 거부한다. (용어: token bucket)
문단 2: 이 팀의 설정과 장기 한도
20. [설정] 노트의 새 rate limiter는 클라이언트마다 token bucket을 하나씩 두고 bucket 하나에 토큰을 최대 100개까지 담는다. (방법, 수치: bucket 최대 토큰 수)
21. [설정] 각 bucket에는 초당 토큰 10개가 다시 채워진다. (수치: bucket 충전 속도)
22. [이유] 초당 10개는 1분에 600개이므로 긴 기간의 평균으로 계산하면 클라이언트 하나가 보낼 수 있는 요청은 기존 fixed window와 같은 분당 600건이다. (수치: 장기 한도)
문단 3: 두 방식의 비교
23. [소개] 아래 표는 노트에 적힌 두 rate limiter 설정을 한도가 다시 생기는 방식과 한 번에 보낼 수 있는 요청 수로 비교한 것이다. (수치: fixed window 한도, bucket 최대 토큰 수, bucket 충전 속도)
- [표] 항목(장기 평균 한도, 한도가 다시 생기는 방식, 한 번에 몰아 보낼 수 있는 최대 요청 수) × fixed window(분당 600건, 다음 window 시작 시각에 600건이 한꺼번에, 600건) × token bucket(분당 600건, 초당 토큰 10개씩, 100건)
24. [분석] fixed window와 token bucket은 장기 평균 한도가 분당 600건으로 같고 한도가 다시 생기는 방식과 한 번에 몰아 보낼 수 있는 요청 수가 다르다. (분석 후보: 장기 한도가 분당 600건으로 같으므로)
25. [분석] token bucket에서는 토큰이 초당 10개씩 생기므로 거부당한 클라이언트가 다시 보낼 수 있는 요청도 다음 window 시작 시각에 600건이 한꺼번에 생기지 않고 초당 10건씩 생긴다. (분석 후보: 토큰이 초당 10개씩 생기므로)
26. [분석] bucket의 최대 토큰 수 100개는 클라이언트 하나가 한 번에 몰아 보낼 수 있는 요청을 100건으로 제한한다. (분석 후보 2)
27. [대조] fixed window에서는 클라이언트 하나가 window 하나의 600건을 window 시작 직후에 한꺼번에 보낼 수 있었다. (분석 후보 2)

## 단위 4. Redis와 Lua 스크립트로 토큰을 차감하는 방법
- 형태: 섹션 "게이트웨이 인스턴스 여러 개가 같은 토큰을 사용하지 않게 하는 방법"
- 전할 내용: bucket 상태는 Redis에 저장돼 있고 Lua 스크립트가 토큰 확인과 차감을 한 번에 실행하므로 게이트웨이 인스턴스 두 개가 같은 토큰을 사용할 수 없다.
- 전개: bucket 상태의 저장 위치(Redis 정의) → 인스턴스 둘 이상 구성과 Redis 한 곳에 저장하는 이유(분석) → 토큰 확인과 차감의 두 단계 → 두 단계를 따로 실행하면 생기는 문제(분석) → Lua 스크립트 정의 → Lua 스크립트가 두 단계를 원자적으로 실행 → 결과

문단 1: bucket 상태의 저장 위치
28. [사실] 클라이언트마다 남은 토큰 수 같은 bucket 상태는 Redis에 저장돼 있다. (방법, 용어: Redis)
29. [정의] Redis는 데이터를 메모리에 저장하는 키-값 저장소다. (용어: Redis)
30. [배경] 게이트웨이를 여러 서버에서 실행한 하나하나를 게이트웨이 인스턴스라고 부르고 노트가 설명하는 게이트웨이는 인스턴스 여러 개로 실행된다. (용어: gateway instance, 분석 후보: 인스턴스 둘 이상)
31. [분석] bucket 상태를 인스턴스마다 따로 저장하면 같은 클라이언트가 요청을 여러 인스턴스에 나눠 보낼 때 클라이언트 하나에 정한 한도보다 많은 요청이 허용될 수 있고, Redis 한 곳에 저장하면 어느 인스턴스가 요청을 받아도 같은 bucket에서 토큰을 차감한다. (분석 후보: 인스턴스마다 따로 두면, Redis 한 곳에 저장)
문단 2: 확인과 차감을 따로 실행할 때 생기는 문제
32. [과정] rate limiter는 요청이 들어오면 남은 토큰이 있는지 확인하고 토큰이 있으면 하나를 줄이는 두 단계를 실행한다. (용어: check-and-decrement)
33. [분석] 두 단계를 따로 실행하면 한 인스턴스가 확인을 마치고 차감하기 전에 다른 인스턴스의 확인이 끼어들 수 있다. (분석 후보: 토큰 확인과 차감을 따로 실행하면)
34. [분석] 이 경우 남은 토큰 하나를 두 인스턴스가 모두 남아 있다고 판단해 요청 두 건을 허용할 수 있다. (분석 후보: 토큰 확인과 차감을 따로 실행하면)
문단 3: Lua 스크립트로 두 단계를 한 번에 실행하는 방법
35. [정의] Lua 스크립트는 Redis 안에서 실행하는 Lua 언어 프로그램이고 Redis는 스크립트 하나를 실행하는 동안 다른 명령을 끼워 넣지 않는다. (용어: Lua script)
36. [방법] 이 팀의 rate limiter는 Lua 스크립트로 토큰 확인과 차감을 원자적으로, 즉 중간에 다른 요청이 끼어들지 못하게 한 번에 실행한다. (방법, 용어: atomic)
37. [결과] 토큰 확인과 차감이 한 번에 실행되므로 게이트웨이 인스턴스 두 개가 같은 토큰을 사용할 수 없다. (의미(주장) 3)

## 단위 5. Retry-After 헤더
- 형태: 섹션 "거부 응답에 넣은 Retry-After 헤더"
- 전할 내용: 거부 응답에는 다음 토큰이 채워질 때까지 남은 시간을 담은 Retry-After 헤더가 들어가고 클라이언트가 이 값을 따르면 재시도 요청이 토큰이 채워진 뒤에 도착한다.
- 전개: Retry-After 헤더 정의 → 이 팀이 헤더 값을 계산하는 방법 → 헤더를 따르는 클라이언트의 재시도(분석) → 헤더의 효과가 미치는 범위

문단 1: Retry-After 헤더의 정의와 값
38. [정의] Retry-After 헤더는 서버가 거부 응답에 넣어 클라이언트에게 몇 초 뒤에 다시 요청하라고 알려 주는 HTTP 응답 헤더다. (용어: Retry-After header)
39. [방법] 이 팀의 rate limiter는 요청을 거부할 때 응답에 Retry-After 헤더를 넣고 헤더 값을 다음 토큰이 채워질 때까지 남은 시간으로 계산한다. (방법)
문단 2: 헤더를 따르는 클라이언트의 재시도
40. [분석] Retry-After 헤더의 값만큼 기다렸다가 재시도한 클라이언트의 요청은 그 클라이언트의 bucket에 다음 토큰이 채워진 뒤에 도착한다. (분석 후보: Retry-After 헤더의 값만큼 기다렸다가)
41. [조건] 같은 클라이언트의 다른 요청이 그 토큰을 먼저 사용하지 않았다면 이 재시도 요청은 토큰이 없다는 이유로 다시 거부되지 않는다. (분석 후보: Retry-After 헤더의 값만큼 기다린 재시도 요청)

## 단위 6. 배포 후 2주 동안의 결과
- 형태: 섹션 "배포 2주 뒤에 측정한 수치"
- 전할 내용: token bucket으로 바꾼 뒤 같은 트래픽 수준에서 초당 최대 요청 수와 게이트웨이 p99 latency가 줄었고 거부 비율과 Redis CPU 사용률은 늘었다.
- 전개: 측정 조건 → 표 → 감소한 두 지표 해석 → 평균 대비 배수 비교(분석) → 늘어난 거부 비율과 팀의 설명 → 경계 문제 풀이 → Redis CPU 사용률

문단 1: 측정 조건과 표
42. [조건] token bucket rate limiter의 결과는 배포하고 2주 뒤에 변경 전과 같은 트래픽 수준에서 측정한 값이다. (의미(주장) 4)
43. [소개] 아래 표는 변경 전과 변경 후의 지표 네 개를 비교한 것이다. (수치: 초당 최대 부하, 게이트웨이 p99 latency, 거부된 요청 비율, Redis CPU 사용률)
- [표] 지표(초당 최대 요청 수, 게이트웨이 p99 latency, 거부된 요청 비율, Redis CPU 사용률) × 변경 전(4,800건, 1,850ms, 2.1%, 노트에 값 없음) × 변경 후(1,400건, 420ms, 2.6%, 변경 전보다 8퍼센트포인트 증가)
문단 2: 줄어든 두 지표
44. [결과] 초당 최대 요청 수는 4,800건에서 1,400건으로 줄어 변경 전의 약 29%가 됐다. (수치: 초당 최대 부하)
45. [결과] 게이트웨이 p99 latency는 1,850ms에서 420ms로 줄어 변경 전의 약 23%가 됐다. (수치: 게이트웨이 p99 latency)
46. [분석] 노트에는 변경 후의 평균 요청 수가 없지만 트래픽 수준이 같다고 했으므로 변경 전 평균인 초당 900건을 기준으로 삼으면 초당 최대 요청 수는 평균의 약 5.3배에서 약 1.6배로 줄었다. (분석 후보: 1.6배와 5.3배)
문단 3: 늘어난 거부 비율
47. [결과] 전체 요청 중 거부된 요청의 비율은 2.1%에서 2.6%로 0.5퍼센트포인트 늘었다. (수치: 거부된 요청 비율, 분석 후보: 0.5퍼센트포인트)
48. [원인] 노트를 작성한 팀은 window 경계에서 한도보다 많이 보내던 요청이 이제 거부되는 것을 거부 비율이 늘어난 원인으로 설명한다. (의미(주장) 2)
49. [풀이] fixed window 방식에서는 클라이언트가 앞 window의 끝에 600건, 다음 window의 시작에 600건을 몰아 보내면 짧은 시간 동안 60초 한도인 600건보다 많은 요청을 보낼 수 있었다. (분석 후보: fixed window 경계 문제, 설명용 예시)
50. [결과] token bucket 방식에서는 같은 방식으로 몰아 보낸 요청 중 bucket에 토큰이 없을 때 도착한 요청이 거부된다. (분석 후보: fixed window 경계 문제, 용어: token bucket)
문단 4: 늘어난 Redis CPU 사용률
51. [결과] Redis CPU 사용률은 변경 전보다 8퍼센트포인트 늘었다. (수치: Redis CPU 사용률)
52. [분석] token bucket rate limiter는 요청마다 Redis에서 Lua 스크립트를 실행하므로 이 실행 비용이 늘어난 사용률의 원인일 수 있다. (분석 후보 4)
53. [한계] 노트는 원인, 변경 전후의 사용률 값, 변경 전에 Redis를 무엇에 사용했는지를 밝히지 않았다. (한계 4, 분석 후보: 변경 전 Redis 사용)

## 단위 7. 해결하지 못한 문제
- 형태: 섹션 "token bucket으로 해결되지 않은 문제와 테스트하지 않은 범위"
- 전할 내용: token bucket은 서로 다른 클라이언트가 동시에 요청을 시작하는 경우와 Retry-After 헤더를 무시하는 클라이언트를 막지 못하고 활성 클라이언트 50,000개를 넘는 환경에서는 테스트되지 않았다.
- 전개: 한계 1(클라이언트별 동작의 한계와 배포 직후 요청 몰림) → 한계 2(Retry-After를 무시하는 클라이언트) → 한계 3(테스트 범위)

문단 1: 여러 클라이언트가 동시에 시작하는 경우
53. [한계] token bucket은 클라이언트별로 요청 수를 제한하므로 서로 다른 클라이언트 여러 개가 같은 순간에 요청을 시작하는 경우에는 요청이 몰리는 것을 막지 못한다. (한계 1)
54. [근거] 노트를 작성한 팀은 배포 직후에 짧은 시간 동안 요청이 몰리는 현상을 아직 관찰하고 있다. (한계 1)
문단 2: Retry-After 헤더를 무시하는 클라이언트
55. [한계] Retry-After 헤더를 무시하는 클라이언트는 token bucket으로 바꾼 뒤에도 거부당한 직후에 바로 재시도한다. (한계 3)
문단 3: 테스트 범위
56. [한계] 노트를 작성한 팀은 활성 클라이언트가 50,000개를 넘는 환경에서 이 설계를 테스트하지 않았다. (한계 2, 수치: 테스트한 활성 클라이언트 수 상한)
57. [풀이] 활성 클라이언트는 일정 기간 안에 실제로 요청을 보내는 클라이언트이고 노트는 그 기간을 밝히지 않았다. (용어: active client)

## 단위 8. 마치며
- 형태: 섹션 "마치며"
- 전할 내용: 이 결과는 분당 한도를 그대로 두고 요청이 들어오는 시점만 바꾼 결과이고 같은 트래픽 수준과 활성 클라이언트 50,000개 이하라는 조건에서 측정됐으므로 독자는 Redis 부하와 클라이언트 규모를 먼저 확인해야 한다.
- 전개: 결론이 성립하는 조건(장기 한도 같음, 측정 조건) → 적용할 때 함께 측정할 지표 → 적용 조건(규모가 큰 서비스) → 노트가 밝히지 않은 값

58. [조건] token bucket으로 바꾼 뒤에도 클라이언트 하나의 장기 평균 한도는 분당 600건 그대로였고 바뀐 것은 요청이 들어오는 시점의 분포였다. (분석 후보: 장기 한도가 분당 600건으로 같으므로)
59. [조건] 초당 최대 요청 수와 게이트웨이 p99 latency가 줄어든 결과는 배포 2주 뒤에 변경 전과 같은 트래픽 수준에서 측정한 값이다. (의미(주장) 4)
60. [적용] 같은 방식을 적용하려는 서비스라면 초당 최대 요청 수와 p99 latency뿐 아니라 이 노트에서 함께 늘어난 거부 비율과 Redis CPU 사용률도 배포 전후로 측정해야 한다. (수치: 거부된 요청 비율, Redis CPU 사용률)
61. [적용] 이 설계는 활성 클라이언트 50,000개를 넘는 환경에서 테스트되지 않았고 bucket 상태는 클라이언트마다 하나씩 Redis에 저장되므로 활성 클라이언트가 50,000개를 넘는 서비스라면 적용 전에 Redis의 메모리 사용량과 CPU 사용률부터 측정할 필요가 있다. (분석 후보: 테스트 범위가 활성 클라이언트 50,000개까지이므로)
62. [한계] Redis CPU 사용률의 절대값과 배포 직후에 몰리는 요청의 크기가 노트에 없으므로 노트의 결과만으로는 적용한 뒤 Redis에 여유가 얼마나 남는지와 배포 직후에 요청이 얼마나 몰리는지 판단할 수 없다. (한계 4)
