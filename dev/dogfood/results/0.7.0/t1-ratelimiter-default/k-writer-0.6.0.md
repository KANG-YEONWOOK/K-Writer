# API rate limiter를 fixed window에서 token bucket으로 바꾼 이유와 결과

외부에 공개된 한 API(Application Programming Interface)는 클라이언트 하나가 60초 동안 보낼 수 있는 요청을 600개로 제한했습니다. API는 프로그램끼리 기능을 요청하고 결과를 주고받는 호출 방식이고 클라이언트는 그 API에 요청을 보내는 프로그램입니다.

이렇게 요청 수를 제한하는 장치를 rate limiter(처리율 제한 장치)라고 부릅니다. rate limiter는 클라이언트마다 정해진 시간 동안 받은 요청 수를 세고 한도를 넘은 요청을 거절합니다. 이 API에서는 60초가 지나 요청 수를 처음부터 다시 세기 시작할 때마다 직전 60초 동안 요청이 거절된 클라이언트들이 같은 순간에 다시 요청을 보냈습니다.

2026년에 작성된 한 사내 엔지니어링 노트는 이 rate limiter를 fixed window 방식에서 클라이언트별 token bucket 방식으로 바꾼 과정과 배포 2주 뒤의 측정 결과를 정리했습니다. fixed window(고정 윈도) 방식은 시간을 60초 같은 고정된 구간으로 나눠 구간마다 요청 수를 세는 방식이고, token bucket(토큰 버킷) 방식은 요청 하나를 보낼 수 있는 몫인 토큰을 버킷이라는 저장 공간에 일정한 속도로 채우고 요청마다 토큰을 하나씩 사용하게 하는 방식입니다.

이 글에서는 rate limiter를 token bucket 방식으로 바꾼 뒤 한꺼번에 몰리던 요청과 응답 시간이 어떻게 달라졌는지 정리합니다. 배포 2주 뒤 배포 전과 같은 트래픽 수준에서 측정한 결과 1초 동안 들어온 요청 수의 최댓값은 초당 4,800개에서 1,400개로 줄었습니다.

## fixed window 방식에서 window가 시작할 때 요청이 몰린 이유

fixed window 방식의 rate limiter는 시간을 일정한 길이의 window로 나눕니다. window는 rate limiter가 요청 수를 세는 시간 구간이고 이 API에서는 60초였습니다. rate limiter는 window 안에서 클라이언트마다 요청 수를 세어 600개를 넘은 요청을 거절하고 새 window가 시작하면 요청 수를 0부터 다시 셉니다.

fixed라는 이름은 window의 시작 시각과 끝 시각이 미리 정해져 있다는 의미입니다.

그래서 한도를 넘어 요청이 거절된 클라이언트는 다음 window가 시작해야 다시 요청을 보낼 수 있습니다. 이 API에서는 window가 시작할 때마다 거절됐던 클라이언트들이 같은 순간에 재시도했습니다. window의 시작 시각이 미리 정해져 있으므로 거절된 클라이언트들이 다시 요청할 수 있게 되는 시각은 다음 window의 시작 시각 하나입니다.

짧은 시간에 평소보다 훨씬 많은 요청이 몰리는 현상을 burst라고 부릅니다. window가 시작한 뒤 첫 1초에 들어온 요청은 가장 많을 때 초당 4,800개였습니다. 평균 부하(1초 동안 들어오는 요청 수의 평균)는 초당 900개였으므로 burst가 가장 컸던 1초에는 평균의 약 5.3배가 들어왔습니다.

게이트웨이는 클라이언트의 요청을 가장 먼저 받아 내부 서버로 전달하는 서버입니다. burst 때문에 게이트웨이의 p99 latency는 1,850ms까지 올라갔습니다.

p99 latency는 요청 100건 중 99건이 이 시간 안에 응답을 받는 지연 시간이고 나머지 1% 요청은 이보다 오래 기다립니다.

## 클라이언트별 token bucket의 동작과 설정값

token bucket 방식은 클라이언트마다 버킷을 하나씩 할당합니다. 버킷은 토큰을 담는 저장 공간이고 토큰은 요청 하나를 보낼 수 있는 몫입니다. 버킷에는 일정한 속도로 토큰이 채워지고 rate limiter는 요청이 들어올 때마다 토큰을 하나 꺼내 사용합니다.

버킷에 토큰이 없으면 rate limiter는 그 요청을 거절합니다.

이 노트의 설계에서 버킷 하나에는 토큰이 최대 100개까지 들어가고 토큰은 초당 10개씩 채워집니다. 초당 10개는 1분에 600개이므로 장기적으로 클라이언트 하나가 보낼 수 있는 요청은 기존 fixed window와 같은 분당 600개입니다.

두 방식은 장기 한도가 같고 클라이언트 하나가 짧은 순간에 보낼 수 있는 요청 수가 다릅니다. fixed window에서는 클라이언트 하나가 window의 한도 600개를 window가 시작한 직후 1초 안에 모두 보낼 수 있었습니다. 앞 window의 마지막 순간에도 600개를 보낸 클라이언트라면 window 경계 앞뒤의 짧은 시간에 1,200개를 보낼 수도 있습니다.

token bucket에서는 버킷이 가득 차 있어도 한 번에 보낼 수 있는 요청이 100개까지이고 그 뒤에는 초당 10개씩 채워지는 토큰만큼만 보낼 수 있습니다. 빈 버킷이 다시 가득 차는 데는 10초가 걸립니다.

노트의 설정값과 두 방식의 동작을 항목별로 비교하면 다음과 같습니다.

| 항목 | fixed window | token bucket |
|---|---|---|
| 한도를 정하는 값 | 60초 window당 요청 600개 | 버킷 최대 토큰 100개, 초당 10개 충전 |
| 장기 한도 | 분당 600개 | 분당 600개 |
| 클라이언트 하나가 짧은 시간에 보낼 수 있는 최대 요청 수 | 600개, window 경계 앞뒤로는 1,200개 | 100개, 그 뒤로는 초당 10개 |
| 거절된 클라이언트가 다시 요청할 수 있는 시각 | 다음 window가 시작할 때 | 그 클라이언트의 버킷에 다음 토큰이 채워졌을 때 |

표의 마지막 행처럼 token bucket에서는 거절된 클라이언트가 다시 요청할 수 있는 시각이 클라이언트마다 버킷 상태에 따라 달라집니다. 다시 요청할 수 있는 시각이 클라이언트마다 다르면 재시도가 window 시작 같은 한 시각에 모이지 않을 수 있습니다.

이 노트의 token bucket 설계는 요청을 거절할 때 응답에 Retry-After 헤더를 넣습니다. Retry-After 헤더는 서버가 응답에 덧붙이는 정보인 HTTP 응답 헤더의 하나로 클라이언트에게 얼마 뒤에 다시 요청하면 되는지 알려 줍니다. 이 설계는 헤더 값을 그 클라이언트의 버킷에 다음 토큰이 채워질 때까지 남은 시간으로 계산합니다.

## 게이트웨이 인스턴스 여러 대가 같은 토큰을 사용하지 않게 하는 방법

token bucket 설계에서 버킷의 토큰을 사용하는 쪽은 게이트웨이(클라이언트의 요청을 가장 먼저 받는 서버)이고 게이트웨이는 인스턴스 여러 대로 실행됩니다. 인스턴스는 같은 게이트웨이 프로그램을 여러 대에서 실행했을 때 그 각각을 가리킵니다. 버킷 상태를 인스턴스 밖의 한곳에 저장하면 같은 클라이언트의 요청이 서로 다른 인스턴스에 도착해도 인스턴스들이 같은 버킷을 확인할 수 있습니다.

token bucket 설계에서 버킷 상태는 Redis에 저장돼 있습니다. Redis는 키 하나로 값 하나를 찾는 key-value 방식의 저장소이고 데이터를 메모리에 저장해 빠르게 읽고 쓸 수 있습니다. 게이트웨이 인스턴스들은 요청마다 Redis에서 버킷 상태를 읽고 바꿉니다.

여러 인스턴스가 버킷 하나를 함께 사용하면 두 인스턴스가 같은 토큰을 사용할 수 있습니다. 예를 들어 버킷에 토큰이 하나 남았을 때 인스턴스 두 대가 거의 동시에 남은 토큰 수를 확인하면 두 인스턴스 모두 토큰이 있다고 판단하고 각자 토큰을 하나씩 뺍니다. 그러면 토큰 하나로 요청 두 개가 통과합니다.

이 설계는 토큰이 남았는지 확인하고 하나를 빼는 동작을 Lua 스크립트(Lua 언어로 작성해 Redis 서버 안에서 실행하는 짧은 프로그램) 하나로 원자적으로 실행합니다. 원자적으로 실행한다는 것은 확인과 차감이 중간에 다른 요청이 끼어들지 않고 한 번에 실행된다는 의미입니다.

Redis는 Lua 스크립트 하나를 실행하는 동안 다른 명령을 실행하지 않으므로 게이트웨이 인스턴스 두 대가 같은 토큰을 사용할 수 없습니다.

## 배포 2주 뒤 측정한 부하와 응답 시간의 변화

아래 결과는 token bucket 방식을 배포하고 2주가 지난 뒤 배포 전과 같은 트래픽 수준에서 측정한 값입니다. 1초 동안 들어온 요청 수의 최댓값, 게이트웨이 p99 latency, 거절된 요청의 비율, Redis CPU 사용률을 교체 전과 비교하면 다음과 같습니다. 이 중 Redis CPU 사용률은 교체 전후의 값 없이 두 값의 차이만 %p(퍼센트포인트, 퍼센트로 나타낸 두 값의 차이) 단위로 노트에 적혀 있습니다.

| 지표 | 교체 전(fixed window) | 교체 후(token bucket) |
|---|---|---|
| 1초 동안 들어온 요청 수의 최댓값 | 초당 4,800개 | 초당 1,400개 |
| 게이트웨이 p99 latency | 1,850ms | 420ms |
| 거절된 요청의 비율 | 2.1% | 2.6% |
| Redis CPU 사용률 | 노트에 값 없음 | 교체 전보다 8%p 높음 |

1초 동안 들어온 요청 수의 최댓값은 교체 전 값의 약 29%인 초당 1,400개로 줄었습니다. 같은 트래픽 수준이 평균 부하가 같다는 뜻이라면 교체 후 요청이 가장 많이 몰린 1초에 들어온 요청은 평균 초당 900개의 약 1.6배였습니다. 교체 전 window 첫 1초에 들어온 요청은 가장 많을 때 초당 4,800개로 평균의 약 5.3배였습니다.

게이트웨이 p99 latency는 1,850ms에서 420ms로 줄어 교체 전 값의 약 23%가 됐습니다. 교체 전 p99 latency를 1,850ms까지 높인 원인이 window 시작의 burst였으므로 burst가 작아진 것이 p99 latency를 낮췄다고 해석할 수 있습니다.

거절된 요청의 비율은 2.1%에서 2.6%로 0.5%p 늘었습니다. 노트는 클라이언트가 더 이상 window 경계에서 한도를 넘을 수 없게 된 것을 그 원인으로 설명합니다. window 경계에서 한도를 넘는다는 것은 window마다 센 요청 수는 600개 이하인데 두 window의 경계 앞뒤 짧은 시간에 600개보다 많은 요청이 통과하는 일을 가리킵니다.

fixed window는 window마다 요청 수를 따로 세므로 예를 들어 클라이언트 하나가 한 window의 마지막 순간에 600개, 다음 window의 첫 순간에 600개를 보내면 짧은 시간에 요청 1,200개가 거절되지 않고 통과합니다. token bucket에서는 같은 클라이언트가 한 번에 보낼 수 있는 요청이 최대 100개이므로 이런 요청의 일부가 거절됩니다.

Redis CPU 사용률은 8%p 늘었습니다. token bucket 방식에서는 요청마다 Redis에서 Lua 스크립트가 실행되므로 이 증가는 버킷 상태를 확인하고 바꾸는 데 드는 비용일 수 있습니다.

## token bucket 설계가 해결하지 못한 문제와 확인하지 않은 조건

token bucket은 서로 다른 클라이언트 여러 개가 같은 순간에 요청을 시작하는 경우에는 burst를 줄이지 못합니다. 그래서 token bucket으로 바꾼 뒤에도 배포 직후에는 짧은 burst가 생깁니다. 무엇을 배포한 직후인지는 노트에 없습니다.

클라이언트별 버킷 구조에서 token bucket이 제한하는 값은 클라이언트 하나의 요청 수이고 클라이언트 전체가 1초 동안 보내는 요청의 합은 제한하지 않습니다. 그래서 클라이언트마다 토큰이 남아 있다면 많은 클라이언트가 같은 순간에 요청을 보내도 rate limiter는 그 요청을 거절하지 않습니다.

이 설계는 활성 클라이언트가 50,000개를 넘는 환경에서 테스트되지 않았습니다. 활성 클라이언트는 요청을 보내고 있는 클라이언트이고 어느 기간 동안 요청을 보낸 클라이언트를 활성으로 세는지는 노트에 없습니다. 버킷 상태가 클라이언트마다 Redis에 저장되고 요청마다 Lua 스크립트가 실행되므로 클라이언트와 요청이 늘면 Redis의 메모리와 CPU 사용량도 늘 수 있습니다.

Retry-After 헤더를 무시하는 클라이언트는 요청이 거절되자마자 다시 요청합니다. Retry-After 헤더는 다시 요청할 시각을 알려 주기만 하고 클라이언트가 그 시각을 지키게 하지는 못합니다.

Redis CPU 사용률의 교체 전 값과 교체 후 값은 노트에 없어서 8%p 증가가 Redis 서버에 어느 정도의 여유를 남기는지는 판단할 수 없습니다. 교체 후 평균 부하와 p99 latency를 계산한 기간도 노트에 없습니다.

burst가 줄어든 원인이 버킷 크기를 100개로 제한한 데 있는지 재시도 시각이 클라이언트마다 흩어진 데 있는지도 노트는 구분하지 않았습니다.

## 마치며

token bucket 방식의 효과는 거절된 클라이언트들의 재시도가 window가 시작하는 순간에 몰려 burst가 생기던 API에서 확인됐습니다. 이 API에서는 분당 한도를 600개로 유지한 채 rate limiter를 token bucket 방식으로 바꾸자 window 시작에 몰리던 burst가 줄었습니다. 이 결과는 배포 2주 뒤 배포 전과 같은 트래픽 수준에서 측정한 값이고 같은 측정에서 거절된 요청의 비율은 0.5%p, Redis CPU 사용률은 8%p 늘었습니다.

운영하는 서비스의 burst가 배포 직후처럼 서로 다른 클라이언트가 같은 순간에 요청을 시작해서 생긴다면 클라이언트별 token bucket만으로는 burst가 줄지 않을 수 있습니다. 배포 직후의 짧은 burst는 이 설계에서도 아직 해결되지 않았고 이 설계는 활성 클라이언트가 50,000개를 넘는 환경에서 테스트되지 않았습니다.
