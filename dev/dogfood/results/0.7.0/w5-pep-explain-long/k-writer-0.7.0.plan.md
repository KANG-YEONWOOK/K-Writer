# 설계

- 핵심 주제: PEP 659는 CPython 인터프리터가 프로그램을 실행하면서 확인한 타입과 값에 맞춰 바이트코드 명령어를 하나씩 그 경우 전용의 빠른 명령어로 바꾸고, 예상이 틀리면 원래 명령어로 적은 비용에 되돌리는 방식(특수화 적응형 인터프리터)을 설명하며, 이 방식은 언어와 API를 바꾸지 않고 실행 속도를 10~60% 높이는 대신 메모리를 조금 더 사용한다.
- 전개 순서: 도입(PEP 659와 특수화 적응형 인터프리터의 정의) → 배경(동적 언어와 특수화, 성능 목표, 워밍업 문제) → 명령어 하나 단위로 특수화하는 이유 → 명령어가 교체되는 과정 → 명령어 형식과 인라인 캐시 → LOAD_ATTR와 LOAD_GLOBAL 예 → 속도 향상 → 호환성과 메모리 비용 → PEP의 범위와 뒤로 미룬 JIT 컴파일 → 참고자료

## 단위 1. 제목과 도입
- 형태: 제목과 첫 문단
- 전할 내용: PEP 659는 CPython 3.11의 인터프리터가 실행 중에 확인한 타입에 맞춰 바이트코드 명령어를 특수화 명령어로 바꾸고 예상이 틀리면 되돌리는 방식을 설명하며, 이 방식은 언어를 바꾸지 않고 속도를 10~60% 높인다.
- 전개: PEP와 PEP 659 소개 → CPython, 바이트코드, 인터프리터 정의 → 특수화 적응형 인터프리터 정의 → 효과와 비용

- [제목] PEP 659: 실행 중에 명령어를 특수화하는 CPython 인터프리터

1. [정의] PEP 659는 Mark Shannon이 2021년 4월에 작성한 PEP(Python에 새 기능이나 변경을 제안하거나 설계를 설명하는 문서)이고 제목은 "Specializing Adaptive Interpreter"다. (자료 정보, 용어: PEP)
2. [배경] CPython(python.org에서 배포하는 Python의 표준 구현)은 Python 소스 코드를 바이트코드라는 내부 명령어 목록으로 컴파일하고, CPython의 인터프리터가 이 바이트코드 명령어를 하나씩 읽어 실행한다. (용어: CPython, 바이트코드, 인터프리터)
3. [핵심] PEP 659는 이 인터프리터를 특수화 적응형 인터프리터로 바꾸는 방식을 설명하고, 이 설계는 CPython 3.11에 들어갔다. (중심 대상: PEP 659, 적용 버전)
4. [정의] 특수화 적응형 인터프리터는 명령어가 실행되면서 받은 값의 타입을 확인해 그 타입 전용의 빠른 명령어로 스스로를 교체하고, 예상한 타입이 아닌 입력이 이어지면 원래 명령어로 되돌리는 인터프리터다. (중심 대상: 특수화 적응형 인터프리터, 방법: 적응형 명령어로 교체, 방법: 최적화 해제)
5. [결과] 특수화 적응형 인터프리터는 Python 언어, 라이브러리, API를 바꾸지 않는다. (한계와 범위: 호환성)
6. [결과] PEP 659는 이 인터프리터가 실행 속도를 10~60% 높인다고 추정한다. (수치: 특수화로 얻는 속도 향상 범위)
7. [조건] 다만 대부분의 애플리케이션에서 3.11은 3.10보다 메모리를 더 사용하는데, PEP 659는 그 차이가 크지 않다고 결론짓는다. (한계와 범위: 메모리 결론)

## 단위 2. 배경
- 형태: 섹션 "동적 언어 Python을 빠르게 실행하는 데 필요한 것"
- 전할 내용: 동적 언어의 가상 머신이 빨라지려면 실행 중인 타입과 값에 맞춰 코드를 특수화해야 하고, PEP 659는 워밍업 없이 특수화하려면 최적화와 그 되돌림을 아주 적은 비용으로 해야 한다고 설명한다.
- 전개: 동적 언어 정의와 예 → 특수화가 필요하다는 PEP의 설명 → 특수화 정의 → JIT 없이도 효과 → 성능 목표와 CPython에서 하는 이유 → 워밍업 문제 → 빠른 특수화의 조건

문단 1: 동적 언어의 가상 머신은 특수화해야 빨라진다.
1. [정의] Python은 동적 언어(변수에 타입을 선언하지 않고 값의 타입이 실행 중에 정해지는 언어)라서 a + b를 실행할 때 a와 b의 타입을 확인해야 정수 덧셈인지 문자열 연결인지 정할 수 있다. (용어: 동적 언어)
2. [주장] PEP 659는 동적 언어의 가상 머신이 빠르게 동작하려면 실행 중인 프로그램의 타입과 값에 맞춰 실행하는 코드를 특수화해야 한다고 설명한다. (문제와 배경: 동적 언어 VM의 특수화 필요)
3. [정의] 가상 머신은 바이트코드 같은 명령어를 실행하는 소프트웨어이고 CPython에서는 인터프리터가 이 일을 한다. (용어: 가상 머신)
4. [정의] 특수화는 실행 중에 확인한 타입과 값에 맞춰 코드를 그 경우에만 맞는 형태로 바꾸는 일이다. (용어: 특수화)
4-1. [예] 예를 들어 a + b의 a와 b가 계속 정수라면 a + b를 정수 덧셈 전용 코드로 바꾸는 것이 특수화다. (설명용 예시: 특수화의 예)
5. [풀이] 특수화는 흔히 JIT 컴파일러(실행 도중 자주 실행되는 코드를 기계어로 번역하는 컴파일러)와 함께 이야기되지만, PEP 659는 기계어를 만들지 않아도 특수화가 성능을 높인다고 설명한다. (문제와 배경: 특수화와 JIT, 용어: JIT 컴파일러)

문단 2: PEP 659의 성능 목표와 CPython에서 이루려는 이유
6. [배경] PEP 659는 Python이 느린 언어로 널리 알려져 있다고 인정한다. (문제와 배경: Python이 느리다는 평가)
7. [목표] PEP 659는 Python이 C, Fortran, Java 같은 저수준 언어의 성능에는 이르지 못하더라도 JavaScript 엔진 V8, Lua 구현 LuaJIT 같은 빠른 스크립트 언어 구현과 겨룰 수 있게 하는 것을 목표로 밝힌다. (문제와 배경: 성능 목표, 용어: V8, LuaJIT)
8. [이유] PEP 659가 이 목표를 CPython에서 이루려는 것은 PyPy(JIT 컴파일러를 사용하는 Python의 다른 구현) 같은 다른 가상 머신을 사용할 수 없는 사용자를 포함해 모든 Python 사용자가 혜택을 받게 하기 위해서다. (문제와 배경: CPython에서 달성하려는 이유, 용어: PyPy)
9. [근거] PEP 659는 목표까지 갈 길이 멀지만 인터프리터를 빠르게 하면 목표에 크게 다가갈 수 있다고 주장하고, 학계 연구와 실제 구현에서 빠른 인터프리터가 빠른 가상 머신의 핵심 요소로 확인됐다는 점을 근거로 든다. (문제와 배경: 인터프리터 가속의 의미)

문단 3: 워밍업 문제와 빠른 특수화의 조건
10. [문제] 가상 머신의 일반적인 최적화는 비용이 커서 최적화할 가치가 있다고 확신할 때까지 코드를 오래 실행하며 지켜보는 워밍업 시간이 필요하다. (문제와 배경: 기존 VM 최적화의 warm-up 문제, 용어: 워밍업)
11. [조건] PEP 659는 워밍업 없이 빨리 속도를 높이려면 함수가 몇 번만 실행돼도 특수화할 가치가 있다고 추측해야 한다고 설명한다. (문제와 배경: 빠른 특수화를 위한 조건)
12. [조건] PEP 659는 이렇게 일찍 추측하는 방식이 효과를 내려면 인터프리터가 최적화와, 추측이 틀렸을 때 최적화를 되돌리는 일을 계속, 아주 적은 비용으로 할 수 있어야 한다고 덧붙인다. (문제와 배경: 빠른 특수화를 위한 조건)

## 단위 3. 명령어 하나 단위로 특수화하는 이유
- 형태: 섹션 "명령어 하나 단위로 특수화하는 이유"
- 전할 내용: 특수화를 명령어 하나 단위로 하면 예상이 틀렸을 때 되돌리는 일이 아주 간단해지므로 PEP 659는 명령어 하나만큼의 작은 영역을 적극적으로 특수화한다.
- 전개: 특수화를 먼저 하는 이유 → 연구 근거 → 기존 연구의 큰 영역과 그 문제 → 명령어 하나 단위의 장점 → 제안 요지 → 가장 가까운 선행 연구와 차이

문단 1: 특수화를 먼저 하는 이유
1. [주장] PEP 659는 동적 언어의 가상 머신을 빠르게 하는 방법 중 특수화가 그 자체로도, 다른 최적화를 가능하게 한다는 점에서도 가장 중요하므로 CPython 성능을 높이려면 특수화부터 해야 한다고 주장한다. (문제와 배경: 특수화를 먼저 하는 이유)
2. [근거] PEP 659는 인터프리터에서 특수화만 해도 성능이 크게 오르고 단순한 컴파일러보다 빨라질 수 있다는 연구[2]를 근거로 든다. (문제와 배경: 인터프리터 특수화의 효과 연구, 참고 문헌 [1])

문단 2: 명령어 하나 단위면 되돌리기가 간단하다
3. [대조] 학술 문헌에 나온 특수화 방법 대부분은 바이트코드 명령어 하나보다 큰 영역을 한꺼번에 최적화한다. (문제와 배경: 기존 연구는 더 큰 영역을 최적화, 참고 문헌 [1], [2])
4. [이유] 최적화하는 영역이 명령어 하나보다 크면 영역 중간에서 예상이 틀렸을 때 최적화한 코드를 되돌리는 일(de-optimization)을 처리하는 코드가 필요하다. (문제와 배경: 기존 연구는 더 큰 영역을 최적화, 용어: de-optimization)
5. [핵심] 명령어 하나 단위로 특수화하면 de-optimization이 영역 중간에서 일어날 수 없으므로 되돌리는 일이 아주 간단해진다. (문제와 배경: 명령어 단위 특수화의 장점)
6. [제안] 그래서 PEP 659가 제안하는 인터프리터는 코드를 적극적으로 특수화하되 명령어 하나만큼의 작은 영역에서만 특수화하고, 특수화가 틀렸을 때 빠르고 적은 비용으로 바로잡는다. (방법: 제안 요지)

문단 3: 가장 가까운 선행 연구와 차이
7. [비교] PEP 659는 문헌에서 가장 가까운 방법으로 "Inline Caching meets Quickening"[4]을 든다. (문제와 배경: 가장 가까운 선행 연구)
8. [대조] PEP 659도 이 방법처럼 인라인 캐시(특수화에 필요한 정보를 명령어 바로 뒤에 붙여 저장하는 캐시)를 사용하고, 여기에 de-optimization을 빠르게 하는 기능을 추가했다. (문제와 배경: 가장 가까운 선행 연구, 용어: 인라인 캐시)
9. [결과] PEP 659는 이 기능 덕분에 특수화가 실패하거나 오래 유지되지 않는 경우에도 이 방법보다 성능이 안정적으로 유지된다고 설명한다. (문제와 배경: 가장 가까운 선행 연구)

## 단위 4. 명령어가 교체되는 과정
- 형태: 섹션 "적응형 명령어와 특수화 명령어의 교체 과정"
- 전할 내용: 특수화할 명령어는 먼저 적응형 명령어로 바뀌고, 충분히 실행되면 특수화 명령어로 바뀌며, 예상과 다른 입력이 이어지면 카운터에 따라 적응형 명령어로 되돌아간다.
- 전개: 두 단계 교체 전체 → quickening 정의 → 대상 명령어와 예 → family 정의와 구성 → 적응형 명령어의 카운터 → 특수화 명령어의 saturating counter → 되돌리기 → 다시 특수화

문단 1: 두 단계 교체와 quickening
1. [전체] PEP 659의 인터프리터는 특수화하면 빨라질 명령어를 먼저 적응형 명령어(카운터로 실행 횟수를 관리하다가 스스로를 특수화하는 명령어)로 교체하고, 그 명령어가 충분히 여러 번 실행되면 다시 특수화 명령어(특정 타입과 값의 경우만 빠르게 처리하는 명령어)로 교체한다. (방법: 적응형 명령어로 교체, 방법: 특수화 시점, 용어: 적응형 명령어, 용어: 특수화 명령어)
2. [정의] PEP 659는 이렇게 느린 명령어를 더 빠른 변형 명령어로 바꿔 가는 교체 과정 전체를 quickening이라고 부른다. (방법: 적응형 명령어로 교체, 방법: quickening의 정의)
3. [대상] PEP 659가 예로 든 특수화 대상은 함수 호출(CALL), 속성 읽기(LOAD_ATTR), 전역 변수 읽기(LOAD_GLOBAL), 덧셈(BINARY_ADD)처럼 고수준 연산을 나타내는 명령어다. (방법: 특수화 대상 명령어)
4. [예] 예를 들어 LOAD_ATTR는 quickening의 첫 단계에서 적응형 명령어 LOAD_ATTR_ADAPTIVE로 교체된다. (방법: 적응형 명령어 예)

문단 2: family
5. [정의] PEP 659는 특수화 대상 명령어마다 family라는 명령어 묶음을 만든다. (방법: 명령어 family)
6. [구성] family 하나에는 적응형 명령어 하나와, 입력이 예상한 경우일 때 원래 명령어와 같은 일을 훨씬 빨리 하는 특수화 명령어가 하나 이상 들어 있다. (방법: family 구성 1, 방법: family 구성 2)
7. [이유] 특수화 명령어 하나는 한 가지 경우만 처리하므로 family로 나누면 특수화가 효과적이다. (방법: 명령어 family)

문단 3: 카운터에 따른 교체와 되돌리기
8. [단계] 적응형 명령어는 실행 횟수를 추적하는 카운터를 유지하고, 이 카운터가 0이 되면 받은 타입과 값을 확인해 스스로를 특수화하려고 시도한다. (방법: family 구성 1, 방법: LOAD_ATTR 특수화 과정)
9. [단계] 특수화 명령어는 saturating counter(최댓값이나 최솟값에 도달하면 그 값에 머무는 카운터)를 유지하고, 입력이 예상과 같으면 카운터를 올린다. (방법: 특수화 명령어의 saturating counter, 용어: saturating counter)
10. [단계] 입력이 예상과 다르면 특수화 명령어는 카운터를 내리고 원래 명령어가 하던 일반 연산을 실행한다. (방법: 특수화 명령어의 saturating counter)
11. [단계] 카운터가 최솟값에 도달하면 인터프리터는 그 명령어의 opcode(연산 코드, 명령어가 어떤 연산인지 나타내는 번호)를 적응형 명령어의 opcode로 바꾸기만 해서 특수화를 되돌린다. (방법: 최적화 해제, 용어: opcode)
12. [결과] 적응형 명령어는 주기적으로 스스로를 특수화하려고 시도하므로, 되돌아간 명령어도 프로그램이 값을 사용하는 패턴이 바뀌면 그 패턴에 맞는 특수화 명령어로 다시 교체될 수 있다. (방법: 적응형 명령어 예, 방법: 특수화와 적응의 역할)

## 단위 5. 명령어 형식과 인라인 캐시
- 형태: 섹션 "명령어 형식과 인라인 캐시"
- 전할 내용: quickening한 명령어는 tracing을 지원하려고 원래 바이트코드와 같은 16비트 형식을 유지하고, operand에 담을 수 없는 특수화 정보는 명령어 바로 뒤의 인라인 캐시에 저장한다.
- 전개: 명령어 형식 → 형식을 유지하는 이유(tracing) → quickening한 코드의 장점 → operand가 부족한 문제 → 인라인 캐시 → 적응형 명령어의 캐시 사용 → 기각한 초기 설계

문단 1: 명령어 형식과 tracing
1. [장점] quickening한 코드는 바꿀 수 없는 원래 바이트코드와 달리 실행 중에 바꿀 수 있다. (방법: quickening한 코드의 장점 1)
2. [장점] tracing(디버거나 커버리지 도구가 sys.settrace 같은 기능으로 코드가 한 줄씩 실행되는 것을 지켜보는 일)이 필요하면 인터프리터가 원래 바이트코드로 돌아가 실행하므로, quickening한 코드는 tracing을 직접 처리하지 않아도 된다. (방법: quickening한 코드의 장점 3, 용어: tracing)
3. [조건] PEP 659는 tracing을 이렇게 지원하려면 quickening한 명령어가 사용자가 볼 수 있는 원래 바이트코드와 같은 형식을 유지해야 한다고 설명한다. (방법: 명령어 형식 유지)
4. [사실] 그 형식은 8비트 opcode 뒤에 8비트 operand(피연산자)가 붙은 16비트 명령어다. (수치: 명령어 형식, 용어: operand)
4-1. [풀이] operand는 명령어가 연산에 사용하는 값이고, CPython 바이트코드에서는 읽을 이름의 번호처럼 연산에 필요한 값을 가리킨다. (용어: operand)

문단 2: 인라인 캐시
5. [문제] 특수화 명령어 family 대부분은 8비트 operand에 담을 수 있는 것보다 많은 정보가 필요하다. (방법: 보조 데이터)
6. [해결] 그래서 PEP 659의 인터프리터는 명령어 바로 뒤에 16비트 항목 여러 개를 붙여 이 정보를 저장한다. (방법: 보조 데이터, 수치: inline data cache 항목 크기)
7. [정의] PEP 659는 명령어 자리에 붙인 이 캐시를 인라인 캐시의 한 형태로 설명하고 inline data cache라고 부른다. (방법: 보조 데이터, 용어: 인라인 캐시)
8. [동작] 아직 특수화되지 않은 적응형 명령어는 인라인 캐시의 첫 항목을 실행 횟수를 추적하는 카운터로 사용하고 나머지 항목은 건너뛴다. (방법: 적응형 명령어의 캐시 사용)

문단 3: 채택하지 않은 초기 설계
9. [비교] CPython 3.11 alpha 버전에 들어간 PEP 659의 초기 구현은 quickening한 명령어를 원래 바이트코드와 같은 형식의 배열에, 특수화에 필요한 정보를 별도 배열에 저장하고 그 정보의 위치를 명령어 위치와 operand로 계산했다. (한계와 범위: 기각한 설계)
10. [결과] PEP 659는 정보를 명령어 바로 뒤에 두는 인라인 캐시 방식이 더 빠르고 단순해서 초기 설계 대신 이 방식을 선택했다고 밝힌다. (한계와 범위: 기각한 설계)

## 단위 6. LOAD_ATTR와 LOAD_GLOBAL 예
- 형태: 섹션 "속성 읽기와 전역 변수 읽기의 특수화"
- 전할 내용: LOAD_ATTR와 LOAD_GLOBAL은 처리할 경우가 여러 가지라서 경우마다 특수화 명령어를 두면 확인할 것이 줄고 코드도 단순해진다.
- 전개: LOAD_ATTR 정의 → 특수화 대상인 이유 → 특수화 과정 → 특수화 명령어 목록 → LOAD_GLOBAL 정의 → 3.9의 문제 → family의 해결 → 특수화 명령어 목록 → LOAD_GLOBAL_BUILTIN이 키만 확인하는 것

문단 1: LOAD_ATTR
1. [정의] LOAD_ATTR는 obj.x처럼 객체의 속성을 읽는 명령어로, 스택(가상 머신이 계산 중인 값을 쌓아 두는 곳) 맨 위의 객체에서 이름으로 지정한 속성을 읽고 그 객체 자리에 속성 값을 놓는다. (방법: LOAD_ATTR의 동작, 용어: LOAD_ATTR, 용어: 스택)
2. [이유] LOAD_ATTR가 읽는 속성은 일반 인스턴스의 속성일 수도 있고 클래스나 모듈의 속성일 수도 있으며, 그 밖에도 특수한 경우가 많아서 PEP 659는 LOAD_ATTR를 특수화하기 좋은 대상으로 꼽는다. (방법: LOAD_ATTR가 특수화 대상인 이유)
3. [단계] LOAD_ATTR는 처음에 LOAD_ATTR_ADAPTIVE로 quickening되고, LOAD_ATTR_ADAPTIVE는 실행 횟수를 세면서 충분히 실행되기 전까지는 원래 LOAD_ATTR의 동작으로 속성을 읽는다. (방법: LOAD_ATTR 특수화 과정)
4. [단계] 충분히 실행되면 LOAD_ATTR_ADAPTIVE는 내부 함수 _Py_Specialize_LoadAttr를 호출해 속성의 종류를 확인하고, 맞는 특수화 명령어가 있으면 그 명령어로 자기 자리를 교체한다. (방법: LOAD_ATTR 특수화 과정)
5. [목록 소개] PEP 659가 예로 든 LOAD_ATTR의 특수화 명령어는 다음 세 가지다. (방법: LOAD_ATTR_INSTANCE_VALUE, LOAD_ATTR_MODULE, LOAD_ATTR_SLOT)
- [목록] LOAD_ATTR_INSTANCE_VALUE: 속성이 객체의 값 배열(인스턴스 속성 값을 담는 배열)에 저장돼 있고 같은 이름의 디스크립터(property처럼 속성을 읽고 쓰는 동작을 클래스에서 직접 정의하는 객체)가 그 속성을 가리지 않는 흔한 경우를 처리한다 / LOAD_ATTR_MODULE: 모듈의 속성을 읽는 경우를 처리한다 / LOAD_ATTR_SLOT: 클래스가 __slots__(인스턴스가 가질 속성 이름을 미리 정해 두는 기능)를 정의한 객체의 속성을 읽는 경우를 처리한다 (용어: 디스크립터, 용어: __slots__, 용어: 값 배열)

문단 2: LOAD_GLOBAL
7. [정의] LOAD_GLOBAL은 함수 안에서 전역 변수나 내장 함수의 이름을 읽는 명령어로, 이름을 전역 네임스페이스에서 먼저 찾고 없으면 내장 네임스페이스(len, print 같은 내장 함수의 이름이 들어 있는 네임스페이스)에서 찾는다. (방법: LOAD_GLOBAL의 동작, 용어: 내장 네임스페이스)
8. [이전 상태] CPython 3.9의 LOAD_GLOBAL은 이미 캐시를 사용했고, 그 C 코드 하나에는 코드 객체(함수 하나의 바이트코드와 이름, 상수, 디버깅 정보를 담은 객체) 전체를 바꿔 캐시를 추가할지 확인하는 코드, 캐시에서 값을 찾는 코드, 캐시를 사용할 수 없을 때의 대체 코드가 모두 들어 있었다. (방법: 3.9의 LOAD_GLOBAL 문제, 용어: 코드 객체, 설명용 예시: 3.9의 LOAD_GLOBAL이 이미 캐시를 사용했다는 것)
9. [문제] PEP 659는 그래서 3.9의 LOAD_GLOBAL 코드가 복잡하고 컸으며 최적화된 상태에서도 불필요한 연산을 많이 실행했다고 설명한다. (방법: 3.9의 LOAD_GLOBAL 문제)
10. [해결] family를 사용하면 명령어 하나가 한 가지 경우만 처리하므로 코드를 유지보수하기 쉬워지고 실행도 빨라진다. (방법: family의 유지보수 이점)
11. [목록 소개] LOAD_GLOBAL의 family에는 다음 명령어가 들어간다. (방법: LOAD_GLOBAL_ADAPTIVE, LOAD_GLOBAL_MODULE, LOAD_GLOBAL_BUILTIN)
- [목록] LOAD_GLOBAL_ADAPTIVE: LOAD_ATTR_ADAPTIVE와 같은 방식으로 동작하는 적응형 명령어 / LOAD_GLOBAL_MODULE: 값이 전역 네임스페이스에 있는 경우. 네임스페이스의 키가 바뀌지 않았는지 확인한 뒤 저장해 둔 인덱스에서 값을 바로 읽음 / LOAD_GLOBAL_BUILTIN: 값이 내장 네임스페이스에 있는 경우. 전역 네임스페이스에 키가 추가되지 않았는지와 내장 네임스페이스가 바뀌지 않았는지 확인함

문단 3: LOAD_GLOBAL_BUILTIN이 키만 확인하는 것
12. [사실] LOAD_GLOBAL_BUILTIN은 전역 네임스페이스의 값이 바뀌었는지는 확인하지 않고 키만 확인한다. (방법: LOAD_GLOBAL_BUILTIN)
13. [풀이] LOAD_GLOBAL은 전역 네임스페이스를 먼저 찾으므로, 전역 네임스페이스에 내장 함수와 같은 이름의 키가 새로 추가되면 내장 함수 대신 그 전역 변수를 읽어야 한다. (방법: LOAD_GLOBAL의 동작, 설명용 예시: LOAD_GLOBAL_BUILTIN이 키만 확인하는 것의 풀이)

문단 4: 구현 위치
14. [사실] PEP 659는 LOAD_ATTR와 LOAD_GLOBAL의 family를 비롯한 명령어의 전체 구현을 CPython 저장소에서 확인할 수 있다고 안내한다. (방법: 구현 위치)
15. [사실] 적응형 명령어와 특수화 명령어는 Python/ceval.c에, 특수화를 수행하는 최적화 코드는 Python/specialize.c에 구현돼 있다. (방법: 구현 위치)

## 단위 7. 속도 향상
- 형태: 섹션 "속도 향상 10~60%와 그 원인"
- 전할 내용: PEP 659는 속도 향상을 10~60%로 추정하고, 향상의 대부분은 속성 읽기, 전역 변수 읽기, 함수 호출의 특수화에서 나온다고 설명한다.
- 전개: 추정 범위 → 측정이 어려운 이유 → 초록의 최대 50% 추정 → 25%여도 가치 있다는 주장 → 향상의 출처(특수화) → 디스패치 정의 → 향상의 출처(디스패치 개선)

문단 1: 속도 향상의 추정
1. [결과] PEP 659는 특수화로 얻는 속도 향상을 10~60%로 추정한다. (수치: 특수화로 얻는 속도 향상 범위)
2. [조건] PEP 659는 많은 특수화가 다른 최적화에 의존하므로 특수화만으로 얻는 속도 향상을 정확히 측정하기 어렵다고 밝힌다. (한계와 범위: 특수화 효과 측정이 어려운 이유)
3. [조건] Abstract 섹션에서도 PEP 659는 속도 향상 수치가 어떤 벤치마크를 사용하는지와 아직 하지 않은 개발 작업에 따라 크게 달라진다는 점을 들어 의미 있는 수치를 내기 어렵다고 덧붙인다. (한계와 범위: 수치를 내기 어려움)
3-1. [추정] 같은 섹션에서 PEP 659는 10~60%와 다른 수치를 제시하는데, 많은 실험 결과를 근거로 최대 50%까지 빨라질 것으로 추정한다. (수치: 특수화 적응형 인터프리터의 속도 향상(초록))
4. [주장] PEP 659는 속도 향상이 25%에 그치더라도 도입할 가치가 있다고 주장한다. (수치: 가치 판단 기준)

문단 2: 속도 향상의 출처
5. [결과] 속도 향상의 대부분은 특수화에서 직접 나오고, 가장 크게 기여하는 것은 속성 읽기, 전역 변수 읽기, 함수 호출이 빨라진 것이다. (한계와 범위: 속도 향상의 출처 1)
6. [결과] 속도 향상 중 작지만 쓸모 있는 일부는 quickening으로 가능해진 최적화에서 나오며, PEP 659가 든 예는 디스패치(인터프리터가 명령어 하나를 실행한 뒤 다음 명령어를 처리하는 코드로 넘어가는 과정) 개선이다. (한계와 범위: 속도 향상의 출처 2, 용어: 디스패치)
7. [예] 디스패치를 개선하는 방법의 예는 super-instruction(명령어 여러 개에 걸친 일을 명령어 하나로 처리하고 operand를 여러 개 받는 명령어)이고, quickening한 코드는 super-instruction을 사용할 수 있다. (한계와 범위: 속도 향상의 출처 2, 방법: quickening한 코드의 장점 2, 용어: super-instruction)

## 단위 8. 호환성과 메모리 비용
- 형태: 섹션 "기존 코드와의 호환성과 메모리 비용"
- 전할 내용: PEP 659는 언어와 API를 바꾸지 않고, 3.11은 함수 상당수가 거의 실행되지 않는 애플리케이션에서 3.10보다 메모리를 조금 더 사용한다.
- 전개: 호환성 → 알아챌 방법 → 메모리 걱정과 짧은 답 → 3.10의 메모리 사용 → 표 → 표 읽기 → 손익분기점 → 코드 객체의 다른 정보 → 결론

문단 1: 호환성
1. [결과] PEP 659가 도입한 인터프리터는 Python 언어, 라이브러리, API를 바꾸지 않으므로, 사용자가 새 인터프리터를 알아챌 수 있는 방법은 실행 시간 측정, 디버깅 도구 사용, 메모리 사용량 측정뿐이다. (한계와 범위: 호환성, 한계와 범위: 사용자가 알아챌 방법)
3. [사실] PEP 659는 보안에 미치는 영향은 없다고 밝힌다. (한계와 범위: 보안 영향)

문단 2: 3.10과 3.11의 메모리 비교
4. [질문] 캐시를 사용하는 방식에서는 메모리를 얼마나 더 사용하는지가 당연한 걱정이고, PEP 659의 짧은 답은 "그리 많지 않다"이다. (한계와 범위: 메모리 질문에 대한 답)
5. [이전 상태] 비교 대상인 CPython 3.10은 코드의 실행 횟수가 약 2,000번이 될 때까지 명령어당 2바이트를 사용했다. (수치: 3.10 기본 메모리)
6. [이전 상태] 실행 횟수가 약 2,000번에 도달하면 3.10은 opcache(3.10이 자주 실행된 코드에 붙이던 캐시)를 만들면서 명령어마다 1바이트를, 캐시를 사용하는 명령어(LOAD_GLOBAL, LOAD_ATTR)마다 32바이트를 추가로 할당했다. (수치: 3.10 hot 추가 할당, 용어: opcache)
7. [표 소개] 아래 표는 PEP 659가 64비트 머신을 기준으로 3.10과 3.11의 명령어 하나당 메모리 사용량을 바이트 단위로 비교한 것이다. (수치: 표)
- [표] 열: 항목, 3.10 cold, 3.10 hot, 3.11 / 행: 특수화된(캐시를 사용하는) 명령어 비율(0%, 약 15%, 약 25%), code(2, 2, 2), opcache_map(0, 1, 0), opcache/data(0, 4.8, 4), 합계(2, 7.8, 6)
8. [표 읽기] 3.10 cold는 코드의 실행 횟수가 약 2,000번에 도달하기 전, 3.10 hot은 그 기준에 도달해 캐시를 만든 뒤의 값이다. (수치: 3.10 cold와 hot의 의미)
9. [표 읽기] 3.10 hot의 opcache_map 1바이트는 명령어마다 추가로 할당한 1바이트이고, opcache/data 4.8바이트는 전체 명령어의 약 15%에 32바이트씩 할당한 양을 명령어 하나당 평균으로 계산한 값과 같다. (설명용 예시: 메모리 표 읽기)
9-1. [표 읽기] 3.11은 cold와 hot을 나누지 않고 명령어당 6바이트로 계산돼 있다. (설명용 예시: 메모리 표 읽기, 수치: 표: 합계)

문단 3: 손익분기점과 결론
10. [조건] 3.10의 명령어당 메모리는 캐시를 만든 코드에서만 2바이트에서 7.8바이트로 늘어나므로, 3.10 대비 3.11의 메모리 사용량은 3.10에서 캐시를 만들 만큼 자주 실행되는 코드가 얼마나 되는지에 따라 달라진다. (수치: 손익분기점, 설명용 예시: 메모리 표 읽기)
11. [수치] PEP 659에 따르면 그런 코드가 약 70%일 때 3.10과 3.11의 메모리 사용량이 같아진다. (수치: 손익분기점)
12. [보충] 또한 PEP 659는 바이트코드가 코드 객체의 일부일 뿐이고, 코드 객체에는 이름, 상수, 상당한 양의 디버깅 정보도 들어 있다고 지적한다. (한계와 범위: 바이트코드는 코드 객체의 일부)
12-1. [추론] 그래서 코드 객체 전체로 보면 3.10과 3.11의 차이는 표의 비율보다 작을 수 있다. (설명용 예시: 코드 객체 전체로 본 차이)
13. [결론] PEP 659는 함수 상당수가 거의 실행되지 않는 대부분의 애플리케이션에서 3.11이 3.10보다 메모리를 더 사용하지만 차이는 크지 않다고 결론짓는다. (한계와 범위: 메모리 결론)

## 단위 9. PEP의 범위와 뒤로 미룬 JIT 컴파일
- 형태: 섹션 "PEP 659가 정하지 않은 것과 뒤로 미룬 JIT 컴파일"
- 전할 내용: PEP 659는 특수화를 관리하는 구조만 정하고 구체적인 최적화와 JIT 컴파일은 정하지 않았으며, 명령어 단위 특수화가 만드는 프로파일링 정보는 앞으로 더 정교한 최적화에 사용할 수 있다.
- 전개: PEP의 범위 → 바뀔 수 있음 → 구현 위치 → JIT는 보류 → 프로파일링 정보

문단 1: PEP의 범위
1. [범위] PEP 659는 특수화를 관리하는 구조만 설명하고 어떤 최적화를 적용할지는 정하지 않는다. (한계와 범위: PEP의 범위)
2. [한계] PEP 659는 개발이 진행되면서 특수화의 세부 사항이나 구현 전체가 바뀔 수 있다고도 밝힌다. (한계와 범위: 변경 가능성)

문단 2: 뒤로 미룬 JIT 컴파일과 프로파일링 정보
4. [사실] PEP 659는 특수화 적응형 인터프리터와 인라인 캐시를 선택한 것이 CPython을 최적화하는 다른 여러 방법을 사실상 택하지 않은 것과 같다고 인정한다. (한계와 범위: JIT는 보류)
4-1. [대조] 다만 JIT 컴파일 같은 방법은 포기한 것이 아니라 뒤로 미뤘을 뿐이라고 강조한다. (한계와 범위: JIT는 보류)
5. [의의] 명령어 하나 단위로 추측하고 적응하는 특수화는 인터프리터를 빠르게 할 뿐 아니라, 앞으로 더 정교한 최적화에 사용할 프로파일링 정보(어떤 코드가 어떤 타입의 값으로 몇 번 실행됐는지 모은 정보)도 만든다. (문제와 배경: 명령어 단위 특수화의 부수 효과, 용어: 프로파일링 정보)

## 제외한 사실
- 3.9 LOAD_GLOBAL 설명 중 "whether either the global or builtins namespace" 구절: 원문 문장이 끊겨 있어 무엇을 확인하는 코드인지 알 수 없다.
- LOAD_ATTR_INSTANCE_VALUE와 lazy dictionary의 조합: 자료에 lazy dictionary 설명이 없어 독자가 이해할 수 없다.
- 기각한 설계의 세부 사항(데이터 위치 계산식 (instruction offset)//2 + (quickened operand), 특수화 가능한 명령어 25~30%, 함수당 약 5,000개와 1,000개 명령어 지원, 데이터 항목 2개(16바이트), POP_TOP 예, 3.10은 오프셋 계산에 의존적인 읽기 2번 필요): 기각된 설계의 내부 구조라 핵심 주제를 설명하지 않고, 기각 이유(인라인 캐시가 더 빠르고 단순함)만으로 인라인 캐시를 선택한 이유를 전할 수 있다.
- 표의 opcache_map, opcache/data 행의 개별 의미: 자료가 행의 의미를 따로 설명하지 않는다. 표에는 값을 그대로 싣고 본문은 합계만 설명한다.
- PEP의 유형 Informational, 상태 Final, Post-History 2021년 5월 11일: 독자가 PEP 659의 내용을 이해하는 데 필요하지 않다. 구현 여부는 "CPython 3.11에 들어갔다"는 문장으로 전한다.
