# PEP 659: 실행 중인 타입에 맞춰 바이트코드 명령어를 바꾸는 CPython 인터프리터

PEP 659[1]는 Mark Shannon이 2021년 4월에 작성한 PEP(Python Enhancement Proposal, Python에 새 기능이나 변경을 제안하는 문서)입니다. PEP 659는 python.org에서 배포하는 표준 Python 구현인 CPython에 특수화 적응형 인터프리터(Specializing Adaptive Interpreter)를 추가하자고 제안합니다. 특수화 적응형 인터프리터는 프로그램이 실행되는 동안 실제로 다루는 타입과 값에 맞춰 바이트코드 명령어(CPython이 Python 소스 코드를 컴파일해 만든, 인터프리터가 실행하는 명령어)를 그 경우만 처리하는 빠른 명령어로 바꾸고, 타입과 값이 달라지면 다시 거기에 맞춰 바뀌는 인터프리터입니다.

PEP 659의 구현은 Python 3.11을 대상으로 만들어졌고, PEP 659는 메모리 사용량을 비교할 때 기존 방식을 Python 3.10, 제안한 인터프리터를 Python 3.11로 표시합니다. PEP 659에 따르면 언어와 라이브러리, API는 바뀌지 않고 보안 영향도 없으며, 사용자가 새 인터프리터를 알아챌 수 있는 방법은 실행 시간 측정, 디버깅 도구 사용, 메모리 사용량 측정뿐입니다. 이 글은 CPython이 바이트코드를 실행하는 방식부터 설명하고, PEP 659가 명령어를 어떻게 바꾸는지와 그 결과 속도와 메모리 사용량이 어떻게 달라지는지 정리합니다.

## CPython이 Python 코드를 실행하는 방식

CPython은 Python 소스 코드를 먼저 바이트코드로 컴파일한 뒤 실행합니다. 바이트코드는 CPython 인터프리터 안에서 Python 프로그램을 나타내는 형식이고, 인터프리터는 바이트코드의 명령어를 하나씩 읽어 실행하는 프로그램입니다. 명령어 하나는 16비트이고, 어떤 연산인지 나타내는 8비트 opcode 뒤에 연산에 넘기는 8비트 피연산자(operand)가 붙습니다.

함수의 바이트코드는 코드 객체에 저장됩니다. 코드 객체에는 바이트코드 외에도 이름과 상수, 상당한 양의 디버깅 정보가 들어 있습니다.

바이트코드 명령어 중에는 고수준 연산을 나타내는 명령어가 많습니다. 함수를 호출하는 `CALL`, 객체의 속성을 읽는 `LOAD_ATTR`, 전역 변수나 내장 이름을 읽는 `LOAD_GLOBAL`, 두 값을 더하는 `BINARY_ADD`가 그 예입니다. `obj.name` 같은 코드를 실행하면 `LOAD_ATTR`가 `obj`에서 `name`이라는 속성을 찾아 읽는데, PEP 659는 속성이 일반 인스턴스, 클래스, 모듈을 비롯한 여러 경우 중 하나에 속할 수 있으므로 `LOAD_ATTR`를 경우마다 따로 처리하는 명령어로 나누기 좋은 대상으로 꼽습니다.

## PEP 659가 해결하려는 문제

PEP 659가 제안의 동기로 처음 드는 사실은 Python이 느리다는 평가가 널리 퍼져 있다는 점입니다. PEP 659는 Python이 C나 Fortran 같은 저수준 언어나 Java만큼 빨라지지는 못하겠지만 JavaScript의 V8, Lua의 LuaJIT처럼 빠른 스크립트 언어 구현과는 경쟁할 수 있기를 바랍니다. 이 목표를 CPython에서 이루려는 이유는 PyPy 같은 다른 Python 구현을 사용할 수 없는 사용자를 포함해 Python 사용자 모두가 혜택을 받게 하려는 것입니다.

PEP 659는 이 목표까지는 아직 멀고 많은 엔지니어링 노력이 필요하지만 인터프리터를 빠르게 하면 목표에 크게 다가갈 수 있다고 말합니다. 그 근거로 학계 연구와 실제 구현 모두 빠른 인터프리터가 빠른 가상 머신(virtual machine)의 핵심 부분이라는 것을 보여 줬다는 점을 듭니다. 가상 머신은 소프트웨어로만 정의한 컴퓨터이고, Python의 가상 머신은 컴파일된 바이트코드를 실행합니다. PEP 659가 빠르게 하려는 인터프리터는 가상 머신에서 바이트코드 명령어를 하나씩 읽어 실행하는 부분입니다.

특수화(specialization)는 실행 중인 프로그램의 타입과 값에 맞춰 실행하는 코드를 바꾸는 일입니다. PEP 659는 가상 머신을 빠르게 하는 여러 방법 중 특수화가 그 자체로도, 다른 최적화를 가능하게 하는 바탕으로도 가장 중요하다고 주장합니다.

특수화는 보통 JIT 컴파일러(프로그램을 실행하는 도중에 코드를 CPU가 직접 실행하는 기계어로 바꾸는 컴파일러)와 함께 언급됩니다. PEP 659는 기계어를 만들지 않는 인터프리터에서도 특수화로 이득을 얻을 수 있다고 설명하고, Mark Shannon의 2011년 논문[2]을 근거로 인터프리터 안의 특수화로도 성능을 크게 높일 수 있고 단순한 컴파일러보다 빠를 수도 있다고 말합니다.

가상 머신의 일반적인 최적화는 비용이 커서 최적화 비용을 들일 가치가 있다는 확신을 얻을 때까지 프로그램을 오래 실행하는 워밍업(warm-up) 시간이 필요합니다. PEP 659는 눈에 띄는 워밍업 시간 없이 곧바로 빨라지려면 함수가 몇 번만 실행된 뒤에도 특수화할 가치가 있다고 추측해야 한다고 설명합니다. 그러려면 인터프리터가 특수화와 특수화를 되돌리는 일(de-optimization)을 계속, 아주 적은 비용으로 할 수 있어야 합니다.

## 명령어 하나 단위로 특수화하는 이유

학계에 제안된 특수화 방법 대부분은 바이트코드 명령어 하나보다 큰 영역을 한꺼번에 최적화합니다[2][3]. 영역이 명령어 하나보다 크면 영역 중간에서 특수화를 되돌리는 경우를 처리하는 코드가 따로 필요합니다. PEP 659는 명령어 하나 단위로 특수화하면 특수화를 되돌리는 일이 영역 중간에서 일어날 수 없으므로 되돌리는 일이 아주 간단해진다고 설명합니다.

PEP 659는 명령어 하나 단위로 추측에 근거해 특수화하면 성능을 크게 높일 수 있고, 이때 필요한 되돌리기는 그 명령어 하나에만 적용되는 구현하기 쉬운 처리뿐이라고 주장합니다. 명령어 하나 단위의 특수화는 인터프리터를 빠르게 할 뿐 아니라 앞으로 더 정교한 최적화에 사용할 프로파일링 정보(프로그램이 실행되는 동안 어떤 명령어가 어떤 타입과 값을 다뤘는지 같은 실행 기록)도 만듭니다.

## 적응형 명령어와 특수화 명령어의 동작

PEP 659는 느린 명령어를 더 빠른 변형으로 바꾸는 과정을 quickening이라고 부릅니다. quickening 과정에서 특수화 적응형 인터프리터는 특수화로 이득을 볼 명령어를 먼저 적응형 명령어(adaptive instruction)로 바꿉니다. 적응형 명령어는 실행되면서 자신이 다루는 타입과 값에 맞춰 스스로를 특수화하는 명령어이고, `LOAD_ATTR`의 적응형 명령어는 `LOAD_ATTR_ADAPTIVE`입니다.

quickening을 거친 코드는 사용자가 볼 수 있는 원래 바이트코드와 달리 실행 중에 바꿀 수 있고, super-instruction(명령어 여러 개가 하던 일을 하나로 합친 명령어)도 사용할 수 있습니다. 디버거처럼 실행을 한 줄씩 따라가는 tracing이 필요하면 원래 바이트코드로 돌아가 실행할 수 있으므로 quickening을 거친 코드는 tracing을 직접 처리하지 않아도 됩니다. PEP 659는 이렇게 tracing을 지원하려면 quickening을 거친 명령어도 원래 바이트코드와 같은 16비트 형식이어야 한다고 설명합니다.

특수화 적응형 인터프리터는 `CALL`, `LOAD_ATTR`, `LOAD_GLOBAL`, `BINARY_ADD` 같은 명령어마다 명령어 family를 만듭니다. 명령어 family는 원래 명령어 하나에 대해 만든 적응형 명령어 하나와 특수화 명령어(specialized instruction) 하나 이상의 묶음입니다. 특수화 명령어는 입력이 예상한 형태일 때 원래 명령어가 하던 일반 연산(여러 경우를 함께 처리하는 연산)과 같은 일을 훨씬 빨리 하는 명령어이고, PEP 659는 특수화 명령어마다 한 가지 일만 맡으므로 특수화가 효과적이라고 설명합니다.

명령어 하나가 적응형 명령어에서 특수화 명령어로 바뀌었다가 다시 적응형 명령어로 돌아오는 과정은 다음과 같습니다.

1. 적응형 명령어는 자신이 실행될 때마다 값이 바뀌는 카운터를 유지하다가 카운터가 0에 이르면 자기 자신을 특수화하려고 시도합니다.
2. 맞는 특수화 명령어를 찾으면 적응형 명령어를 그 특수화 명령어로 바꿉니다.
3. 특수화 명령어는 포화 카운터(최댓값이나 최솟값에 이르면 더 늘거나 줄지 않는 카운터)를 유지합니다. 입력이 예상과 같으면 카운터를 올리고, 입력이 예상과 다르면 카운터를 내린 뒤 일반 연산을 실행합니다.
4. 포화 카운터가 최솟값에 이르면 opcode를 적응형 명령어의 opcode로 바꾸는 것만으로 특수화를 되돌립니다.

4단계에서 되돌아간 적응형 명령어는 1단계처럼 다시 주기적으로 특수화를 시도합니다. PEP 659는 이렇게 적응하는 덕분에 프로그램이 다루는 타입과 값이 바뀌어도 인터프리터가 새 타입과 값에 빠르게 적응하고, 잘못된 특수화로 생기는 추가 작업의 양이 제한된다고 설명합니다.

특수화 명령어 대부분은 8비트 피연산자에 담을 수 있는 것보다 많은 정보가 필요합니다. 그래서 특수화 적응형 인터프리터는 명령어 바로 뒤에 붙은 16비트 칸 여러 개에 이 정보를 저장합니다. PEP 659는 명령어 뒤의 16비트 칸에 데이터를 저장하는 이 방식을 inline data cache라고 부르고, inline cache(명령어가 다시 사용할 데이터를 명령어 바로 옆에 저장해 두는 방식)의 한 형태로 설명합니다. 적응형 명령어는 inline data cache의 첫 칸을 카운터로 사용하고 나머지 칸은 건너뜁니다.

PEP 659는 기존 연구 중 가장 가까운 방식으로 "Inline Caching meets Quickening"[4]을 듭니다. PEP 659는 자신의 방식이 그 연구가 사용한 inline cache의 장점에 특수화를 빠르게 되돌리는 기능을 추가한 것이라고 설명합니다. PEP 659에 따르면 이 기능 덕분에 특수화가 실패하거나 특수화한 상태가 오래 유지되지 않는 경우에도 성능이 덜 흔들립니다.

## LOAD_ATTR와 LOAD_GLOBAL의 특수화 명령어

`LOAD_ATTR`는 처음에 `LOAD_ATTR_ADAPTIVE`로 바뀝니다. `LOAD_ATTR_ADAPTIVE`는 자신이 얼마나 자주 실행되는지 기록하다가 충분히 실행되면 CPython 내부 함수 `_Py_Specialize_LoadAttr`를 호출하고, 그 전까지는 원래 `LOAD_ATTR`가 하던 일반 연산을 실행해 속성을 읽습니다. 특수화할 때는 속성의 종류를 확인하고, 맞는 특수화 명령어가 있으면 `LOAD_ATTR_ADAPTIVE`를 그 자리에서 특수화 명령어로 바꿉니다.

`LOAD_GLOBAL`은 이름을 전역 네임스페이스에서 찾고, 없으면 builtins 네임스페이스에서 찾습니다. 네임스페이스는 변수가 저장되는 곳이고 딕셔너리로 구현돼 있습니다. 전역 네임스페이스에는 모듈의 전역 변수가, builtins 네임스페이스에는 `len`, `print` 같은 내장 이름이 저장됩니다.

PEP 659는 Python 3.9의 `LOAD_GLOBAL`을 예로 들어 명령어 하나가 여러 일을 처리할 때의 문제를 설명합니다. 3.9의 `LOAD_GLOBAL` C 코드에는 찾은 값을 저장해 두는 캐시를 추가하려고 코드 객체 전체를 수정해야 하는지 판단하는 코드, 이름이 전역 네임스페이스와 builtins 네임스페이스 중 어느 쪽에 있는지 확인하는 코드, 캐시에서 값을 찾는 코드, 캐시를 사용할 수 없을 때 실행하는 대체 코드가 모두 들어 있습니다. PEP 659는 이 C 코드가 복잡하고 크며 최적화된 상태에서도 불필요한 연산을 많이 한다고 지적하고, 명령어 family로 나누면 명령어마다 한 가지 일만 처리하므로 코드를 유지보수하기 쉬워지고 더 빨라진다고 설명합니다. `LOAD_GLOBAL` family의 적응형 명령어인 `LOAD_GLOBAL_ADAPTIVE`는 `LOAD_ATTR_ADAPTIVE`와 같은 방식으로 동작합니다.

PEP 659가 후보로 든 `LOAD_ATTR`와 `LOAD_GLOBAL`의 특수화 명령어와 각 명령어가 처리하는 경우는 아래 표와 같습니다.

| 원래 명령어 | 특수화 명령어 | 처리하는 경우 |
|---|---|---|
| `LOAD_ATTR` | `LOAD_ATTR_INSTANCE_VALUE` | 속성 값이 객체의 값 배열(value array, 객체가 속성 값을 저장하는 배열)에 있고, 인스턴스 속성보다 우선하는 descriptor가 없는 흔한 경우 |
| `LOAD_ATTR` | `LOAD_ATTR_MODULE` | 모듈의 속성을 읽는 경우 |
| `LOAD_ATTR` | `LOAD_ATTR_SLOT` | 클래스가 `__slots__`를 정의한 객체의 속성을 읽는 경우 |
| `LOAD_GLOBAL` | `LOAD_GLOBAL_MODULE` | 값이 전역 네임스페이스에 있는 경우 |
| `LOAD_GLOBAL` | `LOAD_GLOBAL_BUILTIN` | 값이 builtins 네임스페이스에 있는 경우 |

표의 descriptor는 `__get__()`, `__set__()`, `__delete__()` 중 하나를 정의한 객체입니다. 인스턴스 속성보다 우선하는 descriptor는 클래스에 정의돼 있어서 같은 이름의 인스턴스 속성보다 먼저 사용되는 descriptor이고, property가 그 예입니다. `__slots__`는 인스턴스 속성의 자리를 클래스 안에 미리 정해 두어 인스턴스 딕셔너리를 만들지 않게 하는 선언입니다.

`LOAD_GLOBAL_MODULE`은 전역 네임스페이스의 키(변수 이름)가 바뀌지 않았는지 확인한 뒤 저장해 둔 인덱스(네임스페이스 딕셔너리 안에서 값이 있는 위치)에서 값을 읽습니다. `LOAD_GLOBAL_BUILTIN`은 전역 네임스페이스에 키가 추가되지 않았는지와 builtins 네임스페이스가 바뀌지 않았는지를 확인합니다. PEP 659는 두 명령어가 전역 네임스페이스에서 확인하는 것은 키뿐이고 전역 변수의 값이 바뀌었는지는 상관없다고 강조합니다.

PEP 659는 전체 구현이 CPython 저장소의 `ceval.c`(적응형 명령어와 특수화 명령어)와 `specialize.c`(최적화)에 있다고 안내합니다[5].

## 속도 향상 추정치

PEP 659는 의미 있는 속도 향상 수치를 내기 어렵다고 밝힙니다. 속도 향상이 어떤 벤치마크를 사용하는지와 PEP를 작성할 때 아직 하지 않은 작업에 따라 크게 달라지고, 많은 특수화가 다른 최적화에 의존하기 때문입니다.

PEP 659는 문서 첫머리의 요약에서 특수화 적응형 인터프리터를 CPython에 추가하면 여러 실험 결과로 미루어 속도가 최대 50% 향상될 것으로 추정하고, 속도 향상이 25%에 그치더라도 추가할 가치가 있다고 주장합니다. 성능을 다룬 부분에서는 특수화로 얻는 속도 향상을 10~60% 범위로 추정합니다. PEP 659는 두 추정치를 어떤 벤치마크에서 무엇과 비교해 얻었는지 밝히지 않습니다.

PEP 659에 따르면 속도 향상의 대부분은 특수화 자체에서 나오고, 가장 크게 기여하는 부분은 속성 조회, 전역 변수 조회, 함수 호출을 빠르게 한 것입니다.

속도 향상의 작지만 쓸모 있는 일부는 super-instruction 같은 dispatch(인터프리터가 다음 명령어를 읽고 그 명령어를 처리하는 코드로 이동하는 과정) 개선과 quickening 덕분에 가능해진 다른 최적화에서 나옵니다.

## Python 3.10과 비교한 메모리 사용량

PEP 659는 캐시를 사용하는 방식이라면 "메모리를 얼마나 더 사용하는가"라는 걱정이 당연히 생긴다고 말하고, 이 질문에 "그리 많지 않다"고 답합니다. 비교 대상인 CPython 3.10은 코드의 실행 횟수가 약 2,000번에 이르기 전까지 명령어 하나당 2바이트를 사용했습니다. 실행 횟수가 약 2,000번에 이르면 3.10은 opcache라는 캐시를 만들면서 명령어마다 1바이트를 더 할당하고, 캐시를 사용하는 `LOAD_GLOBAL`과 `LOAD_ATTR` 명령어마다 32바이트를 더 할당했습니다.

아래 표는 64비트 컴퓨터에서 3.10의 opcache와 특수화 적응형 인터프리터가 명령어 하나당 사용하는 바이트 수를 비교한 PEP 659의 표입니다. 3.10 cold는 코드가 약 2,000번 실행되기 전, 3.10 hot은 그 기준에 이른 뒤의 상태이고, 3.11 열은 특수화 적응형 인터프리터의 값입니다. code 행은 명령어 자체가 차지하는 바이트 수이고, opcache_map 행과 opcache/data 행은 캐시를 위해 명령어 하나당 추가로 사용하는 바이트 수입니다.

| 항목 | 3.10 cold | 3.10 hot | 3.11 |
|---|---|---|---|
| 특수화된 명령어의 비율 | 0% | 약 15% | 약 25% |
| code | 2 | 2 | 2 |
| opcache_map | 0 | 1 | 0 |
| opcache/data | 0 | 4.8 | 4 |
| 합계 | 2 | 7.8 | 6 |

표의 합계 행에서 명령어 하나당 메모리는 3.10 cold가 2바이트, 3.10 hot이 7.8바이트, 3.11이 6바이트입니다. 명령어 하나당 메모리로 비교하면 3.11은 약 2,000번 실행되기 전의 3.10 코드보다 더 사용하고, 그 기준에 이른 3.10 코드보다는 덜 사용합니다.

그래서 두 버전의 메모리 사용량 차이는 3.10에서 캐시를 만들 만큼 자주 실행되는 코드가 얼마나 되는지에 따라 달라집니다. PEP 659에 따르면 그런 코드의 비율이 약 70%일 때 3.10과 3.11의 메모리 사용량이 같아집니다.

PEP 659는 바이트코드가 코드 객체의 일부일 뿐이라는 점도 지적합니다. 코드 객체에는 바이트코드 외에도 이름과 상수, 상당한 양의 디버깅 정보가 들어 있습니다. PEP 659는 대부분의 애플리케이션처럼 함수 상당수가 거의 실행되지 않는 경우 3.11이 3.10보다 메모리를 더 사용하지만 그 차이는 크지 않다고 결론짓습니다.

## 채택하지 않은 방식과 PEP 659가 정하지 않은 부분

3.11 alpha용으로 만든 PEP 659의 이전 구현은 quickening을 거친 명령어를 원래 바이트코드와 같은 형식의 배열에 저장하고, 특수화 명령어가 사용할 데이터는 별도의 배열에 저장했습니다. 이전 구현의 실험에서는 명령어의 25~30%를 쓸모 있게 특수화할 수 있었고, 명령어 family 대부분은 데이터 항목이 2개(64비트 컴퓨터에서 16바이트) 필요했습니다.

3.10의 opcache는 데이터 위치를 계산하려고 메모리를 두 번 읽고, 두 번째 읽기는 첫 번째 읽기의 결과에 의존합니다. 이전 구현은 데이터 위치를 명령어의 위치와 피연산자만으로 계산해 메모리를 읽지 않았으므로 3.10보다 빨랐습니다. 이전 구현은 family마다 데이터 크기를 다르게 할 수 있고 데이터 위치를 기록하는 배열이 따로 필요 없어서 메모리도 훨씬 적게 사용했습니다. 각 캐시 방식이 지원하는 함수의 크기도 3.10은 명령어 약 1,000개까지, 이전 구현은 약 5,000개까지였습니다.

PEP 659는 inline data cache 방식이 더 빠르고 단순하다는 이유로 이전 구현의 방식을 채택하지 않았다고 밝힙니다. PEP 659는 inline data cache를 사용하는 특수화 적응형 인터프리터를 구현하는 것 자체가 CPython을 최적화하는 다른 많은 방법을 채택하지 않는 일이라고 말하지만, JIT 컴파일 같은 아이디어는 거부하지 않고 뒤로 미뤘을 뿐이라고 강조합니다.

PEP 659는 특수화를 관리하는 방식만 설명하고 실제로 적용할 개별 최적화는 정하지 않습니다. 앞에서 소개한 `LOAD_ATTR`와 `LOAD_GLOBAL`의 특수화 명령어도 PEP 659가 후보로 든 예이고, PEP 659는 코드가 더 개발되면서 세부 사항이나 구현 전체가 바뀔 가능성이 높다고 밝힙니다.
