# PEP 659: 실행 중에 명령어를 특수화하는 CPython 인터프리터

PEP 659는 Mark Shannon이 2021년 4월에 작성한 PEP(Python에 새 기능이나 변경을 제안하거나 설계를 설명하는 문서)로, 제목은 "Specializing Adaptive Interpreter"입니다[1]. CPython(python.org에서 배포하는 Python의 표준 구현)은 Python 소스 코드를 바이트코드라는 내부 명령어 목록으로 컴파일하고, CPython의 인터프리터가 이 바이트코드 명령어를 하나씩 읽어 실행합니다. PEP 659는 이 인터프리터를 특수화 적응형 인터프리터로 바꾸는 방식을 설명하며, 이 설계는 CPython 3.11에 적용됐습니다. 특수화 적응형 인터프리터는 명령어가 실행되면서 받은 입력의 타입과 값을 확인해 그 명령어를 그 경우 전용의 빠른 명령어로 교체하고, 예상과 다른 입력이 이어지면 그 교체를 되돌립니다. 이 인터프리터는 Python 언어, 라이브러리, API를 바꾸지 않습니다. PEP 659는 특수화 적응형 인터프리터가 실행 속도를 10~60% 높인다고 추정합니다. 다만 대부분의 애플리케이션에서 3.11은 3.10보다 메모리를 더 사용하는데, PEP 659는 그 차이가 크지 않다고 결론짓습니다.

## 동적 언어 Python을 빠르게 실행하는 데 필요한 것

Python은 동적 언어(변수에 타입을 선언하지 않고 값의 타입이 실행 중에 정해지는 언어)라서 a + b를 실행할 때 a와 b의 타입을 확인해야 정수 덧셈인지 문자열 연결인지 정할 수 있습니다. PEP 659는 동적 언어의 가상 머신이 빠르게 동작하려면 실행 중인 프로그램의 타입과 값에 맞춰 실행하는 코드를 특수화해야 한다고 설명합니다. 가상 머신은 바이트코드 같은 명령어를 실행하는 소프트웨어이고, CPython에서는 인터프리터가 이 일을 합니다. 특수화는 실행 중에 확인한 타입과 값에 맞춰 코드를 그 경우에만 맞는 형태로 바꾸는 일입니다. 예를 들어 a + b의 a와 b가 계속 정수라면 a + b를 정수 덧셈만 처리하는 코드로 바꾸는 것이 특수화입니다. 특수화는 흔히 JIT 컴파일러(Just-In-Time 컴파일러, 실행 도중 자주 실행되는 코드를 기계어로 번역하는 컴파일러)와 함께 이야기되지만, PEP 659는 기계어를 만들지 않아도 특수화가 성능을 높인다고 설명합니다.

PEP 659는 Python이 느린 언어로 널리 알려져 있다는 데서 출발합니다. PEP 659가 밝힌 목표는 Python이 C, Fortran, Java 같은 저수준 언어의 성능에는 이르지 못하더라도 JavaScript 엔진인 V8이나 Lua를 JIT 컴파일러로 실행하는 LuaJIT처럼 빠른 스크립트 언어 구현과는 겨룰 수 있게 하는 것입니다. 이 목표를 CPython에서 이루려는 것은 PyPy(JIT 컴파일러를 사용하는 Python의 다른 구현) 같은 다른 가상 머신을 사용할 수 없는 사용자를 포함해 모든 Python 사용자가 혜택을 받게 하기 위해서입니다. PEP 659는 목표까지 갈 길이 멀지만 인터프리터를 빠르게 하면 목표에 크게 다가갈 수 있다고 주장하고, 학계 연구와 실제 구현에서 빠른 인터프리터가 빠른 가상 머신의 핵심 요소로 확인됐다는 점을 근거로 듭니다.

가상 머신의 일반적인 최적화는 비용이 커서 최적화할 가치가 있다고 확신할 때까지 코드를 오래 실행하며 지켜보는 워밍업 시간이 필요합니다. PEP 659는 눈에 띄는 워밍업 없이 빨리 속도를 높이려면 함수가 몇 번만 실행돼도 특수화할 가치가 있다고 추측해야 한다고 설명합니다. 그리고 이렇게 일찍 추측하는 방식이 효과를 내려면 인터프리터가 코드를 최적화하는 일과 추측이 틀렸을 때 그 최적화를 되돌리는 일을 아주 적은 비용으로 계속할 수 있어야 한다고 덧붙입니다.

## 명령어 하나 단위로 특수화하는 이유

PEP 659는 동적 언어의 가상 머신을 빠르게 하는 여러 방법 중 특수화가 그 자체로도, 다른 최적화를 가능하게 한다는 점에서도 가장 중요하므로 CPython의 성능을 높이려면 특수화부터 해야 한다고 주장합니다. PEP 659가 그 근거로 든 것은 인터프리터에서 특수화만 해도 성능이 크게 오르고 단순한 컴파일러보다 빨라질 수도 있다는 연구[2]입니다.

학술 문헌에 나온 특수화 방법 대부분은 바이트코드 명령어 하나보다 큰 영역을 한꺼번에 최적화합니다[2], [3]. 최적화하는 영역이 명령어 하나보다 크면 영역 중간에서 예상이 틀렸을 때 최적화한 코드를 되돌리는 일(de-optimization)을 처리하는 코드가 따로 필요합니다. 반면 명령어 하나 단위로 특수화하면 de-optimization이 영역 중간에서 일어날 수 없으므로 되돌리는 일이 아주 간단해집니다. 그래서 PEP 659가 제안하는 인터프리터는 코드를 적극적으로 특수화하되 명령어 하나만큼의 작은 영역에서만 특수화하고, 특수화가 틀렸을 때 빠르고 적은 비용으로 바로잡습니다.

PEP 659는 문헌에서 자신과 가장 가까운 방법으로 "Inline Caching meets Quickening"[4]을 꼽습니다. PEP 659도 이 방법처럼 인라인 캐시(특수화에 필요한 정보를 명령어 바로 뒤에 붙여 저장하는 캐시)를 사용하고, 여기에 de-optimization을 빠르게 하는 기능을 추가했습니다. PEP 659는 이 기능 덕분에 특수화가 실패하거나 오래 유지되지 않는 경우에도 이 방법보다 성능이 안정적으로 유지된다고 설명합니다.

## 적응형 명령어와 특수화 명령어의 교체 과정

PEP 659의 인터프리터는 특수화하면 빨라질 명령어를 먼저 적응형 명령어(카운터로 실행 횟수를 관리하다가 스스로를 특수화하는 명령어)로 교체하고, 그 명령어가 충분히 여러 번 실행되면 다시 특수화 명령어(특정 타입과 값의 경우만 빠르게 처리하는 명령어)로 교체합니다. PEP 659는 이렇게 느린 명령어를 더 빠른 변형 명령어로 바꿔 가는 교체 과정 전체를 quickening이라고 부릅니다. PEP 659가 예로 든 특수화 대상은 함수 호출(`CALL`), 속성 읽기(`LOAD_ATTR`), 전역 변수 읽기(`LOAD_GLOBAL`), 덧셈(`BINARY_ADD`)처럼 고수준 연산을 나타내는 명령어입니다. 예를 들어 `LOAD_ATTR`는 quickening의 첫 단계에서 적응형 명령어인 `LOAD_ATTR_ADAPTIVE`로 교체됩니다.

PEP 659는 특수화 대상 명령어마다 family라는 명령어 묶음을 만듭니다. family 하나에는 적응형 명령어 하나와, 입력이 예상한 경우일 때 원래 명령어와 같은 일을 훨씬 빨리 하는 특수화 명령어가 하나 이상 들어 있습니다. 특수화 명령어 하나가 한 가지 경우만 처리하므로 family를 사용하면 특수화가 효과적이라고 PEP 659는 설명합니다.

적응형 명령어는 실행 횟수를 관리하는 카운터를 유지하고, 이 카운터가 0이 되면 받은 타입과 값을 확인해 스스로를 특수화하려고 시도합니다. 적응형 명령어를 대체한 특수화 명령어는 saturating counter(최댓값이나 최솟값에 도달하면 그 값에 머무는 카운터)를 유지하고, 입력이 예상과 같으면 카운터를 올립니다. 입력이 예상과 다르면 특수화 명령어는 카운터를 내리고 원래 명령어가 하던 일반 연산을 실행합니다. 카운터가 최솟값에 도달하면 인터프리터는 그 명령어의 opcode(연산 코드, 명령어가 어떤 연산인지 나타내는 번호)를 적응형 명령어의 opcode로 바꾸는 것만으로 특수화를 되돌립니다. 적응형 명령어는 주기적으로 스스로를 특수화하려고 시도하므로, 되돌아간 명령어도 프로그램이 값을 사용하는 패턴이 바뀌면 그 패턴에 맞는 특수화 명령어로 다시 교체될 수 있습니다.

## 명령어 형식과 인라인 캐시

quickening한 코드는 바꿀 수 없는 원래 바이트코드와 달리 실행 중에 바꿀 수 있습니다. 또 tracing(디버거나 커버리지 도구가 `sys.settrace` 같은 기능으로 코드가 한 줄씩 실행되는 것을 지켜보는 일)이 필요하면 인터프리터가 원래 바이트코드로 돌아가 실행하므로, quickening한 코드는 tracing을 직접 처리하지 않아도 됩니다. PEP 659는 tracing을 이렇게 지원하려면 quickening한 명령어가 사용자가 볼 수 있는 원래 바이트코드와 같은 형식을 유지해야 한다고 설명합니다. 그 형식은 8비트 opcode 뒤에 8비트 operand(피연산자)가 붙은 16비트 명령어입니다. operand는 명령어가 연산에 사용하는 값이고, CPython 바이트코드에서는 읽을 이름의 번호처럼 연산에 필요한 값을 가리킵니다.

특수화 명령어 family 대부분은 8비트 operand에 담을 수 있는 것보다 많은 정보가 필요합니다. 그래서 PEP 659의 인터프리터는 명령어 바로 뒤에 16비트 항목 여러 개를 붙여 이 정보를 저장합니다. PEP 659는 명령어가 있는 자리에 붙인 이 캐시를 인라인 캐시의 한 형태로 설명하고 inline data cache라고 부릅니다. 아직 특수화되지 않은 적응형 명령어는 인라인 캐시의 첫 항목을 실행 횟수를 관리하는 카운터로 사용하고 나머지 항목은 건너뜁니다.

CPython 3.11 alpha 버전에 들어간 PEP 659의 초기 구현은 quickening한 명령어를 원래 바이트코드와 같은 형식의 배열에, 특수화에 필요한 정보를 별도 배열에 저장하고 그 정보의 위치를 명령어 위치와 operand로 계산했습니다. PEP 659는 정보를 명령어 바로 뒤에 두는 인라인 캐시 방식이 더 빠르고 단순해서 초기 설계 대신 이 방식을 선택했다고 밝힙니다.

## 속성 읽기와 전역 변수 읽기의 특수화

`LOAD_ATTR`는 `obj.x`처럼 객체의 속성을 읽는 명령어로, 스택(가상 머신이 계산 중인 값을 쌓아 두는 곳) 맨 위의 객체에서 이름으로 지정한 속성을 읽고 그 객체 자리에 속성 값을 놓습니다. `LOAD_ATTR`가 읽는 속성은 일반 인스턴스의 속성일 수도 있고 클래스나 모듈의 속성일 수도 있으며, 그 밖에도 특수한 경우가 많아서 PEP 659는 `LOAD_ATTR`를 특수화하기 좋은 대상으로 꼽습니다. `LOAD_ATTR`는 처음에 `LOAD_ATTR_ADAPTIVE`로 quickening되고, `LOAD_ATTR_ADAPTIVE`는 실행 횟수를 세면서 충분히 실행되기 전까지는 원래 `LOAD_ATTR`의 동작으로 속성을 읽습니다. 충분히 실행되면 `LOAD_ATTR_ADAPTIVE`는 내부 함수 `_Py_Specialize_LoadAttr`를 호출해 속성의 종류를 확인하고, 맞는 특수화 명령어가 있으면 `LOAD_ATTR_ADAPTIVE`를 그 특수화 명령어로 교체합니다. PEP 659가 예로 든 `LOAD_ATTR`의 특수화 명령어는 다음 세 가지입니다.

- `LOAD_ATTR_INSTANCE_VALUE`: 속성이 객체의 값 배열(인스턴스 속성 값을 담는 배열)에 저장돼 있고 같은 이름의 디스크립터(property처럼 속성을 읽고 쓰는 동작을 클래스에서 직접 정의하는 객체)가 그 속성을 가리지 않는 흔한 경우를 처리합니다.
- `LOAD_ATTR_MODULE`: 모듈의 속성을 읽는 경우를 처리합니다.
- `LOAD_ATTR_SLOT`: 클래스가 `__slots__`(인스턴스가 가질 속성 이름을 미리 정해 두는 기능)를 정의한 객체의 속성을 읽는 경우를 처리합니다.

`LOAD_GLOBAL`은 함수 안에서 전역 변수나 내장 함수의 이름을 읽는 명령어로, 이름을 전역 네임스페이스에서 먼저 찾고 없으면 내장 네임스페이스(`len`, `print` 같은 내장 함수의 이름이 들어 있는 네임스페이스)에서 찾습니다. CPython 3.9의 `LOAD_GLOBAL`은 이미 캐시를 사용했고, 그 C 코드 하나에는 코드 객체(함수 하나의 바이트코드와 이름, 상수, 디버깅 정보를 담은 객체) 전체를 바꿔 캐시를 추가할지 확인하는 코드, 캐시에서 값을 찾는 코드, 캐시를 사용할 수 없을 때의 대체 코드가 모두 들어 있었습니다. 그래서 PEP 659는 3.9의 `LOAD_GLOBAL` 코드가 복잡하고 컸으며 최적화된 상태에서도 불필요한 연산을 많이 실행했다고 설명합니다. 반면 family를 사용하면 명령어 하나가 한 가지 경우만 처리하므로 코드를 유지보수하기 쉬워지고 실행도 빨라집니다. `LOAD_GLOBAL`의 family에는 다음 명령어가 들어갑니다.

- `LOAD_GLOBAL_ADAPTIVE`: `LOAD_ATTR_ADAPTIVE`와 같은 방식으로 동작하는 적응형 명령어입니다.
- `LOAD_GLOBAL_MODULE`: 값이 전역 네임스페이스에 있는 경우를 처리합니다. 네임스페이스의 키가 바뀌지 않았는지 확인한 뒤, 네임스페이스 안에서 값이 있는 위치로 저장해 둔 인덱스에서 값을 바로 읽습니다.
- `LOAD_GLOBAL_BUILTIN`: 값이 내장 네임스페이스에 있는 경우를 처리합니다. 전역 네임스페이스에 키가 추가되지 않았는지와 내장 네임스페이스가 바뀌지 않았는지를 확인합니다.

특수화 명령어 `LOAD_GLOBAL_BUILTIN`은 전역 네임스페이스의 값이 바뀌었는지는 확인하지 않고 키만 확인합니다. `LOAD_GLOBAL`은 전역 네임스페이스를 먼저 찾으므로, 전역 네임스페이스에 내장 함수와 같은 이름의 키가 새로 추가되면 내장 함수 대신 그 전역 변수를 읽어야 합니다.

PEP 659는 `LOAD_ATTR`와 `LOAD_GLOBAL`의 family를 비롯한 명령어의 전체 구현을 CPython 저장소에서 확인할 수 있다고 안내합니다. 적응형 명령어와 특수화 명령어는 `Python/ceval.c`에, 특수화를 수행하는 최적화 코드는 `Python/specialize.c`에 구현돼 있습니다[5].

## 속도 향상 10~60%와 그 원인

PEP 659는 특수화로 얻는 속도 향상을 10~60%로 추정합니다. 다만 많은 특수화가 다른 최적화에 의존하므로 특수화만으로 얻는 속도 향상은 정확히 측정하기 어렵다고 밝힙니다. Abstract 섹션에서도 PEP 659는 속도 향상 수치가 어떤 벤치마크를 사용하는지와 아직 하지 않은 개발 작업에 따라 크게 달라진다는 점을 들어 의미 있는 수치를 내기 어렵다고 덧붙입니다. 같은 섹션에서 PEP 659는 10~60%와 다른 수치를 제시하는데, 많은 실험 결과를 근거로 최대 50%까지 빨라질 것으로 추정합니다. 그리고 속도 향상이 25%에 그치더라도 도입할 가치가 있다고 주장합니다.

속도 향상의 대부분은 특수화에서 직접 나오고, 가장 크게 기여하는 것은 속성 읽기, 전역 변수 읽기, 함수 호출이 빨라진 것입니다. 속도 향상 중 작지만 쓸모 있는 일부는 quickening으로 가능해진 최적화에서 나오며, PEP 659가 든 예는 디스패치(인터프리터가 명령어 하나를 실행한 뒤 다음 명령어를 처리하는 코드로 넘어가는 과정) 개선입니다. 디스패치를 개선하는 방법의 예는 super-instruction(명령어 여러 개에 걸친 일을 명령어 하나로 처리하고 operand를 여러 개 받는 명령어)이고, quickening한 코드는 super-instruction을 사용할 수 있습니다.

## 기존 코드와의 호환성과 메모리 비용

PEP 659가 도입한 인터프리터는 Python 언어, 라이브러리, API를 바꾸지 않으므로, 사용자가 새 인터프리터를 알아챌 수 있는 방법은 실행 시간 측정, 디버깅 도구 사용, 메모리 사용량 측정뿐입니다. PEP 659는 보안에 미치는 영향도 없다고 밝힙니다.

캐시를 사용하는 방식이면 메모리를 얼마나 더 사용하는지가 당연한 걱정이고, PEP 659의 짧은 답은 "그리 많지 않다"입니다. 비교 대상인 CPython 3.10은 코드의 실행 횟수가 약 2,000번이 될 때까지 명령어당 2바이트를 사용했습니다. 실행 횟수가 약 2,000번에 도달하면 3.10은 opcache(3.10이 자주 실행된 코드에 붙이던 캐시)를 만들면서 명령어마다 1바이트를, 캐시를 사용하는 명령어(`LOAD_GLOBAL`, `LOAD_ATTR`)마다 32바이트를 추가로 할당했습니다. 아래 표는 PEP 659가 64비트 머신을 기준으로 3.10과 3.11의 명령어 하나당 메모리 사용량을 바이트 단위로 비교한 것입니다.

| 항목 | 3.10 cold | 3.10 hot | 3.11 |
|---|---|---|---|
| 특수화된(캐시를 사용하는) 명령어 비율 | 0% | 약 15% | 약 25% |
| code | 2 | 2 | 2 |
| opcache_map | 0 | 1 | 0 |
| opcache/data | 0 | 4.8 | 4 |
| 합계 | 2 | 7.8 | 6 |

표의 3.10 cold는 코드의 실행 횟수가 약 2,000번에 도달하기 전, 3.10 hot은 그 기준에 도달해 캐시를 만든 뒤의 값입니다. 3.10 hot의 opcache_map 1바이트는 명령어마다 추가로 할당한 1바이트이고, opcache/data 4.8바이트는 전체 명령어의 약 15%에 32바이트씩 할당한 양을 명령어 하나당 평균으로 계산한 값과 같습니다. 3.11은 cold와 hot을 나누지 않고 명령어당 6바이트로 계산돼 있습니다.

3.10의 명령어당 메모리는 캐시를 만든 코드에서만 2바이트에서 7.8바이트로 늘어나므로, 3.10 대비 3.11의 메모리 사용량은 3.10에서 캐시를 만들 만큼 자주 실행되는 코드가 얼마나 되는지에 따라 달라집니다. PEP 659에 따르면 그런 코드가 약 70%일 때 3.10과 3.11의 메모리 사용량이 같아집니다. 또한 PEP 659는 바이트코드가 코드 객체의 일부일 뿐이고, 코드 객체에는 이름, 상수, 상당한 양의 디버깅 정보도 들어 있다고 지적합니다. 그래서 코드 객체 전체로 보면 3.10과 3.11의 차이는 표의 비율보다 작을 수 있습니다. PEP 659는 함수 상당수가 거의 실행되지 않는 대부분의 애플리케이션에서 3.11이 3.10보다 메모리를 더 사용하지만 차이는 크지 않다고 결론짓습니다.

## PEP 659가 정하지 않은 것과 뒤로 미룬 JIT 컴파일

PEP 659는 특수화를 관리하는 구조만 설명하고 어떤 최적화를 적용할지는 정하지 않습니다. PEP 659는 개발이 진행되면서 특수화의 세부 사항이나 구현 전체가 바뀔 수 있다고도 밝힙니다.

PEP 659는 특수화 적응형 인터프리터와 인라인 캐시를 선택한 것이 CPython을 최적화하는 다른 여러 방법을 사실상 택하지 않은 것과 같다고 인정합니다. 다만 JIT 컴파일 같은 방법은 포기한 것이 아니라 뒤로 미뤘을 뿐이라고 강조합니다. 명령어 하나 단위로 추측하고 적응하는 특수화는 인터프리터를 빠르게 할 뿐 아니라, 앞으로 더 정교한 최적화에 사용할 프로파일링 정보(어떤 코드가 어떤 타입의 값으로 몇 번 실행됐는지 모은 정보)도 만듭니다.
