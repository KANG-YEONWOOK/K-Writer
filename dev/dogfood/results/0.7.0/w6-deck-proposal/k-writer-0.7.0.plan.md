# 설계

- 핵심 주제: 팀장과 팀원은 3분기 리뷰 지연의 수치와 추정 원인을 보고, PR을 올릴 때 리뷰어 2명을 자동 지정하고 변경 500줄을 넘는 PR은 나눠 올리는 방식을 12월 한 달 동안 결제 서비스 저장소에서 시범 운영할지 11월 25일(수)까지 결정한다.
- 전개 순서: 제안 요약 → 지금의 리뷰 방식과 3분기 리뷰 지연 → 리뷰 지연의 추정 원인 → 리뷰어 자동 지정과 큰 PR 나눠 올리기 → 시범 운영 계획과 휴가자 대응 → 시범 운영 승인 요청
- 구성: genre.md "목적별 구성"의 설득(제안, 지금 상황과 문제, 제안 내용, 근거, 비용과 위험, 결정할 일). 발표 제목은 H1 "코드 리뷰 방식 변경 제안"이고 슬라이드 6장은 H2로 쓴다.

## 단위 1. 제안 요약
- 형태: 제목과 슬라이드 "## 제안 요약", 부제 "### 리뷰어 2명 자동 지정과 500줄 넘는 PR 나눠 올리기", 목록
- 전할 내용: 코드 리뷰 방식 변경 제안은 리뷰어 2명 자동 지정과 500줄 넘는 PR 나눠 올리기를 12월 한 달 동안 결제 서비스 저장소에서 시범 운영하자는 제안이고, 11월 25일(수)까지 결정해야 한다.
- 전개: 제안 → 제안이 필요한 가장 큰 근거 → 시범 운영 기간과 대상 → 결정 기한

1. [제안] 코드 리뷰 방식 변경 제안은 PR을 올릴 때 리뷰어 2명을 자동으로 지정하고 변경 500줄을 넘는 PR은 나눠 올리도록 코드 리뷰 방식을 바꾸자는 제안이다. (중심 대상, 사실 9, 사실 11)
- [목록] 근거, 시범 운영, 결정 기한 세 항목
2. [근거] 3분기 PR의 32%는 첫 리뷰까지 24시간 넘게 걸렸다. (사실 3)
3. [계획] 시범 운영은 12월 1일부터 31일까지 결제 서비스 저장소에서 한다. (사실 13, 사실 14)
4. [결정] 이 제안은 11월 25일(수)까지 결정해야 한다. (사실 22)

## 단위 2. 지금의 리뷰 방식과 3분기 리뷰 지연
- 형태: 슬라이드 "## 리뷰어를 지정하지 않는 지금의 리뷰 방식", 부제 "### 3분기 PR 412건의 첫 리뷰까지 걸린 시간과 리뷰 없는 머지", 목록
- 전할 내용: 지금은 리뷰어를 지정하지 않고 팀원 누구나 리뷰하는데, 3분기 PR 412건 중 131건(32%)은 첫 리뷰까지 24시간 넘게 걸렸고 18건은 리뷰 없이 머지됐다.
- 전개: 지금의 리뷰 방식 → 24시간 넘게 걸린 PR → 48시간 넘게 걸린 PR → 리뷰 없이 머지된 PR

5. [배경] 지금은 PR을 올리면 팀 채널에 PR 링크를 올리고 리뷰어를 지정하지 않은 채 팀원 누구나 리뷰한다. (사실 1)
6. [근거] 3분기 PR 412건 중 131건(32%)은 첫 리뷰까지 24시간 넘게 걸렸다. (사실 2, 사실 3)
7. [근거] 3분기 PR 중 47건은 첫 리뷰까지 48시간 넘게 걸렸다. (사실 4)
8. [근거] 3분기 PR 중 18건은 리뷰를 받지 않고 머지됐다. (사실 5)

## 단위 3. 리뷰 지연의 추정 원인
- 형태: 슬라이드 "## 리뷰 지연의 추정 원인", 부제 "### 리뷰어 미지정과 변경 500줄 이상의 큰 PR", 목록
- 전할 내용: 리뷰가 늦어지는 원인은 리뷰어를 정하지 않아 팀원들이 리뷰를 서로 미루는 것과 변경 500줄 이상인 큰 PR이 특히 늦어지는 것으로 추정한다.
- 전개: 추정 원인 1 → 추정 원인 2 → 추정 원인 2를 보여 주는 수치

9. [원인] 누가 리뷰할지 정해져 있지 않아 팀원들이 리뷰를 서로 미루는 것으로 추정한다. (사실 6)
10. [원인] 변경 500줄 이상인 큰 PR은 리뷰가 특히 늦어지는 것으로 추정한다. (사실 7)
11. [근거] 첫 리뷰까지 24시간 넘게 걸린 PR 131건 중 74건은 변경이 500줄 이상이었다. (사실 8)

## 단위 4. 리뷰어 자동 지정과 큰 PR 나눠 올리기
- 형태: 슬라이드 "## 리뷰어 자동 지정과 큰 PR 나눠 올리기", 부제 "### 리뷰어를 정하는 기준과 나누지 못한 PR의 처리", 목록
- 전할 내용: PR을 올리면 코드 소유자 파일을 기준으로 주 단위 순번에 따라 리뷰어 2명을 자동 지정하고, 변경 500줄을 넘는 PR은 나눠 올리되 나누지 못하면 PR 설명에 이유를 적는다.
- 전개: 제안 1 → 제안 1의 리뷰어 지정 기준과 용어 설명 → 제안 2 → 제안 2의 예외

12. [제안] PR을 올리면 리뷰어 2명을 자동으로 지정한다. (사실 9)
13. [방법] 자동 지정할 리뷰어는 코드 소유자 파일(파일 경로마다 담당자를 적어 둔 파일)을 기준으로 주 단위 순번에 따라 정한다. (사실 10, 용어: 코드 소유자 파일)
14. [제안] 변경 500줄을 넘는 PR은 올리기 전에 나눠 올린다. (사실 11)
15. [조건] 500줄 넘는 PR을 나눌 수 없으면 PR 설명에 나누지 못한 이유를 적는다. (사실 12)

## 단위 5. 시범 운영 계획과 휴가자 대응
- 형태: 슬라이드 "## 시범 운영 계획", 부제 "### 12월 1일~31일 결제 서비스 저장소에서 한 달 운영", 목록
- 전할 내용: 12월 한 달 동안 결제 서비스 저장소에서 시범 운영하며 첫 리뷰까지 걸린 시간의 중앙값과 24시간 넘게 걸린 PR 비율을 3분기 값과 함께 확인하고, 휴가 중인 리뷰어는 수동으로 바꿔 지정한다.
- 전개: 기간과 대상 → 지표 1과 3분기 값 → 지표 2와 3분기 값 → 순번의 위험 → 시범 기간의 대응

16. [일정] 시범 운영은 12월 1일부터 31일까지 한 달 동안 결제 서비스 저장소에만 적용한다. (사실 13, 사실 14)
17. [방법] 시범 운영에서는 첫 리뷰까지 걸린 시간의 중앙값을 확인하고 3분기 값은 9.5시간이다. (사실 15)
18. [방법] 시범 운영에서는 첫 리뷰까지 24시간 넘게 걸린 PR 비율을 확인하고 3분기 값은 32%다. (사실 16)
19. [위험] 주 단위 순번에 따라 휴가 중인 팀원이 리뷰어로 지정될 수 있다. (사실 17)
20. [대응] 리뷰어 자동 지정이 아직 휴가 캘린더와 연동되지 않아 시범 기간에는 리뷰어를 수동으로 바꿔 지정한다. (사실 18, 사실 19)

## 단위 6. 시범 운영 승인 요청
- 형태: 슬라이드 "## 시범 운영 승인 요청", 부제 "### 11월 25일(수)까지 결정 필요", 목록
- 전할 내용: 시범 운영을 시작하려면 11월 25일(수)까지 팀장이 승인해야 하고, 인프라팀에 저장소 설정 변경 권한을 요청해 받기까지 하루가 걸린다.
- 전개: 결정 기한 → 필요한 승인 → 필요한 권한 → 권한을 받는 데 걸리는 시간

21. [결정] 이 제안은 11월 25일(수)까지 결정해야 한다. (사실 22)
22. [요청] 시범 운영에는 팀장 승인이 필요하다. (사실 20)
23. [요청] 시범 운영에는 저장소 설정 변경 권한이 필요하고 이 권한은 인프라팀에 요청한다. (사실 21)
24. [조건] 인프라팀에 요청한 저장소 설정 변경 권한을 받기까지 하루가 걸린다. (사실 21)

## 제외한 사실
- 사실 23. 메모 작성자(백엔드팀 정유나): 슬라이드의 내용이 아니고 발표자가 메모 작성자와 같은지 알 수 없다. 결과 보고에 적는다.
- 사실 8의 비율: 자료에 74건의 비율이 없으므로 새 비율을 계산해 쓰지 않는다.
- 사실 22의 2026년: 오늘 날짜와 비교하려고 적은 값이고 자료에 연도가 없으므로 슬라이드에 연도를 쓰지 않는다. 결정 기한이 지났다는 점은 결과 보고에 적는다.
- 단위 1과 단위 2, 4, 5의 겹치는 문장: 단위 1은 발표의 핵심을 한 장에 모은 슬라이드이고 뒤 슬라이드는 따로 넘겨 봐도 이해되어야 하므로 32%, 시범 운영 기간, 리뷰어 2명 자동 지정을 두 곳에 쓴다.
