# 설계

- 핵심 주제: 2026년 11월 7일 DB 커넥션 풀 설정 변경 때문에 checkout API가 52분 동안 느려지고 요청 일부가 실패한 장애가 어떻게 일어나 어떻게 끝났는지, 원인과 후속 조치가 무엇인지 알게 된다.
- 전개 순서: 장애 요약 → 경과 → 원인 → 후속 조치

## 단위 1. 장애 요약
- 형태: 제목과 첫 문단
- 전할 내용: 11월 7일 checkout API가 52분 동안 느려지고 요청 일부가 실패했으며, DB 커넥션 풀 설정 변경을 되돌린 뒤 장애가 끝났다.
- 전개: 무슨 일이 언제 있었는지 → 영향을 보여 주는 수치 → 원인과 끝난 방법

- [제목] 11월 7일 checkout API 응답 지연 장애 보고
1. [핵심] 2026년 11월 7일 14시 10분부터 15시 2분까지 52분 동안 checkout API의 응답이 느려지고 checkout 요청 일부가 실패했다. (사실: 장애 날짜, 장애 시간)
2. [결과] checkout 요청의 실패율은 평소 0.2%였는데 장애가 이어진 52분 동안은 3.8%였다. (사실: 장애 중 checkout 요청 실패율, 평소 checkout 요청 실패율)
3. [원인] 장애는 13시 50분에 배포된 DB 커넥션 풀 설정 변경 때문에 생겼고, 14시 58분에 이 설정을 되돌린 뒤 15시 2분에 끝났다. (사실: 설정 변경 배포 시각, 롤백 시각)

## 단위 2. 장애 경과
- 형태: 목록
- 전할 내용: 설정 변경 배포부터 응답 시간 회복까지 시각별로 무슨 일이 있었는지 알게 된다.
- 전개: 목록 소개 → 시각 순서대로 한 항목에 한 사건

4. [전환] 장애 경과를 시각 순서로 정리하면 다음과 같다. (사실: 장애 날짜)
- [목록] 13시 50분 설정 변경 배포, 14시 10분 응답 시간 상승과 알림, 14시 25분 원인 확인, 14시 58분 설정 되돌림, 15시 2분 응답 시간 회복
5. [단계] 13시 50분에 인스턴스 하나의 DB 커넥션 풀 최댓값을 50에서 200으로 올리는 설정 변경이 인스턴스 12대에 배포됐다. (사실: 설정 변경 배포 시각, 설정 변경이 적용된 인스턴스 수)
6. [단계] 14시 10분에 요청의 99%가 응답을 받는 시간인 checkout API의 p99 응답 시간이 180ms에서 2,400ms로 올랐다. (사실: 응답 시간이 오른 시각, p99의 백분위)
7. [단계] 같은 14시 10분에 알림이 발생했다. (사실: 알림 발생)
8. [단계] 14시 25분에 온콜 담당자 Mina Park 님이 DB 커넥션 수가 DB 커넥션 한도인 2,000개에 도달해 DB가 새 커넥션을 거부하고 있는 것을 확인했다. (사실: 원인 확인 시각, DB 커넥션 한도)
9. [단계] 14시 58분에 커넥션 풀 최댓값을 다시 50으로 되돌렸다. (사실: 롤백 시각)
10. [단계] 15시 2분에 checkout API의 p99 응답 시간이 190ms로 낮아졌다. (사실: 회복 시각, 회복 후 p99 응답 시간)

## 단위 3. 장애 원인
- 형태: 문단
- 전할 내용: 인스턴스 12대가 DB에 열 수 있는 커넥션이 모두 2,400개가 되어 DB 커넥션 한도 2,000개를 넘었고, 스테이징에서는 이 변경을 부하 테스트하지 않았다.
- 전개: 원인이 생기는 과정 → 원인 → 스테이징에서 걸러지지 않은 이유

11. [과정] 커넥션 풀 최댓값이 인스턴스마다 200으로 올라가면서 인스턴스 12대가 DB에 열 수 있는 커넥션은 모두 2,400개가 됐다. (사실: 변경 후 커넥션 풀 최댓값, 전체 커넥션 최댓값)
12. [원인] 이렇게 합친 커넥션 수 2,400개가 DB 커넥션 한도인 2,000개를 넘은 것이 장애의 원인이다. (사실: 전체 커넥션 최댓값, DB 커넥션 한도)
13. [이유] 스테이징은 인스턴스를 2대만 운영하기 때문에 이 설정 변경은 스테이징에서 부하 테스트를 거치지 않았다. (사실: 스테이징 부하 테스트, 스테이징 인스턴스 수)

## 단위 4. 후속 조치
- 형태: 문단
- 전할 내용: 전체 커넥션 최댓값을 배포할 때 검사하는 조치를 Jisoo Han 님이 11월 21일까지 추가하고, DB 커넥션 한도를 올릴지는 아직 정하지 않았으며 11월 14일에 논의한다.
- 전개: 결정한 조치 → 담당자와 기한 → 정하지 않은 일과 논의 날짜

14. [결정] 후속 조치로 커넥션 풀 최댓값에 인스턴스 수를 곱한 값이 DB 커넥션 한도의 80% 미만인지 배포할 때 확인하는 검사를 추가하기로 했다. (사실: 후속 조치 1, 배포 검사의 기준 비율)
15. [담당] 이 배포 검사는 Jisoo Han 님이 맡았고 기한은 11월 21일이다. (사실: 후속 조치 1 담당자, 후속 조치 1 기한)
16. [계획] DB 커넥션 한도를 올릴지는 아직 정하지 않았고 11월 14일에 논의할 예정이다. (사실: 후속 조치 2, 후속 조치 2 논의 날짜)

## 제외한 사실
- 배포와 롤백을 한 사람: 자료에 없어서 쓰지 않는다. 결과 보고의 "채워야 할 사실"에 적는다.
- 알림의 종류와 알림을 받은 사람: 자료에 없어서 쓰지 않는다.
- 설정 변경이 적용된 인스턴스가 어느 서비스의 인스턴스인지: 자료에 명시가 없어서 "인스턴스 12대"로만 쓴다.
