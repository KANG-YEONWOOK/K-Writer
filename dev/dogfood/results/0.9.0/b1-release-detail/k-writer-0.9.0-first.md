# K-Writer 0.5.0 write, brief 스킬 추가와 short 모드 삭제 요약

K-Writer 0.5.0은 글의 목적, 문체, 구성을 미리 정하지 않는 기본 스킬 write와 요약 스킬 brief를 추가했고 techblog의 short 모드는 삭제하고 짧은 글을 brief로 쓰기로 했습니다. write는 자료나 주제가 없으면 먼저 요청하고 목적(설명, 설득, 안내, 기록, 직접 입력), 분량, 어투 중 요청에 없는 값을 한 번에 묻고, brief는 분량(한 줄, 한 문단, 자세히)과 어투만 묻습니다. 두 스킬을 추가한 뒤 `python -m unittest discover -s tests`로 실행한 테스트 210개가 통과했습니다. `dev/sync_core.py --check`, `dev/borrow_thresholds.py --check`, `claude plugin validate .`도 통과했습니다. 다만 `claude plugin eval`과 dogfood는 실행하지 않았습니다. 새 eval 케이스 4개(`brief-note`, `brief-meeting-plain`, `write-notice-casual`, `write-report-plain`)는 작성만 했습니다. write와 brief로 쓴 글을 스킬 없이 쓴 글이나 사람이 쓴 글과 비교한 결과도 없습니다.

techblog의 short 모드를 삭제하면서 `short.md`, `short` 인자, `thresholds.json`의 short 설정도 함께 삭제했습니다. lint의 `--source`와 `--terms` 옵션, 원문 대조 항목 F1~F8, 테스트 파일 `tests/test_short_mode.py`도 삭제했습니다. `lint_ko.py`를 수정하기 전과 후에 예시 글, eval 글, 평가 기록의 글 34개 파일을 `--tone default`와 `--tone casual`로 검사해 출력 68개를 비교했습니다. 출력 68개에서 달라진 부분은 문구를 바꾼 G4.off_tone 항목의 "수정 방향" 한 줄뿐이었고 항목의 값과 판정은 모두 같았습니다. 감사를 맡은 subagent는 `revise_ko.py`의 `check`와 `audit`가 core의 `rules.json`에 있는 짧은 글 기준을 적용하지 않아 `lint_ko.py --short`와 판정이 다르다는 것을 찾았습니다. `lint_ko.py`를 통과한 요약이 수정하지 않은 상태로 `check`에서 FAIL로 판정됐고 `lint_ko.py`가 찾은 번역투 두 개를 `check`는 통과시켰습니다. 그래서 `check`와 `audit`에 이 짧은 글 기준을 적용하는 `--short`를 추가했고 판정이 달랐던 두 경우를 테스트로 남겼습니다.

core의 어투에는 해라체와 사용자가 직접 정한 어투를 추가했고, `lint_ko.py --tone`과 `tone_check.py --tone`은 해라체를 `plain`으로, 사용자가 직접 정한 어투를 `free`로 받습니다. 수정 후의 `lint_ko.py`를 `--tone auto`로 실행하면 해라체로 쓴 문서 7개를 `plain`으로 인식해 출력이 수정 전과 달라졌습니다. 기준 글 표본이 없으면 부정 대구나 번역투도 판정하지 못해서, write와 brief에는 기술 블로그 글에서 측정한 techblog의 기준치 중 특정 표현의 빈도를 세는 항목 15개를 가져왔습니다. 문장 길이, 문단, 목록 비중 같은 분포 항목의 기준치는 가져오지 않았습니다.

write와 brief는 스킬 문서를 작성하지 않은 subagent에게 스킬 문서만 주고 사용자 요청을 실행하게 하는 테스트 실행으로 확인했고, 1차 실행 뒤에 스킬 문서를 수정하고 2차 실행을 했습니다. brief는 1차와 2차에 같은 자료와 요청을 사용했고, 영어 엔지니어링 노트의 한 문단 요약은 590자에서 296자로, 걸린 시간은 27분에서 9분으로 줄었습니다. 회의록을 항목 형식으로 쓴 요약은 338자에서 189자로, 걸린 시간은 14분에서 3분으로 줄었습니다. 1차 실행에서 brief의 요약이 길어진 원인 하나는 기본 독자를 techblog처럼 "자료 분야의 지식이 없을 수 있는 사람"으로 정해 용어마다 설명이 붙은 것이었습니다. 그래서 brief의 기본 독자는 "자료가 대상으로 삼은 독자와 같은 수준의 사람"으로 바꿨습니다. 다른 원인은 독립 점검이 그 안의 독자 점검에서 나온 질문마다 요약에 설명을 추가한 것이고, 이 설명으로 469자였던 요약 하나가 630자가 됐습니다. brief의 독립 점검은 요약만 읽는 subagent가 읽다가 멈춘 부분을 보고하고 상위 agent가 분량 안에서 요약을 수정하는 방식으로 바꿨습니다.

write 2차 실행의 글에서 "저희"와 해라체 종결이 함께 쓰인 문장 6개는 어투 변환이 합니다체 초안의 종결부만 바꾸기 때문에 생겼습니다. genre.md, drafting.md, tone.md는 조직이 주어인 문장에 "우리 팀은"이나 조직의 이름을 쓰도록 수정했습니다. 다만 테스트 실행은 자료와 요청의 조합마다 한 번씩만 했고, 2차 실행 뒤에 수정한 "저희" 규칙은 다시 실행해 확인하지 않았습니다. 테스트 실행은 subagent 안에서 했고, AskUserQuestion으로 설정을 묻는 흐름과 대화에서 자료나 주제를 요청하는 흐름은 실행해 보지 못했습니다. 대화에서 자료를 요청하면 턴이 끝나는데, 이어진 턴에서 검사 스크립트 실행의 사전 허용이 유지되는지도 확인하지 못했습니다.
