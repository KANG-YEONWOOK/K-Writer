# 설계

- 핵심 주제: K-Writer를 이미 사용하는 사람은 0.5.0에서 write와 brief 스킬이 추가되고 techblog의 short 모드가 삭제되었으며 해라체와 직접 정한 어투를 사용할 수 있게 된 것, 기존 검사 결과는 그대로라는 것, 아직 확인하지 않은 부분을 알게 된다.
- 전개 순서: 0.5.0의 변경 요약 → write 스킬 → short 모드 삭제와 brief 스킬 → 새 어투 → 기존 lint 결과 → 검사 기준의 한계 → 확인하지 않은 부분

## 단위 1. 0.5.0의 변경 요약
- 형태: 제목과 첫 문단
- 전할 내용: 0.5.0에서 write와 brief 스킬이 추가되고 techblog의 short 모드가 삭제되었으며 어투 두 가지가 추가됐다.
- 전개: 추가와 삭제 → 새 어투 → 기존 판정과 남은 확인

- [제목] K-Writer 0.5.0의 write, brief 스킬 추가와 techblog short 모드 삭제
1. [핵심] K-Writer 0.5.0에서는 사용자가 정한 목적, 분량, 어투에 맞춰 글을 쓰는 write 스킬과 자료를 요약하는 brief 스킬이 추가됐고 techblog의 short 모드가 삭제됐다. (사실 0.5.0의 큰 변경, 용어: write, 용어: brief)
2. [핵심] 스킬이 공통으로 사용하는 어투 규칙(core)에도 해라체(Plain)와 사용자가 직접 정한 어투가 추가됐다. (사실 추가된 어투)
3. [핵심] 문체 검사 스크립트 `lint_ko.py`가 기존 글에 내리는 판정은 합니다체와 해요체 설정에서 0.5.0 이전과 같았다. (사실 기존 lint 결과 비교 결과, 용어: lint_ko.py)

## 단위 2. write 스킬
- 형태: 문단
- 전할 내용: write는 자료나 주제, 목적, 분량, 어투를 받아 글을 쓰는 기본 스킬이고 자료나 주제를 먼저 요청한 뒤 나머지 값을 한 번에 묻는다.
- 전개: 정의 → 다른 스킬과의 관계 → 질문 순서 → 목적의 선택지와 하는 일

4. [정의] write는 자료나 주제, 목적, 분량, 어투를 사용자에게 받은 뒤 그에 맞는 글을 쓰는 K-Writer의 기본 스킬이다. (용어: write, 사실 write가 받는 값, 사실 write의 성격)
6. [단계] write는 요청에 자료나 주제가 없으면 대화에서 먼저 요청하고 받지 못하면 글을 쓰기 시작하지 않는다. (사실 write의 질문 순서)
7. [단계] write는 자료나 주제를 받은 뒤 목적, 분량, 어투 중 요청에 없는 값을 한 번에 묻는다. (사실 write의 질문 순서)
8. [풀이] 목적은 설명, 설득, 안내, 기록, 직접 입력 중에서 선택하고 write는 선택한 목적에 따라 글의 독자와 구성을 정한다. (사실 write의 목적 선택지, 사실 write의 독자와 구성)

## 단위 3. short 모드 삭제와 brief 스킬
- 형태: 문단
- 전할 내용: techblog의 short 모드와 관련 인자와 옵션이 삭제됐고 짧은 글은 분량과 어투만 묻는 brief로 쓴다.
- 전개: 삭제한 것 → 대신 사용할 스킬 → brief의 정의 → brief가 묻는 값 → brief의 출력

9. [바뀐 일] techblog의 short 모드가 삭제되면서 `short` 인자가 없어졌고 `lint_ko.py`에서도 `--source`와 `--terms` 옵션, 원문 대조 항목 F1~F8이 삭제됐다. (사실 short 모드 삭제 대상)
10. [바뀐 일] 0.5.0부터 짧은 글은 short 모드 대신 brief로 쓴다. (사실 짧은 글의 대안)
11. [정의] brief는 사용자가 요약을 요청한 자료나 내용을 자연스러운 한국어로 요약하는 스킬이다. (용어: brief)
12. [단계] brief는 분량과 어투만 묻고 분량은 한 줄, 한 문단, 자세히 중에서 선택한다. (사실 brief가 묻는 값)
13. [결과] brief는 요약을 대화에 답하고 `-o`를 붙이면 요약을 파일에도 저장한다. (사실 brief의 출력)

## 단위 4. 새 어투
- 형태: 문단
- 전할 내용: Plain(해라체)과 사용자가 직접 정한 어투는 합니다체 초안의 종결부만 바꿔 만들고 검사 스크립트의 `--tone`에 `plain`과 `free`를 지정할 수 있다.
- 전개: 두 어투의 정의 → 만드는 방법 → 스크립트 옵션

14. [정의] 해라체는 문장을 "~다"로 끝내는 어투이고 사용자가 직접 정한 어투는 사용자가 요청에 적은 대로 문장을 끝내는 어투다. (용어: Plain, 용어: user-defined tone)
15. [과정] 어느 어투로 요청하든 스킬은 합니다체 초안의 종결부만 바꿔 그 어투의 글을 만든다. (사실 어투를 만드는 방법)
16. [방법] `lint_ko.py`와 어투 검사 스크립트 `tone_check.py`의 `--tone` 옵션에는 `plain`과 `free`를 지정할 수 있다. (사실 어투 옵션 값, 용어: tone_check.py)

## 단위 5. 기존 lint 결과
- 형태: 문단
- 전할 내용: 기존 글의 lint 값과 판정은 수정 전과 같고 `--tone auto`의 출력만 해라체 문서에서 달라졌다.
- 전개: 비교한 대상과 조건 → 결과 → 예외

17. [근거] 0.5.0을 만들면서 예시 글, eval 글, 평가 기록의 글 34개 파일에 수정 전후의 lint를 `--tone default`와 `--tone casual`로 실행해 출력 68개를 비교했다. (사실 기존 lint 결과 비교 대상)
18. [결과] 출력 68개에서 달라진 부분은 문구를 수정한 G4.off_tone 항목의 수정 방향 한 줄뿐이었고 항목의 값과 판정은 모두 수정 전과 같았다. (사실 기존 lint 결과 비교 결과)
19. [조건] `--tone auto`로 실행하면 lint가 해라체로 쓴 문서 7개를 `plain`으로 인식해서 출력이 수정 전과 달라졌다. (사실 `--tone auto`의 변화)

## 단위 6. 검사 기준의 한계
- 형태: 문단
- 전할 내용: write와 brief의 검사 기준치 일부는 techblog에서 가져온 값이고 lint는 해라체 글의 반말 종결을 찾지 못한다.
- 전개: 표본이 없는 이유와 가져온 기준치 → lint가 찾지 못하는 종결

20. [한계] write와 brief는 문체의 기준으로 삼을 사람 글 표본이 없어서 특정 표현의 빈도를 세는 항목 15개의 기준치를 techblog에서 가져왔다. (사실 가져온 기준치)
22. [한계] lint는 해라체 글에 섞인 합니다체와 해요체 종결은 찾지만 반말 종결은 명사로 분류해서 찾지 못한다. (사실 lint가 못 찾는 것)

## 단위 7. 확인하지 않은 부분
- 형태: 문단
- 전할 내용: 0.5.0은 `claude plugin eval`을 실행하지 않았고 설정과 자료를 묻는 대화 흐름을 실행해 보지 못했다.
- 전개: 실행하지 않은 평가 → 실행해 보지 못한 흐름

23. [한계] 0.5.0에서는 `claude plugin eval`을 실행하지 않았고 새 eval 케이스 4개는 작성만 했다. (사실 실행하지 않은 평가)
25. [한계] 설정값을 사용자에게 묻는 흐름과 대화에서 자료나 주제를 요청하는 흐름은 아직 실행해 보지 못했다. (사실 확인하지 못한 흐름)

## 제외한 사실
- 첫 문단에서 한계를 미리 말하는 문장: 단위 6, 7과 같은 내용을 반복하고 분량 상한(1,200자)을 넘게 해서 삭제했다.
- write가 아닌 다른 스킬이 목적, 문체, 구성을 미리 정해 둔 스킬이라는 설명: 분량 안에서 핵심 요소 3차에서 제외했다.
- 짧은 글 기준을 core의 `rules.json`으로 옮긴 일: 사용자가 사용하는 기능의 동작이 바뀌지 않는 내부 구조 변경이다.
- `thresholds.json`의 `allow_patterns` 등 설정: 검사 설정의 내부 구조다.
- settings-protocol.md의 "반드시 받는 값": write의 질문 순서(문장 6)로 전했다.
- 정규식 두 개를 맞춘 일, README 점검, 단위 테스트 210개, `tone_check.py` 비교 결과: lint 비교 결과와 같은 결론을 덧붙이는 개발 과정이다.
- 테스트 실행의 1차, 2차 결과와 소요 시간: 개발 중 문서를 수정한 경과다.
- "저희" 규칙: 문서 규칙의 세부 수정이다.
- write가 본문 1,500자를 기준으로 독립 점검의 범위를 나누는 일: 사용자가 정하는 값이 아닌 점검 절차의 세부다.
- `short.md`, `thresholds.json`의 short 설정, `tests/test_short_mode.py`: short 모드를 사용하던 사람이 직접 지정하던 인자와 옵션이 아닌 내부 파일이다.
- 테스트 실행 횟수와 2차 실행 뒤 재확인하지 않은 수정, 사전 허용 유지 여부, 구성과 분량 범위와 Plain 종결 분포를 측정하지 않은 일: 분량 안에서 핵심 요소 1차 목록에서 제외했다.
