source.md, 원래 article.md, 수정본 전체를 읽고 판단한다. 수정본이 둘 이상이면 어느 버전이 썼는지 모르는 상태로 같은 기준을 적용한다. 낱말이 일치하는지가 아니라, 서술어가 자료가 밝힌 일을 그 주어, 목적어와 사람이 쓴 한국어 글에서 함께 쓰는 말로 나타내는지를 본다.

## 심은 문장

article.md에는 서술어가 주어나 목적어와 어울리지 않거나 무슨 일인지 여러 가지로 읽히는 문장 15개를 심었다. 묶음 1은 사용자가 지적한 형태, 2는 skill 문서의 사례 표와 같은 짝이지만 다른 문장, 3은 어느 skill 문서에도 없는 짝(held-out), 4는 자료를 확인해야 고칠 방향이 정해지는 문장이다.

| 번호 | 묶음 | 초안 문장 | 자료가 밝힌 일 | 맞게 고친 예 | 틀리게 고친 예 |
|---|---|---|---|---|---|
| S1 | 1 | Redis로 옮긴 뒤 새로운 문제가 열렸습니다. | 옮긴 뒤 새 문제가 생겼다 | 새로운 문제가 발생했습니다, 생겼습니다 | 공개됐습니다 |
| S2 | 1 | 이 stale read 문제는 2.3 버전에서 닫혔습니다. | 2.3에서 고쳤다(fixed) | 2.3 버전에서 해결됐습니다, 2.3 버전에서 고쳤습니다 | |
| S3 | 2 | 세션 데이터는 이제 Redis에 삽니다. | Redis에 저장된다(lives in) | Redis에 저장됩니다, Redis에 있습니다 | |
| S4 | 2 | 플랫폼 팀이 Redis 클러스터를 소유하고, 애플리케이션 팀이 세션 코드를 소유합니다. | 맡는다(owns) | 담당하고, 맡고 | |
| S5 | 2 | 팀은 2.3 버전을 3월에 출하했습니다. | 배포했다(shipped) | 배포했습니다, 출시했습니다 | |
| S6 | 2 | 직렬화는 요청마다 약 0.4 ms의 오버헤드를 도입합니다. | 0.4 ms가 더 든다 | 오버헤드가 생깁니다, 0.4 ms가 더 걸립니다 | |
| S7 | 2 | 애플리케이션 서버는 응답 시간의 40%를 JSON 직렬화에 보냈습니다. | 직렬화가 응답 시간의 40%(spend) | JSON 직렬화가 응답 시간의 40%를 차지했습니다 | 40%가 걸렸습니다(걸리다는 기간을 받는다) |
| S8 | 2 | 쓰기가 많은 tenant에서도 효과가 있는지는 열린 질문으로 남아 있습니다. | 아직 측정하지 않았다 | 아직 측정하지 않았습니다, 아직 확인되지 않았습니다 | 효과가 없습니다 |
| S9 | 3 | 전용 큐는 리전 간 failover도 잠금 해제했습니다. | failover를 할 수 있게 됐다(unlocked) | 전용 큐로 리전 간 failover도 할 수 있게 됐습니다 | |
| S10 | 3 | 프로파일링은 응답 시간이 어디에 쓰이는지에 빛을 비췄습니다. | 어디에 쓰이는지 보여 줬다(shed light) | 프로파일링으로 응답 시간이 어디에 쓰이는지 확인했습니다 | |
| S11 | 3 | 실패한 요청은 다시 보내기 전까지 재시도 큐에 최대 2초 동안 앉아 있습니다. | 최대 2초 기다린다(sit) | 재시도 큐에서 최대 2초 동안 기다립니다, 대기합니다 | |
| S12 | 3 | TTL을 늘리면 오래된 세션을 읽는다는 비용을 지불하고 cache miss 비율을 낮춥니다. | miss 비율이 낮아지는 대신 더 오래된 세션을 읽는다(buy at the cost of) | TTL을 늘리면 cache miss 비율은 낮아지지만 더 오래된 세션을 읽게 됩니다 | |
| S13 | 4 | 이 중복 warm-up 요청 문제도 3월에 닫혔습니다. | 고치지 않기로 하고 이슈를 닫았다(won't fix, 추가 부하가 최대 트래픽의 1% 미만) | 3월에 고치지 않기로 했습니다, 고치지 않기로 하고 이슈를 닫았습니다 | 해결됐습니다, 수정됐습니다 |
| S14 | 4 | 2.3 버전은 서울 리전과 도쿄 리전의 p99 지연 격차를 닫았습니다. | 12%에서 3%로 줄었다 | 12%에서 3%로 줄었습니다, 좁혔습니다 | 없앴습니다, 없어졌습니다 |
| S15 | 4 | 5월에는 캐시 통계 API도 열렸습니다. | 외부 개발자에게 공개됐다 | 외부 개발자에게 공개됐습니다 | 시작됐습니다, 서버가 열렸습니다 |

판정: 서술어가 자료의 일과 같고 그 주어, 목적어와 자연스럽게 쓰였으면 FIXED, 고쳤지만 일이 자료와 다르면 WRONG, 그대로 두었으면 MISS로 적는다. 문장을 나누거나 합쳤으면 그 내용을 담은 문장으로 판정한다.

## 대조 문장

아래 문장은 그대로 두어야 한다. 서술어와 그 주어, 목적어가 같으면 KEPT로 본다. 용어 설명을 덧붙인 것은 KEPT다.

| 번호 | 문장 | 그대로 두는 이유 |
|---|---|---|
| C1 | 각 서버는 요청을 처리한 뒤 Redis 연결(connection)을 닫지 않고 connection pool에 돌려줍니다. | 실제로 닫는 대상 |
| C2 | 서버는 사용자가 로그인할 때마다 세션 토큰을 새로 만듭니다. | 구체적인 대상의 만들다 |
| C3 | 운영자는 설정 파일을 열어 세션 TTL 값을 바꿉니다. | 실제로 여는 대상 |
| C4 | 2.3 배포 직후에는 새 오류가 생겼습니다. | 생기다(발생하다로 바꿀 이유가 없다) |
| C5 | 옮기는 기간에는 장애 대응 회의가 매주 화요일에 열렸습니다. | 굳은 말 |
| C6 | 세션 TTL을 120초에서 30초로 줄인 설정은 stale read 비율을 0.8%에서 0.1%로 낮췄습니다. | style-guide.md가 권하는 문형 |
| C7 | 리전 간 복제 방식은 아직 풀리지 않은 문제로 남아 있습니다. | 굳은 말(문제가 남다) |
| C8 | 팀은 TTL을 다시 늘릴 가능성을 열어 두었습니다. | 굳은 말 |

## 과교정과 사실

- 줄다, 늘다, 만들다, 생기다를 다른 말로 바꾼 곳, 생기다와 발생하다를 서로 바꾼 곳을 모두 적는다.
- 같은 일을 가리키는 서술어가 글 안에서 서로 다르게 바뀐 곳을 적는다.
- 해결 여부(S2, S13), 정도(S14), 공개 대상(S15), 추정 강도, 수치가 자료와 달라진 곳을 적는다.
- 심은 문장과 대조 문장 밖에서 서술어를 바꾼 문장을 모두 적고, 바꾼 이유가 korean-review.md의 유형에 맞는지 적는다.
- 수정본에 `lint_ko.py --tone default`를 실행할 수 있으면 Gate, FAIL 수와 남은 A6.open_close, A6.open_close_check 줄을 적는다.

## 보고

수정본마다 묶음별 FIXED, WRONG, MISS 수, 대조 문장의 KEPT 수, 과교정과 사실 항목을 표로 적는다. 근거로 수정 전후 문장을 그대로 인용한다. lint의 Gate 0이나 CHECK 수만으로 통과시키지 않는다.
