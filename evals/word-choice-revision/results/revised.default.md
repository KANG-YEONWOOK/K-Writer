# 세션 캐시를 Redis로 옮긴 뒤의 변화

## 세션을 서버 메모리에 저장할 때의 문제

1월까지는 애플리케이션 서버마다 사용자 세션을 자기 메모리에 저장했습니다. 사용자의 다음 요청이 다른 서버로 가면 그 서버에는 세션이 없어서 사용자가 로그아웃됐습니다. 2월에 팀은 세션 캐시를 모든 서버가 함께 사용하는 Redis 클러스터로 옮겼습니다. 세션 데이터는 이제 Redis에 저장돼 있습니다. 모든 서버는 네트워크로 Redis에서 세션을 읽습니다.

플랫폼 팀은 Redis 클러스터를, 애플리케이션 팀은 세션 코드를 담당합니다.

각 서버는 요청을 처리한 뒤 Redis 연결(connection)을 닫지 않고 connection pool에 돌려줍니다. 서버는 사용자가 로그인할 때마다 세션 토큰을 새로 만듭니다. 운영자는 설정 파일을 열어 세션 TTL 값을 바꿉니다.

## 옮긴 뒤에 생긴 문제

세션 캐시를 Redis로 옮긴 뒤 새로운 문제가 생겼습니다. 서울 리전과 도쿄 리전 사이의 무효화 메시지가 최대 4초 늦게 도착해서, 도쿄의 사용자가 예전 세션을 읽는 경우가 있었습니다. 이 stale read 문제(이슈 #4182)는 2.3 버전에서 해결됐습니다. 2.3 버전은 무효화 메시지를 전용 큐로 보냅니다. 전용 큐는 리전 간 failover도 가능하게 했습니다. 팀은 2.3 버전을 3월에 배포했습니다.

2.3 배포 직후에는 새 오류가 생겼습니다. 큐 worker 수가 늘어날 때까지 5분 동안 요청의 약 2%가 HTTP 503을 받았습니다.

세션 캐시를 Redis로 옮기는 기간에는 장애 리뷰 회의가 매주 화요일에 열렸습니다.

서버가 시작할 때 warm-up 요청이 중복으로 나가는 문제도 보고됐습니다(이슈 #4377). 팀은 3월에 이슈 #4377을 고치지 않기로 하고 닫았습니다. 중복 warm-up 요청으로 생긴 추가 부하가 최대 트래픽의 1% 미만이었기 때문입니다.

## 직렬화와 재시도에 드는 시간

직렬화 때문에 요청마다 약 0.4 ms의 오버헤드가 생깁니다. 프로파일링으로 응답 시간이 어디에 쓰이는지 드러났습니다. 애플리케이션 서버는 응답 시간의 40%를 JSON 직렬화에 썼습니다. 직렬화 시간의 대부분은 세션 데이터를 JSON으로 바꾸는 세션 encoder가 차지했습니다. 실패한 요청은 다시 보내기 전까지 재시도 큐에서 최대 2초 동안 대기합니다.

## 결과

2.3 버전을 배포한 뒤 서울 리전과 도쿄 리전의 p99 지연 격차는 12%에서 3%로 줄었습니다. 세션 TTL을 120초에서 30초로 줄인 설정은 stale read 비율을 0.8%에서 0.1%로 낮췄습니다. TTL을 늘리면 cache miss 비율은 낮아지지만 서버가 더 오래된 세션을 읽습니다. 5월에는 캐시 통계 API가 외부 개발자에게 공개됐습니다.

## 마치며

쓰기가 많은 tenant에서도 효과가 있는지는 아직 확인되지 않았습니다. 팀이 쓰기가 많은 tenant를 측정하지 않았기 때문입니다. 리전 간 복제 방식은 아직 풀리지 않은 문제로 남아 있습니다. 팀은 TTL을 다시 늘릴 가능성을 열어 두었습니다.
