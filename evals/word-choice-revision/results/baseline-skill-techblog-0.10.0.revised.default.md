# 세션 캐시를 Redis로 옮긴 뒤의 변화

## 세션을 서버 메모리에 저장할 때의 문제

1월까지는 애플리케이션 서버마다 사용자 세션을 자기 메모리에 저장했습니다. 사용자의 다음 요청이 다른 서버로 가면 그 서버에는 세션이 없어서 사용자가 로그아웃됐습니다. 2월에 팀은 세션 캐시를 모든 서버가 함께 사용하는 Redis 클러스터로 옮겼습니다. 이제 세션 데이터는 Redis에 저장됩니다. 모든 서버는 네트워크로 Redis에서 세션을 읽습니다.

Redis 클러스터는 플랫폼 팀이, 세션 코드는 애플리케이션 팀이 담당합니다.

각 서버는 요청을 처리한 뒤 Redis 연결(connection)을 닫지 않고 connection pool에 돌려줍니다. 서버는 사용자가 로그인할 때마다 세션 토큰을 새로 만듭니다. 운영자는 설정 파일을 열어 세션 TTL 값을 바꿉니다.

## 옮긴 뒤에 생긴 문제

세션 캐시를 Redis로 옮긴 뒤에는 새 문제가 생겼습니다. 서울 리전과 도쿄 리전 사이의 무효화 메시지가 최대 4초 늦게 도착해서, 도쿄의 사용자가 예전 세션을 읽는 경우가 있었습니다. 이 stale read 문제는 팀이 3월에 배포한 2.3 버전에서 해결됐습니다. 2.3 버전은 무효화 메시지를 전용 큐로 보냅니다. 전용 큐 덕분에 리전 간 failover도 가능해졌습니다.

2.3 배포 직후에는 새 오류가 생겼습니다. 큐 worker 수가 늘어날 때까지 5분 동안 요청의 약 2%가 HTTP 503을 받았습니다.

세션 캐시를 Redis로 옮기는 동안 팀은 매주 화요일에 incident review 회의를 열었습니다.

서버가 시작할 때 warm-up 요청이 중복으로 나가는 문제도 보고됐습니다(이슈 #4377). 중복 요청으로 늘어난 부하가 피크 트래픽의 1% 미만이라서 팀은 3월에 이슈 #4377을 고치지 않기로(won't fix) 하고 닫았습니다.

## 직렬화와 재시도에 드는 시간

직렬화는 요청마다 약 0.4 ms의 오버헤드를 더합니다. 프로파일링 결과 응답 시간이 어디에 쓰이는지 드러났습니다. 애플리케이션 서버의 응답 시간 가운데 40%는 JSON 직렬화에 걸린 시간이었습니다. 직렬화 시간의 대부분은 세션 encoder가 차지했습니다. 실패한 요청은 재시도 큐에서 최대 2초 동안 기다린 뒤 다시 전송됩니다.

## 결과

2.3 버전을 배포한 뒤 서울 리전과 도쿄 리전의 p99 지연 격차는 12%에서 3%로 줄었습니다. 세션 TTL을 120초에서 30초로 줄인 설정은 stale read 비율을 0.8%에서 0.1%로 낮췄습니다. 세션 TTL을 늘리면 cache miss 비율이 낮아지는 대신 서버가 더 오래된 세션으로 응답합니다. 5월에는 캐시 통계 API가 외부 개발자에게 공개됐습니다.

## 마치며

세션 캐시를 Redis로 옮긴 효과가 쓰기가 많은 tenant에서도 나타나는지는 아직 확인하지 못했습니다. 팀은 이런 tenant를 측정하지 않았습니다. 리전 간 복제 방식도 아직 정하지 못했습니다. 팀은 TTL을 다시 늘릴 가능성을 열어 두었습니다.
