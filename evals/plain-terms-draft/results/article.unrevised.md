# 노트북 약 4,000대의 동기화 에이전트를 Python에서 Rust로 옮기는 방법

회사 노트북 약 4,000대에는 동기화 에이전트(sync agent)가 설치돼 있습니다. 동기화 에이전트는 노트북에서 파일 변경을 감지하고 동기화를 실행하는 프로그램입니다. 동기화는 여러 곳에 있는 데이터를 같은 상태로 맞추는 일입니다.

Python과 Rust는 프로그램을 작성하는 언어이고, 이 글에서 Python 버전과 Rust 버전은 각 언어로 작성한 동기화 에이전트를 의미합니다.

Python 버전은 2023년부터 운영 환경(실제 사용자가 사용하는 환경)에서 실행되고 있습니다. Python 버전은 아무 작업도 하지 않고 대기하는 유휴 상태에서 메모리를 210 MB 사용했고 시작하는 데 1.9초가 걸렸습니다. 담당 팀은 이 두 값 때문에 3월에 Rust 버전을 만들기 시작했습니다.

이 글의 자료는 사내 노트 "Internal note: moving the sync agent from Python to Rust"입니다. 이 노트는 글쓰기 평가용으로 작성한 가상의 자료이므로 실제 결과로 인용하면 안 됩니다. 이 글에서는 동기화 에이전트의 두 버전을 함께 배포한 방법과 Rust 버전의 측정 결과를 정리합니다.

## 마이그레이션 기간에 두 버전을 함께 배포한 방법

동기화 에이전트의 마이그레이션은 Python 버전을 사용하던 노트북을 Rust 버전으로 옮기는 작업입니다. 담당 팀은 마이그레이션이 끝날 때까지 Python 버전과 Rust 버전을 모두 담당합니다.

6주 동안은 설치 프로그램에 두 버전을 모두 넣어 배포했습니다. 1.8 버전은 Python으로 작성한 마지막 버전이고 2.0 버전은 Rust로 작성한 첫 버전입니다.

Python 버전과 Rust 버전은 같은 설정 파일(프로그램이 읽는 설정값을 저장한 파일)을 읽습니다. 그래서 노트북은 설정을 잃지 않고 Rust 버전으로 옮겨 갔다가 Python 버전으로 돌아올 수 있었습니다.

Rust 버전은 시작할 때 레지스트리에서 설치된 버전 번호를 읽습니다. 레지스트리는 Windows와 Windows에서 실행되는 프로그램에 필요한 데이터를 모아 저장하는 데이터베이스입니다. 설치된 버전이 1.6보다 오래됐으면 Rust 버전은 실행을 거부합니다.

바이너리는 소스 코드를 컴퓨터가 바로 실행할 수 있는 형태로 변환한 프로그램 파일입니다. 설치 프로그램은 이전 바이너리의 복사본을 새 바이너리 옆에 남겨 둡니다.

덕분에 이전 버전으로 되돌리는 데 40초가 걸리고 다운로드는 필요하지 않습니다. 다운로드 없이 되돌리므로 네트워크에 연결되지 않은 노트북도 이전 버전으로 돌아갈 수 있습니다.

최신 버전은 항상 업데이트 서버(프로그램의 새 버전을 제공하는 서버)에 공개됩니다.

패치 버전(버그 수정 같은 작은 변경을 담은 버전)은 버전 번호의 세 번째 숫자만 바꿉니다. 2.0.3이 패치 버전의 예입니다.

## 첫 Rust 빌드에서 실패한 테스트 31개

동기화 에이전트의 테스트 스위트(프로그램이 예상대로 동작하는지 자동으로 확인하는 테스트 모음)에는 테스트가 1,240개 있습니다.

빌드는 소스 코드를 실행할 수 있는 프로그램으로 변환한 결과물입니다. 첫 Rust 빌드에서는 테스트 1,240개 중 31개가 실패했습니다.

실패한 테스트 31개 중 9개는 Python 버전에서도 실패했으므로 회귀 버그(regression)가 아니었습니다. 회귀 버그는 전에 정상으로 동작하던 기능이 새 변경 때문에 동작하지 않게 된 버그입니다. 나머지 22개는 실제 버그였습니다.

Python 버전의 결과와 비교하지 않았다면 실제 버그를 22개가 아닌 31개로 셌을 수 있습니다. 실패한 테스트 중 실제 버그로 분류한 22개는 전체 테스트 1,240개의 약 1.8%입니다.

가장 심각한 버그는 file watcher(파일과 폴더의 변경을 감지하는 구성 요소)에서 발생했습니다. 사용자가 폴더 이름을 바꾸면 Rust 버전은 그 뒤 폴더 안에서 생긴 변경을 하나도 감지하지 못했습니다.

이 버그는 2.0.3 버전에서 수정됐고 지금은 테스트 스위트가 폴더 이름을 바꿀 때 실행되는 코드 경로를 커버합니다. 테스트가 어떤 코드 경로를 커버한다는 것은 테스트가 그 상황의 코드를 실행해 결과를 확인한다는 의미입니다.

네트워크 드라이브(다른 컴퓨터나 서버의 저장 공간을 내 컴퓨터의 드라이브처럼 연결한 것)는 테스트 스위트가 아직 커버하지 않습니다.

## 동기화 에이전트의 락, update checker, worker, 큐

락(lock)은 한 프로그램이 파일 같은 자원을 사용하는 동안 다른 프로그램이 동시에 변경하지 못하게 막는 장치입니다. 동기화가 실행되는 동안 동기화 에이전트는 데이터베이스 파일의 락을 보유합니다.

update checker는 최신 버전을 확인하는 구성 요소입니다. HTTP는 웹에서 서버와 데이터를 주고받는 규칙이고 응답 헤더는 서버가 응답 본문과 함께 보내는 부가 정보입니다.

update checker는 HTTP 응답 헤더를 읽고 로컬 캐시(노트북에 저장해 둔 임시 복사본)를 갱신한 뒤 최신 버전 문자열을 반환합니다. 버전 문자열은 버전을 나타내는 글자와 숫자의 나열입니다.

worker는 프로그램 안에서 일을 나눠 처리하는 실행 단위입니다. worker마다 동시에 열어 둘 수 있는 파일은 최대 8개이고 이 상한은 넘을 수 없습니다.

큐(queue)는 처리할 항목을 들어온 순서대로 쌓아 두는 자료 구조입니다. 크래시(프로그램이 오류로 갑자기 종료되는 일) 뒤에는 큐에 남은 항목을 순서대로 다시 처리합니다.

## 설계 문서에서 락 설명을 삭제하고 단어의 의미를 정리한 과정

설계 문서는 프로그램의 구조와 동작 방식을 설명한 문서입니다.

동기화 에이전트 설계 문서의 첫 초안은 락의 동작 방식을 잘못 설명했습니다. 그래서 설계 문서의 두 번째 버전에서는 그 절을 삭제했습니다.

커밋은 Git(코드와 문서의 변경 이력을 관리하는 도구)의 변경 이력에 기록된 한 시점의 상태이고, HEAD 커밋은 현재 작업의 기준이 되는 커밋입니다. 리뷰어(문서나 코드를 검토하는 사람)들은 설계 문서의 현재 버전을 HEAD 커밋에 있는 버전과 비교했습니다.

설계 문서의 초안에서는 "sync"와 "commit" 같은 단어가 두 가지 의미로 사용됐습니다. 그래서 문서 작성자들은 단어마다 의미를 하나만 남기고 모든 용어에 짧은 정의를 붙였습니다.

문서 작성자들은 단어의 의미를 점검하는 이 작업을 절마다 반복했고 부록은 제외했습니다. 부록은 점검하지 않았으므로 부록에는 두 가지 의미로 사용한 단어가 남아 있을 수 있습니다.

## 파일 감시 라이브러리를 비교한 Lee et al.(2024)의 벤치마크

라이브러리는 다른 프로그램이 가져다 사용하는 코드 묶음이고 벤치마크는 같은 기준으로 성능이나 기능을 측정해 비교하는 시험입니다. 담당 팀은 파일 변경을 감지하는 라이브러리를 비교하려고 Lee et al.(2024)의 벤치마크를 사용했습니다. Lee et al.(2024)은 Lee를 포함한 저자들이 2024년에 발표한 논문입니다.

Lee et al.(2024)의 논문에는 arXiv 버전과 출판된 IEEE 버전이 있습니다. arXiv는 누구나 논문을 읽을 수 있는 연구 공유 사이트이고 IEEE(Institute of Electrical and Electronics Engineers)는 학술지와 학회 논문집을 출판하는 전기전자공학 전문가 단체입니다. 두 버전은 수식 번호가 서로 달라서 사내 노트는 출판된 버전의 번호를 사용합니다.

벤치마크에 포함된 라이브러리 12개 중 3개가 Windows junction을 지원합니다. Windows junction은 한 폴더를 같은 컴퓨터의 다른 폴더에 연결하는 Windows 파일 시스템 기능입니다.

Windows junction을 지원해야 하는 프로그램이라면 이 벤치마크의 후보는 12개에서 3개로 줄어듭니다.

Lee et al.(2024)은 watch count(라이브러리가 감시하는 대상의 수)와 메모리 사용량 사이 관계의 강도를 r = 0.91로 보고했습니다. r은 두 값이 함께 변하는 정도를 나타내는 상관계수이고 절댓값이 클수록 관계가 강합니다.

## Rust 버전을 노트북 500대에서 2주 동안 측정한 결과

담당 팀은 Rust 버전을 노트북 500대에서 2주 동안 측정했습니다. 측정한 500대는 전체 약 4,000대의 12.5% 정도입니다.

로그는 프로그램이 동작 내용을 남기는 기록입니다. 아래 표는 Python 버전과 Rust 버전의 메모리 사용량, 시작 시간, 로그 줄 수를 비교합니다.

| 측정 항목 | Python 버전 | Rust 버전 |
|---|---|---|
| 유휴 상태의 메모리 사용량 | 210 MB | 38 MB |
| 시작 시간 | 1.9초 | 0.3초 |
| 동기화 1회마다 출력하는 로그 | 약 40줄 | 1줄 |

유휴 상태의 메모리 사용량은 210 MB에서 38 MB로 줄어 Python 버전의 약 18%가 됐고, 시작 시간은 1.9초에서 0.3초로 줄어 Python 버전의 약 16%가 됐습니다.

노트북 약 120대는 아직 Python 버전을 실행합니다. 보안 도구가 Rust 바이너리를 차단하기 때문입니다. 이 노트북 수는 전체 약 4,000대의 3% 정도입니다.

## 비슷한 마이그레이션에 이 결과를 적용한다면

회사 노트북에 보안 도구가 설치돼 있다면 새 바이너리를 배포하기 전에 보안 도구가 그 바이너리를 차단하는지 먼저 확인해야 합니다. 이 사례에서는 보안 도구가 Rust 바이너리를 차단한 노트북 약 120대가 Python 버전에 남았습니다. 마이그레이션이 끝날 때까지 두 버전을 모두 담당하는 팀은 이 노트북 때문에 Python 버전을 더 오래 담당할 수 있습니다.

새 버전과 이전 버전이 같은 설정 파일을 읽지 못한다면 이전 버전으로 되돌릴 때 설정이 사라질 수 있습니다. 설정 파일의 형식을 바꾸는 마이그레이션이라면 되돌리는 과정을 먼저 테스트해야 합니다.

watch count와 메모리 사용량 사이 관계의 강도 r = 0.91은 Lee et al.(2024)이 보고한 값이고 동기화 에이전트에서 측정한 값이 아닙니다. 이 관계가 동기화 에이전트에도 적용된다면 감시하는 대상이 많은 노트북에서는 유휴 상태의 메모리 사용량이 38 MB보다 많을 수 있습니다.

동기화 1회마다 출력하는 로그가 약 40줄에서 1줄로 줄면 문제를 조사할 때 읽을 수 있는 기록도 줄어들 수 있습니다.

## 마치며

Rust 버전의 유휴 상태 메모리 사용량 38 MB와 시작 시간 0.3초는 노트북 500대에서 2주 동안 측정한 값입니다.

담당 팀은 Rust 버전이 네트워크 드라이브에서도 같게 동작하는지 아직 모릅니다. 네트워크 드라이브에서 Rust 버전을 테스트한 사람이 아직 없기 때문입니다. 저장 위치가 네트워크 드라이브인 환경이라면 이 측정 결과를 그대로 적용할 근거가 없습니다.

사내 노트는 Python 버전의 값을 같은 노트북 500대에서 측정했는지 밝히지 않았습니다. 실제 버그 22개가 모두 수정됐는지, 벤치마크에서 어떤 라이브러리를 선택했는지, 동기화 에이전트가 파일을 어디로 동기화하는지도 사내 노트에 없습니다.
