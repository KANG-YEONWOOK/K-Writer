# 동기화 에이전트를 Python에서 Rust로 옮기기: 대기 상태 메모리 사용량은 210 MB에서 38 MB로

회사 노트북 약 4,000대에서 동기화 에이전트가 실행되고 있습니다. 동기화 에이전트는 사용자가 직접 조작하지 않아도 백그라운드(사용자가 보는 화면 뒤)에서 실행되면서 동기화를 처리하는 프로그램입니다. 동기화는 서로 다른 저장 위치의 데이터를 같은 내용으로 맞추는 일입니다.

개발 팀은 Python으로 만든 동기화 에이전트를 Rust로 다시 만들고, 노트북이 Rust로 만든 동기화 에이전트를 실행하도록 바꾸는 전환 작업을 진행하고 있습니다. Python은 코드를 읽기 쉽게 작성하는 데 중점을 둔 프로그래밍 언어이고, Rust는 실행 속도와 코드 안전성에 중점을 둔 프로그래밍 언어입니다. 아래에서는 Python으로 만든 동기화 에이전트를 Python 버전, Rust로 만든 동기화 에이전트를 Rust 버전이라고 부릅니다.

내부 노트 "Internal note: moving the sync agent from Python to Rust"는 동기화 에이전트의 전환 과정을 정리한 문서입니다. 이 내부 노트는 글쓰기 평가를 위해 만든 가상의 문서이므로 이 글의 수치를 실제 결과로 인용하면 안 됩니다.

이 글에서는 Python 버전과 Rust 버전을 함께 배포한 방법과 전환 결과를 정리합니다.

노트북 500대에서 2주 동안 측정한 결과 동기화 에이전트가 시작하는 데 걸리는 시간은 Python 버전의 1.9초에서 Rust 버전의 0.3초로 줄었습니다.

## Python 버전을 Rust로 다시 만든 이유

동기화 에이전트의 Python 버전은 2023년부터 운영 환경(사용자가 실제로 사용하는 환경)에서 실행되고 있습니다.

프로그램은 실행되는 동안 메모리(데이터를 올려 두는 저장 공간)를 사용합니다. Python 버전은 대기 상태에서 메모리 210 MB(메가바이트, 데이터 크기의 단위)를 사용했습니다. 대기 상태는 프로그램이 실행 중이지만 맡은 작업을 하지 않고 기다리는 상태입니다.

Python 버전은 시작하는 데 1.9초가 걸렸습니다. 대기 상태의 메모리 사용량과 시작 시간 때문에 개발 팀은 3월에 Rust 버전을 만들기 시작했습니다.

개발 팀은 전환(노트북이 Rust 버전을 실행하도록 바꾸는 작업)이 끝날 때까지 Python 버전과 Rust 버전을 모두 담당합니다.

## 두 버전을 6주 동안 함께 배포한 방법

개발 팀은 6주 동안 동기화 에이전트의 Python 버전과 Rust 버전을 모두 담은 설치 프로그램을 배포했습니다. 마지막 Python 버전은 1.8 버전이고 첫 Rust 버전은 2.0 버전입니다.

Python 버전과 Rust 버전은 같은 설정 파일(프로그램의 설정값을 저장한 파일)을 읽습니다. 그래서 노트북은 설정을 잃지 않고 Rust 버전으로 전환했다가 Python 버전으로 되돌아갈 수 있었습니다.

Rust 버전은 시작할 때 레지스트리(Windows에서 프로그램과 시스템이 설정 데이터를 저장하고 읽는 저장소)에서 설치된 버전 번호를 읽습니다. 그 번호가 1.6보다 오래된 버전이면 Rust 버전은 실행을 거부합니다.

마지막 Python 버전인 1.8은 1.6보다 오래되지 않았으므로 1.8 버전이 설치된 노트북에서 Rust 버전은 실행을 거부하지 않습니다.

설치 프로그램은 Python 버전의 실행 파일(컴퓨터가 바로 실행할 수 있는 형태로 만든 프로그램 파일) 사본을 Rust 버전의 실행 파일 옆에 보관합니다. 그래서 Python 버전으로 되돌리는 작업은 40초가 걸리고 다운로드가 필요 없습니다.

동기화 에이전트의 최신 버전은 항상 업데이트 서버에 공개됩니다. 업데이트 서버는 최신 버전을 공개해 두는 서버이고, 서버는 다른 컴퓨터에 데이터를 제공하는 컴퓨터입니다.

패치 버전(버그를 수정하려고 내놓는 작은 변경의 버전)은 버전 번호의 세 번째 숫자만 바꿉니다. 예를 들어 2.0.3은 세 번째 숫자가 3인 패치 버전입니다.

## 테스트 1,240개로 찾은 버그와 아직 검사하지 않는 범위

동기화 에이전트의 테스트 스위트에는 테스트 1,240개가 있습니다. 테스트 스위트는 프로그램이 정해진 대로 동작하는지 확인하는 테스트를 모은 묶음입니다.

빌드는 소스 코드를 실행 파일로 만든 결과물이고, 소스 코드는 사람이 읽을 수 있는 글자로 작성한 프로그램의 원본입니다.

Rust 버전의 첫 빌드에서는 테스트 1,240개 가운데 31개(2.5%)가 실패했습니다.

첫 빌드에서 실패한 테스트 31개 가운데 9개는 Python 버전에서도 실패했으므로 회귀(regression)가 아닙니다. 회귀는 전에는 정상으로 동작하던 기능이 이후 버전에서 고장 나는 버그입니다.

첫 빌드에서 실패한 테스트 가운데 나머지 22개는 실제 버그였습니다.

Rust 버전에서 가장 심각한 버그는 file watcher에 있었습니다. file watcher는 폴더와 파일의 변경을 감지해 알려 주는 구성 요소입니다. 사용자가 폴더 이름을 변경하면 Rust 버전은 그 폴더 안에서 이후에 생기는 변경을 하나도 감지하지 못했습니다.

file watcher 버그의 수정은 2.0.3 버전에 포함돼 배포됐고, 테스트 스위트는 이제 폴더 이름을 변경하는 경우도 검사합니다. 수정이 2.0.3 버전에 포함됐으므로 2.0.3보다 앞선 Rust 버전에서는 이 버그가 나타날 수 있습니다.

테스트 스위트는 아직 네트워크 드라이브(다른 컴퓨터의 공유 폴더를 내 컴퓨터의 드라이브처럼 연결해 사용하는 저장 공간)를 검사하지 않습니다.

## 동기화 에이전트의 실행 중 동작

동기화가 실행되는 동안 동기화 에이전트는 데이터베이스 파일에 잠금(lock)을 걸어 둡니다. 데이터베이스 파일은 데이터를 정리해 저장하고 찾을 수 있게 만든 파일이고, 잠금은 여러 작업이 같은 데이터를 동시에 변경하지 못하게 막는 장치입니다.

업데이트 확인 기능은 동기화 에이전트에서 최신 버전을 확인하는 부분입니다.

HTTP(HyperText Transfer Protocol)는 웹 브라우저와 서버처럼 컴퓨터끼리 데이터를 주고받을 때 따르는 규칙이고, 응답 헤더는 서버가 응답에 덧붙이는 부가 정보입니다. 로컬 캐시는 같은 데이터를 다시 요청할 때 더 빨리 응답하려고 노트북 안에 저장해 둔 데이터입니다.

업데이트 확인 기능은 HTTP 응답 헤더를 읽고 로컬 캐시를 갱신한 뒤 최신 버전 문자열을 돌려줍니다. 버전 문자열은 버전 번호를 글자로 나타낸 값입니다.

worker는 프로그램 안에서 작업을 나눠 맡아 실행하는 부분입니다. worker 하나가 동시에 열어 둘 수 있는 파일은 8개이고 이 상한은 넘을 수 없습니다.

동기화 에이전트는 크래시(프로그램이 정상 동작을 멈추고 종료되는 일)가 발생한 뒤 큐에 남아 있던 항목을 순서대로 다시 처리합니다. 큐는 먼저 들어온 항목을 먼저 꺼내 처리하는 대기 목록입니다.

## 설계 문서에서 낱말마다 뜻을 하나로 정한 과정

동기화 에이전트의 설계 문서(프로그램을 어떻게 만들지 정리한 문서) 첫 초안은 잠금(같은 데이터의 동시 변경을 막는 장치)의 동작 방식을 잘못 설명했습니다. 그래서 설계 문서의 두 번째 판에서는 잠금을 설명한 절을 삭제했습니다.

Git은 코드와 문서의 변경 이력을 저장하고 관리하는 도구이고, 커밋은 Git에 저장한 프로젝트 상태 하나입니다. HEAD 커밋은 지금 작업 기준이 되는 가장 최근 커밋입니다.

리뷰어(문서를 검토하는 사람)는 현재 문서와 HEAD 커밋에 저장된 문서를 비교했습니다. 이 비교는 가장 최근 커밋 이후 문서에서 바뀐 내용을 보여 줍니다.

설계 문서 초안에서 "sync"와 "commit" 같은 낱말은 각각 두 가지 뜻으로 사용됐습니다. 그래서 문서 작성자들은 낱말마다 뜻을 하나만 남기고 모든 용어에 짧은 정의를 붙였습니다. 문서 작성자들은 이 점검을 절마다 반복했고 부록은 점검에서 제외했습니다.

## 파일 감시 라이브러리를 비교한 벤치마크 논문

라이브러리는 프로그램을 만들 때 가져다 사용하는, 미리 만들어 둔 코드 묶음입니다. 파일 감시 라이브러리는 폴더와 파일의 변경을 감지하는 기능을 제공합니다. 벤치마크는 정해진 시험을 실행해 여러 소프트웨어의 성능을 비교하는 방법입니다.

개발 팀은 Lee et al.(2024)의 벤치마크를 사용해 파일 감시 라이브러리를 비교했습니다. 이 벤치마크에 포함된 라이브러리 12개 가운데 3개가 Windows junction을 지원합니다. Windows junction은 Windows에서 한 폴더를 다른 폴더로 연결하는 파일 시스템 기능입니다. 프로그램이 Windows junction을 다뤄야 한다면 후보는 12개에서 3개로 줄어듭니다.

Lee et al.(2024)은 감시 대상 수(변경을 감지하도록 지정한 파일과 폴더의 수)와 메모리 사용량 사이의 관계 강도를 r = 0.91로 보고했습니다. r은 상관계수로, 두 값이 함께 변하는 정도를 나타내는 통계 값입니다. r이 양수이면 한 값이 늘 때 다른 값도 함께 늘고, 절댓값이 클수록 관계가 강합니다.

r = 0.91은 Lee et al.(2024)이 보고한 값이고 동기화 에이전트에서 측정한 값이 아닙니다.

Lee et al.(2024)의 arXiv 공개본과 IEEE 출판본은 수식 번호를 다르게 매겼습니다. arXiv는 연구자가 논문을 공개하는 온라인 서비스이고, 올라온 논문을 arXiv가 동료 심사(같은 분야 전문가가 논문의 방법과 결과를 검토하는 절차)하지는 않습니다. IEEE(Institute of Electrical and Electronics Engineers)는 전기전자 공학 분야의 전문가 단체로 학술지와 학회 논문집을 출판합니다.

수식 번호가 달라서 내부 노트는 IEEE 출판본의 번호를 따릅니다. 내부 노트가 수식을 번호로 가리키면 arXiv 공개본에서는 그 번호가 다른 수식을 가리킬 수 있습니다.

## 노트북 500대에서 2주 동안 측정한 결과

개발 팀은 노트북 500대에서 2주 동안 Rust 버전을 측정했습니다. 노트북 500대는 동기화 에이전트가 실행되는 회사 노트북 약 4,000대의 8분의 1 규모입니다.

아래 표는 Python 버전과 Rust 버전의 값을 항목별로 비교합니다. 표의 로그는 프로그램이 실행 중에 일어난 일을 남긴 기록입니다.

| 항목 | Python 버전 | Rust 버전 |
|---|---|---|
| 대기 상태의 메모리 사용량 | 210 MB | 38 MB |
| 시작 시간 | 1.9초 | 0.3초 |
| 동기화 1회당 로그 줄 수 | 약 40줄 | 1줄 |

대기 상태(맡은 작업 없이 기다리는 상태)의 메모리 사용량은 210 MB에서 38 MB로 172 MB(약 82%) 줄었습니다. 시작 시간은 1.9초에서 0.3초로 1.6초(약 84%) 줄었습니다.

Rust 버전은 동기화 1회마다 로그를 1줄 남깁니다. Python 버전은 동기화 1회마다 로그를 약 40줄 남겼습니다.

회사 노트북 약 4,000대 가운데 약 120대(약 3%)는 아직 Python 버전을 실행합니다. 보안 도구가 Rust 버전의 실행 파일을 차단하기 때문입니다.

개발 팀은 Rust 버전이 네트워크 드라이브(다른 컴퓨터의 공유 폴더를 연결한 저장 공간)에서도 같은 방식으로 동작하는지 아직 모릅니다. 아무도 네트워크 드라이브에서 Rust 버전을 테스트하지 않았기 때문입니다.

## 마치며

동기화 에이전트의 결과를 다른 프로그램에 적용하려면 먼저 측정 조건을 확인해야 합니다. Rust 버전의 38 MB와 0.3초는 노트북 500대에서 2주 동안 측정한 값입니다. 비교 대상인 Python 버전의 210 MB와 1.9초를 어떤 조건에서 측정했는지는 내부 노트에 없습니다.

메모리 사용량과 시작 시간이 줄어든 원인을 언어 변경과 다른 변경으로 나눈 분석도 내부 노트에 없습니다. 그래서 Rust로 옮기기만 하면 메모리 사용량과 시작 시간이 같은 폭으로 줄어든다고 판단할 수 없습니다.

회사 노트북에 보안 도구가 설치돼 있다면 전환하기 전에 새 실행 파일이 차단되는지 확인해야 합니다. 문제를 조사할 때 로그에 의존한다면 동기화 1회당 로그 1줄로 원인을 찾을 수 있는지도 확인해야 합니다. 전환 중에 되돌릴 수 있어야 한다면 두 버전이 같은 설정 파일을 읽게 하고 이전 실행 파일의 사본을 보관하는 구성을 검토할 수 있습니다.

아직 확인하지 않은 범위는 네트워크 드라이브입니다. 테스트 스위트는 네트워크 드라이브를 검사하지 않고, 아무도 네트워크 드라이브에서 Rust 버전을 테스트하지 않았습니다. 개발에 들어간 기간과 인력, 전환이 끝나는 시점도 내부 노트에 없습니다.
