자료(엔지니어링 노트)가 말한 내용은 다음과 같다. fixed window 방식에서는 window가 시작할 때 제한에 걸렸던 클라이언트가 동시에 재시도해서 부하가 몰렸다. 클라이언트마다 token bucket(최대 100 tokens, 초당 10 tokens 충전)을 두는 방식으로 바꿨다. 배포 2주 뒤 초당 최대 부하, gateway p99 latency가 줄었고 거절된 요청의 비율은 2.1%에서 2.6%로 늘었으며 Redis CPU 사용률은 8 percentage points 늘었다. 한계는 세 가지다. 여러 클라이언트가 같은 순간에 시작하면 효과가 없고, 활성 클라이언트 50,000개가 넘는 경우는 테스트하지 않았으며, Retry-After를 무시하는 클라이언트는 여전히 바로 재시도한다.

요약의 문장을 하나씩 읽고 위 내용에 근거가 있는지 확인한다.

PASS: 모든 문장이 자료의 내용이다. 자료에 없는 평가("효과적인 방법입니다"), 조언("도입을 검토해야 합니다"), 전망, 일반론이 없다.
FAIL: 자료에 없는 평가, 조언, 전망, 원인, 사례를 쓴 문장이 하나라도 있다. 또는 자료의 내용과 다르게 쓴 문장이 있다(예: 거절된 요청의 비율이 줄었다고 씀). 판정 근거로 해당 문장을 인용한다.
