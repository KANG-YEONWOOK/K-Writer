# 검색 indexer의 배치 방식: 부산 클러스터의 index lag를 9분에서 2분으로 줄인 변경

판매자가 팔 물건을 소개하는 상품 글을 올렸는데 다른 사용자가 상품 이름으로 검색해도 한동안 그 상품 글이 검색되지 않는 일이 있습니다.

상품 글이 검색되려면 먼저 검색 indexer가 그 상품 글을 처리해야 합니다. 검색 indexer는 판매자가 올린 상품 글을 검색 인덱스의 항목으로 바꾸는 프로그램입니다. 검색 인덱스는 검색어로 원하는 상품 글을 빨리 찾을 수 있게 미리 정리해 둔 데이터입니다.

판매자가 상품 글을 올린 때부터 그 상품 글을 검색할 수 있게 된 때까지 걸리는 시간은 index lag라고 부릅니다. lag는 '뒤처짐'이라는 뜻입니다.

검색 indexer의 처리 방식을 바꾼 과정은 내부 메모 "Internal note: batching in the search indexer"에 기록돼 있습니다. 메모는 글쓰기 평가용으로 만든 가상 자료입니다. 메모에는 저자와 작성 연도가 없습니다. 이 글에서는 검색 indexer가 데이터를 묶어 저장하는 배치 방식으로 바뀐 뒤 index lag가 어떻게 달라졌고 배치 방식 때문에 새로 생긴 문제를 어떻게 해결했는지 정리합니다.

## 문서마다 쓰기 요청을 따로 보내던 검색 indexer

4월까지 검색 indexer는 문서를 한 번에 하나씩 처리했습니다. 검색 시스템에서는 검색 인덱스에 넣으려고 처리하는 데이터 한 건을 문서라고 부릅니다.

검색 인덱스의 데이터는 object storage(객체 스토리지)에 저장돼 있습니다. object storage는 데이터를 파일 같은 객체 단위로 저장하고 네트워크로 요청을 보내 읽고 쓰는 저장소입니다. 문서를 하나씩 처리하던 검색 indexer는 문서 하나를 처리할 때마다 object storage에 쓰기 요청(데이터를 저장해 달라는 요청)을 따로 보내야 했습니다.

큐(queue)는 처리할 작업이 들어온 순서대로 차례를 기다리는 대기열입니다. 검색 indexer가 처리할 문서도 큐에서 차례를 기다립니다. 문서를 하나씩 처리하던 때에는 문서가 큐에서 기다린 시간(큐 대기 시간)이 index lag의 대부분인 70%를 차지했습니다.

index lag에서 큐 대기 시간 70%를 뺀 나머지는 30%이므로, 큐 대기 시간은 나머지 30%를 모두 합친 시간의 2배가 넘었습니다.

## 문서 최대 200개를 쓰기 요청 한 번으로 저장하는 배치 방식

배치 방식에서 검색 indexer는 문서를 최대 200개까지 묶어 object storage에 쓰기 요청 한 번으로 저장합니다. 메모는 문서마다 쓰기 요청을 따로 보내야 했던 구조와 index lag의 70%를 차지한 큐 대기 시간을 검색 indexer를 바꾼 이유로 들었습니다.

여러 문서를 하나로 묶은 단위는 배치(batch), 배치 하나에 넣는 문서 수는 배치 크기라고 부릅니다. 예를 들어 문서 200개를 저장한다면 문서마다 쓰기 요청을 보내던 방식에서는 쓰기 요청이 200번 필요하고 배치 방식에서는 쓰기 요청 한 번이면 됩니다.

배치를 압축하면 문서 하나당 약 3 ms(밀리초, 0.003초)의 overhead가 생깁니다. overhead는 본래 하려는 일 외에 추가로 드는 처리 시간입니다. 문서 200개를 담은 배치라면 압축 overhead가 배치 하나에 약 600 ms(0.6초)인 셈입니다.

worker는 대기 중인 작업을 받아 처리하는 프로그램입니다. CPU 시간은 프로그램이 CPU(중앙 처리 장치, 컴퓨터에서 계산을 맡는 부품)를 실제로 사용한 시간입니다. 문서의 압축을 해제하는 일이 worker의 CPU 시간 가운데 60%를 차지합니다.

## 부산 클러스터와 서울 클러스터의 index lag

클러스터는 여러 컴퓨터(서버)를 묶어 하나의 시스템처럼 운영하는 단위입니다. 메모가 보고한 index lag는 부산 클러스터와 서울 클러스터 두 곳의 값입니다.

| 클러스터 | 배치 방식 도입 전 index lag | 배치 방식 도입 후 index lag |
|---|---|---|
| 부산 클러스터 | 9분 | 2분 |
| 서울 클러스터 | 1.5분 | 1.5분 |
| 두 클러스터의 차이(계산값) | 7.5분 | 0.5분 |

배치 방식을 도입한 뒤 부산 클러스터의 index lag는 9분에서 2분으로 7분 줄었습니다. 서울 클러스터의 index lag는 1.5분 그대로였습니다. 두 클러스터의 index lag 차이는 7.5분에서 0.5분(30초)이 돼 약 93% 줄었습니다.

배치 방식을 도입한 뒤 object storage에 보내는 쓰기 요청의 최대치는 85% 줄었습니다. 쓰기 요청이 가장 많이 몰린 때의 요청 수가 배치 방식을 도입하기 전의 15% 수준이 됐다는 뜻입니다.

## 배치 전체가 거부되던 문제와 v4.1의 수정

배치 방식을 도입하자 새 문제가 생겼습니다. 배치 안의 문서 하나가 검증(문서가 정해진 형식과 규칙에 맞는지 확인하는 단계)에 실패하면 그 배치 전체가 거부됐습니다.

배치 하나에는 문서가 최대 200개 담기므로, 문서 하나가 검증에 실패하면 같은 배치에 담긴 다른 문서 최대 199개도 함께 거부될 수 있었습니다.

배치 전체가 거부되는 문제는 SEARCH-311이라는 티켓에 기록됐습니다. 티켓은 해야 할 일이나 발견한 문제를 한 건씩 등록하고 처리 상태를 관리하는 항목입니다.

SEARCH-311의 수정 사항은 v4.1이라는 버전에 반영됐습니다. 그 뒤 배치 전체가 거부되는 문제는 해결됐고 SEARCH-311 티켓도 닫혔습니다.

v4.1부터 검색 indexer는 검증에 실패한 문서만 다시 처리합니다. v4.1은 6월에 배포돼 실제 서비스에 적용됐습니다.

v4.1에는 schema registry도 추가됐습니다. schema registry는 데이터가 어떤 항목을 어떤 형식으로 담는지 정한 정의(schema)를 한곳에 등록해 두는 저장소(registry)이고 여러 프로그램이 같은 정의를 사용하게 합니다. schema registry 덕분에 예전 형식으로 저장된 상품 글을 새 형식으로 옮기는 마이그레이션 가운데 남은 작업도 진행할 수 있게 됐습니다.

## 판매자에게 인덱싱 오류를 보여 주는 업로드 클라이언트

업로드 클라이언트는 판매자가 상품 글을 올릴 때 사용하는 프로그램입니다. 새 업로드 클라이언트는 인덱싱 오류(상품 글을 검색 인덱스에 넣는 과정에서 생긴 오류)를 판매자에게 보여 줍니다. 판매자는 어느 상품 글의 인덱싱이 실패했고 왜 실패했는지 알 수 있습니다.

검색 indexer는 검색 인프라 팀이 맡고 업로드 클라이언트는 다른 팀인 listing 팀이 맡습니다.

## 수정하지 않기로 한 중복 문서 문제

검색 인덱스에 중복 문서가 있다는 보고는 SEARCH-327 티켓에 기록됐습니다. 중복 문서는 검색 인덱스에 같은 문서가 두 번 이상 들어간 것입니다.

중복 문서 문제는 수정하지 않기로 결정됐고 SEARCH-327 티켓은 won't fix(수정하지 않음)라는 종료 사유로 닫혔습니다. 수정하지 않기로 한 첫째 근거는 사용자가 보낸 검색 요청 가운데 중복 문서가 나타난 검색 요청이 0.01% 미만(1만 건 가운데 1건 미만)이었다는 점입니다.

수정하지 않기로 한 둘째 근거는 다음 full reindex가 중복 문서를 지운다는 점입니다. full reindex는 검색 인덱스 전체를 처음부터 다시 만드는 작업입니다.

full reindex를 드물게 실행하는 시스템이라면, 다음 full reindex까지 중복 문서가 검색 결과에 남아 있는 기간이 길어질 수 있습니다.

## 이미지가 있는 상품 글과 급한 상품 글에 적용한다면

5 MB보다 큰 이미지가 있는 상품 글에서도 배치 방식이 통하는지는 아직 답이 없습니다. 배치 방식은 이미지가 없는 상품 글로만 시험했으므로 5 MB 이하의 이미지가 있는 상품 글도 시험한 범위 밖입니다.

이미지가 있는 상품 글이 많은 서비스라면, 부산 클러스터에서 측정한 index lag 감소폭(9분에서 2분)이 그대로 나타날지 따로 측정해야 합니다.

급한 상품 글에 배치 크기를 더 작게 설정하는 방안은 아직 결정되지 않았고 선택지로 남아 있습니다. 메모는 어떤 상품 글을 급한 상품 글로 분류하는지 밝히지 않았습니다.

## 마치며

부산 클러스터의 index lag가 9분에서 2분으로 줄어든 결과는 이미지가 없는 상품 글로만 시험해서 얻은 것입니다.

문서를 묶어 저장하는 방식을 도입한다면, 문서 하나가 검증에 실패해도 같은 배치의 다른 문서가 함께 거부되지 않게 하는 처리가 필요합니다. 메모의 검색 indexer는 v4.1부터 검증에 실패한 문서만 다시 처리해 이 문제를 해결했습니다.

SEARCH-327 티켓의 중복 문서 문제를 수정하지 않기로 한 결정은 중복 문서가 0.01% 미만의 검색 요청에서 나타나고 다음 full reindex에서 지워진다는 두 조건에서 성립합니다.

5 MB보다 큰 이미지가 있는 상품 글에서 배치 방식이 통하는지는 아직 답이 없고 급한 상품 글에 더 작은 배치 크기를 설정할지도 아직 결정되지 않았습니다.
