# K-Writer 0.5.0 write, brief 스킬 추가와 short 모드 삭제 요약

K-Writer 0.5.0은 사용자의 요청에 따라 기본 글쓰기 스킬 write와 요약 스킬 brief를 추가하고, techblog의 short 모드를 삭제해 짧은 글은 brief로 쓰게 했습니다. write는 자료나 주제, 목적, 분량, 어투를 사용자에게 받아 글을 쓰고, write 외의 스킬은 글의 목적, 문체, 구성을 미리 정해 둔 스킬입니다. 단위 테스트 210개와 `claude plugin validate` 검사는 통과했지만 `claude plugin eval`은 실행하지 않았습니다.

- write는 자료나 주제가 없으면 먼저 요청하고 목적(설명, 설득, 안내, 기록, 직접 입력), 분량, 어투 중 요청에 없는 값을 한 번에 묻습니다. 본문이 공백 제외 1,500자 이상이면 독립 점검을 모두 subagent에게 맡기고 미만이면 독자 점검과 한국어 문장 점검만 맡깁니다.
- brief는 분량(한 줄, 한 문단, 자세히)과 어투만 묻습니다. 요약은 대화에 보여 주고 `-o`가 있으면 파일에도 저장합니다.
- short 모드와 함께 `short.md`, `short` 인자, `lint_ko.py`의 `--source`와 `--terms`, 원문 대조 항목 F1~F8을 삭제했습니다.
- core의 어투에 Plain(해라체)과 사용자가 직접 정한 어투를 추가했습니다. 어느 어투로 쓴 글이든 합니다체 초안의 종결부만 바꿔 만듭니다.
- 짧은 글 기준은 core의 `rules.json`으로 옮겼고 `lint_ko.py --short`와 `revise_ko.py`의 `check --short`, `audit --short`가 이 기준을 적용합니다.
- write와 brief는 기준으로 삼을 사람 글 표본이 없어서 특정 표현의 빈도를 세는 항목 15개의 기준치를 techblog에서 가져왔습니다.

short 모드 코드를 삭제하기 전과 뒤의 `lint_ko.py`를 예시 글, eval 글, 평가 기록의 글 34개에 `--tone default`와 `--tone casual`로 실행했습니다. 수정 전후의 출력 68개를 비교한 결과 항목의 값과 판정은 모두 같았습니다. 문서를 작성하지 않은 subagent에게 스킬 문서만 주고 요청을 실행하게 한 테스트도 했습니다. brief로 영어 엔지니어링 노트를 한 문단으로 요약한 글은 스킬 문서를 수정하기 전 1차 실행에서 590자였고 수정 뒤 2차 실행에서 296자였습니다. 1차 요약이 길어진 원인은 두 가지였습니다. 기본 독자를 분야 지식이 없을 수 있는 사람으로 정해 용어마다 설명이 붙었고, 독립 점검이 독자 점검의 질문마다 설명을 추가했습니다. 그래서 기본 독자를 자료가 대상으로 삼은 독자와 같은 수준의 사람으로 바꿨습니다. 다른 subagent는 `revise_ko.py`의 `check`와 `audit`가 짧은 글 기준을 적용하지 않아 `lint_ko.py --short`와 판정이 다르다는 것을 찾았습니다. 두 명령에 `--short`를 추가했고 이 차이를 테스트로 남겼습니다. write 2차 실행의 장애 대응 기록에는 "저희"와 Plain 종결이 함께 쓰인 문장이 6개 있었습니다. 그래서 조직을 주어로 쓸 때 "우리 팀은"이나 조직 이름을 쓰도록 genre.md, drafting.md, tone.md를 수정했습니다.

dogfood도 실행하지 않았고 새 eval 케이스 4개는 작성만 했습니다. 테스트 실행은 자료와 요청의 조합마다 한 번이고 "저희" 규칙은 추가한 뒤 다시 실행해 확인하지 않았습니다. AskUserQuestion으로 분량과 어투 같은 설정을 묻는 흐름도 실행하지 못했습니다. lint는 해라체 글에 섞인 합니다체와 해요체 종결은 검출하지만 반말 종결은 검출하지 못합니다.
