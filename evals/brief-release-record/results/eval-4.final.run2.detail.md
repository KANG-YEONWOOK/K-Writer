# K-Writer 0.5.0 write, brief 스킬 추가와 short 모드 삭제 요약

K-Writer 0.5.0은 글쓰기 스킬 write와 요약 스킬 brief를 추가하고 techblog의 short 모드를 삭제했습니다. 짧은 글은 short 모드 대신 brief로 작성합니다. 두 스킬을 요청한 사용자는 write가 기본 스킬이고 다른 스킬은 글의 목적, 문체, 구성을 미리 정해 둔 스킬이라고 설명했습니다.

- write는 자료나 주제가 없으면 먼저 요청하고 목적, 분량, 어투 중 요청에 없는 값을 한 번에 묻습니다.
- brief는 분량(한 줄, 한 문단, 자세히)과 어투만 묻습니다. 요약은 대화로 답하고 `-o`가 있으면 파일에도 저장합니다.
- core의 어투에 해라체(Plain)와 사용자가 직접 정한 어투를 추가했고 어느 어투의 글이든 합니다체 초안의 종결부만 바꿔서 만듭니다.
- 짧은 글 기준을 core의 `rules.json`으로 옮겼고 `lint_ko.py --short`와 `revise_ko.py`의 `check --short`, `audit --short`가 이 기준을 적용합니다.
- 기준 글 표본이 없는 write와 brief에는 특정 표현의 빈도를 세는 항목 15개의 기준치를 techblog에서 가져와 적용했습니다.

short 모드 코드를 삭제하면서 `lint_ko.py`에 두 번 정의된 정규식 `INLINE_CODE_RE`와 `URL_RE`의 앞 정의를 실행 때 사용되던 뒤 정의와 같게 맞췄습니다. 예시 글, eval 글, 평가 기록의 글 34개 파일에 이 수정 전후의 lint를 `--tone default`와 `--tone casual`로 실행했습니다. 두 어투의 출력 68개에서 항목의 값과 판정은 모두 같았고 G4.off_tone의 수정 방향 한 줄만 달라졌습니다.

문서를 작성하지 않은 subagent에게 스킬 문서만 주고 brief와 write의 요청을 실행하게 했고 1차 실행 뒤 문서를 수정해 2차 실행을 했습니다. 영어 엔지니어링 노트를 한 문단으로 요약한 brief 결과는 1차의 590자, 27분에서 2차의 296자, 9분으로 줄었습니다. 1차 요약이 길어진 원인은 기본 독자를 자료 분야의 지식이 없을 수 있는 사람으로 정한 것과 독립 점검이 독자 점검의 질문마다 설명을 추가해 469자가 630자가 된 것이었습니다. 그래서 기본 독자를 자료가 대상으로 삼은 독자와 같은 수준의 사람으로 바꾸고 분량을 글자 수 범위로 정해 넘기지 않게 했습니다.

검토를 맡은 다른 subagent는 `revise_ko.py`의 `check`와 `audit`가 짧은 글 기준을 적용하지 않아 `lint_ko.py --short`와 판정이 다르다는 것을 찾았습니다. 그래서 두 명령에 `--short`를 추가하고 두 경우를 테스트로 남겼습니다. 영어 장애 대응 메모로 쓴 write 2차 실행의 해라체 글에는 "저희"와 해라체가 함께 쓰인 문장이 6개 있었습니다. 조직을 주어로 쓸 때 "우리 팀은"이나 조직의 이름을 쓰도록 genre.md, drafting.md, tone.md를 수정했습니다. 단위 테스트 210개가 통과했습니다.

`claude plugin eval`과 dogfood는 실행하지 않았고 새 eval 케이스 4개는 작성만 했습니다. subagent 테스트 실행은 설정마다 한 번이었고 2차 실행 뒤 genre.md, drafting.md, tone.md에 추가한 "저희" 규칙은 다시 실행해 확인하지 않았습니다. AskUserQuestion으로 설정값을 묻는 흐름도 실행해 보지 못했습니다. lint는 해라체 글에 섞인 합니다체와 해요체 종결은 검출하지만 반말 종결은 명사로 분류해서 검출하지 못합니다.
