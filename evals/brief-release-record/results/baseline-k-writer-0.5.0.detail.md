K-Writer 0.5.0은 write와 brief 스킬을 추가하고 techblog의 short 모드를 삭제했습니다. write는 자료나 주제, 목적, 분량, 어투를 사용자에게 받아 그에 맞는 글을 쓰는 스킬이고 brief는 사용자가 요약을 요청한 자료나 내용을 한국어로 요약하는 스킬입니다. 두 스킬을 요청한 사용자는 write를 기본 스킬로, 다른 스킬을 글의 목적, 문체, 구성을 미리 정해 둔 스킬로 설명했습니다. 짧은 글은 short 모드 대신 brief로 작성하기로 했습니다. 다만 0.5.0에서는 `claude plugin eval`과 dogfood를 실행하지 않았습니다.

write는 자료나 주제가 없으면 대화에서 먼저 요청하고 목적, 분량, 어투 중 요청에 없는 값을 한 번에 묻습니다. 본문이 공백 제외 1,500자 이상이면 독립 점검 네 가지를 모두 subagent에게 맡기고 1,500자 미만이면 독자 점검과 한국어 문장 점검만 맡깁니다. brief는 분량과 어투만 묻고 호출 인자에 `-o`가 있으면 요약을 파일에도 저장합니다. core의 어투에는 Plain(해라체)과 사용자가 직접 정한 어투를 추가했고 어느 어투의 글이든 합니다체 초안의 종결부만 바꿔서 만듭니다. 짧은 글 기준은 core의 `rules.json`으로 옮겼고 `lint_ko.py --short`가 이 기준을 적용합니다. write와 brief에는 기준 글 표본이 없어서 특정 표현의 빈도를 세는 검사 항목 15개의 기준치를 techblog에서 가져왔습니다.

short 모드 코드를 삭제하기 전과 후의 `lint_ko.py`를 글 파일 34개에 `--tone default`와 `--tone casual`로 실행했을 때 검사 항목의 값과 판정은 모두 같았습니다. 스킬 문서를 작성하지 않은 subagent에게 그 문서만 주고 사용자 요청을 맡기는 테스트 실행은 문서 수정 전후로 두 번 했습니다. 영어 엔지니어링 노트를 한 문단으로 요약한 brief의 결과는 1차 590자, 2차 296자였습니다. brief의 1차 요약이 길어진 원인은 기본 독자를 자료 분야의 지식이 없을 수 있는 사람으로 정해 용어마다 설명이 붙은 것과 독립 점검에서 독자 점검의 질문마다 설명을 추가한 것이었습니다. 그래서 기본 독자를 자료가 대상으로 삼은 독자와 같은 수준의 사람으로 바꾸고 분량을 글자 수 범위로 정했습니다. 감사를 맡은 subagent는 `revise_ko.py`의 `check`, `audit` 명령이 짧은 글 기준을 적용하지 않아 `lint_ko.py --short`와 판정이 다르다는 것을 발견했습니다. 이 두 명령에도 `--short`를 추가했습니다. `python -m unittest`로 실행한 단위 테스트 210개가 통과했습니다.

새 eval 케이스 4개는 작성만 했고 스킬 없이 쓴 글이나 사람이 쓴 글과 비교한 결과도 없습니다. 테스트 실행은 설정마다 한 번이었고 2차 실행 뒤에 수정한 "저희" 사용 규칙, 사실 표의 열, brief의 출력 파일 조립은 다시 실행해 확인하지 않았습니다. 테스트 실행은 subagent 안에서 했고 AskUserQuestion으로 설정을 묻는 흐름과 대화에서 자료나 주제를 요청하는 흐름은 실행해 보지 못했습니다. write와 brief의 구성과 분량 범위는 측정해서 정한 값이 아니고 techblog에서 가져온 기준치는 기술 블로그 글에서 측정한 값입니다.
